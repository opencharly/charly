  verb exists for them — can't be cli-reentry), and the SHARED core helpers it calls

  `bedCheckLiveRefs`/…) — these stay core, shared with `runCheckBed` +

## 19. B7 spike — verdict reported, HOLDING for team-lead's ruling

Per the confirmed order: B7 (`charly/check_endpoint_resolve.go` spike, #43 CheckContext) → A10
(lifecycle consolidation, 8 handlers → 1). B7 is explicitly a SPIKE per team-lead's framing — the
question is whether the resolution bodies (`resolveVerbEndpointFor`/`resolveImageLabelFor`)
relocate BEHIND the fixed SERVICE surface via peer dispatch, or thread as DATA — report the
verdict BEFORE implementing anything.

**Traced**: the reverse-RPC SERVICE surface (out-of-process cdp/wl/vnc/dbus/mcp dialing back into
`CheckContextService.ResolveEndpoint`/`ResolveGraphicsEndpoint`/`ResolveImageLabel`) is genuinely
fixed — `hostVerbResolver.RunVerb` wraps `providerRegistry.ResolveVerb`, a core-private
M-mechanism no out-of-process dispatch can bypass. Matches team-lead's "SERVICE surface stays."

Inside the handlers: `resolveCheckVenueReply` (the venue-classification step both resolution
bodies call first) is ALREADY a thin `providerRegistry.resolve`+`Invoke` routing call to
`candy/plugin-check`'s `verb:check-resolve` — the SAME defines-vs-calls shape as B3/B4's
relocated functions. The downstream resolution work (`checkhost.EndpointForVenue`,
`container.ContainerImageRef`/`InspectImageLabels`) is spec-portable, zero core-private
dependency in the LOGIC itself.

**The one genuine constraint, investigated and resolved**: `checkhost.EndpointForVenue`'s ssh-venue
branch opens a real `ssh -NT -L` subprocess and returns a live `.Close` cleanup closure
`hostVerbResolver` tracks per-Invoke (`h.endpointCleanups`). Initially suspected this blocks
relocation outright (a closure can't cross `InvokeProvider`'s `[]byte` wire, compiled-in or not)
— traced the actual call path and found this is a non-issue for the CURRENT design: the closure
is NEVER sent to the calling verb plugin at all — pure core-internal bookkeeping. The
container/shell venue branches (the common case) open no live resource — cleanup is nil. The
constraint that DOES matter: whoever owns the cleanup-tracking must live in the same PROCESS as
whoever calls `.Close()` after the Invoke — since `candy/plugin-check` is compiled-in
(same process), relocating the resolution bodies there with the plugin owning its own
cleanup-tracking state satisfies this via a DIRECT in-proc Go call (`ContextWithExecutor`/
`NewInProcExecutor`), not the generic byte-marshaled `InvokeProvider` path — the SAME
"compiled-in-REQUIRED" placement class B2-full already established and proved for
`bed_session.go`.

**Checked "thread as data" as an alternative**: pre-resolving the endpoint before Invoke dispatch,
threading it through the existing per-Invoke `spec.CheckEnv` envelope (like Box/Instance/Mode/
VenueKind already are). Not cleanly viable — a verb's port is a compile-time-fixed constant known
ONLY inside the verb itself (confirmed: `candy/plugin-cdp/provider.go` hardcodes
`cc.ResolveEndpoint(ctx, 9222)`), never declared to core ahead of time. Threading it as data would
require inventing a new per-verb port-declaration/metadata mechanism that doesn't exist today —
more invasive than relocating the resolution bodies behind the existing reverse-RPC shape.

**Recommended verdict, reported to team-lead**: relocate via peer dispatch to `candy/plugin-check`
(already owns `verb:check-resolve`, the venue-classification leg these bodies already call),
compiled-in-REQUIRED placement class (same documented shape as `bed_session.go`).
`hostVerbResolver.resolveVerbEndpoint`/`resolveImageLabel` +
`resolveVerbEndpointFor`/`resolveImageLabelFor` relocate with their own cleanup-tracking;
`check_endpoint_resolve.go` likely shrinks to just the thin `ResolveEndpoint`/
`ResolveGraphicsEndpoint`/`ResolveImageLabel` `CheckContext`-interface methods (the fixed service
surface itself stays) plus a thin cross-process cleanup signal.

**HOLDING** — this touches every out-of-process live-container verb (cdp/wl/vnc/dbus/mcp), so
waiting for team-lead's sign-off on the relocation shape before cutting any code.

# 2026.205.0130 — K5-A item 2: DescribeProvider RPC + pod-overlay step-emit dispatch relocation

Wave K1-α's K5-A item 2 (the last item in the K5-A queue): a new class-generic
reverse-channel RPC, `DescribeProvider`, plus the full relocation of the
pod-overlay Containerfile step-emit dispatch DECISION out of `charly/`
core and into the compiled-in `class:step` plugin `candy/plugin-installstep`.

## DescribeProvider — a cached capability-metadata query

A plugin can now ask the host "what StepContract does provider (class, word)
declare?" without holding the registry — `ExecutorService.DescribeProvider`
returns `found` + the target's `StepContract` from the SAME `capMeta` snapshot
populated once at connect/register time (no live Invoke). Wired end-to-end:
`sdk/protocol/schema/plugin.cue` (request/reply messages + the method),
`sdk/executor.go`'s `Executor.DescribeProvider` client method,
`charly/plugin_dispatch_reverse.go`'s host handler (resolves via
`providerRegistry.resolve` + a `spec.StepContractCarrier` type-assert),
`charly/plugin_inproc_reverse.go`'s in-proc bridge delegation (required for
COMPILED-IN callers), and the F11 `TestNoSinglePluginAPISurface` fixed
method-set allowlist (the new RPC is class-generic — class/word are the
request's plain DATA fields, never named in the RPC itself, exactly like the
existing `InvokeProvider`).

Proven end-to-end (not merely unit-tested against a hand-built fake) by
extending the existing `TestExternalStepKind_EndToEnd` test with a
verification block that queries a REAL out-of-process, gRPC-connected plugin
(`candy/plugin-example-stepkind`) and asserts the round-tripped `StepContract`
matches the plugin's own `DeclaredStepContract()` exactly.

## Pod-overlay step-emit dispatch relocation

The former `charly/oci_step_emit.go` held ~130 LOC of core logic
(`ociEmitStep`/`ociSpliceClassStepEmit`): resolve the `class:step` provider
serving a given InstallStep's word via `providerRegistry.resolve`, consult its
declared `StepContract.Emits`, and `Invoke` its `OpEmit`. That dispatch
DECISION relocates into `candy/plugin-installstep`'s new `"oci-dispatch"`
word (`candy/plugin-installstep/oci_dispatch.go`), using `DescribeProvider`
(cached metadata, no live Invoke) + `InvokeProvider` (dispatch) instead of a
direct in-core registry consult — `candy/plugin-installstep` was already the
seam's server for the other 12 compiler-emitted kinds, so the dispatch
decision now lives alongside the words it routes to (R3: one relocation
target, not a second seam).

`charly/oci_step_emit.go` is now a thin forwarder (`dispatchOCIStep`):
resolve the compiled-in `"oci-dispatch"` provider, thread the SAME in-proc
reverse channel + host-side `buildEngineContext` the former dispatch used to
(so a host-coupled peer's own `OpEmit` can still call back `HostBuild`), and
Invoke. `ociEmitStep` survives as a Go-object-typed compatibility wrapper the
existing unit-test suite (`apk_format_test.go`, `build_target_oci_test.go`,
`localpkg_test.go`, `plugin_externalstep_e2e_test.go`) drives directly —
a real path through the SAME relocated seam, not a parallel implementation.

`pluginEmitStepWords` (the kind→word map for the 12 compiler-emitted kinds)
relocated to `sdk/deploykit` as the exported `PluginEmitStepWords`, since both
the host's `checkStepProviderBijection` and the plugin's new `"oci-dispatch"`
word now need the identical lookup (R3) — `charly/provider_step.go` keeps a
thin alias for its existing bijection check.

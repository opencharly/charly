# 2026.205.0718 — fix: project-declared deploy-level `volume:` overrides now persist and take effect

A project-declared deploy-level `volume:` override (e.g. a disposable check bed's
`volume: [{name: enc-data, type: encrypted}]` authored directly in
`box/<distro>/charly.yml`) never reached the per-host deploy overlay
(`~/.config/charly/charly.yml`) `charly config` reads from — so it was silently dropped
and the declared backing (encrypted, bind, …) was never established. This gate-broke an
entire class of R10 beds that rely on a project-declared volume override,
`check-enc-pod` foremost among them (`enc-status-mounted` failed with "No encrypted
bind mounts configured").

**Note on this branch's history:** an earlier round of this PR carried an
independently-tested `sdk`-consumer adaptation for the resource arbiter
(`candy/plugin-preempt`), forced onto this branch by an intermediate `sdk` gitlink bump
that crossed a breaking change on sdk's `main`. Per the operator's landing-order
directive that adaptation was extracted to its own standalone PR
(`opencharly/charly#184`, now MERGED), and this branch merged the resulting `main` to
drop its own now-duplicate copy — see the merge commit for the full mechanics. This
entry now covers ONLY the volume-persistence + charlyBin-resolution fix, this PR's
actual scope.

## Root cause (independently re-verified)

`candy/plugin-deploy-pod/config_setup.go`'s `runConfig` (the ported
`BoxConfigSetupCmd` body, invoked via `sdk.OpConfigSetup`) resolved
`deployVolumes` from exactly three sources, in order: the CLI
`--volume`/`--bind`/`--encrypt` flags, the `CHARLY_VOLUMES_<BOX>` env var,
and the per-host overlay's own existing `Volume` entry
(`dc.Bundle[key].Volume`, loaded via `deploykit.LoadDeployConfigForRead` —
`~/.config/charly/charly.yml` only). The overlay is populated ONLY by an
explicit `charly config --bind/--encrypt/-v` invocation or a prior
`persistResourceCaps`-style write — never by the PROJECT's own declared
node. So a bed like `check-enc-pod`, whose `volume:` lives entirely in
`box/fedora/charly.yml`, had its declaration read at `charly bundle add`
compile time (feeding the InstallPlan) but never again at `charly config`
time, where the actual gocryptfs mount + quadlet volume line are decided.

## Fix (round 1)

`resolveDeployVolumes` (new, `candy/plugin-deploy-pod/config_setup_helpers.go`)
adds a fourth, LAST fallback: the deploy's project-declared `volume:`,
resolved via a new narrow host seam (`pod-config-project-volume`,
`hostBuildPodConfigProjectVolume` in `charly/host_build_pod_config_seams.go`)
that reuses the EXISTING `resolveTreeRoot` merge (`charly bundle add`'s own
project+per-host-overlay merge, `deploy_tree.go`) scoped to the one deploy
key — so overlay precedence is unchanged (an explicit overlay entry still
wins). A hit is persisted into the overlay via `persistDeployVolumes`
(mirroring `persistResourceCaps`' Security-write shape), so the declaration
takes effect immediately and every subsequent read (`charly config status`,
the enc mount/unmount plan, …) resolves it without re-consulting the
project. New wire type `#PodConfigProjectVolumeRequest`/`Reply`
(`sdk/schema/seam.cue`, regenerated).

## A second, dependent bug the fix exposed and closed in the same cutover (R2 — blocking)

Once a project-declared volume resolves for the first time, `check-enc-pod`'s
quadlet gained a REAL `ExecStartPre=… config mount …` line
(`deploykit.QuadletConfig.CharlyBin`,
`deploykit.HasEncryptedBindMounts(bindMounts)` finally true) — which
immediately failed with "This binary is a plugin. These are not meant to be
executed directly." `charlyBin, _ := os.Executable()` in `runConfig` (and in
the sibling `--update-all` path, `updateAllDeployedQuadlets`) resolves to the
PLUGIN's OWN binary path when called from inside this out-of-process plugin
— the exact bug class `unified_targets.go`'s `hostEnvJSON()` already
documents and fixes for the lifecycle-Op family (R10 bed-found bug #5, S3b).
Setup shared the same defect independently; it was dormant here only because
no bed previously exercised an actually-resolving encrypted volume through
this path. Fix: `hostBuildPodConfigSetup` now populates a new
`host_env_json` field on `#PodConfigSetupRequest` via the SAME core
`hostEnvJSON()` helper (never a second one); the plugin decodes it via the
new `resolveHostCharlyBin` (falling back to `os.Executable()` only when the
field is absent, e.g. an old core build) and threads the resolved binary
into `updateAllDeployedQuadlets` too, deleting its own independent
`os.Executable()` call (R3 — one fix, both call sites).

## Round 2 fix — conditional project lookup, later found incomplete (val-volfix)

val-volfix's review surfaced a genuine regression in the round-1 fix: `resolveDeployVolumes`
gated its project-declared-volume fallback on `len(deployVolumes) == 0`, which is ALSO true
for the overwhelmingly common case of an ALREADY-CONFIGURED, genuinely volume-less deploy
(e.g. any sibling group member whose per-host overlay entry exists from its initial `charly
bundle add` but never carries a volume) — so EVERY subsequent `charly config`/`charly update`
re-config of such a deploy re-triggered the project's `HostBuild("pod-config-project-volume")`
seam (a full `LoadUnified` project resolution) on every single call: a redundant per-call cost
the round-1 shape never paid.

The round-2 fix gated the project fallback on overlay-key ABSENCE (`!ok`) instead of
`len(overlay.Volume) == 0`. **This was itself INCOMPLETE** — see "Round 3 fix" below, which
replaces it.

## Round 3 fix — the actual, complete mechanism (team-lead RCA, BLOCKING)

team-lead's independent verification of round 2 found a cross-stage ordering hole the round-2
fix's own unit tests could not see: `config_setup.go`'s PORT-RESOLUTION block runs BEFORE
`resolveDeployVolumes` and writes `dc.Bundle[key]` (with a resolved `ResolvedPort`, empty
`Volume`) the moment a deploy declares ANY container port. So on a PORTED deploy's FIRST
`charly config` — exactly the scenario this PR exists to fix — the round-2 `!ok` gate saw the
port block's write, concluded "already configured", and skipped the project consult entirely:
the project-declared volume was silently dropped again, just via a different path. Overlay-key
existence cannot distinguish "an unrelated write already happened, project never consulted"
from "the project WAS consulted and genuinely declares nothing" — both produce an identical
"key exists, `Volume` empty" shape. The round-2 unit tests never caught this because they call
`resolveDeployVolumes` in isolation, never preceded by the port-resolution block (R7: unit
tests never substitute for runtime/integration verification).

**Fix:** a new persisted marker bit, `Deploy.VolumeProjectChecked` (`sdk/schema/deploy.cue`,
`@go(VolumeProjectChecked)`), following the EXACT `resolved_port`/`resolved_image`
"charly-written state, never authored" pattern (R3, same shape). The project fallback now
fires exactly when `VolumeProjectChecked` is unset for this deploy key — independent of
whatever ELSE lives on the overlay entry (ports, resource caps). `persistDeployVolumes` now
sets this bit UNCONDITIONALLY after every project consult, regardless of whether the project
declared a volume, so the "genuinely declares nothing" case is durably recorded too (closing
round 2's regression) while the "port block wrote first" case no longer masks the consult
(closing round 3's regression) — one bit correctly discriminates both.

Companion `opencharly/sdk` change (this PR's `sdk` gitlink + `charly/go.mod` require bumped
accordingly — see this repo's own CHANGELOG entry for the schema addition + `task cue:gen`
regeneration evidence) and a companion `box/fedora` change (new bed `check-enc-port-pod` — see
its own CHANGELOG entry) that gives this fix a LIVE ported-deploy fixture, since `check-enc-pod`
alone (reusing the port-less `check-pod` image) never exercises this ordering hazard.

# 2026.205.1120 — add_candy-on-pod: three-bug fix making the feature actually work end-to-end

`add_candy:` on a `pod:` deploy has NEVER worked via a real `charly bundle add`
invocation — a severe, pre-existing, user-facing bug that had gone undetected because
no disposable bed in this repo ever combined the `pod:` substrate with `add_candy:`.
The new disposable bed `check-pod-overlay` (`pod: {image: check-k8s-deploy-app,
add_candy: [ripgrep]}`) is the first live exerciser, and its R10 run surfaced the
feature's FULL bug stack in one pass. All three fixes land together — they are one
coherent theme ("make add_candy-on-pod work"), proven by one bed.

## Bug 1 — the overlay build never saw the compiled InstallPlan

`hostBuildOverlay` (`charly/build_overlay.go`) reads the deploy's compiled
`[]*deploykit.InstallPlan` from a ctx-threaded `*overlayBuildInputs` (`plans` +
the live, non-serializable `parentExec`/`parentNode` for a nested pod-in-pod
overlay) to compute the overlay's extra-candy scan (`collectOverlayCandies(plans)`).
Nothing in production ever seeded that ctx value — the only real construction of
`&overlayBuildInputs{plans: ...}` anywhere in the repo was in
`build_overlay_test.go`'s own test setup; the sole production caller
(`plugin_dispatch_reverse.go`'s `HostBuild`) only RE-THREADS an already-populated
value, never seeds one. So `hostBuildOverlay` always computed an EMPTY candy scan,
and `add_candy:` silently baked nothing into the overlay image.

Fixed in `charly/unified_targets.go`'s `(*pluginDeployTarget).Add` — the one call
site holding both the live `plans` slice and `opts.ParentExec`/`opts.ParentNode`
before the ctx is threaded, unbroken, in-process, all the way to
candy/plugin-deploy-pod's `HostBuild("overlay", ...)` call:

```go
ctx = withOverlayBuildInputs(ctx, &overlayBuildInputs{plans: plans, parentExec: opts.ParentExec, parentNode: opts.ParentNode})
```

`overlayBuildInputs` carries a live, non-serializable `DeployExecutor` — a genuine
in-process ctx carrier, not a CUE-wire type (SDD does not apply here; see the boundary
discussion in the PR).

## Bug 2 — the overlay's first-ever resolved_image (and later volume_project_checked) write corrupted charly.yml

Once bug 1 let the overlay build actually run, its `PrepareVenue` state-save
persists a State patch carrying ONLY `ResolvedImage` on a deploy's first-ever
overlay build (no `Box`/`Image` set yet). `charly/deploy_nodeform.go`'s
`bundleDiscForEntity` — the function that decides whether an empty-`target` entry
serializes as `pod:` or `group:` — checked `image`/`resolved_port`/`port` as
pod-workload indicators, but not `resolved_image`, so the entry fell through to
`group:`, and `#GroupInput` (which forbids `resolved_image`) then failed to parse
the WHOLE `charly.yml` on the next read. This is the SAME bug class as two prior,
already-fixed instances in the same function (the 2026-07 `resolved_port`
corruption; the FINAL/K5 unit-6a `vm_state` ephemeral corruration) — both
documented in the existing `TestBundleDiscForEntity_PodWorkloadNotGroup` table.

A concurrently-landed `Deploy.VolumeProjectChecked` wire field produced a FOURTH
instance of the identical failure mode during this same fix's R10 verification (a
fresh worktree off current `main` exercises `charly config`'s own first-ever
project-declared-volume persist, which ALSO writes a lone new field before
`Image`/`port` land). Both `resolved_image` and `volume_project_checked` are now
in `bundleDiscForEntity`'s pod-workload-indicator list, with a new table case each
in the existing precedent test.

## Bug 3 — the check-bed runner's `--tag` clobbered the just-built overlay ref

Even with bugs 1 and 2 fixed, `candy/plugin-check`'s bed runner still failed the
live check: its `config`/`start` steps pass `--tag <bed's base-image-build-tag>`
unconditionally. `charly/host_build_pod_config_seams.go`'s
`hostBuildPodConfigResolveRef` treats an explicit ref/tag as ABSOLUTE PRECEDENCE
over `resolveDeployResolvedImage` (the seam's contract is correct and untouched —
an explicit ref SHOULD win), so `config`/`start` deployed
`<base-image>:<bed-build-tag>` — a real, existing, but WRONG (un-overlaid)
reference — instead of the overlay tag `deploy-add` had just built and persisted.

Fixed plugin-side, where the add_candy knowledge lives: `CheckBedReply` gains
`has_add_candy` (companion `sdk` schema change), and `candy/plugin-check/bed_run.go`
now omits `--tag` at the config/start steps for an add_candy overlay bed (new
`configStartArgs` helper, unit-tested) — letting `config`/`start` resolve the
freshly-built overlay via `resolveDeployResolvedImage` (now correctly discriminated
as a pod entry per bug 2's fix). A non-overlay bed is unaffected: it keeps `--tag`
at config/start exactly as before (its freshness proof IS the base build tag).
`image-build`/`deploy-add` keep `--tag` unconditionally in both cases — those
correctly build the base + the overlay FROM the fresh base.

## Bug 4 (found by an independent fresh pr-validator) — the bed's own post-rebuild check was vacuous

A fresh, independent `pr-validator` review of this cutover found that
`check-pod-overlay`'s `pod-overlay-ripgrep-installed-post-rebuild` check never
actually evaluated post-rebuild state: all of the deploy's plan steps ran in a
SINGLE `charly check live` pass (verify-only, so the plan's embedded `run: charly
update` step was silently skipped), and `candy/plugin-check/bed_run.go`'s
post-rebuild `checkLiveTree("check-live-rebuild")` pass was gated on
`len(d.ChildKeys) > 0` — true for nested beds, but false for a plain, childless
pod bed like `check-pod-overlay`. So the "post-rebuild" check silently re-checked
the never-rebuilt initial-deploy state, and a regression that broke ONLY the
fresh-rebuild path would still show the bed at 100% green.

Fixed at the root: `bed_run.go`'s post-rebuild `checkLiveTree` pass no longer
requires nested children — every `RunRuntime`, non-in-place bed now gets a
genuine post-rebuild check-live pass after the bed's real `charly update` step
(the nested-child redeploy logic stays conditional on actually having children;
only the check-live-rebuild TRIGGER itself is now unconditional). This benefits
every runtime pod/vm bed in the repo, not just this one — a bed's OWN deploy-level
`check:` steps (ADE's contract already requires them to be idempotent) are now
genuinely re-verified against the post-rebuild container everywhere, closing the
exact gap class R10's own principle names ("a gate that cannot fail on the change
proves nothing"). `check-pod-overlay`'s plan was simplified to match: the
vestigial embedded `run: charly update` step (always skipped, never functional)
and the redundant second check are removed — the SAME `pod-overlay-ripgrep-installed`
check is now genuinely re-evaluated by the bed runner's new unconditional
post-rebuild pass, so it is both the initial-deploy AND the fresh-rebuild proof.

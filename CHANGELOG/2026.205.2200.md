## Five regressions found and fixed during integration

The full disposable-bed R10 roster — run across the integrated wave, not any
single leg in isolation — surfaced five genuine regressions. Per R1/R2 every
one was root-caused and fixed in this same cutover; none was deferred or
downgraded to a follow-up.

1. **SIGSEGV in `WriteLabels`/`ResolveBaseImage`: nil `BakedMetadata` for a
   namespaced box** (`3c8fe869`). `fillNamespacedBoxes` (an earlier wave-2 unit
   in this same cutover) rebuilt a namespace's boxes without running them
   through render-prep and without preserving an already-render-prepped entry
   already in `rp.Boxes`, so a namespaced box's `BakedMetadata`/`DistroDef`
   stayed nil past generation, crashing `WriteLabels` (nil `meta.Version`
   dereference) and `ResolveBaseImage` (`parentImg.FullTag` on an unresolved
   parent) for 9 `cachyos` images. Fixed by render-prepping namespace boxes via
   a temporary `Generator` and by skipping any `rp.Boxes` entry already
   correctly populated by `buildkit.ResolveAllBox`'s demand-pull.

2. **`charly update` on a k3s deploy never re-establishes the forwarded
   kubeconfig port** (`dd4ce3d6`). `pluginDeployTarget.Update()` never called
   `K3sPostProvision` — only `Add()` did, gated on the deploy's candy list
   declaring `register: kubeconfig`. Fixed by adding the same call to
   `Update()`, gated on `providerRegistry.ResolveVerb("kube")` (a pure,
   side-effect-free check — the same guard class `Add()`'s candy-list check
   already provides, adapted since `Update()` has no fresh candy list to read).

3. **`--add-candy <ref>` / a deploy's `add_candy:` — candy not in
   resolved-project envelope (the STANDARD compile path)** (`a9dc2c7c`). The
   host's own scan for a remote add-candy ref (`scanCandiesForRef`) and
   `candy/plugin-bundle`'s `compileDeployPlans` handler's OWN independent
   `HostBuild("resolved-project")` re-fetch ran without sharing the widened
   candy set. Fixed by adding `extra_candy_refs?` to
   `#ResolvedProjectRequest`/`#DeployCompileRequest` (sdk schema) and
   threading the host's `ExtraCandyRefs` through `compileSelectionViaPlugin`.

4. **The SAME class of bug on the pod-overlay build path (envelope)**
   (`067940bd`). `candy/plugin-installstep`'s `getGenerator` — used to render
   HOST-COUPLED step words (`system-packages`/`builder`/`op`) during an
   overlay build — independently re-fetches its OWN "resolved-project"
   envelope, which ALSO needed the widened candy set. Fixed by adding
   `extra_candy_refs?` to `#BuildEnv` and threading it through
   `dispatchOCIStep` → `emitHostCoupled` → `getGenerator`.

5. **The SAME class of bug, final round — `OCITarget.Emit(<candy>): task emit:
   candy "<candy>" not found`** (`4b3d94eb`). Fixing (4) closed the envelope
   gap but the failure persisted one step later, at the OpStep build-emit's own
   `candyByName` lookup. Root cause: `compileNodePlans` (`charly/bundle_add_cmd.go`
   — shared by BOTH the CLI `--add-candy` flag and a declared `add_candy:` node
   field, via `hostBuildDeployNodeDispatch`) recorded only each add-candy
   plan's BARE resolved candy name into `InstallPlan.AddCandies`. Every
   downstream site that unions `AddCandies` into `ResolveOpts.ExtraCandyRefs`
   to widen a re-fetch — `hostBuildOverlay`'s own overlay `Generator`/envelope
   AND `plugin-installstep`'s `getGenerator` (fixed in (4)) — therefore got fed
   a bare name, a silent no-op for a REMOTE ref: `ScanAllCandyWithConfigOpts`'s
   `addRef` gates on `IsRemoteCandyRef`, which is a plain `strings.HasPrefix(ref,
   "@")` check. A remote add_candy candy resolved correctly at COMPILE time
   (fixes (3)/(4)) but was silently dropped from every LATER independent
   re-fetch. The fix itself (see (4)'s own commit for the anti-pattern's first
   appearance) also had a residual instance: `charly/oci_step_emit.go`'s
   `dispatchOCIStep` derived its `ExtraCandyRefs` from `Generator.Candies`'s map
   KEYS — those keys are the scan result's own bare/repo-path-qualified names,
   never `"@"`-prefixed, so an equally silent no-op. Fixed by (a) threading the
   ORIGINAL authored ref through `AddCandies` alongside the bare name(s) in
   `compileNodePlans`, and (b) adding a `Generator.ExtraCandyRefs` field
   recording the ORIGINAL `ResolveOpts.ExtraCandyRefs` a `Generator` was built
   with (mirroring `DevLocalPkg`), threaded through instead of re-derived.
   Regression-guarded by the existing `TestGeneratorCandyByNameRemoteQualifiedKey`
   (charly) plus the new end-to-end proof: `charly check run check-addcandy-pod`
   PASS (13 steps, full build → deploy → check → feature → fresh-`update` cycle).
   Audited every other `ExtraCandyRefs` producer/consumer and every
   `range X.Candies` site across `charly/*.go`, `candy/plugin-bundle`,
   `candy/plugin-installstep`, `candy/plugin-deploy-pod`, and `sdk/deploykit` —
   no other instance of the bare-vs-qualified anti-pattern found.

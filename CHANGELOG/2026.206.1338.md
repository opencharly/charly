## The three units landed

- **Unit A** — `candy/plugin-bundle`'s `resolveNodeTemplate` (a `local:` node's
  `from:` template lookup) now reads the SAME resolved-project envelope its
  compile step already fetches (`Templates.Local` RawBody map) and projects it
  via the `kind:local` provider's own `OpResolve` leg
  (`sdk.Executor.InvokeProvider`), instead of a per-node HostBuild round-trip
  through `LoadUnified`. The "deploy-entity-resolve" seam's `kind="local"` case
  (its only caller) is deleted — dead code, no replacement needed.
- **Unit B candy-half** — `compileStandaloneCandySelection` (a `target: local`/`vm`
  deploy with no base image): the plugin resolves the candy topo order
  (`deploykit.ResolveCandyOrder` over its own `rp.CandyModels`) and builds its
  own synthetic host/vm box (`vmshared.DetectHostDistro`/`DetectHostGlibc` for a
  host target; the `kind:vm` provider's own `OpResolve` leg for a vm target) —
  no `LoadUnified`, no registry, no new `HostBuild` kind. `charly` core's
  `syntheticHostBox`/`syntheticVmBox` are DELETED (R5) — their sole remaining
  caller moved. `pruneContainerInitForSystemd` relocates to `sdk/deploykit`
  (pure, no core-only dependency) so both this path and the still-host-side box
  path share one copy (R3) instead of duplicating it.
- **Unit B box-half** — `compileBoxSelection` (a primary pod/k8s image deploy):
  the plugin reads `rp.Boxes[box_ref]` directly — the SAME `ResolvedBoxView` the
  host used to build the envelope in the first place, zero re-derivation — and
  resolves the candy order the same way as the candy-half. `ResolveBox`/
  `ScanAllCandyWithConfig`/the host-side candy-order resolve/the builder
  pre-connect call are all deleted from this path.

**Unit C deferred as tracked K4-exit debt** (per operator ruling, not attempted

`SaveBundleConfig`).

## The builder-connect finding — no new seam needed

Both Unit B shapes drop the host-side builder pre-connect
(`preresolveBuildersInto`/`ensureBuildersConnectedForOrder`) entirely, relying
on `candy/plugin-bundle`'s ALREADY-EXISTING `preresolveBuilderContexts`
(unconditional for every `OpCompile`, box or candy) — it already
S2-lazy-connects any externalized builder the resolved order+img trigger via
`sdk.Executor.InvokeProvider`. An exhaustive repo grep (the superproject
`charly.yml` and every `box/*/charly.yml`) found zero `target: local`/`vm` or
primary pod/k8s deploy anywhere needing a builder plugin outside the calling
project's own candy closure — the one edge `InvokeProvider`'s S2 Pass-1
project-scan can't cover (a builder vendored only in a box/&lt;distro&gt;
submodule, reachable only via `CHARLY_REPO_OVERRIDE`) is exclusively a
BOX-BUILD-time concern (`external_builder:`, `emitExternalBuilderStages`),
never reached from a deploy-time compile. So no new `HostBuild` kind was
needed — the generic F10 plugin↔plugin dispatch already IS the seam.

## RCA'd along the way

- Live-bed-caught (fixed same cutover): `resolveVmEntity` threads `node.From`
  into `vmEntity` UNCONDITIONALLY (not only for a genuine `vm:` cross-ref) — a
  plain `local: {from: <template>}` node's kind:local template ref also lands
  in `vmEntity`. The first draft treated a non-empty `vmEntity` as authoritative
  and hard-errored on the miss; fixed to mirror the OLD host code's own
  tolerant fall-through (try the vm lookup, fall through to a host box on a
  miss) — `check-preempt-local` failed then passed after the fix.
- Applied proactively before it could bite live (box-half): `ResolveBox`
  never checked `IsEnabled()` — enabled-filtering is a `ResolveAllBox`/listing
  concern — but the envelope's box loop skips disabled boxes by default.
  `HostBuild("resolved-project")`'s box_ref fetch now sets `IncludeDisabled:
  true` so an explicitly-named `enabled: false` box still resolves (zero live
  cost today — zero disabled boxes exist repo-wide — future-proofing only).

## #57 — the `command:` check verb gains `expect_non_zero` (negative-expect coverage)

The `command:` check verb could assert an EXACT exit code via the base `#Op`
`exit_status` matcher (default 0), but had NO way to assert "this command SHOULD fail"
when the failure code is non-deterministic (127 vs 1 vs 2) or simply irrelevant. That gap
left the whole class of negative-expectation checks inexpressible.

SDD schema change (CUE is the single source):
- `candy/plugin-command/schema/command.cue` — new `expect_non_zero?: bool
  @go(ExpectNonZero)` field on `#CommandInput`, regenerated into
  `candy/plugin-command/params/cue_types_gen.go` via `task cue:gen` (idempotent /
  reproducible — a clean re-run is a no-op; no `sdk/spec` or sibling-plugin drift).
- `candy/plugin-command/plugin.go` `RunVerb` — when `expect_non_zero` is true, assert
  `exitCode != 0` (any non-zero) and IGNORE `exit_status` (the two are mutually-exclusive
  intents: any-non-zero vs exact-code). Default false preserves the historic exit_status
  behaviour exactly. The stdout/stderr matchers still run, so an expected-failure's stderr
  remains assertable.

Coverage:
- `candy/plugin-command/plugin_test.go` (new) — three unit tests that FAIL without the
  field: `expect_non_zero` PASSES on exits 1/2/127, FAILS on exit 0, and the historic
  exact-code path (default 0, explicit exit_status:3) is unchanged.
- `candy/check-stack-layer/charly.yml` — a `check-expect-non-zero` plan step
  (`command: false; expect_non_zero: true`) so the `check-pod` bed exercises the field on
  a LIVE deployment. Proven on `check-pod` (calver 2026.209.2224, 13/13): the step PASSED
  `exit=1` in check-image, check-live, feature-run, AND both fresh-rebuild phases
  (check-live-rebuild, feature-run-rebuild), and is baked into the image's
  `ai.opencharly.description` label.

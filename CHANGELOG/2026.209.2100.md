## #57 — the `command:` check verb gains `expect_non_zero` (negative-expect coverage)

The `command:` check verb could assert an EXACT exit code via the base `#Op`
`exit_status` matcher (default 0), but had NO way to assert "this command SHOULD
fail" when the failure code is non-deterministic (127 vs 1 vs 2) or simply
irrelevant. That gap left the whole class of negative-expectation checks
inexpressible.

SDD schema change (CUE is the single source):
- `candy/plugin-command/schema/command.cue` — new `expect_non_zero?: bool
  @go(ExpectNonZero)` field on `#CommandInput`, regenerated into
  `candy/plugin-command/params/cue_types_gen.go` via `task cue:gen` (idempotent /
  reproducible — a clean re-run is a no-op; no `sdk/spec` or sibling-plugin drift).
- `candy/plugin-command/plugin.go` `RunVerb` — when `expect_non_zero` is true, assert
  `exitCode != 0` (any non-zero) and IGNORE `exit_status` (the two are
  mutually-exclusive intents: any-non-zero vs exact-code). Default false preserves the
  historic exit_status behaviour exactly. The stdout/stderr matchers still run, so an
  expected-failure's stderr remains assertable.

Coverage:
- `candy/plugin-command/plugin_test.go` (new) — three tests that FAIL without the
  field: `expect_non_zero` PASSES on exits 1/2/127, FAILS on exit 0, and the historic
  exact-code path (default 0, explicit exit_status:3) is unchanged.
- `candy/check-stack-layer/charly.yml` — a `check-expect-non-zero` plan step
  (`command: false; expect_non_zero: true`) so the `check-pod` bed exercises the field
  on a live deployment. Deterministic + idempotent (`false` always exits 1), runs
  standalone with no agent.

## #61 — k3s-server candy kubeconfig artifact-wait was too tight for a fresh deploy

`candy/k3s-server/charly.yml`'s `artifact:` kubeconfig-wait was `wait_second: 120`.
A genuinely fresh `check-k3s-vm` deploy-add timed out with
`timeout after 2m0s waiting for /etc/rancher/k3s/k3s.yaml`: k3s first-boot on a cold
libvirt guest is itself ~2m, and it is PRECEDED by this deploy's own dependency
install (ethtool/socat/conntrack/fuse), so the cumulative wall-clock to the first
kubeconfig routinely exceeded the 2m deadline. `wait_second` is the existing
per-artifact, config-sourced field (`sdk/deploykit/artifact_retrieve.go`
`waitForArtifactPath`, `WaitCapped` preserves it EXACTLY) — the fix is a named value
bump to `300` (5m), covering first-boot + dep-install with headroom (R4: a named,
config-sourced value with a documenting comment, not a magic number). File existence
is still the synchronization primitive and polling stays 1s, so a fast boot returns
as soon as the file appears — the larger deadline only raises the ceiling, never the
common-case latency. `check-k3s-vm` composes k3s-vm → k3s-server, so the longer wait
flows through automatically (no separate override).

Candy `version:` bumped on both edited candies (`k3s-server`, `check-stack-layer`) per
per-entity content-versioning.

# 2026.215.1735 — opencharly.ai: the docs submodule, the `charly docs` runtime plugin, and the docs-site bed

OpenCharly gets a public documentation site. `opencharly/docs` joins as the `docs/` submodule, a
new RUNTIME plugin generates the site's reference half from this repo's own declarations, and a
disposable bed builds and proves the result.

## `candy/plugin-docs` — a RUNTIME (out-of-process) command plugin

`charly docs generate` renders the generated half of the site. It is **deliberately absent from
`charly/charly.yml`'s `compiled_plugins:`**: a dev-time documentation generator has no business
inside every shipped `charly` binary. charly prescans the declared `docs` word into the Kong
grammar before parse and syscall.Exec's the plugin in CLI mode on first invocation.

The placement is free here because the generator is self-contained — it reads files and writes
markdown, never reaching the host reverse channel — the same property that lets `charly candy`
and `charly migrate` run in either placement. Being outside `compiled_plugins:` also puts it
outside `go.work`, so it builds and tests with `GOWORK=off`.

### It generates from declarative sources, not from the CLI's help output

The obvious approach — scrape `charly --help` — was spiked and refuted. The host renders every
dynamic command word with a generic stub description and intercepts the depth-1 `--help` itself;
`charly <word> help` forwards for kong-based plugins (`bundle`, `alias`, `agent`) but
`charly secrets help` errors and `charly candy help` returns a custom usage line; there is no
machine-readable dump. Three-plus incompatible formats with no dump is the fragile shim R4
forbids.

Every fact the site needs is already declared: `plugin.providers`, the per-plugin `schema/*.cue`,
and each candy's `description:`. That source is also placement-invisible, which is what lets the
generator itself run out-of-process.

### Defined, not default-active

The catalog walks **each repo as its own project root** — the superproject plus every
`box/<distro>` submodule — and unions the results. The resolver's own surfaces are wrong for a
catalog, in both directions: `charly box list boxes` lists *enabled* boxes and resolves through
main's `import:` closure, which pulls arch, cachyos and fedora but **not** debian or ubuntu — so
ten checked-out box definitions (every `debian.*` and `ubuntu.*`, families the README advertises
and that have their own skills) are invisible to it, while ten more appear as transitive
`cachyos.arch.*` aliases of boxes that already exist under `arch.*`.

Likewise all 86 plugin candies are documented, not just the 58 in `compiled_plugins:` — a plugin
absent from that list still loads out-of-process when a plan references its word.

### Link integrity — two gates

**Harness cross-references** (`links.go`). The skill corpus is densely self-linked: 3665
references across 257 distinct targets in the `SKILL.md` + `references/*.md` files the generator
reads, `/charly-check:check` alone appearing 268 times. **3654 of those are rewritten** into site
links — every reference in a skill BODY. The remaining 11 sit in `SKILL.md` frontmatter
`description:` fields and reach the published site **nowhere**: the generator strips the
frontmatter before rewriting, and `firstLine` then truncates the description to its first sentence
for the page subtitle, dropping all 11. They resolve, so nothing breaks — but for that reason,
not because they are published unlinked. An unresolvable body reference fails generation.

This paragraph took four attempts across four review rounds (`258`→`257` targets, "four
trees"→three, `256`→`257` in `links.go`, and "published as subtitle text"→published nowhere).
Every one was the same error: measuring at one scope and describing another. It is recorded rather
than quietly fixed because the lesson generalizes to any claim made about a generator — check it
against the generator, not against its documentation. Three guards keep real
content from being mangled into links, each earned from an actual corpus case and locked in by
`links_test.go`: the skill part must start with a letter (else `redis://charly-redis:6379`
matches), the reference must not follow `/` (URL authorities), and it must not follow a word
character (image tags such as `localhost/charly-selkies-kde:latest`).

**Every internal site link** (`links_site.go`). The gate above covers only harness references
inside skill bodies, which is narrower than "the build checks its links" — and the gap shipped a
real defect: three pages linked to `/recipes/`, which emitted no page because the sidebar entry
for it is an autogenerated group label rather than a route, and the build stayed green. One of
the three was itself generated, from the vision page's rewrite table. So a second gate resolves
**every** site-absolute markdown link — generated and hand-authored alike — against the routes
the content tree actually emits, and the generator now emits a real `recipes/index.md` landing
page. Regression-guarded by `links_site_test.go`.

Both gates cover markdown: bodies and YAML frontmatter (`link:` targets, which is how a Starlight
splash page declares its hero buttons — the most prominent links on the site, and invisible to a
body-only scan). **One class remains unchecked and is stated here rather than left implicit:** the
two sidebar `link:` entries in `astro.config.mjs` are JavaScript, outside a markdown-tree gate.
Both resolve today, and the built-site audit covers them because the sidebar renders into every
page — but statically they are the remaining way this defect class returns. Closing it would mean
teaching the generator to parse the Astro config, which it should not do.

The lesson is worth keeping: a half-checking gate is worse than none, because the claim built on
it gets believed. The narrow gate was accurately described in code and over-claimed in prose.

## `candy/docs-site` + `docs-site-app` + `check-docs`

The candy clones the published `opencharly/docs` repository, runs `npm ci` against its committed
lockfile, and runs the production Astro build — so a bad frontmatter scalar or an invalidated
Starlight config fails the IMAGE BUILD, from the same input Cloudflare Pages builds.

It clones rather than reading the sibling `docs/` submodule because a candy cannot reach outside
its own directory: `copy:` rejects `..` at validate time, and the `directory:` field that
`/charly-image:layer` documented **does not exist** (absent from `spec/schema/candy.cue`, from
the generated spec types and from the loader; `charly box validate` rejects it as
`field not allowed`). That divergence is fixed in the plugins repo this release. The consequence
is an ordering dependency: the bed goes green only once docs content is merged to that repo's
`main`.

The bed's load-bearing assertion reads the page of `plugin-cdp` — a plugin that is **not**
compiled in — and requires both its rendered runtime placement and its CUE parameter schema. That
step fails the moment the generator narrows to documenting only what ships in the binary, which
is the most plausible way for this catalog to go quietly wrong.

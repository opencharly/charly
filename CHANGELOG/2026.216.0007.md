# 2026.216.0007 — init `depends_candy:` auto-injection (superproject leg)

The superproject leg of the init-dependency injection cutover. Declaring a `service:` in a
candy is what SELECTS an init system and assembles its config — but nothing installed the
selected init's own binary. A box composing only service candies validated clean, built clean,
baked `ai.opencharly.init="supervisord"` and a fully assembled `/etc/supervisord.conf`, and
then failed at deploy `[start]` with no supervisord in the image. The
`fallback_entrypoint: [sleep, infinity]` did not mask it.

## What lands here

- **`candy/plugin-build/resolve.go`** — call `deploykit.InjectInitDependsCandy(cfg, layers,
  initCfg)` in `resolveBuildEngine` after the candy scan (the pass resolves the init over the
  scanned set) and **BEFORE** `buildkit.ResolveAllBox`. The ordering is load-bearing: the pass
  writes the AUTHORED composition on `cfg`, which is the one source both the resolved boxes and
  every `cfg`-walking chain collector derive from. Writing it here is what carries the injected
  candy into the intermediate trie, the render candy order, the emitted Containerfile, the baked
  labels, AND the collected `ai.opencharly.description` acceptance plan.

  An earlier revision of this entry described the call as running *after* `ResolveAllBox`, which
  was true of the first design and false of the shipped one — `opencharly/sdk#120` moved the
  write from the derived `ResolvedBox.Candy` view to its `cfg` source precisely because the
  collectors read the source. The placement inverted; the entry had not.

- **`candy/plugin-box/validate_graph.go` + `validate.go`** — **R5 deletion** of
  `validateInitDependencies` and its now-unreachable helpers (`initDefRequirementsMet`,
  `checkInitSystemRequirements`, `collectInitSystemNeeds`, `checkDualInitFallback`,
  `candyHasInit`). A box can no longer be missing its init's dependency candy, because injection
  adds it at every box-composition path. The guard was also unable to catch the case that
  actually broke deploys: it WAIVED itself, via a dual-init fallback, for exactly the mixed
  `use_packaged:`/`exec:` service shape the layer skill recommends everywhere — which is what
  `candy/sshd` is. The deleted code had **zero test coverage**, which is part of why the defect
  survived. `boxPreserveUser` is kept: another rule reads it.

- **`candy/plugin-docs/go.mod`** — re-point the `spec` pin so the docs generator builds again.
  `GOWORK=off go build ./...` — the exact way charly's loader builds an out-of-tree plugin —
  failed with "updates to go.mod needed", which breaks `task docs:sync` and any bed whose plugin
  load reaches the generator.

## Why deleting the guard is safe

`buildkit.ResolveBox` is the ONLY place a box's `Candy` list is set, so every composition path
funnels through one of three seams. Since `opencharly/sdk#120` all three are satisfied by a single
write to `cfg`, because each derives its candy list from it:

| Seam | Feeds |
|---|---|
| `ResolveAllBox`'s returned map | the build/generate path — the call wired here |
| `loaderkit.ProjectResolvedProject` fresh-box loop | validate, inspect, bundle-deploy |
| `deploykit.FillNamespaceBoxViews` | import-namespace boxes |

The bundle-deploy path needs no separate call: `resolveBoxSelection` reads `rp.Boxes` from the
envelope the second seam produces. A `local:`/VM deploy compiles candies rather than boxes, so no
box composition happens there at all.

## Verification

R10 on the final tree:

```
charly check run check-tutorial-shell: PASS (steps=13)
charly check run check-migrate-local:  PASS (steps=6)
```

`check-tutorial-shell` is the discriminating one: its box composes NO supervisord candy, and
`/etc/supervisord.conf` still carries `[program:sshd]`. Live step counts are 24/22 — the same as
before the init was dropped from the composition, which is what proves the injected candy
contributes its acceptance plan and not merely its binary.

`go build` green in `charly`, every in-workspace module and every out-of-work candy under
`GOWORK=off` (`plugin-docs` included — its `spec` pin changes here, and the old pin fails in place
with `updates to go.mod needed`). `go test` green with ONE disclosed exception:
`candy/plugin-tmux`'s `TestConcurrentTmuxRunsIsolateTypedPasteAndHighVolumeOutput` passes in
isolation but fails under a loaded parallel run. It is untouched by this cutover, imports neither
`deploykit` nor `loaderkit`, and is routed to the candy-hygiene batch — where the defect on record
is the INTERMITTENCY itself, since "it fails" and "it flakes" need different fixes and R1 does not
accept "flake" as a resting place. `gofmt -l` empty; binary rebuilt via `task build:binary`.

## Landing

Consumer leg of a chain: `spec` → `sdk` (#119 + #120) → `box/fedora` (#11) → **this**. It lands
BEFORE `opencharly/plugins#125` and `opencharly/docs#8`, both of which document the injection: the
call site and the validator deletion live here, so until this merges, `charly` on `main` neither
injects nor has stopped policing, and those pages would describe behaviour the tool does not have.

This is a SEPARATE cutover from the gourmet-kitchen documentation rebrand, which lands on its own
branch. Both were accumulated on one integration branch during development; two cutovers must not
share one PR, so they are split here.

# 2026.216.0808 — 326 Kong flag tags that never took effect; four published commands exited 80

Kong renames a flag with `name:"..."`. The tree used `long:"..."` — go-flags
syntax that Kong does not read — in 326 struct tags. Kong silently fell back to
deriving each flag from the FIELD NAME. Nothing errored. The author's stated
intent was discarded 326 times.

311 of those were harmless: `Session []string` yields `--session` whichever tag
is present. The defect surfaced in the 15 places where the field name does not
produce the intended flag — and in four of them the flag was PUBLISHED on
opencharly.ai, so a reader who copy-pasted the documented command got exit 80.

## The four published-and-broken commands

| Documented | Shipped | Published at |
|---|---|---|
| `charly box new box … --candy <a,b,c>` | `--candies` | `plugins/image/skills/image/SKILL.md` |
| `charly box write <path> --from-stdin` | `--from-in` | `plugins/image/skills/image/SKILL.md` |
| `charly config <box> --volume <spec>` | `--volume-flag` | `plugins/core/skills/charly-config/SKILL.md` |
| `charly secrets gpg setup --skip-secret-service` | `--skip-ss` | `plugins/build/skills/secrets/SKILL.md` |

`--candy` was fixed in the previous entry. The other three are fixed here. In
every case the documentation was right and the binary was wrong: the field name
had leaked a Go artifact — a plural, an abbreviation ("In" for stdin, "SS" for
Secret Service), or the word "Flag" — into the published vocabulary.

## BREAKING — flags renamed

| Command(s) | Old (removed) | New |
|---|---|---|
| `charly box write` | `--from-in` | `--from-stdin` |
| `charly config` / `charly start` / `charly shell` | `--volume-flag` | `--volume` (the `-v` short form is unchanged) |
| `charly secrets gpg setup` | `--skip-ss` | `--skip-secret-service` |
| the `libvirt:` check verb's `passwd` grammar | `--persist` | `--persistent` |

None of the removed spellings was documented anywhere. `--volume` also
harmonizes `charly config <box> --volume` with `charly config mount --volume`,
which already worked — the two had silently diverged because one field was named
`VolumeFlag` and the other `Volume`.

The `--persist` rename is inert in practice: `LibvirtPasswdCmd` is not mounted on
any user-facing Kong tree, and `dispatchLibvirtVerb` builds its argv from the
`libvirtMethods` table, which never passes the flag. The flag is unreachable from
every surface — recorded here because the tag now says what it would ship.

## Kept deliberately, tag corrected to match

Where the derived name was already the better word, the flag STAYS and the tag
now states it, so the declaration and the binary agree:

- `--assume-yes` (not `--yes`): `spec.BundleDelArgv` emits it, three repos assert
  it in tests, four call sites shell out with it, and `spec/spec/deploy_key.go`
  documents it as the one valid spelling.
- `--run-id` (not `--run`) on `charly agent incident create`: the other eight
  `charly agent terminal …` commands and five skills already use `--run-id`.
- `--no-auto-detect` (not `--no-autodetect`) on `charly config` / `start` /
  `shell` / `vm create`: `plugins/vm/skills/arch-cloud-vm` documents a runnable
  `--no-auto-detect` invocation, and it is what `--help` has always printed.

Six skill lines documented the `--no-autodetect` spelling, which has never
worked. They are corrected to `--no-auto-detect` — rather than the flag being
renamed to match them — in the `plugins` repo (`docs(core): six lines documented
--no-autodetect, which has never worked`); the six generated `docs/` mirrors
follow from `task docs:sync`, never a hand edit. `charly doctor` printed the same
broken hint ("Disable with: --no-autodetect") at runtime; that string lives in
this repo and is corrected here.

## Dead code

`charly/devices.go` declared an `AutoDetectFlags` struct that nothing embedded:
the pod commands that once used it moved to `candy/plugin-pod` and now declare
the field inline. A whole-tree, all-submodule grep found zero consumers, so it is
deleted. The comment in `candy/plugin-vm/vm_move_aliases.go` asserting that core
"keeps its own (shell/start/config_image commands embed it too)" was false and is
corrected.

## The gate

`charly/kong_flag_tag_test.go` fails on any `long:` key in any struct tag under
`charly/` or `candy/`, reporting the file, the field, and — by asking Kong itself,
never by reimplementing its derivation — the flag that would actually have
shipped. It refuses to pass vacuously: it asserts it found at least 250
`name:`-tagged fields, so a moved directory surfaces as a failure rather than as
a green run over an empty walk.

## Measurement note

`charly secrets` and `charly vm` are served by out-of-process plugins that this
host also has installed system-wide under `/usr/lib/charly/plugins` (the
`opencharly-git` package). `resolveCommandPluginBinary` consults those baked
binaries BEFORE the project's candy source, so on such a host `./bin/charly`
silently runs a stale system plugin and a worktree edit appears to have no
effect. Verification of those two used `CHARLY_PLUGIN_DIR`, which takes
precedence, pointed at binaries freshly built from the worktree.

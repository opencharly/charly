# 2026.216.1449 — `--repo` could not deliver a working command from the binary alone

`--repo` exists so someone who installed `charly` as a native package, with no
checkout anywhere, can run a documented command. It could not. Three independent
defects sat in that one path, and fixing any one of them alone still left the
command broken — which is why they land together.

## 1. The verb was never registered

`charly --repo opencharly/charly mcp serve` printed `Usage:` — unknown verb —
from any directory that was not already a charly project. From inside a project
the same command worked, so the flag appeared to work only where it was not
needed.

ROOT CAUSE. `prescanProjectCommandWords()` is what puts an out-of-process
command word into the Kong grammar, and it asked `projectDirPreParse()` for the
project. That resolver knew `CHARLY_PROJECT_DIR`, `-C`/`--dir`, and cwd — but
not `--repo`. Since `kong.Parse` freezes the grammar before main()'s post-parse
`--repo` chdir, a verb living only in the `--repo` target was never registered.
Reading `charly.yml` worked, because that happens after the chdir; finding the
verb did not.

The blast radius was every command word not baked into the binary. The packaged
build bakes nine (candy clean doctor feature preempt secrets settings udev vm),
so those resolved anywhere; `mcp`, `bundle`, `status`, `agent`, `tmux`, `tui`
and the rest needed a local checkout.

THE FIX. `projectDirPreParse()` now also resolves `--repo` and
`CHARLY_PROJECT_REPO`, via the same `ResolveProjectRepo` main() uses. This
matches the existing design rather than restructuring startup — the function
already answers "which project dir, before parse"; it simply did not know about
one of the three ways to say it. Resolution can clone, so it is attempted only
when the flag or env var is present — a bare invocation never touches the network.

An UNRESOLVABLE spec falls through to cwd: main() resolves the same spec moments
later and reports `cannot resolve --repo` properly, so a broken `--repo` must not
also take the LOCAL grammar away. The first draft of this change described that
behaviour and did not implement it — it returned "" instead, before the cwd
branch, so from inside a real project `charly --repo <bad> mcp …` died on
`unexpected argument mcp, did you mean "cp"?`. That is verbatim the unknown-verb
dead end this cutover exists to remove, reproduced in its own error path, and it
shipped past a test that called `projectDirPreParse()` and asserted nothing on
the result. Both are fixed: the fallthrough is real, and the test now asserts it
returns cwd for an unresolvable spec via both the flag and the env var.

Unit coverage in `plugin_command_prescan_repo_test.go` pins the argv scanning
(both `--repo <spec>` and `--repo=<spec>`, argv[0] skipped) and the precedence
chain, including that a bare invocation falls back to cwd rather than "" — an
empty return would silently disable the prescan and drop every project-provided
verb from the grammar.

## 2. The fetched cache was missing eleven of its twelve submodules

Registering the verb only exposed the next failure. The fix lives in the `spec`
submodule (`refs.populateSubmodules`, entry 2026.216.1015) and is required by
this one: out-of-process candies build standalone under `GOWORK=off` against
`replace … => ../../sdk` and `=> ../../spec`, and `spec/` was an empty
directory, so every such build died on `../../spec/go.mod: no such file`.

## 3. The staleness guard refused to run against the cache

With the verb registered and the cache complete, `CheckBinaryFreshness` aborted
instead: *"The source tree has been edited since this binary was built."*

ROOT CAUSE. The guard walks up from cwd for a directory holding both
`charly/main.go` and `charly.yml`, and a `--repo` cache holds exactly that — so
it is detected as a source tree. Its premise, "you edited source this binary
predates", cannot hold there: git just wrote every file, so the cache mtime
ALWAYS beats the binary, and the guard fired on every `charly --repo … <heavy
verb>`. The remedy it printed — `cd <cache> && task build:binary` — is both
impossible to act on for a packaged user and pointless, since that cache is not
where their `charly` came from.

THE FIX. `isUnderRepoCache` short-circuits the check when the detected source
root lies inside the repo cache (`~/.cache/charly/repos`, or
`CHARLY_REPO_CACHE`). It is phrased as a property of the TREE rather than of how
the project dir was chosen, so it holds however cwd got there — `--repo`,
`CHARLY_PROJECT_REPO`, or a user who simply cd'd into a cache. A real checkout
is still guarded: verified by touching `charly/main.go` and confirming
`charly box build` still aborts with the stale-binary error.

## Proof

Earlier drafts of this entry claimed defect 1's fix was proven end to end by
`--repo … mcp serve` returning exit 124. **That was a warm-cache false
positive** — the run reused a cache a previous checkout had populated. On a cold
cache the same command exited 1 on the missing `spec/go.mod`. The claim is
recorded here because the correction is the reason defects 2 and 3 were found at
all: a green exit code that only reproduces on a dirty machine is not proof.

The honest end-to-end run, from `/tmp`, with `CHARLY_REPO_CACHE` pointed at a
path verified absent beforehand, and no charly checkout involved:

    charly --repo opencharly/charly mcp serve
    → Downloading github.com/opencharly/charly:main...
    → charly mcp: serving 70 tools on http://:18765/mcp
    → EXIT=124 (still serving) after 100s

The same cold cache shows 12/12 submodules populated, and
`charly --repo opencharly/charly box list boxes` returns the arch, cachyos and
fedora box catalogs in 44s.

FOUND BY a requirement that every command in the documentation must run as
written. Two doc pages had been weakened to say "-C a project you already have",
which was documenting around the bug instead of fixing it. They go back to
`--repo` in the docs leg.

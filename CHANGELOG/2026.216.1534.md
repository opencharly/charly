# 2026.216.1534 — the gourmet-kitchen rebrand, and a README that led with the wrong thing

The tagline described what charly *produces*. The bet it actually makes — the
opening of `VISION.md` and its first tenet — is that you hand an agent
*everything* rather than taking things away. **"The fully stocked gourmet kitchen
for you and your agents"** says that directly: a kitchen is where you work, and
*fully stocked* is the whole argument.

## What changed

- **`README.md` — cut to roughly a quarter of its length.** It was a pitch, a concept primer, a
  29-verb command reference, a catalog index and a troubleshooting table at once,
  most of it duplicated on opencharly.ai where the reference and recipe halves are
  GENERATED and cannot drift while a hand-kept copy can. It is now a door: what
  this is, the words, one worked example, install, where to learn more. The verb
  table, the catalogs and the troubleshooting matrix live in their generated homes.
- **`VISION.md` — one bullet.** Not a tenet: the twelve numbered tenets are
  byte-identical to `main`. The changed line is one of the six bullets under
  "Where the factory is heading", and it used "kitchen" for the *small kernel*
  while the new tagline uses it for the *whole product*. It now reads "A gourmet
  kitchen: a tiny core, an all-you-can-eat buffet." Everything else in the file
  keeps its factory voice deliberately; this was the single line whose MEANING
  collided with the new name.
- **`CLAUDE.md`** — the H1 is the tagline, so it follows or the sweep is false.
  `AGENTS.md` carries no tagline (verified, not assumed).
- **`GRIEVANCES.md`** (new) — the four DevOps grievances charly is
  reacting to, each with the status quo stated fairly rather than strawmanned,
  the mechanism charly answers it with, and an explicit *honest limits* section.
  Linked from the README rather than inlined.

## Two defects fixed along the way

**The README's own install section led with the checkout.** It opened with
"Development — the one workflow, per checkout" and treated native packages as an
afterthought "for end users". That is backwards: the package is how you use
charly, and every page on the site assumes it with no checkout anywhere. The
section now leads with the package and scopes the clone to working ON charly —
the same correction `start/install.md` needed. The `--repo` example added there
was run before it was written: `charly --repo opencharly/charly box list boxes`
exits 0 and lists the catalog.

**`taskfiles/Docs.yml` — four tasks that had never worked.** `task docs:build`
failed with
`ENOENT … /home/atrawog/Atrapub/o/charly/home/atrawog/Atrapub/o/charly/docs/package.json`.
`DOCS_DIR` is absolute (`{{.ROOT_DIR}}/docs`) and was used as a task-level `dir:`,
which Task resolves relative to the include's own `dir: {{.ROOT_DIR}}` — so the
two concatenate. `install`, `dev`, `build` and `preview` all used it that way, so
none of them had ever run; only `sync`/`drift`, which reference `DOCS_DIR` inside
commands rather than as `dir:`, worked. Fixed to a relative `dir: docs`.

## Deliberately not here

`scripts/verify-doc-excerpts.py` — the checker asserting every fenced YAML block
in the hand-authored docs is a real excerpt of a committed file. It belongs in the
superproject, because that is the only place that can see both the docs and the
sources they quote — but it CANNOT be green here. It reads pages
(`guides/authoring-a-candy.md` among them) that exist only on the branch
`opencharly/docs`#8 lands; against the `docs` gitlink this commit pins, it exits 1
on missing pages. Landing a gate that fails on its own tree is worse than landing
it late, so it moves to the leg that bumps the `docs` gitlink — the first tree
where it can pass. Its absence here is why this entry claims no excerpt
verification.

The rebrand branch this content came from also added a `check-docs-local` bed to
`charly.yml`. The docs no longer reference it — they quote `check-group`, which
is real on `main` today — so the bed would be a new, unreferenced R10 surface. It
is left out rather than landed unused; nothing depends on it.

The `docs` gitlink is NOT bumped here. `opencharly/docs`#8 is still open, and
pinning a gitlink at an unmerged branch head is the exact defect that blocked
charly#207. It moves in the leg after #8 merges, together with the
`candy/docs-site` `DOCS_REF` re-pin.

# 2026.217.0034 — a secret stored in cleartext now says so

`secret_backend: config` stays fully supported. What changes is that charly tells you when a
password or passphrase lands unencrypted on disk, instead of doing it silently.

## What triggers it

**Cleartext reaching disk — never a backend name.** That distinction is the whole design. The
common case is not an operator who deliberately pinned `secret_backend: config`; it is the
**default `auto`** falling back to the config-file store on a host with no keyring. A check keyed
on the backend's name would pass over exactly those machines in silence.

## Where it lives, and why only there

One warning, at `ConfigFileStore.Set` (`candy/plugin-secrets/credential_config.go`). That method
is the single funnel every cleartext credential write passes through — `charly secrets set`,
auto-generated `secret_require:` tokens, enc passphrases and VNC passwords alike — so warning
there covers all of them and cannot drift out of sync with a caller added later. Warning at call
sites would have been N copies and a standing invitation to miss the next one (R3).

It fires **after** the write succeeds, because the warning asserts that a secret is now sitting
unencrypted on disk, and that is not true if the save failed.

It fires **once per process**. A single `charly config` run can store several secrets; repeating
the same paragraph for each is how operators learn to scroll past the one message that matters.

## What deliberately does NOT warn

A false positive here is precisely what would make the real warning ignorable, so three
neighbouring writes stay silent:

| Not warned | Why |
|---|---|
| `Get` / `List` / `Delete` on the config store | no value is written |
| `addKeyringIndex` / `removeKeyringIndex` | they write the keyring shadow **index** to the same file — service/key NAMES, no values |
| `migrate-secrets` | it writes to the **keyring** and then clears the plaintext maps; it is the remedy for this warning, not an instance of it |

The keyring-index case is the subtle one: it writes the same `config.yml` through the same
`SaveRuntimeConfig`, so a warning keyed on "the config file was written" rather than on "a secret
went in unencrypted" would fire on the encrypted path. Covered by a test for that reason.

## Live proof

Default `auto`, no reachable keyring, isolated `XDG_CONFIG_HOME`:

```
charly: WARNING — secret stored in CLEARTEXT.
  "charly/enc/live-demo-box" was written unencrypted to …/charly/config.yml (mode 0600).
  Any further secret stored in this run lands there in the clear too; file
  permissions are the only thing protecting it.
  To store secrets encrypted instead, run a Secret Service provider (gnome-keyring,
  kwalletd, or KeePassXC with FdoSecrets enabled) — charly picks it up automatically.
  To move what is already stored: charly secrets migrate-secrets
```

The secret's VALUE is never echoed — asserted by test, not just by inspection.

**The first live run proved nothing and was discarded.** `charly secrets set` dispatches to the
out-of-process plugin, and it picked up the packaged `/usr/lib/charly/plugins/plugin-secrets`
rather than the rebuild, so the run exercised stale code and printed no warning. R9's rule that
the binary under test must be the one invoked applies to the PLUGIN binary too, not just
`charly` itself; the run above sets `CHARLY_PLUGIN_DIR` at a freshly built one.

## Coverage

Five tests, each mutation-proven red before being cited:

| Mutation | Result |
|---|---|
| warning removed entirely | RED — fires-on-set, once-per-process |
| fresh `sync.Once` per call (warns every time) | RED — once-per-process |
| warn before the save-error check | RED — not-on-failed-write |
| warning moved into `SaveRuntimeConfig` (keyed on "file written") | RED — fires-on-set, silent-on-non-writes, silent-on-keyring-index |

The last one is the placement proof: three tests catch it.

`TestCleartextWarning_NotOnFailedWrite` initially passed against its own mutation — it pointed the
config at a path whose parent was a file, which makes `LoadRuntimeConfig` fail first, so `Set`
returned before reaching either the warning or the save. It was asserting the right thing for the
wrong reason. Rewritten to use a read-only parent directory, so the load genuinely succeeds and
only the save fails — with the precondition asserted in the test rather than assumed — it now
fails against that mutation.

## The messages around it, folded in

A warning is only worth reading if nothing beside it says to ignore it. Adding this one turned an
existing wart into a contradiction, so it comes out in the same change (R2 — "pre-existing" is not
a classification this project accepts).

**Seven messages told the operator to run a command that does nothing.**
`charly config set secret_backend …` appeared 5× in `store.go` and 2× in `credential_keyring.go`.
`config` is the DEPLOY verb, so `set` is parsed as a box name:

```
$ charly config set secret_backend config
Usage: config setup [<box>] [flags]

$ charly settings set secret_backend config
Set secret_backend = config
```

All seven now name `charly settings set`, the form `credential_admin.go` already used.

**The suppression advice is deleted.** `PrintStoreInfo` offered "To suppress this message: … secret_backend config" — a documented path to exactly the outcome the new warning exists to flag, printed three lines above it.

**The duplicated advice is collapsed.** That branch also restated where credentials land, the file mode, and how to get Secret Service storage — all of which the warning now says, three lines later. It is reduced to the one thing the warning does not say: *why* the fallback happened. Both callers of `PrintStoreInfo` store immediately afterwards, so the warning always follows and nothing is lost.

Before and after, on the same command:

```
- System keyring not available (no D-Bus session bus).
- Credentials will be stored in ~/.config/charly/config.yml (permissions: 0600).
- To suppress this message: charly config set secret_backend config
- For Secret Service storage, run a keyring provider (gnome-keyring, kwalletd, KeePassXC ...).
+ System keyring not available (no D-Bus session bus).
  charly: WARNING — secret stored in CLEARTEXT.
  ...
```

`TestNoBrokenSecretBackendVerb` keeps the verb from coming back. It asserts over the package's own
source, because these strings sit on error paths no unit test drives, and it carries a
guard-the-guard clause that fails if the scan stops finding files — a source-scanning test that
finds nothing otherwise passes forever. Mutation-proven three ways: reintroduce the verb in
`store.go` (RED), in `credential_keyring.go` (RED, the second file), and point the scan at an empty
directory (RED on the guard).

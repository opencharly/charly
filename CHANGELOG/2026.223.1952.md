# 2026.223.1952 — charly under reasonix: the sandbox jail that broke podman

Root-caused and fixed a container-engine failure that hit every reasonix deployment
driving charly: podman "works in a terminal, fails for the agent" with
`read-only file system` (on `/run/user/1000`) and `newuidmap: Could not set caps`.

## Root cause

Reasonix's OS-level Bash sandbox (global `~/.reasonix/config.toml` `[sandbox]
bash = "enforce"`) jails every agent Bash call. The jail:
sets `NoNewPrivs=1`, empties the capability bounding set (`CapBnd: 0000…0000`),
drops the process into a nested user namespace (`uid_map 1000 0 1`), and remounts
`/run` and `$HOME` read-only.

Rootless podman — which charly uses for every box build/check/deploy op — requires
**both** a writable runroot (a subdir of `/run`) **and** the `newuidmap`/`newgidmap`
subordinate-id-mapping capabilities. The jail strips both, so podman fails only for
the agent while a normal operator terminal (no jail) runs it fine. The earlier
"environmental, unfixable" conclusion was wrong: it measured the sandbox, not the
host.

## Fix

Project-scoped override in `reasonix.toml`:

```toml
[sandbox]
bash = "off"
```

Resolution order is `flag > ./reasonix.toml > ~/.reasonix/config.toml`, so this
project override wins over the global jail and runs the project's agent Bash commands
on the real host — like an operator terminal — restoring podman. It is project-scoped
and does not change the operator's global reasonix security posture. The fix applies
on the next reasonix session (the jail is configured at session launch).

The `reasonix.toml` comment carries the full mechanism so future deployments (and
future readers of the file) do not rediscover it.

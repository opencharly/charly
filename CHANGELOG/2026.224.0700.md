# 2026.224.0700 — AgentTeams Unit 5: the compiled-in `charly agentteams` management plugin

The `charly agentteams` command tree lands as a compiled-in plugin (`candy/plugin-agentteams`, `command:agentteams`): a plain `net/http` REST client for the AgentTeams controller — no upstream `agt` binary, no SDK. `charly agentteams status` reports controller health + manager/worker/team/human counts; `worker list|get|create|update|apply|delete` manages Worker CRs (apply incl. ZIP/package import via multipart POST `/api/v1/packages`); `team apply|list|get|delete` and `human apply|list|get|delete` manage Teams and Humans; `apply -f <file>` applies declarative YAML (create-or-update per kind); `config` shows the resolved endpoint and token source. Token discovery matches upstream `agt` exactly (`AGENTTEAMS_AUTH_TOKEN` env → `AGENTTEAMS_AUTH_TOKEN_FILE` file → empty); the endpoint comes from `AGENTTEAMS_CONTROLLER_URL` (default `http://127.0.0.1:18090`).

The plugin is wired into the binary via `compiled_plugins:` in `charly/charly.yml` (pluginsgen regenerates `charly/plugins_generated.go` + `go.work`). The `check-agentteams-pod` bed gains two HOST-side check steps that pull the admin SA token out of the running controller with the charly-native `charly cp`, point `AGENTTEAMS_CONTROLLER_URL` at the controller's effective host port, and run `charly agentteams status` / `charly agentteams worker list` — proving the plugin's REST client + token discovery end-to-end against the live controller in both check-live phases.

R10 gate: `charly check run check-agentteams-pod` (disposable) — PASS (steps=13), zero warnings, on a fresh `charly update`, with both plugin checks green in the initial and fresh-rebuild check-live phases.

# 2026.225.2248 — Unit 1 helm cutover: `step:helm-release` + `verb:helm` + the `--enable-helm` apply path

The north-star's Unit 1 gap cutover (the approved factory plan, `PROGRAM/factory-north-star.md`): the out-of-tree `candy/plugin-helm` owns both helm words. The **step** is a plugin-contributed `external:helm-release` install-step KIND (F3): its opaque payload is the `#HelmReleaseStep` def, carried through the InstallPlan IR and validated against the plugin's served schema; the step performs `helm upgrade --install` **IN-VENUE** against the venue's kubeconfig (`/etc/rancher/k3s/k3s.yaml` on a k3s guest) and returns a teardown ReverseOp (`helm uninstall`) the host records + replays. The **verb** is the declarative release-status assertion (the `verb:kube` analog): method + method-exclusive modifiers ride the desugared plugin input, validated against `#HelmInput`; EXEC-based — it drives the venue's helm binary over the host's live DeployExecutor reverse channel, owning no Kubernetes client library.

- **`candy/plugin-helm`** (new, out-of-tree): `providers: [step:helm-release, verb:helm]`, the `#HelmReleaseStep` / `#HelmInput` CUE schemas, the in-venue `helm upgrade --install` OpExecute + the `helm uninstall` teardown ReverseOp, and the EXEC-based verb methods (release-exists / status / revision).
- **`candy/helm-chart`** (new): the check-helm-vm bed's install leg — the mutating install lives in a CANDY's `run:` steps (fleet add lowers only candy plans' `run:` steps; the bed's own plan is verify-only), plus its own ADE `check:` step asserting the release exists (R3).
- **`candy/k3s-kernel`** (new, `reboot: true`): the Arch cloud image boots a minimal kernel without overlayfs or iptables/netfilter — k3s's containerd and kube-proxy both fail on it. The candy installs the full distro kernel and the vm deploy's RebootStep reboots the venue mid-deploy (R1/R2 — the RCA of the 2026.225.1721 FAILED run: the system upgrade installs the full `linux` package but the running kernel stays minimal until a reboot, so k3s’s containerd/kube-proxy fail → apiserver-not-ready; the 2026.225.1748 failure was a separate issue — the install step authored in the bed’s own plan is skipped in verify-only mode — fixed by moving the install into the `candy/helm-chart` candy’s `run:` steps).

- **`candy/plugin-k8sgen`**: emits `deployment.kubernetes.helm_charts` into the overlay kustomization's `helmCharts:` list (chart→name, release→releaseName, values_files→valuesFile, includeCRDs: true) — the missing half the north-star calls out.
- **`candy/plugin-kube/deploy.go`**: the `--enable-helm` apply path — `kubectl apply -k` cannot render a `helmCharts:` overlay (the kustomize helmCharts transformer is gated behind `--enable-helm`, which only `kubectl kustomize` accepts), so when the overlay carries helmCharts the deploy renders with `kubectl kustomize --enable-helm` and applies the stream via `kubectl apply -f -`. The transformer sets each rendered resource's namespace but does NOT create the namespace object, so the deploy creates the declared namespaces first (idempotently, via `create --dry-run=client -o yaml | apply -f -`) and deletes them at teardown.

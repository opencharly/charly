# 2026.226.0953 — VM bootstrap: cloud-init unit-layout split + idempotent qemu `vm start`

Two root-caused defects in the VM bootstrap path, both surfaced by the
`check-debian-debootstrap-vm` bed and both fixed here.

- **Debian/Ubuntu debootstrap unit enablement (`charly/charly.yml` + the faithful copy
  in `candy/plugin-vm/build_defaults.yml`, R3).** The bootloader `install_template`
  enabled a fixed unit list that named the legacy `cloud-init` service
  unconditionally. cloud-init 24.3 (upstream PR #5489, "Single Process
  Optimization") SPLIT that unit: `cloud-init.service` was renamed to
  `cloud-init-network.service` and a new `cloud-init-main.service` daemon was
  added, with the four stage services becoming shims that connect to it over
  `/run/cloud-init/share/*.sock`. Debian 13 ships cloud-init 25.1.4, where the
  legacy name no longer exists, so the enable emitted `Failed to enable unit: Unit
  cloud-init.service does not exist` on every debootstrap build — swallowed by the
  step's `|| true`, so the bed passed while the template's own comment described a
  layout the distro had not shipped in two releases (R1: a warning is not a pass).
  Ubuntu 24.04 ships 24.1.3, BELOW the split, where the legacy unit is the real one
  and the template's enable is load-bearing (the package postinst does not enable
  the daemon there) — so neither name can simply replace the other. The enable loop
  now tests for each unit file before enabling it and covers BOTH layouts, and the
  comment states the version pivot instead of asserting one layout.

- **`charly vm start` was not idempotent on the QEMU backend
  (`candy/plugin-vm/vm.go`, `candy/plugin-vm/vm_qemu.go`).** Starting a VM whose
  QEMU process was already running re-executed the stored command, and the second
  QEMU failed to lock the pidfile — `qemu-system-x86_64: cannot create PID file:
  Cannot lock pid file: Resource temporarily unavailable`, exit 1. This broke the
  `update` step of every QEMU-backed bed: `vm create` already starts the domain, so
  the rebuild path's ensure-running guard hit an already-live VM every time. `vm
  start` now returns a clean no-op when the recorded process is alive, matching the
  libvirt backend's `already_running` semantic. The liveness probe is extracted as
  `qemuAlive` and shared with `vm list`'s state scan (R3, one probe): it reads
  `<stateDir>/qemu.pid`, checks the PID with `Signal(0)`, and confirms
  `/proc/<pid>/cmdline` contains `qemu-system` — the cmdline check is what closes
  the reused-PID false positive, which a `Signal(0)` probe alone reports as
  "running".

Code/config change class. Both fixes proved live on the `disposable: true`
`check-debian-debootstrap-vm` bed: the vm-build log shows zero `Failed to enable`
occurrences with `cloud-init-main`/`cloud-init-network` enabled, and the `update`
step — which failed at 3.982s against the unfixed `vm start` — now completes.

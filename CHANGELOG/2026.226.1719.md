# 2026.226.1719 — VM bootstrap: cloud-init unit-layout split + idempotent qemu `vm start`

Two root-caused defects in the VM bootstrap path, both surfaced by the
`check-debian-debootstrap-vm` bed and both fixed here.

- **Debian/Ubuntu debootstrap unit enablement (`charly/charly.yml` + the faithful copy
  in `candy/plugin-vm/build_defaults.yml`, R3).** The bootloader `install_template`
  enabled a fixed unit list that named the legacy `cloud-init` service
  unconditionally. cloud-init 24.3 (upstream PR #5489, "Single Process
  Optimization") SPLIT that unit: `cloud-init.service` was renamed to
  `cloud-init-network.service` and a new `cloud-init-main.service` daemon was
  added, with the four stage services becoming shims that connect to it over
  `/run/cloud-init/share/*.sock`. Debian 13 ships cloud-init 25.1.4, where the
  legacy name no longer exists, so the enable emitted `Failed to enable unit: Unit
  cloud-init.service does not exist` on every debootstrap build — swallowed by the
  step's `|| true`, so the bed passed while the template's own comment described a
  layout the distro had not shipped in two releases (R1: a warning is not a pass).
  Ubuntu 24.04 ships 24.1.3, BELOW the split, where `cloud-init.service` is the
  real unit and the two post-split names do not exist — so neither name can simply
  replace the other, and the loop has to carry both. The enable loop now tests for
  each unit file before enabling it and covers BOTH layouts, and the comment states
  the version pivot instead of asserting one layout.

  On Ubuntu the enable is a no-op in practice — the cloud-init postinst already
  creates `/etc/systemd/system/cloud-init.target.wants/cloud-init.service`, and the
  template's `systemctl enable` there prints nothing (systemd reports "Created
  symlink …" whenever an enable has anything to create, so silence means
  already-enabled). The loop keeps the legacy name regardless: relying on a
  package's postinst to have enabled a unit the bootstrap requires is an
  undeclared dependency on packaging behaviour, and the existence guard makes
  carrying it free.

- **`charly vm start` was not idempotent on the QEMU backend
  (`candy/plugin-vm/vm.go`).** Starting a VM whose QEMU process was already running
  re-executed the stored command, and the second QEMU failed to lock the pidfile —
  `qemu-system-x86_64: cannot create PID file: Cannot lock pid file: Resource
  temporarily unavailable`, exit 1. This broke the `update` step of every
  QEMU-backed bed: `vm create` already starts the domain, so the rebuild path's
  ensure-running guard hit an already-live VM every time. `vm start` now returns a
  clean no-op when the recorded process is alive, matching the libvirt backend's
  `already_running` semantic.

- **One QEMU liveness predicate, in `sdk/vmshared` (`QemuAlive`, R3).** The probe
  existed in THREE places: inline in `vm start`, inline in `vm list`'s state scan,
  and — unhardened — in `candy/plugin-preempt`'s holder probe, the arbiter that
  decides whether a preemptible GPU-holder VM is running. All three now call one
  `vmshared.QemuAlive`; the two inline copies are deleted. The predicate belongs in
  `sdk/vmshared` because it has consumers in more than one module and the module
  already owns this class (`VmStateRoot`, `RenderQemuArgv`).

  It also asserts more than the earlier copy did. A bare `Signal(0)` probe reports
  a recycled PID as "running", and a `/proc/<pid>/cmdline` substring match on
  `qemu-system` narrows that only to "some qemu" — a PID reused by a DIFFERENT
  VM's qemu still passes, so `vm start` would no-op on a stopped VM and the
  arbiter would refuse to preempt a departed holder. `QemuAlive` matches
  `-pidfile <stateDir>/qemu.pid` as adjacent NUL-separated argv fields, so a live
  process is confirmed to be the qemu started for THAT state dir. That match rests
  on a CALLER invariant, not a renderer guarantee: `RenderQemuArgv` appends
  `-pidfile` conditionally (`if paths.PidFile != ""`), and what makes the argv
  reliable is that every production launch sets `PidFile` to
  `<vmStateDir>/qemu.pid` — byte-identical to what the predicate computes. A future
  caller leaving it empty would make `QemuAlive` report its VMs dead, the worse
  failure direction, so the predicate's own comment warns the maintainer. Table-tested
  (`qemu_liveness_test.go`), including the recycled-onto-another-VM case that the
  substring check accepted.

Code/config change class. Both fixes proved live on the `disposable: true`
debootstrap beds for BOTH distros on the version pivot — `check-debian-debootstrap-vm`
(cloud-init 25.1.4, above the split) and `check-ubuntu-debootstrap-vm` (24.1.3,
below it). The debian vm-build log shows zero `Failed to enable` occurrences with
`cloud-init-main`/`cloud-init-network` enabled; the ubuntu run proves the existence
guard still enables the legacy unit rather than silently skipping it. The `update`
step — which failed at 3.982s against the unfixed `vm start` — now completes.

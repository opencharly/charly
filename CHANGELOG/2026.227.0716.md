# 2026.227.0716 — rebrand to the Agent-in-the-Loop Factory

OpenCharly's positioning line becomes **the fully equipped factory floor for you
and your agents**, under the brand name **The Agent-in-the-Loop Factory**. The
previous line — "the fully stocked gourmet kitchen for you and your agents" —
retires everywhere except `VISION.md`.

The rebrand also converges three wordings that had drifted apart because the
sentence had no single home: the site said one thing, `charly --help` said
"the container management experience for you and your agents" (an older line
matching nothing else, with an ASCII hyphen), and the native packages said
"OpenCharly container management CLI".

## The metaphors reconcile — they were never two

The confectionery vocabulary is not a legacy register the rebrand tolerates; it
is what the factory **makes**. `VISION.md` already said so, verbatim: *"a whole
factory ready to produce every candy imaginable."* The brand promotes the
factory half of the project's own sentence to the front, and `README.md` now
opens its bridge paragraph with that same sentence so the two files share the
line that joins the registers.

So: **factory** = the line and the loop. **Candy** = the product. **Kitchen** —
gourmet, pantry, buffet — retires outside `VISION.md`, because a domestic
kitchen is the wrong scale for a production line.

Consequences recorded so a later session does not undo them:

- **`VISION.md` and `LIBERATION.md` are untouched by design.** `VISION.md` is
  now cited as the origin of the factory framing rather than treated as an
  exception; `LIBERATION.md` is authored first-person voice whose dessert
  imagery is argument, not product positioning. Neither is a doc-vs-doc
  divergence to file under R1.
- **`VISION.md:5` is now a quotation source.** Its "whole factory ready to
  produce every candy imaginable" sentence is reproduced verbatim in
  `README.md`; any future edit to it touches both.
- **Load-bearing identifiers are unchanged and reinforced** — `candy:`,
  `charly box`, `candyboxing`, the `candy/` and `box/` trees, the `/recipes/`
  site route, the `agentteams-factory` candy/box. No schema change, no
  migration-table entry, no `#SchemaVersion` bump.
- **The "kitchen-sink" idiom stays** (~30 uses in candy `docs:` prose and box
  READMEs). It is ordinary English for "everything included", not branding. The
  one thing cut is the `README.md` pun that tied it back to the retired tagline.

## The tagline now has exactly one home

`candy/plugin-docs/gen_landing.go` hardcoded the tagline four times, one of them
a regex keyed to its literal wording whose job was to strip the line from the
projected README body so the site hero would not print it twice. Changing the
README alone would have left that strip silently inoperative and rendered the
new tagline twice on the home page.

The generator now **derives** the tagline: it lifts the bold line immediately
following the H1 out of the README and uses that one string for the hero
tagline, the frontmatter description, and the `<title>` override. `README.md` is
the only place the sentence is authored.

The extraction is **position-anchored**, not a search for the first bold run in
the document — the new bridge paragraph also opens in bold, so a first-match
search would work today and silently hoist that paragraph into the hero the
moment the two were reordered, deleting real prose from the page. It also
requires the bold run to span the whole line with no internal emphasis, which is
what separates a tagline from a paragraph that merely starts bold. A README with
no tagline is a hard error rather than an empty hero or a built-in default.

Side effect, accepted: the hero loses its trailing "— a tiny core, an
all-you-can-eat buffet", becoming exactly the README line. That is the point,
and it was buffet vocabulary this cutover retires anyway.

## `candy/rpmfusion` — the release packages are now signature-verified

Surfaced by this cutover's own R10 bed, which passed 13/13 while its image-build
log carried `Warning: skipped OpenPGP checks for 2 packages from repository:
@commandline`. A warning is not a pass (R1), and "it predates this change" is
not a classification this project accepts (R2), so it is fixed here.

**The defect.** `dnf install -y <release rpm URLs>` installs the RPM Fusion
release packages from the `@commandline` pseudo-repo, which dnf does not
OpenPGP-verify by default. Both packages went in **unverified**, on TLS trust
alone, in every Fedora-derived image (`fedora-nonfree` → `fedora-builder` and
everything above them).

**Why the obvious fixes are wrong.** RPM Fusion publishes no standalone key
file — every documented URL on `rpmfusion.org/keys` 404s, and the keys ship
*inside* the very packages needing verification, so extracting one from the
unverified rpm is circular. `--nogpgcheck` would remove the warning while
keeping the cause, which is hiding, not fixing.

**The fix, which upstream documents and this cutover proved.** Fedora's own
signed repo ships `distribution-gpg-keys`, which carries the RPM Fusion keys.
That makes the chain non-circular: Fedora's trusted repo → the keys →
`--setopt=localpkg_gpgcheck=1` verifying the release rpms for real. Proven in a
throwaway `fedora:43` container before any file was edited: the warning
disappears and the install exits 0.

**Coverage, and exactly how far it is gated.** A new `rpmfusion-key-imported`
check asserts an RPM Fusion key is in the rpm database. It discriminates the
mechanism it names rather than passing on a bystander condition — measured on
real images, the freshly built `fedora-nonfree` carries **2** rpmfusion keys
while the pre-change published image carries **0**, because installing the
release package drops key FILES on disk without importing them.

Stated plainly so nobody reads more into this than was proven: **no bed in this
cutover executes that check step.** `check-docs` is the bed this cutover runs,
and it composes `docs-site` on a plain Fedora base — rpmfusion reaches it only
through `fedora-nonfree`, built as a builder dependency whose candy checks the
bed does not run. What the bed DOES prove is the `run` step: a fresh-rebuild
13/13 pass with the OpenPGP warning gone and `distribution-gpg-keys` installing.

`charly check box fedora-nonfree` does not close the gap either, and the way it
fails is worth recording: it resolves to the published image tag rather than the
one just built from source, so it reports "5 passed, 0 failed" while running the
OLD plan against an image that predates the change. A PASS from that command was
nearly mistaken for proof. There is no flag to point `check box` at a specific
built tag.

So the check ships as coverage that will gate every FUTURE `fedora-nonfree`
build, not as something this cutover's gate exercised.

## Investigated and found NOT to be a defect: `charly generate-packages`

Recorded because the investigation nearly produced a duplicate implementation,
and the failure mode generalizes.

A PR validator reported, and this session escalated, that `charly
generate-packages` did not exist: ~10 candy files name it, `sdk/deploykit/
localpkg.go:204` execs it, and running it printed `unexpected argument`. The
conclusion was wrong. The command is an **external, out-of-tree plugin** —
`opencharly/plugin-generate-packages`, released `v2026.227.0013` — exactly as
`PROGRAM/nfpm-packaging-north-star.md:15` designs it. Proven by downloading the
release, pointing `CHARLY_PLUGIN_DIR` at it, and running it end to end with the
flags `localpkg.go:203-212` passes; it produced an 82 MB
`charly-2026.227.800-1-x86_64.pkg.tar.zst` from this cutover's own edited
`packaging:` section.

Root cause: the verb was tested with a **dev-worktree binary on a machine that
had not installed the released plugin asset**. `charly/plugin_loader.go:430
discoverBakedPluginWords` registers external commands from a `.providers` file
in the baked-plugin dir; absent that file the word never registers. Both the
validator and this session read an environment fact as a product fact.

The general rule, which cost two sessions an hour: **a from-source binary
falling back to root usage never proves a verb is absent** — it proves only that
this tree has not installed the plugin providing it. Check the plugin's release
and its `.providers` before concluding anything about the product.

The candy documentation naming the plugin is therefore **accurate and unchanged**.
A real gap does remain — the superproject never DECLARES the external plugin, so
lazy resolution cannot find it — but that is a declaration, not an
implementation, and it belongs to the nFPM program's Phase 3.

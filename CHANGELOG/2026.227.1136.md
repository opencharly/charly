## Lesson 1 — editing a source is a docs landing

The lesson splits across two owners, because the MECHANISM and the LANDING SEQUENCE
are owned by different skills.

The mechanism goes to the `docs-skill:` entity in `candy/charly-build/charly.yml`
(`/charly-build:docs`), which already owned the generator and the DO-NOT-EDIT
contract: new section "Editing a source is a docs landing".

The sequence goes to the `git-workflow-skill:` entity in
`candy/charly-internals/charly.yml`, as `### B6a — the documentation landing is the
same chain` inside `references/multi-repo-coordination.md`. Two reasons, and the
first is the stronger one:

- The authoritative-copy registry in `/charly-internals:skills` names
  `/charly-internals:git-workflow` the SOLE owner of "Landing mechanics … multi-repo
  order". A landing sequence in `/charly-build:docs` would be a second copy of
  registry-owned content (R3), independent of anything else.
- R4a. `/charly-build:docs` is a reader-facing page whose body named ZERO `task`
  targets at `origin/main`; an earlier revision of this cutover added five of them as
  numbered steps a reader runs, which R4a forbids — a `task` target needs the
  repository, and the page is written for someone who installed only the binary. B6a
  states outright that its commands are maintenance this repository performs on
  itself. `/charly-build:docs` now names no `task` target in its body at all.

The mechanism is two chains of DIFFERENT length, and the distinction is the part
that was never written down:

- **Candy and box prose — one hop.** `reference/candy/` and `reference/box/` are
  read straight off disk (`candy/plugin-docs/sources.go` walks each repo as its own
  project root). A `description:` or `plan:` edit re-projects its page in the same
  tree, so the `docs` commit belongs to the same cutover as the candy edit.
- **Skill prose — two hops.** `recipes/` is NOT read from `candy/*/charly.yml`.
  `charly marketplace generate` projects a `skill:` entity into
  `plugins/<plugin>/skills/<name>/SKILL.md`, and `charly docs generate` reads that
  projection. On a clean checkout the tree it reads is the pinned gitlink, so a
  skill edit reaches readers only once the `plugins` landing merges and the gitlink
  advances — and advancing that gitlink without regenerating `docs` is exactly how
  the mirror falls behind.

Supporting edits, each in its own owner so the mechanism has one authoritative copy
(R3):

- `candy/docs-site/charly.yml` (`/charly-tools:docs-site`) — the pin contract stated
  exactly: the sha is TWO occurrences (`DOCS_REF` plus a LITERAL in the
  `docs-site-pinned-commit` matcher, because a check step's substitution does not
  resolve a candy `var:` and would SKIP the step), and `task docs:pin` asserts both
  — it compares `DOCS_REF` to the gitlink AND requires at least two occurrences, so
  a half-done re-pin fails the gate.
- `candy/charly-image/charly.yml` (`/charly-image:layer`) — a pointer where candy
  authors actually work, since that is where someone editing a `description:` is
  looking. It names the cost and links to the owners; it restates no mechanism.

  This one is deliberately SCOPED. `/charly-image:layer` is the kind bucket — its own
  frontmatter says it must be invoked for candy authoring and "any file under
  `candy/`" — so its audience is anyone authoring a candy anywhere, not only
  contributors here. An earlier revision asserted unconditionally that a candy's prose
  "is PUBLISHED", that editing it fails a drift gate, and that it requires re-pinning
  the site candy; for a candy authored outside this repository every one of those is
  false. The page now says what is true generally (`description:` and `plan:` are
  projected by `charly docs generate`, so in a project that publishes a site they are
  published prose), then scopes the obligation to this repository, and names no
  repository-only command at all.

## Lesson 2 — `charly box reconcile --remote` is not idempotent against a moving remote

Owner: the `reconcile-skill:` entity in `candy/charly-build/charly.yml`
(`/charly-build:reconcile`). This is a CORRECTION as much as an addition: the skill
asserted idempotency twice with no qualification, and that claim is false for
`--remote`.

`reconcileTargetVersion` (`candy/plugin-box/reconcile.go:163`) returns
`refs.GitLatestTag` without consulting the referenced-version set at all, so
`--remote`'s target is whatever `git ls-remote --tags` reports at call time. The
default mode instead takes the maximum of the versions already referenced — a fixed
point after one run, which is what makes it safe to run as a question.

A precision worth having: the re-bump is reported, but its explanation is not.
`rewrote N pin(s):` prints, while the per-repo `<repo> -> <tag> (was at N versions)`
summary is emitted only for a repo found at MORE than one version. A freshly-aligned
repo is at exactly one, so the line that would say why the target moved is suppressed
in precisely the case where it moved for a reason outside the tree.

The operational rule: use the plain `charly box reconcile` (or `--dry-run`) to CHECK
alignment; run `--remote` deliberately, once, at the B6 point where adopting the
producer's newest tag is the intent. Evidence gathered before a `--remote` run may no
longer describe the tree.

## Non-blocking finding, routed not dropped

Neither projection hop has a mechanical gate: `.github/workflows/` holds only
`release-binary.yml`, and nothing in `.github/` or `.claude/hooks/` invokes
`task docs:drift` or `charly marketplace generate`. Both hops rest on a validator's
judgement, which is how two landings broke them within hours. Adding CI is a
config change whose gate is not this class, so it routes to the next
gate-infrastructure batch rather than riding along here.

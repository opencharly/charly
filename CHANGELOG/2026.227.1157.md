# 2026.227.1157 — the build-scope verdict verbs certify the artifact you built

`charly check box <box>` could run against an image that was not the one you had
just built, report every step green, and give no sign. A gate that certifies the
wrong artifact is the highest-severity defect this system has, because a false
pass is indistinguishable from a real one — this one nearly produced a false R10
proof in a landed cutover, caught only by reading the `Image:` line.

Landed across `spec` (the resolver), `sdk` (the label emitter), this superproject
(the call sites, the retention ordering, and the check skill), and `plugins` /
`docs` (the regenerated skill + site page) — five repos, enumerated rather than
totalled for the reason given under Separable findings.

## The defect, reproduced

Measured 2026-08-15 (day 227). A `check:` step was added to `candy/rpmfusion`;
`charly box build fedora.fedora-nonfree` produced
`ghcr.io/opencharly/fedora-nonfree:2026.227.0835` / `:0836`; then
`charly check box fedora-nonfree` printed
`Image: ghcr.io/opencharly/fedora-nonfree:2026.216.1908` and `5 passed, 0 failed`
— the OLD baked plan, the new step absent entirely.

Two independent causes compounded, both traced with `podman image inspect`
against the real store rather than inferred:

1. **The label and the ref disagreed.** The render labelled an imported box's
   image with the namespace-qualified Generator key (`fedora.fedora-nonfree`)
   while tagging the ref with the leaf name. The local-image resolver's label
   family is keyed on exactly that equality and DISCARDS the name family whole
   when the label family is non-empty, so the fresh build was invisible to a
   resolve of its own image name and an older bare-labelled image was elected.
   Fixed in `sdk` (`deploykit.buildBakedMetadata` → `spec.LeafName(boxName)`).
2. **The election's ordering can pass over the newest build even with consistent
   labels.** Its PRIMARY key is the content-derived `ai.opencharly.version`
   label; the per-build tag is only a tiebreak. An image built from a
   differently-versioned source tree — a sibling worktree, a pulled release —
   outranks a newer build regardless of when either was produced. Both shapes
   were live in the same `podman images` capture. Fixed in `spec`
   (`container.ResolveBuiltImageRef`).

The project had already met cause 2 once and worked around it locally: the R10
bed sequence pins `<image>:<run-tag>` for its check step, with a comment saying
why (`candy/plugin-check/bed_run.go`'s `runTaggedImageRef`). The interactive,
untagged form had no such protection. R3 — the fix belongs at the resolver, not
per-caller.

## What changed here

The three verbs that pronounce a VERDICT on a built artifact now resolve through
`kit.ResolveBuiltImageRef`, which refuses a stale election instead of taking it:

- `candy/plugin-check/run_box.go` — `charly check box`
- `candy/plugin-check/feature_box_gather.go` — `charly box feature run` (the
  build-scope ADE acceptance run)
- `candy/plugin-box/box.go` — `charly box labels`, the charly-native R8 artifact
  check; reporting an older image's labels as the fresh build's is the same
  false-proof class

Every other consumer of a short name (deploy, `charly vm build`, builder
bootstrap, kube preresolve) keeps the lenient election — the guard is a property
of the verdict verbs, not a change to resolution.

The two escapes are pre-existing and now stated in `--help` on all three verbs: a
full ref, or the `<box>:<calver>` pin. The pin is why the bed sequence is
untouched.

## Who this can break, stated plainly

An unpinned `charly check box <box>` / `box labels <box>` / `box feature run
<box>` on a host where a build of that box exists that the election passes over
now ERRORS where it previously answered. That is the defect being surfaced, not a
new one — the previous answer was the wrong artifact — and the message names both
refs and the exact re-invocation. Beds are unaffected (they pin).

## Corrections from validation

**The first fix's ordering key was blind to bed tags**, and a validator proved it
live: `check box docs-site-app` certified an image ~17 hours old, green, exit 0 —
the very defect this cutover exists to remove, past the new guard. `--tag`
REPLACES the CalVer tag, so every bed build carries `check-<bed>-<calver>`, which
`ExtractCalVerTag` reads as empty; the election then fell to a lexicographic last
resort and elected the OLDEST build, while the guard's "newest build" probe
returned `""` and was treated as "nothing to worry about".

It had been root-caused once already and routed around rather than fixed —
`candy/plugin-check/live_image.go` names the mechanism verbatim (2026-08-05,
"the OLDEST local build of the box won"); that fix made the LIVE path ask the
container, which a build-scope verdict cannot do. Build recency is now keyed on
the image's CREATION TIME, the only key total over arbitrary `--tag` values.
Full detail: `spec` `CHANGELOG/<CalVer>.md`.

**The generalisable lesson is about the 2026-08-05 fix, not about missing it.**
That RCA fixed its CONSUMER and left the MECHANISM broken. `ResolveLocalImageRef`
stayed wrong, and its comment — an accurate, detailed description of exactly how
it was wrong — became the only thing standing between the defect and the next
person to build on it. That is not a guard: the next consumer inherited the
defect and added a second on top of it, which is this cutover's own history.
Routing around a broken mechanism leaves a trap for whoever comes next, and
documenting the workaround is not a substitute for fixing the thing. This cutover
is what that RCA should have been.

**`charly clean`'s retention sort shared the blind spot — destructively.**
`candy/plugin-clean/retention.go` ordered by the same label/tag CalVer keys, so

delete the newest bed build while keeping older ones. In-use images are skipped,
so a running deploy was never at risk; a freshly built artifact was.

Of the surfaces in this cutover this is the only one that DESTROYS rather than
mis-answers — every other produces a false verdict, this one removes an image —
which is why it lands here rather than in a follow-up. Same root cause, same
struct, same repo, one comparator clause. (That is the RETENTION comparator, a
single ordering with one right answer. It is not the resolver's two orderings,
which must NOT be unified — unifying those turned the staleness guard into a
tautology; see the `spec` CHANGELOG.)

The magnitude, measured rather than characterised: pre-fix the sweep deletes

the tag is a build-REQUEST stamp with no relation to build time, and ordering by

## The submodule pins, and the go.mod floor sweep they force

All four gitlinks are re-pointed from this batch's branch heads to their
producers' MERGED SQUASH commits, because a squash mints a new sha and leaves the
branch head unreferenced for anyone cloning fresh:

```
spec     bbb3c6a2c842…    sdk  2f6a3a76b203…
plugins  853e72a9ffc5…    docs 69f979260718…
```

`plugins` and `docs` were re-derived a second time when this leg absorbed the
other three cutovers' sources — the earlier values `bcbfdcbc` / `620839538` were
correct for a tree carrying only this leg's own source, and became wrong the
moment it carried three producers'. The rule that produces the final pair is
under "The forced union" below: **reach the newest projection any source in this
tree covers**, which is not the same as this leg's own producer merge.

Each verified two ways, because the two checks are blind in opposite directions:
**ancestry** (is the pin on the submodule's `main`?) catches an orphaned pin but
passes green on a tip that never received the producer; **content** (is the
producer's own work in that commit?) catches the dropped-content direction.
Ancestry PASS on all four; content confirmed per repo — the resolver's three
comparators and the single-family test in `spec`, the `LeafName` label and the
spec pin in `sdk`, this batch's skill section and stderr contract in `plugins`
and `docs`. Tree-diff against the branch heads is CalVer CHANGELOG renames only,
except `plugins`, which additionally carries the three projections stacked under
it. `git rev-parse --is-shallow-repository` was asserted false first — ancestry
is silently wrong past a shallow graft.

**Advancing the `sdk` gitlink forces a go.mod sweep, and that is why it is in
this cutover rather than a follow-up.** `main`'s sdk gitlink requires `spec
v0.2026225.1800`, which every plugin module already matches, so `main` is
consistent. This PR advances that gitlink to an sdk requiring `v0.2026227.1854`,
and under MVS every module that depends on `sdk` *and* requires `spec` directly
must raise its own floor to match. Without the sweep, this PR breaks 30 plugins
the moment it merges — R2's discriminator answers plainly: the tree is not
correct without it.

90 `candy/*/go.mod` files are raised to `v0.2026227.1854`. Not the 30 that break
today: the other 60 are inside `go.work`, which masks the identical defect — the
same mechanism that hid it in `sdk` from five rounds of green suites — and
splitting them would leave the second half invisible until someone builds
out-of-workspace.

### The standing gate this adds

```
for m in candy/*/go.mod; do (cd "${m%/go.mod}" && GOWORK=off go build ./...) || echo "FAIL $m"; done
```

Run for any change to `spec`, `sdk`, or a plugin's `go.mod`. **The reason matters
more than the command**, or the next person drops it as slow: `go.work`'s `use`
directives override module pins in-tree, so an ordinary `go build ./...` resolves
against local directories and never reads `go.mod` at all. These plugins ship
**out-of-workspace**, resolved through the module proxy — the one configuration
no in-tree gate exercises. It is the check that would have caught the `sdk` pin
before a validator did.

Result: **91 modules built standalone, 1 failure**, and that failure is reported
rather than forced. `candy/plugin-dsh` fails for a DIFFERENT cause — a `go`
directive bump (1.26.0 → 1.26.4) plus transitive `golang.org/x/*` rewrites, and a
third spec version this sweep does not match. It fails identically on `main`'s
tree, so this cutover neither causes nor worsens it and its claim holds without
it; forcing it would be a different change class riding an unrelated gate.

**That is a classification, not a dismissal.** It is NOT blocking for this
cutover, and it therefore joins a named batch — **module hygiene** — which is
scoped and owned now rather than noted. Measured membership, because a batch
without a measured scope is just a deferral wearing better clothes:

| module | condition | in this batch? |
|---|---|---|
| `candy/plugin-dsh` | `go 1.26.0`, transitive `x/*` rewrites, spec pin `v0.2026224.1942` | yes — the only standalone build failure |
| `charly` | `go.sum` incomplete for cuelang's transitive deps (`x/text`, `x/net`); its `go.mod` is already tidy-clean and its spec pin is genuinely sufficient | yes — fails standalone on `main` too |
| `spec` | `go 1.26.0` against 92 modules at `1.26.4` | to DETERMINE — a contract module deliberately holding a lower floor so older consumers can resolve it is correct, not drift. Establish intent before touching it |

So the batch is not a broad inconsistency: **92 of 94 modules already share the
`1.26.4` floor**, and 91 of 92 build standalone. It is two stragglers and one
question of intent — which is worth knowing before someone assumes a sweep is
needed. Its acceptance criterion is the standing gate above at **91/91**, plus
`charly` and `spec` resolved deliberately.

**`spec` is held deliberately, and the rule is stronger than the caution.** Do
not raise a contract module's `go` floor on the strength of a majority count.
`spec` is what every plugin and every out-of-tree consumer resolves through the
proxy, so a floor raise there is a COMPATIBILITY decision, not hygiene: it can
strand consumers that a 92-of-94 tally says nothing about. Establish whether the
lower floor is deliberate; if that cannot be established, leave it and say so.
A sweep that bulk-bumps a contract module to make a number even is the kind of
change that looks clean and breaks someone you never hear from.

### The glob was narrower than the claim

Recorded as its own finding because it is a failure mode distinct from every
other one in this cutover. The others were all *measuring the wrong tree*. This
one measured the right tree **through a filter that excluded part of the claim's
subject**: the sweep ran over `candy/*/go.mod` while the claim was "every module
raised to the new floor" — and `charly/go.mod` pins spec too. Both halves were
reasonable in isolation and they did not match.

No gate would ever have caught it, because the gate iterated the same glob. It
surfaced only when scoping the follow-on batch went looking somewhere else.

**The general form: when a sweep is defined by a pattern, the pattern is part of
the claim and needs its own justification.** State the glob and why it is
complete, or state the claim narrowly enough that the glob satisfies it. It
turned out not to matter here — `charly`'s pin is genuinely tidy-clean — but that
was established afterwards, by checking. A claim that is true by luck and a claim
that is true by verification read identically in a commit message.

### The forced union: this leg carries four cutovers' sources

An earlier revision of this entry reported 11 stale artifacts at this pin as
"expected drift, clearing when the three legs ahead land". **That framing was a
waiting posture, and it was wrong about the mechanism.** The legs ahead landed
their PROJECTIONS; their candy SOURCES had nowhere to land but here. So the drift
never cleared by waiting — it cleared by this leg absorbing the sources.

The root cause, stated as the scheduling rule that makes the rest unnecessary:

> **A mirror leg that lands ahead of its own superproject leg makes the mirror
> unpinnable by any state the superproject can reach.**

The mirror becomes a composite of projections from several submodule commits, and
no single pin reproduces a composite. Once that has happened the constraints bind
simultaneously — the mirror fixes the pin, the pin demands every source — so the
first leg through the gate must carry ALL of them. That is a structural property,
not a batching preference.

**This entry therefore covers four cutovers, named so a squash does not bury
other authors' provenance:**

|---|---|

| the git-workflow landing lessons (`#176`) | `git-workflow-skill` + `docs-site-skill` source, projected at `plugins` `4458a400` / `docs` `65009964` |

### Applied as patches, never as file copies

inherited.**

### The staging discipline has a prior clause

`never git add -A after a regeneration; stage by named path` protects a tree
that already holds the work. It does nothing for work that exists in only one
place. When this leg established that `#177`'s source restored 152 lines present
in **no** superproject tree, the only copies of that work were an uncommitted
working-tree file and a patch under `/tmp` — on the host we had been planning a
disk cleanup on. Its author had conflated *"this cannot merge separately"*
(measured, true) with *"this should not be committed separately"*, which nothing
implies. Recovering it also surfaced a 50-line CHANGELOG swept into
`stash@{0}^3` by a `git stash -u`, one `git stash drop` from gone.

So the first step is **commit the source before anyone can regenerate over it**,
and the citation for a handed-over source is a pushed commit — `c144ad11` here —
never a path that does not survive a reboot. The content is identical either way
(both copies `sha256 a32ac7cd…`, verified); what changes is whether it still
exists tomorrow.

### `DOCS_REF` had drifted three merges behind, on this branch, unnoticed

Found by dry-running an incoming patch rather than by any gate. At this branch's
head `task docs:pin` failed:

```
docs: DOCS_REF drift
  gitlink:  620839538b24025b2e58174f48910c386a43cb46
  DOCS_REF: 93085fb92245025fb561e17a18de4afbdf2728bf
```

**Root cause: five commits on this branch moved the `docs` gitlink and none
carried the pin that names it** — four documentation projections plus the
four-pin re-pin. The invariant holds at the merge-base and holds on
`origin/main`; it failed at every commit on this branch.

The consequence is this cutover's own subject wearing different clothes. The
`check-docs` bed would clone `93085fb9` — a commit predating all four
projections — and the `docs-site-pinned-commit` step would assert that same
`93085fb9` and pass. **A gate that certifies the wrong artifact and cannot tell,
because the thing it checks against is the thing that is wrong.** Not a check
that fails to fire; a check that fires and agrees with the defect.

**A projection commit must carry the page AND the pin.** Carrying only the page
is the easy asymmetry to hold wrong, because the page is the visible half.

Fixed here at both occurrence sites, with `task docs:pin` as the proof. Two
findings about the gate itself are separable and named below.

### One planned step was skipped, with its reason

`charly clean` was announced and planned as an ENOSPC mitigation for the bed,
when the host was at 26G free / 95%. It was **not run**: free space recovered to
125G before the bed started, so the mitigation addressed a risk that no longer
existed at run time, and a store-wide prune on a shared host would have taken
another session's cached layers for no benefit. Recorded rather than silently
omitted, because a step that was planned in the open and then dropped should say
why.

That the host swung 26G → 125G on background teardowns, over 82 GB of
unreclaimable plugin cache, is itself the argument for the retention batch below:
**free space here is a function of what happens to be running, not of any
retention policy.**

## The generated-ahead-of-source gap: pending at the tip, not red on `main`

An earlier revision of this entry stated that landing the projections leaves
`main` drift-red until this PR carries their source. **That is false, and the
mechanism is worth recording because it fooled several of us.**

`charly marketplace drift` compares the candy sources against the `plugins` tree
**at the submodule checkout**. `main` pins `plugins` at a gitlink that PREDATES
the projections:

```
measured at superproject main = 396e4bfe's era (day 227, before #285 landed)
superproject main pins plugins at 396e4bfe
aa80ca9f (#174) ancestor of 396e4bfe?  NO — the gitlink predates it
4458a40  (#176) ancestor of 396e4bfe?  NO
```

That figure is anchored to the `main` of the moment, and `main` has since
advanced — it now pins `plugins` at `aa80ca9f`, and this leg advances it again.
The section's own rule applied to itself: a drift statement about `main` is a
statement about the gitlink `main` held **when it was measured**, so it carries
that pointer or it decays into a present-tense claim about a moving ref.

Main's candy source and its pinned `plugins` tree were therefore both pre-#174 —
consistent, and the gate was GREEN on it. Landing a projection PR does not change
that, because the superproject gitlink does not move when a submodule's `main`
advances.

**The true statement is that the gap is PENDING AT THE PLUGINS TIP.** It
materializes only when a superproject leg bumps the gitlink past those commits,
and the leg that advances the pointer owns carrying the matching source with it.
For this batch that leg is this PR.

The red 8-artifact state is reproducible, but only in an ordinary developer
working tree whose `plugins/` has been fetched past the gitlink — which is not
`main`. Which is the first of two traps worth keeping:

- **A drift result is a fact about a CHECKOUT, not about the tree.** Measuring
  `main` means reconstructing main's tree — submodules at their **gitlink**, not
  at their own `origin/main`. Standing on the `main` branch with fetched
  submodules is a DIFFERENT tree and routinely shows stale artifacts `main` does
  not have. Quote a drift figure with its pointer or not at all. Measured for
  this branch: 8 stale at superproject `92246b52` with the `plugins` gitlink at
  `4bc92b33` — a statement about that checkout, and about nothing else.
- **The reassuring `clean (N artifact(s)) match the committed tree` line prints
  only on the CLEAN path**, so its absence is not evidence of anything;
  `charly marketplace generate`'s unconditional header is the substitute signal.

## Separable findings, named rather than swept in (R2)

Every defect surfaced while verifying this one is named below; none is parked.
(`candy/plugin-clean`'s retention ordering was FOLDED INTO this cutover rather
than named here — it is the one that destroys an artifact rather than producing a
false answer.) None of them changes this cutover's claim or its gate's verdict,
and each is a different concern; they are reported with their root cause for their
thematic batch rather than widened into here.

**The numerals are deliberately gone.** This narrative miscounted its own findings
in three consecutive validation rounds — 3-vs-5, then 3-vs-4, then 3-vs-4 again —
because every round appended a bullet and the total was corrected in the PR bodies
while the artifact of record kept the stale figure. A running total is a claim that
decays the moment the list grows, in a document whose whole subject is claims that
decay; an enumeration cannot go stale that way. Same reasoning applied to the R1
and R2 lines in the PR bodies.

- **An imported box bakes NO `ai.opencharly.description`.** Same root-cause
  family as fix 1 — a namespace-qualified box key handed to a namespace-unaware
  consumer — but a much wider one:
  `deploykit.CollectDescriptions` reaches `cfg.BoxConfig(boxName)` and
  `cfg.WalkBaseChain(boxName)`, both flat map lookups with no namespace descent,
  so for `fedora.fedora-nonfree` both return nothing and the label is omitted
  entirely. Proven by building the SAME box two ways: from this superproject
  (namespaced key) the image has no description label and `charly check box`
  answers "No plan steps defined for this image"; from `box/fedora` (unqualified
  key) the identical box bakes the plan and runs it. After the 2026-06 box
  inversion that is every box the superproject builds — ADE's "the spec is the
  test, baked into the image" is silently void for all of them. Fixing it means
  making the deploykit collector family namespace-aware (the descent
  `buildkit.ResolveBox` already has), which is an architectural change well
  outside check-verb correctness.
- **`charly box feature run <image>` is unreachable.** It routes to the
  top-level `charly feature` grammar and errors with
  `unknown feature subcommand "run"` / `usage: charly feature <list | pending |
  validate>`, instead of `candy/plugin-box`'s `dispatchFeature`. Confirmed on a
  clean baseline tree with a from-source binary, so it is not this change and not
  a stale binary. Consequence: the documented build-scope ADE surface cannot be
  invoked at all; its guard here is unit-covered but could not be exercised live.
- **`charly check box` exits 0 when an image carries no baked plan.** Distinct
  from the provenance gap fixed above: printing the ref makes the report honest,
  but the ADE surface still reports success for an image with no acceptance plan
  — arguably the same class as certifying a stale artifact, a gate that cannot
  fail. Changing the exit code needs a survey of which images legitimately carry
  no plan, which belongs with the ADE cutover that makes the cause rare, not with
  the resolver.
- **`charly clean` retention counts REFS, not ARTIFACTS — and this one DESTROYS
  too.** Named separately from the ordering fix folded into this cutover because
  it is a different question with a different remedy, not because it is smaller.
  One image wearing three tags consumes the entire `keep_images: 3` budget alone,
  so every OTHER image of that box is queued for deletion regardless of age. It is
  live right now, not hypothetical: `fedora-nonfree` id `e2efeb1c` wears three
  tags and is exactly that case, which is why everything older in its group is
  queued. Fixing it means deciding what `keep_images: N` COUNTS — refs or
  artifacts — which is a user-facing contract change touching the schema field's
  meaning and its documentation, not a comparator clause, so it cannot ride this
  cutover's gate. It needs an owner of its own, at the same severity as the
  ordering half: both remove images. **Direction matters and is easy to invert:
  this makes retention keep FEWER distinct images, so it over-prunes within
  managed families — it cannot cause under-reclaim.** It is the first of three
  members of a named retention batch, whose shared gate is *after a full run and
  a `charly clean`, only entries that should have survived remain*.
- **The plugin build cache has no retention at all** — retention batch member 2.
  `charly clean` has no scope for `~/.cache/charly/plugins`; measured 82 GB
  across 7689 entries, of which ~68% (55.8 GiB) are `plugin-example-*` test
  fixtures, growing **+210 entries within a single session**. It is content-keyed
  per `charly/plugin_loader.go:192` and `git grep` finds no reclamation code
  anywhere, so it is unbounded by construction. **The rate is the defect; the
  level is a fact about today.**
- **The default image sweep cannot reach the majority of what accumulates** —
  retention batch member 3. `selectDanglingImages` with `onlyCharly=true` sees
  only `ai.opencharly.box`-labelled images, and `WriteLabels` stamps the FINAL
  build stage only, so every multi-stage intermediate is invisible to it by
  construction; `--deep` exists to close that gap. Two adjacent facts belong with
  it, both already documented in `candy/plugin-clean/retention.go` and both easy
  to misread as defects in a run: the reclaimable byte total is an **upper bound**
  because dangling images share layers with images that stay (`:477`), and while
  any build is live the sweep **returns success having deleted nothing** (`:482`)
  — so free space before and after is the measurement, never the exit code.
- **`spec/proc.SweepStaleTemps` globs a hardcoded `/tmp/`** while its creators
  use `proc.MkdirTempHeld("", …)`, which honours `$TMPDIR`. On any host with
  `TMPDIR` set the sweep never sees the temps it exists to reap.
  `TestSweepStaleTemps_UnheldCreatorIsSwept` and
  `TestSweepStaleTemps_ReleasedTempIsSwept` fail there and pass under
  `env -u TMPDIR` — the tests are honest, the sweep is environment-specific (R4).
- **`task docs:pin` binds on nothing automatic.** It is the only gate that
  catches the `DOCS_REF` defect fixed above, and `git grep docs:pin` finds it in
  no CI workflow, no hook, no bed, and in neither `docs:sync` nor `docs:drift` —
  only in two candies' prose. A gate that exists, is correct, and is never
  invoked is why that defect reached a pushed branch. Two smaller edges belong
  with it: its failure message prints two shas without saying which side each was
  read from (which sent another leg hunting a pin it had just written
  correctly), and it reads `git ls-tree HEAD`, so it reports drift against a
  *staged* gitlink and passes only once committed — a post-commit gate that looks
  like a pre-commit one. Wiring it cannot ride this cutover: the text would be
  new skill prose whose `plugins` and `docs` projections do not exist, which is
  the source-ahead-of-projection inversion this entry documents, introduced by
  the commit documenting it.
- **`git apply --3way` exits `rc=0` while printing "applied with conflicts".**
  A check that reports success while conflicting, in the same family as a `PASS`
  line that does not echo what it asserted. Read the output, not the code.
- **`git merge-tree` reports a submodule CONFLICT for a strict fast-forward**
  (git 2.55.0), naming an object that is present. Diagnosed rather than worked
  around: `docs` and `plugins` were structurally identical two-sided cases and
  git fast-forwarded one and failed the other, because `docs`' theirs is ours'
  direct parent — no walk — while `plugins` advances three commits and dies on
  the first intermediate reached from our side, which the superproject's object
  store cannot read. It never names the second intermediate, which is what
  confirms a walk stopping at first failure rather than a wholesale read failure.
  `git submodule update --init --recursive` does not help when the submodule is
  already initialised, and **persistence after initialisation classifies
  nothing** — persistent error and provable fast-forward were observed together.
  `merge-base(ours, theirs) == theirs` remains the only test that decides it, and
  the danger is directional: "genuinely divergent" invites taking theirs, which
  here would have rewound three commits.

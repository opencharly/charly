# 2026.227.1157 — the build-scope verdict verbs certify the artifact you built

`charly check box <box>` could run against an image that was not the one you had
just built, report every step green, and give no sign. A gate that certifies the
wrong artifact is the highest-severity defect this system has, because a false
pass is indistinguishable from a real one — this one nearly produced a false R10
proof in a landed cutover, caught only by reading the `Image:` line.

Landed across four repos: `spec` (the resolver), `sdk` (the label emitter),
this superproject (the call sites + the check skill), and `plugins` / `docs`
(the regenerated skill + site page).

## The defect, reproduced

Measured 2026-08-15 (day 227). A `check:` step was added to `candy/rpmfusion`;
`charly box build fedora.fedora-nonfree` produced
`ghcr.io/opencharly/fedora-nonfree:2026.227.0835` / `:0836`; then
`charly check box fedora-nonfree` printed
`Image: ghcr.io/opencharly/fedora-nonfree:2026.216.1908` and `5 passed, 0 failed`
— the OLD baked plan, the new step absent entirely.

Two independent causes compounded, both traced with `podman image inspect`
against the real store rather than inferred:

1. **The label and the ref disagreed.** The render labelled an imported box's
   image with the namespace-qualified Generator key (`fedora.fedora-nonfree`)
   while tagging the ref with the leaf name. The local-image resolver's label
   family is keyed on exactly that equality and DISCARDS the name family whole
   when the label family is non-empty, so the fresh build was invisible to a
   resolve of its own image name and an older bare-labelled image was elected.
   Fixed in `sdk` (`deploykit.buildBakedMetadata` → `spec.LeafName(boxName)`).
2. **The election's ordering can pass over the newest build even with consistent
   labels.** Its PRIMARY key is the content-derived `ai.opencharly.version`
   label; the per-build tag is only a tiebreak. An image built from a
   differently-versioned source tree — a sibling worktree, a pulled release —
   outranks a newer build regardless of when either was produced. Both shapes
   were live in the same `podman images` capture. Fixed in `spec`
   (`container.ResolveBuiltImageRef`).

The project had already met cause 2 once and worked around it locally: the R10
bed sequence pins `<image>:<run-tag>` for its check step, with a comment saying
why (`candy/plugin-check/bed_run.go`'s `runTaggedImageRef`). The interactive,
untagged form had no such protection. R3 — the fix belongs at the resolver, not
per-caller.

## What changed here

The three verbs that pronounce a VERDICT on a built artifact now resolve through
`kit.ResolveBuiltImageRef`, which refuses a stale election instead of taking it:

- `candy/plugin-check/run_box.go` — `charly check box`
- `candy/plugin-check/feature_box_gather.go` — `charly box feature run` (the
  build-scope ADE acceptance run)
- `candy/plugin-box/box.go` — `charly box labels`, the charly-native R8 artifact
  check; reporting an older image's labels as the fresh build's is the same
  false-proof class

Every other consumer of a short name (deploy, `charly vm build`, builder
bootstrap, kube preresolve) keeps the lenient election — the guard is a property
of the verdict verbs, not a change to resolution.

The two escapes are pre-existing and now stated in `--help` on all three verbs: a
full ref, or the `<box>:<calver>` pin. The pin is why the bed sequence is
untouched.

## Who this can break, stated plainly

An unpinned `charly check box <box>` / `box labels <box>` / `box feature run
<box>` on a host where a build of that box exists that the election passes over
now ERRORS where it previously answered. That is the defect being surfaced, not a
new one — the previous answer was the wrong artifact — and the message names both
refs and the exact re-invocation. Beds are unaffected (they pin).

## Separable findings, named rather than swept in (R2)

Three defects surfaced while verifying this one. None changes this cutover's
claim or its gate's verdict, and each is a different concern; they are reported
with their root cause for their thematic batch rather than widened into here.

- **An imported box bakes NO `ai.opencharly.description`.** Same root-cause
  family as fix 1 — a namespace-qualified box key handed to a namespace-unaware
  consumer — but a much wider one:
  `deploykit.CollectDescriptions` reaches `cfg.BoxConfig(boxName)` and
  `cfg.WalkBaseChain(boxName)`, both flat map lookups with no namespace descent,
  so for `fedora.fedora-nonfree` both return nothing and the label is omitted
  entirely. Proven by building the SAME box two ways: from this superproject
  (namespaced key) the image has no description label and `charly check box`
  answers "No plan steps defined for this image"; from `box/fedora` (unqualified
  key) the identical box bakes the plan and runs it. After the 2026-06 box
  inversion that is every box the superproject builds — ADE's "the spec is the
  test, baked into the image" is silently void for all of them. Fixing it means
  making the deploykit collector family namespace-aware (the descent
  `buildkit.ResolveBox` already has), which is an architectural change well
  outside check-verb correctness.
- **`charly box feature run <image>` is unreachable.** It routes to the
  top-level `charly feature` grammar and errors with
  `unknown feature subcommand "run"` / `usage: charly feature <list | pending |
  validate>`, instead of `candy/plugin-box`'s `dispatchFeature`. Confirmed on a
  clean baseline tree with a from-source binary, so it is not this change and not
  a stale binary. Consequence: the documented build-scope ADE surface cannot be
  invoked at all; its guard here is unit-covered but could not be exercised live.
- **`spec/proc.SweepStaleTemps` globs a hardcoded `/tmp/`** while its creators
  use `proc.MkdirTempHeld("", …)`, which honours `$TMPDIR`. On any host with
  `TMPDIR` set the sweep never sees the temps it exists to reap.
  `TestSweepStaleTemps_UnheldCreatorIsSwept` and
  `TestSweepStaleTemps_ReleasedTempIsSwept` fail there and pass under
  `env -u TMPDIR` — the tests are honest, the sweep is environment-specific (R4).

# 2026.227.1157 — the build-scope verdict verbs certify the artifact you built

`charly check box <box>` could run against an image that was not the one you had
just built, report every step green, and give no sign. A gate that certifies the
wrong artifact is the highest-severity defect this system has, because a false
pass is indistinguishable from a real one — this one nearly produced a false R10
proof in a landed cutover, caught only by reading the `Image:` line.

Landed across `spec` (the resolver), `sdk` (the label emitter), this superproject
(the call sites, the retention ordering, and the check skill), and `plugins` /
`docs` (the regenerated skill + site page) — five repos, enumerated rather than
totalled for the reason given under Separable findings.

## The defect, reproduced

Measured 2026-08-15 (day 227). A `check:` step was added to `candy/rpmfusion`;
`charly box build fedora.fedora-nonfree` produced
`ghcr.io/opencharly/fedora-nonfree:2026.227.0835` / `:0836`; then
`charly check box fedora-nonfree` printed
`Image: ghcr.io/opencharly/fedora-nonfree:2026.216.1908` and `5 passed, 0 failed`
— the OLD baked plan, the new step absent entirely.

Two independent causes compounded, both traced with `podman image inspect`
against the real store rather than inferred:

1. **The label and the ref disagreed.** The render labelled an imported box's
   image with the namespace-qualified Generator key (`fedora.fedora-nonfree`)
   while tagging the ref with the leaf name. The local-image resolver's label
   family is keyed on exactly that equality and DISCARDS the name family whole
   when the label family is non-empty, so the fresh build was invisible to a
   resolve of its own image name and an older bare-labelled image was elected.
   Fixed in `sdk` (`deploykit.buildBakedMetadata` → `spec.LeafName(boxName)`).
2. **The election's ordering can pass over the newest build even with consistent
   labels.** Its PRIMARY key is the content-derived `ai.opencharly.version`
   label; the per-build tag is only a tiebreak. An image built from a
   differently-versioned source tree — a sibling worktree, a pulled release —
   outranks a newer build regardless of when either was produced. Both shapes
   were live in the same `podman images` capture. Fixed in `spec`
   (`container.ResolveBuiltImageRef`).

The project had already met cause 2 once and worked around it locally: the R10
bed sequence pins `<image>:<run-tag>` for its check step, with a comment saying
why (`candy/plugin-check/bed_run.go`'s `runTaggedImageRef`). The interactive,
untagged form had no such protection. R3 — the fix belongs at the resolver, not
per-caller.

## What changed here

The three verbs that pronounce a VERDICT on a built artifact now resolve through
`kit.ResolveBuiltImageRef`, which refuses a stale election instead of taking it:

- `candy/plugin-check/run_box.go` — `charly check box`
- `candy/plugin-check/feature_box_gather.go` — `charly box feature run` (the
  build-scope ADE acceptance run)
- `candy/plugin-box/box.go` — `charly box labels`, the charly-native R8 artifact
  check; reporting an older image's labels as the fresh build's is the same
  false-proof class

Every other consumer of a short name (deploy, `charly vm build`, builder
bootstrap, kube preresolve) keeps the lenient election — the guard is a property
of the verdict verbs, not a change to resolution.

The two escapes are pre-existing and now stated in `--help` on all three verbs: a
full ref, or the `<box>:<calver>` pin. The pin is why the bed sequence is
untouched.

## Who this can break, stated plainly

An unpinned `charly check box <box>` / `box labels <box>` / `box feature run
<box>` on a host where a build of that box exists that the election passes over
now ERRORS where it previously answered. That is the defect being surfaced, not a
new one — the previous answer was the wrong artifact — and the message names both
refs and the exact re-invocation. Beds are unaffected (they pin).

## Corrections from validation

**The first fix's ordering key was blind to bed tags**, and a validator proved it
live: `check box docs-site-app` certified an image ~17 hours old, green, exit 0 —
the very defect this cutover exists to remove, past the new guard. `--tag`
REPLACES the CalVer tag, so every bed build carries `check-<bed>-<calver>`, which
`ExtractCalVerTag` reads as empty; the election then fell to a lexicographic last
resort and elected the OLDEST build, while the guard's "newest build" probe
returned `""` and was treated as "nothing to worry about".

It had been root-caused once already and routed around rather than fixed —
`candy/plugin-check/live_image.go` names the mechanism verbatim (2026-08-05,
"the OLDEST local build of the box won"); that fix made the LIVE path ask the
container, which a build-scope verdict cannot do. Build recency is now keyed on
the image's CREATION TIME, the only key total over arbitrary `--tag` values.
Full detail: `spec` `CHANGELOG/<CalVer>.md`.

**The generalisable lesson is about the 2026-08-05 fix, not about missing it.**
That RCA fixed its CONSUMER and left the MECHANISM broken. `ResolveLocalImageRef`
stayed wrong, and its comment — an accurate, detailed description of exactly how
it was wrong — became the only thing standing between the defect and the next
person to build on it. That is not a guard: the next consumer inherited the
defect and added a second on top of it, which is this cutover's own history.
Routing around a broken mechanism leaves a trap for whoever comes next, and
documenting the workaround is not a substitute for fixing the thing. This cutover
is what that RCA should have been.

Live, on the fix, same command the validator ran:

```
$ charly check box docs-site-app
Image: ghcr.io/opencharly/docs-site-app:check-docs-2026.227.1227   ← the newest build
```

**A verdict verb printed no artifact identity when it bailed.** Reported twice
independently. `charly check box` returned before its `Image:` line whenever the
image carried no baked plan, so exactly the artifacts where provenance matters
most produced no ref, no version, nothing — and exited 0. The mitigation this
cutover told operators to use — "read the `Image:` line before believing a
verdict" — silently assumed a line existed. The ref was already in the reply; it
simply was not printed. Both build-scope verbs now print it FIRST, on every path
(`candy/plugin-check/check_cmd.go` and `feature_box_gather.go`, R3):

```
$ charly check box fedora-nonfree:2026.227.1139
Image: ghcr.io/opencharly/fedora-nonfree:2026.227.1139
No plan steps defined for this image.
```

**`charly clean`'s retention sort shared the blind spot — destructively.**
`candy/plugin-clean/retention.go` ordered by the same label/tag CalVer keys, so
for a group of bed-tagged images every candidate had `OkTag == false`, the sort's
final comparator was false for every pair, and the surviving order was whatever
`podman images` emitted. `keep_images: N` therefore kept an ARBITRARY N and could
delete the newest bed build while keeping older ones. In-use images are skipped,
so a running deploy was never at risk; a freshly built artifact was.

Of the surfaces in this cutover this is the only one that DESTROYS rather than
mis-answers — every other produces a false verdict, this one removes an image —
which is why it lands here rather than in a follow-up. Same root cause, same
struct, same repo, one comparator clause. (That is the RETENTION comparator, a
single ordering with one right answer. It is not the resolver's two orderings,
which must NOT be unified — unifying those turned the staleness guard into a
tautology; see the `spec` CHANGELOG.)

The magnitude, measured rather than characterised: pre-fix the sweep deletes
`fedora-nonfree:check-marketplace-2026.227.1148` (created **13:40:20**) while
KEEPING `:2026.227.1131` and `:2026.227.1050` (created **11:35:12**) — destroying
a build **2h05m newer than what it retains**, purely because the retained tags
*parse* as a CalVer and the newer one does not. That is the defect in one line:
the tag is a build-REQUEST stamp with no relation to build time, and ordering by
it discards the only fact that matters.

**The provenance rule now covers all THREE verdict verbs, each gated.** The first
pass applied it to two and cited R3 by name for the pair — while `charly box
labels`, the verb this cutover reclassifies as a verdict verb and whose four
unpinned calls are the headline evidence that the guard engages, printed no
artifact identity at all. And the sibling that DID get the line was ungated:
deleting it broke no test. Ungated is not applied. All three now print `Image:`
on every path, with a test per arm.

For `box labels` the line goes to STDERR, deliberately: `--format <key>` emits a
single raw value on stdout that every plan step pipes into grep, so a provenance
line there would have broken the beds it exists to make auditable. Both halves are
asserted — the ref on stderr, and stdout byte-unchanged.

**A test written to fix an unauditable verb was itself unauditable.** The two
`charly box labels` provenance tests stubbed `container.InspectLabels` — but
`container.InspectImageLabels` is a plain FUNCTION that shells out to `podman
inspect`, and `kit.InspectImageLabels` copied that function value at init, so the
override redirected nothing. Both tests reached real podman, never reached their
assertions, and PASSED because the image happened to be in the local store. When
a concurrent bed's retention sweep pruned it, they went red.

"The test passed" and "the test ran its assertion" are different claims, exactly
as "the bed passed" and "the bed had something to decide" are — and this cutover
now contains one instance of each, the second inside the fix for the first. The
fixture stubs `kit.InspectImageLabels` and installs a `kit.LocalImageExists` stub
that `t.Fatal()`s on any real-storage fallthrough, so the failure mode is loud
rather than silent; verified by confirming the image is ABSENT from the store
while the tests pass.

**The primary gate moved to the bed that can actually fail.** `check-marketplace`
passed by naming coincidence — `marketplace-app` had no CalVer-tagged sibling on
that host, so the guard never engaged. `box/arch`'s `check-agent-pod` runs the
guarded verb with a BARE short name four times in one host-side step against a
box it builds under a bed tag, which is precisely the shape at issue. **The gate of record is run `2026.227.1451` (13 steps, 365s), re-run on the final
tree after the comparator split — not the earlier 526s run.** That distinction is the point, not bookkeeping: at the earlier run
storage held exactly ONE image named `check-agent-box`, so the election had a
single candidate and the four `box labels` calls could not discriminate — it went
green because there was nothing to decide. That is the same coincidence this gate
was moved to `check-agent-pod` to escape, reproduced on the replacement, and it is
the third instance in this cutover.

There is ONE gate of record, and the candidate set is pinned beside it because a
PASS line cannot show whether an election happened:

```
26e1f933  14:28:46  lbl=2026.226.1600  check-agent-box:check-agent-pod-2026.227.1427
29302afe  14:26:38  lbl=2026.200.1654  check-agent-box:2026.227.1421
```

(Snapshot taken during the run; the bed's own build joins them as a third.)

Two candidates, so the election was real. A concurrent bed's retention sweep had
emptied this box's group beforehand, so a first candidate was built deliberately
(`charly box build check-agent-box --dev-local-pkg`) rather than hoping one
survived — a run whose store happens to hold one image proves nothing, which is
the lesson this cutover keeps re-learning.

Here the two candidates carry DIFFERENT content labels, so the election resolved
on the PRIMARY key. The creation-time tiebreak specifically — two candidates
sharing one label — is covered by the bed-tag unit tests (which fail without it)
and was additionally observed end-to-end on run `2026.227.1403`, where both
candidates carried `2026.226.1600`. Stated separately because they exercise
different keys and neither substitutes for the other.

Warnings on the gate run: **2 `warning:` lines, both `pacman … is up to date --
reinstalling`; 0 `.pacnew`; 0 `npm warn`; zero charly-emitted.** An earlier count
of "7" in this narrative described the 526s run (which had 9 — 7 reinstall plus 2
`.pacnew`, plus 6 `npm warn` lines that carry no `warning:` prefix). That
miscount was not carelessness about warnings; it was the SAME gate-of-record
confusion, surfacing a second time.

A PASS line alone cannot show whether an election happened, so the candidates are
recorded with it — but recorded OUT OF BAND. The bed does not capture host-side
stderr, so the four `box labels` calls' new `Image:` lines are absent from
`check-live.log`, and the candidate set above rests on a separate `podman images`
capture rather than on the run artifacts. That is self-REPORTED evidence where
self-EVIDENCING was available, and it is named as a follow-on rather than fixed
here: capturing stderr for host-side `command:` steps changes what every check
step captures (a `stdout: contains` assertion would begin seeing stderr), so it is
the check-runner output contract's decision and needs a gate across every bed's
step assertions, not this cutover's. The run also answers the scope question the batch left open: the
resolver fix is sufficient — `box/arch` needs no change and this stays a five-repo
batch.

## Separable findings, named rather than swept in (R2)

Every defect surfaced while verifying this one is named below; none is parked.
(`candy/plugin-clean`'s retention ordering was FOLDED INTO this cutover rather
than named here — it is the one that destroys an artifact rather than producing a
false answer.) None of them changes this cutover's claim or its gate's verdict,
and each is a different concern; they are reported with their root cause for their
thematic batch rather than widened into here.

**The numerals are deliberately gone.** This narrative miscounted its own findings
in three consecutive validation rounds — 3-vs-5, then 3-vs-4, then 3-vs-4 again —
because every round appended a bullet and the total was corrected in the PR bodies
while the artifact of record kept the stale figure. A running total is a claim that
decays the moment the list grows, in a document whose whole subject is claims that
decay; an enumeration cannot go stale that way. Same reasoning applied to the R1
and R2 lines in the PR bodies.

- **An imported box bakes NO `ai.opencharly.description`.** Same root-cause
  family as fix 1 — a namespace-qualified box key handed to a namespace-unaware
  consumer — but a much wider one:
  `deploykit.CollectDescriptions` reaches `cfg.BoxConfig(boxName)` and
  `cfg.WalkBaseChain(boxName)`, both flat map lookups with no namespace descent,
  so for `fedora.fedora-nonfree` both return nothing and the label is omitted
  entirely. Proven by building the SAME box two ways: from this superproject
  (namespaced key) the image has no description label and `charly check box`
  answers "No plan steps defined for this image"; from `box/fedora` (unqualified
  key) the identical box bakes the plan and runs it. After the 2026-06 box
  inversion that is every box the superproject builds — ADE's "the spec is the
  test, baked into the image" is silently void for all of them. Fixing it means
  making the deploykit collector family namespace-aware (the descent
  `buildkit.ResolveBox` already has), which is an architectural change well
  outside check-verb correctness.
- **`charly box feature run <image>` is unreachable.** It routes to the
  top-level `charly feature` grammar and errors with
  `unknown feature subcommand "run"` / `usage: charly feature <list | pending |
  validate>`, instead of `candy/plugin-box`'s `dispatchFeature`. Confirmed on a
  clean baseline tree with a from-source binary, so it is not this change and not
  a stale binary. Consequence: the documented build-scope ADE surface cannot be
  invoked at all; its guard here is unit-covered but could not be exercised live.
- **`charly check box` exits 0 when an image carries no baked plan.** Distinct
  from the provenance gap fixed above: printing the ref makes the report honest,
  but the ADE surface still reports success for an image with no acceptance plan
  — arguably the same class as certifying a stale artifact, a gate that cannot
  fail. Changing the exit code needs a survey of which images legitimately carry
  no plan, which belongs with the ADE cutover that makes the cause rare, not with
  the resolver.
- **`charly clean` retention counts REFS, not ARTIFACTS — and this one DESTROYS
  too.** Named separately from the ordering fix folded into this cutover because
  it is a different question with a different remedy, not because it is smaller.
  One image wearing three tags consumes the entire `keep_images: 3` budget alone,
  so every OTHER image of that box is queued for deletion regardless of age. It is
  live right now, not hypothetical: `fedora-nonfree` id `e2efeb1c` wears three
  tags and is exactly that case, which is why everything older in its group is
  queued. Fixing it means deciding what `keep_images: N` COUNTS — refs or
  artifacts — which is a user-facing contract change touching the schema field's
  meaning and its documentation, not a comparator clause, so it cannot ride this
  cutover's gate. It needs an owner of its own, at the same severity as the
  ordering half: both remove images.
- **`spec/proc.SweepStaleTemps` globs a hardcoded `/tmp/`** while its creators
  use `proc.MkdirTempHeld("", …)`, which honours `$TMPDIR`. On any host with
  `TMPDIR` set the sweep never sees the temps it exists to reap.
  `TestSweepStaleTemps_UnheldCreatorIsSwept` and
  `TestSweepStaleTemps_ReleasedTempIsSwept` fail there and pass under
  `env -u TMPDIR` — the tests are honest, the sweep is environment-specific (R4).

# 2026.227.1230 — `charly box feature run` is reachable for the first time

The documented build-scope Agent Driven Evaluation surface — `charly box feature
run <image>`, the verb that runs an image's baked plan as acceptance tests — has
never once dispatched to its implementation. It routed to the top-level `charly
feature` grammar and died:

```
charly: error: command "feature": unknown feature subcommand "run"
               usage: charly feature <list [kind] | pending [entity] | validate [entity]>
```

Member two of the check-verb correctness batch (member one:
`CHANGELOG/2026.227.1157.md`, the build-scope verdict verbs). Same theme — a
verdict surface that cannot be invoked is the sibling of one that certifies the
wrong artifact.

## Three defects in one dispatch chain

Each is independently fatal to the verb; fixing any two still leaves it broken,
and fixing only the first two makes the binary PANIC at startup. They are one
cutover because they are one path.

**1. Dispatch resolved a nested command by its plain word.**
`charly/provider_registry.go`'s `register` is CommandParent-aware: when a NESTED
command word collides with a TOP-LEVEL one it parks the nested capability at
`command:<word>:<parent>` and gives the plain key to the top-level (its own
comment names `box feature` vs `charly feature` as the case). But
`dispatchCommand` (`charly/provider_command_external.go`) resolved with
`providerRegistry.resolve(ClassCommand, d.word)` — the PLAIN key — so a `box
feature` invocation was handed the top-level `charly feature` capability, whose
grammar has no `run`. `externalCommandDispatch` did not even carry the parent, so
the lookup had nothing to disambiguate with.

Fixed by `Registry.resolveCommand(word, parent)`, the exact inverse of the
parking rule, placed beside it so the two cannot drift; `externalCommandDispatch`
gains `parent`, set where `collectExternalCommandPlugins` already knows it.

**Measured blast radius: exactly one word.** Intersecting the live top-level
command list with the live `box` subcommand list yields `feature` and nothing
else — every other `box <word>` (build, validate, list, inspect, …) is uniquely
worded, was never parked, and dispatched correctly all along.

**2. The Kong tag that looked like a name was not one.**
`candy/plugin-check`'s bridge leaf was declared `cmd:"__feature-box"`. Kong never
reads a `cmd:` tag's VALUE as the command name — the tag is a pure presence
marker and the name falls back to the dash-cased FIELD name — so the leaf
actually dispatched as `feature-box`, while `candy/plugin-box`'s `dispatchFeature`
forwarded `__feature-box`. The result, once defect 1 was fixed:
`InvokeProvider command:check op=run: unexpected argument __feature-box`.

This is not new knowledge: `sdk/kong_reflect.go` documents the exact trap, from
an RDD spike ("a value-carrying `cmd:"foo"` with no separate `name:` tag does NOT
mean the command is named foo"). The declaration was simply written against the
wrong assumption.

Every `cmd:` tag in `CheckCmd` is now a bare presence marker paired with an
explicit `name:`, so the declared name is the dispatched name. Five siblings
(`run-local`, `sync-credential`, `last-tag`, `self-evaluate`) agreed with their
field's dash-case and worked BY COINCIDENCE; one did not — `cmd:"list-ai"`
dispatched as `list-agent`. `list-ai` is documented nowhere and answered nothing,
so no user contract changes: the tag is corrected to the name that actually
dispatches, and the coincidences are made explicit rather than left to survive
the next field rename by luck.

**3. `exportedCommandField` did not guarantee an exported name.**
Renaming the leaf surfaced this immediately: `__feature-box` sanitizes to
`__feature_box`, and `strings.ToUpper` leaves a leading `_` alone, so the derived
Go field stayed unexported and `reflect.StructOf` PANICKED —

```
panic: reflect.StructOf: field "__feature_box" is unexported but missing PkgPath
  main.nestedSubcommandType ... main.collectExternalCommandPlugins ... main.main
```

— inside `main()`, before any command could run. Not a degraded command: a dead
binary. A first byte that is not an ASCII letter now takes a `Cmd` prefix, so the
function's whole reason to exist holds for every input rather than for the ones
that happen to start with a letter.

## Was it ever reachable? No.

`git log -S` settles it. The parking scheme in `register` AND `dispatchFeature`
in `candy/plugin-box` both arrived in the SAME commit — `d3f668db`, 2026-07-28,
the #118 core-minimization cutover — while `dispatchCommand`'s plain-word resolve
dates to genesis and was never parent-aware. The top-level `charly feature`
predates both (genesis, externalized in `377d093b`). So the nested capability was
born already shadowed, and the verb has never worked since the day it was
introduced.

## Coverage

Three gates, one per defect, each failing on its own pre-fix body:

- `charly/provider_command_external_test.go`
  `TestResolveCommand_NestedWinsOverCollidingTopLevel` — registers a colliding
  top-level + nested pair and asserts the nested invocation reaches the nested
  capability, the top-level one is unchanged, and a uniquely-worded nested
  command still answers on the plain key (the reason only `feature` broke).
- `TestExportedCommandField_AlwaysExported` — asserts the exported-first-byte
  property across leading `_`/digit/letter inputs, then calls
  `nestedSubcommandType` on a `__feature-box` catalog: that call is what panicked
  the real binary, so the test reproduces the startup abort rather than
  paraphrasing it.
- `TestCollectExternalCommandPlugins_NestedCarriesParent` — the wiring between
  the two: a nested dispatch entry must carry its parent or the parented lookup
  has nothing to work with.
- `candy/plugin-check/check_cmd_names_test.go` `TestCheckCmdDeclaredNames` —
  asserts the DECLARED name set, `__feature-box` included and `feature-box`
  absent. The names are a contract between two plugins, so they are asserted
  rather than left to a tag that merely looks authoritative.
  `TestCheckCmdFeatureBoxHidden` pins hidden-but-reachable.

## Note on a sibling instance not fixed here

`candy/plugin-pod` and `candy/plugin-secrets` carry the same value-carrying
`cmd:"<name>"` shape (`mount`, `passwd`, `migrate-secrets`, `add-recipient`,
`export-key`, `import-key`, …). Every one of them agrees with its field's
dash-case, so all currently dispatch correctly — coincidence-correct, exactly
like the five siblings inside `CheckCmd` were. They are named here rather than
swept in: no defect exists to fix, this cutover's gate does not exercise them,
and rewriting tags in two more plugins would widen a CLI-grammar fix into a
cross-plugin sweep with nothing to prove it. The `CheckCmd` struct was included
because the actual defect lives in it and a second misleading tag sat two lines
away.

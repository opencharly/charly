# 2026.227.1243 — carry the namespace-aware box collectors

The `sdk` gitlink moves to `c1c41b06`, which makes the box-collector family
namespace-aware. This entry records the consequence for THIS repository, where
the defect actually bit.

## The pin, and why it is not the one this branch opened with

The branch originally pinned `15b89eac`, the head of sdk#137 BEFORE that PR's
own update-branch merge. sdk#137 was squash-merged and its branch deleted, so
`15b89eac` is unreachable from `sdk` `main`: it resolves in a checkout that
still holds the deleted branch and resolves to NOTHING in a fresh clone, and no
drift gate catches that. Verified in a full clone (`--is-shallow-repository` =
`false`):

    git -C sdk merge-base --is-ancestor c1c41b06 origin/main   -> exit 0
    git -C sdk merge-base --is-ancestor 15b89eac origin/main   -> exit 1

The correction is NOT a pure pointer move. `15b89eac` predates two `sdk` `main`
commits, so it could not be repinned on its own: `c1c41b06` re-exports symbols
that exist only in `spec` `bbb3c6a`, and its module graph needs the 90-module
`spec v0.2026225.1800 -> v0.2026227.1854` bump. Repinning before that landed
failed to build outright:

    ../sdk/kit/local_image.go:28:31: undefined: spec.ErrStaleLocalImage
    ../sdk/kit/local_image.go:52:39: undefined: container.LocalImageResolution

`charly#278` carries exactly that prerequisite — `spec` `bbb3c6a`, `sdk`
`2f6a3a7`, and the 90 `go.mod` bumps — so this branch waited for it rather than
duplicating another cutover's content, and merged it in.

The `sdk` gitlink was a GENUINE two-sided conflict at that merge, not the false
one `merge-tree` reports for a fast-forward: base `7a81472`, ours `15b89eac`,
theirs `2f6a3a7`, and `merge-base(ours, theirs)` equals the base — so taking
either side alone would drop the other's content. Resolved FORWARD to
`c1c41b06`, which contains theirs (`2f6a3a7` is an ancestor) and supersedes ours
(`15b89eac` is the side that squash replaced). The pin is read off the MERGE
COMMIT, never the working tree, since a tree that was already correct cannot
prove a resolution:

    git ls-tree <merge> sdk   -> c1c41b06
    git ls-tree <merge> spec  -> bbb3c6a   (one-sided, taken from main)

`charly#281` then landed too, so the branch took a SECOND `main` merge. That one
was one-sided on both gitlinks and resolved without a conflict — `spec` advanced
to `2c6e2bd6` (ours equalled the base, so theirs won) while `sdk` kept
`c1c41b06` (theirs equalled the base, so ours survived). Verified the same way,
off the merge commit:

    git ls-tree <merge2> sdk   -> c1c41b06
    git ls-tree <merge2> spec  -> 2c6e2bd6

Every figure in the Gate section below was measured AFTER that second merge.

## What was wrong here

After the box inversion, every box this repository builds lives in a
`box/<distro>` submodule and is reached under an import namespace
(`fedora.charly-fedora`, `arch.charly-arch`, `cachyos.versa`, …). The collectors
that produce the `ai.opencharly.*` label contract entered on that qualified name
through flat, root-internal lookups, found nothing, and produced empty results.

So **every box this superproject built** shipped without
`ai.opencharly.description`, `port`, `volume`, `security`, `shell`, `alias`,
`hook`, `skills`, `data`, or the box-level `env` — and with **no `EXPOSE`
directives**.

The `description` label is ADE's baked `plan:`. With it absent,
`charly check box <image>` answered `No plan steps defined for this image` and
exited **0** — a gate that could not fail, across the whole catalog. `charly box
validate` did not catch it either: the plan is authored correctly, it just never
reached the image.

Measured on `fedora.charly-fedora`: from here the Containerfile carried 21
`ai.opencharly.*` labels and zero `EXPOSE`, against 27 labels and one `EXPOSE`
once the collectors resolve the qualified name. The A/B that produces those two
numbers is below, run against `main`'s own `sdk` pin.

## Why the beds did not catch it

Every bed image in this repository's `charly.yml` is a ROOT box with an external
base, so the beds only ever exercised the bare-name path. No bed deploys a
namespace-qualified box. That is the gap that let a catalog-wide missing label
sit behind a green gate.

## The proof this repository can reproduce

Re-derived on the merged tree, and stated as an A/B against **`main`'s own `sdk`
pin** rather than a hand-reverted subtree — so the discriminator is exactly "this
PR's gitlink vs. what is on `main` today":

    # WITHOUT this PR (sdk 2f6a3a7 = main's pin):
    charly box generate fedora.charly-fedora
    grep -c '^EXPOSE' .build/fedora.charly-fedora/Containerfile                 -> 0
    grep -o 'ai\.opencharly\.[a-z_.]*' … | sort -u | wc -l                      -> 21

    # WITH this PR (sdk c1c41b06):
    grep -c '^EXPOSE' .build/fedora.charly-fedora/Containerfile                 -> 1   (EXPOSE 2222)
    grep -o 'ai\.opencharly\.[a-z_.]*' … | sort -u | wc -l                      -> 27

The six labels present only with the fix are exactly the box-level contract the

    ai.opencharly.description  ai.opencharly.port      ai.opencharly.security
    ai.opencharly.shell        ai.opencharly.skill     ai.opencharly.volume

`description` is ADE's baked `plan:`; with it absent `charly check box` answered
`No plan steps defined for this image` and exited 0 — a gate that could not fail.

here on `cachyos.jupyter-ml` (an imported box composing the `notebook-templates`
data candy): the `ai.opencharly.data` label is absent before the fix, and after

    [{"volume":"workspace","staging":"/data/workspace/","candy":"…/notebook-templates"}]

The sdk's own `CHANGELOG/2026.227.1923.md` — renamed from `2026.227.1243.md` by

# 2026.227.1243 — carry the namespace-aware box collectors

The `sdk` gitlink moves to `5d783113`, which makes the box-collector family
namespace-aware. This entry records the consequence for THIS repository, where
the defect actually bit.

## What was wrong here

After the box inversion, every box this repository builds lives in a
`box/<distro>` submodule and is reached under an import namespace
(`fedora.charly-fedora`, `arch.charly-arch`, `cachyos.versa`, …). The collectors
that produce the `ai.opencharly.*` label contract entered on that qualified name
through flat, root-internal lookups, found nothing, and produced empty results.

So **every box this superproject built** shipped without
`ai.opencharly.description`, `port`, `volume`, `security`, `shell`, `alias`,
`hook`, `skills`, or the box-level `env` — and with **no `EXPOSE` directives**.

The `description` label is ADE's baked `plan:`. With it absent,
`charly check box <image>` answered `No plan steps defined for this image` and
exited **0** — a gate that could not fail, across the whole catalog. `charly box
validate` did not catch it either: the plan is authored correctly, it just never
reached the image.

Measured on `fedora.charly-fedora` built both ways — from here, 21
`ai.opencharly.*` labels and zero `EXPOSE`; from `box/fedora` as its own project
root, 25 labels and one `EXPOSE`.

## Why the beds did not catch it

Every bed image in this repository's `charly.yml` is a ROOT box with an external
base, so the beds only ever exercised the bare-name path. No bed deploys a
namespace-qualified box. That is the gap that let a catalog-wide missing label
sit behind a green gate.

## The proof this repository can reproduce

    charly box build fedora.fedora-nonfree
    charly box labels <the built tag> --format ai.opencharly.description
    charly check box <the built tag>

Against an image built before the bump the label read is
`label "ai.opencharly.description" not present`, and `charly check box` prints
`No plan steps defined for this image`. After it, the label carries the full plan
and `charly check box` runs `7 steps: 6 passed, 0 failed, 1 skipped`.

The sdk's own `CHANGELOG/2026.227.1243.md` records the seam (`deploykit.BoxOwner`),
why the fix is in `deploykit` rather than `spec`, and the second bug it surfaced
(`generateContainerfile` reading the port seam by the leaf `ResolvedBox.Name`
instead of the qualified box key, which is why `EXPOSE` stayed missing after the
label came back).

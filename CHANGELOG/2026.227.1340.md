# 2026.227.1340 — R4a sweep: task-target residue on reader-facing published pages

The R4a residue sweep across the **non-development** half of the published skill corpus — every page `charly docs generate` emits as a recipe card outside the `charly-internals` (development) bucket. R4a's standard is that every command a reader is told to run works with nothing but the `charly` binary installed; a page may NAME a repository-maintenance command as maintenance this project performs, but never as a step the reader runs. This cutover fixes the pages that crossed that line, and corrects a false-claim class the sweep surfaced.

## Measurement

Residue keyed to the actual Taskfile target NAMESPACE (an alternation of every real target from `task --list-all` on the superproject plus `spec/Taskfile.yml`, plus the three names the docs used that are not real), together with `./bin/charly` and `GOWORK=off`. A shape-based pattern is not usable here: a loose `task [a-z:]+` matches English prose ("task involves", "/task releases"), and the tighter `task [a-z]+:[a-z:]+` silently misses the colon-less `task install-portable`.

That published declaration, not the `plugins/README.md` bucket table, is the basis: it is defensible to a reader who never saw the marketplace manifest. ## Submodule branches are based on the submodule's own `main`, never on the superproject gitlink

The submodule legs of this cutover were first branched from the **superproject's gitlinks** — `plugins` at `61f5e9bf`, `docs` at `b3c08a46` — which is what a submodule checkout gives you. Both were behind their own repositories' `main` (`396e4bf`, `93085fb`). Because `charly marketplace generate` and `charly docs generate` rewrite their outputs **wholesale**, regenerating from a behind-base produced a diff that was impossible to read: 37 `reference/box/fedora/` pages re-applying a pin projection `93085fb` had already landed, and an apparent 249-line deletion of `recipes/internals/git-workflow/evidence-and-freshness.md`, a page whose source is not in this repository.

**Both were artifacts of the stale base, and neither would have survived a merge.** That correction matters more than the original alarm, because an earlier draft of this entry asserted the branch was poised to revert merged work, and two reviews accepted it. Git says otherwise — the merge keeps a file added on one side only:

```
$ git merge-tree --write-tree 93085fb bec4881        # docs main x the pre-rebase commit
9a12a78e1b3c908a8941df739e9018e18e2dd733
$ git cat-file -e 9a12a78:…/evidence-and-freshness.md && echo SURVIVES
SURVIVES
```

The 37 fedora pages were likewise byte-identical to what `main` already carried, so they too merged to nothing. The real cost of a stale base is therefore **analytical, not data-loss**: it produces a diff that reads as churn and reverts, invites a confident and wrong RCA, and burns review cycles proving the alarm false. That is reason enough to fix it, and it is the honest reason.

**The standing rule: a submodule branch is cut from that submodule's `origin/main`, and a wholesale generator is only ever run from that base.** The gitlink records what the superproject last pinned, not what the submodule currently is.

The upstream half, verified from the history: **a gitlink bump that changes candy pins needs a `docs:sync` in the same landing.** `chore(box): bump box/fedora to v2026.227.1110 (#277)` merged at 13:46 reconciling 158 pins with no mirror regeneration; the gap survived an intervening docs landing at 14:24 and was repaired only at 15:42 by `93085fb`, which had to carry all 37 pages itself.

**How to measure any of this is already settled, and not by this cutover.** `/charly-internals:git-workflow` → `references/evidence-and-freshness.md` ("The gate that matters at merge is the merged tree's, not the head's") carries the recipe, and its `BASE=$(git rev-parse origin/main)  # the base TIP, never the merge-base — the merge-base reproduces this section's bug` is exactly the blind spot this cutover re-derived from scratch. Two ranges were tried here and both are wrong: three-dot diffs from the merge-base and under-reports; two-dot over-reports on any branch whose `main` has moved (measured: it flagged `CHANGELOG/2026.227.1410.md`, a different PR's file, purely because `main` advanced to `f968abbb` mid-work). A "rebase first, then two-dot" formulation was drafted and discarded — **rebasing is illegal on a pushed branch**, since it requires the force-push this project forbids everywhere, so a rule that assumes it cannot be run by a validator on an open PR. `git merge-tree --write-tree` against the base tip answers the question without rewriting history, works before and after the first push, and is what the landed page already prescribes. Note its `head -1`: on a conflicting merge `merge-tree` prints the tree oid on line 1 and conflict detail after it.

### This section was itself the failure it describes

The paragraph above stood in present tense — "no candy `skill:` entity produces it", "it is in flight as charly#284" — for the whole interval after `80a662bc` became this branch's base. Every one of its four assertions was disproved *on this tree*, while the gate section below already discarded a bed run **because** #284 had landed. The sweep reached one section and stopped at the next.

(The first draft of this very correction cited that gate section *by line number*. It was wrong within one edit — the rewrite above moved it. Cited by content instead, for the same reason a line number in a generated file is worthless: any edit ahead of it silently invalidates the reference.)

That is precisely the rule this cutover carries, sprung on the document carrying it: *re-running the bed is half the fix; the prose still cites the superseded state*. It is the fourth instance in a single day of a claim that was true when written and false when read — alongside the stale-base rule catching its own author, and a validator's own noun-slip on the page cataloguing noun-slips.

The pattern is stronger evidence than the rule stated alone, so it is recorded rather than quietly corrected: **a claim-keyed sweep must reach every present-tense assertion about a state that has since moved, not merely the section being edited.** A cutover that changes its own base mid-flight invalidates prose that never mentions the base — which is why the sweep key is the *state*, never the string.

## Standing correction: for a docs-generation occurrence the remedy is REFRAME, never re-spell

The natural first remedy for R4a residue is "a binary-only equivalent exists → name that instead" — for the docs family, `charly docs generate` in place of `task docs:sync`. **For this family that remedy is wrong, and applying it would make the page worse than it was.**

`charly docs generate` is **not available to a binary-only reader.** `plugin-docs` is absent from `charly/charly.yml`'s `compiled_plugins:` AND from `pkg/host-command-plugins.txt`, the single-source list of plugins baked beside the binary at `/usr/lib/charly/plugins` on every native package install. So the substitution trades a repo-only command for one the reader ALSO cannot run — a false claim replacing a true-but-misaudienced one, which is strictly the worse failure: the misaudienced command at least runs for someone with a checkout.

This is **not** a defect to fix in `charly`. Documentation generation IS repository maintenance, and R4a explicitly permits naming maintenance as maintenance; exposing `charly docs` to every installed binary would be building a capability to satisfy a rule that does not require it. Every docs-generation occurrence is therefore **reframed with an audience declaration, never re-spelled as a charly verb.** `docs/src/content/docs/concepts/10-the-cookbook-never-lies.md` already states the limitation correctly and is the model to copy.

Recorded here as a standing rule because the substitution is the reflex a later sweep will reach for first.

## Change class — config, not documentation-only

The prose in this cutover is documentation, but the commit is **not** in the documentation-only class, because it re-pins `DOCS_REF`. The rulebook's own enumeration decides it: `documentation reviewed` covers "docs, comment-only edits, docs-only gitlink bump" and is "forbidden the moment code/config behavior is touched". A docs-only gitlink bump is named as inside the class; a candy `var:` is not.

The reason that omission is principled, and the test to reuse: **a change class must be decidable from the diff.** If "the referenced content is documentation" were the test, classifying this commit would require cloning a remote repo at a named commit and reading it — the class would be a property of someone else's tree rather than of the change under review, and no reviewer could rule on it without leaving the PR. `DOCS_REF` feeds the clone layer's cache key, so the `docs-site` box builds different bytes. That is config, and it stays config regardless of what `ee3d162e` happens to contain.

Consequence for every future landing, not just this one: the standard multi-repo sequence ends with "re-pin `DOCS_REF` after the docs leg merges", so **any cutover that re-pins `DOCS_REF` is a config change and takes the config gate** — `charly box validate` plus the `check-docs` bed — however documentary its prose. That is a standing rule this cutover discovered rather than a property of this cutover.

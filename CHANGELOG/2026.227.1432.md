# 2026.227.1432 — evidence page: guard the merge-tree probe, scope the execution rule to content

Authoring half of a three-repo documentation cutover. The source is `candy/charly-internals/charly.yml`'s `git-workflow-skill:` entity; the generated halves are `opencharly/plugins#175` and `opencharly/docs#58`, both merged before this leg pins them.

## The defect

`v2026.227.1426` (charly#284) published an evidence-discipline reference whose merged-tree probe recipe fed `git merge-tree --write-tree` into a bare command substitution. `merge-tree` exits 1 on conflict and prints the tree oid followed by the conflict stages, so `git commit-tree` rejects the multi-line capture:

```
$ git merge-tree --write-tree side-a side-b   # conflicting pair
$ echo $?
1
$ git commit-tree "$(git merge-tree --write-tree side-a side-b)" -p side-a -m probe
fatal: not a valid object name c5045be2…
```

The obvious repair is worse than the bug. `head -1` yields a real, checkoutable tree whose files contain conflict markers:

```
$ git cat-file -p "$(git merge-tree --write-tree side-a side-b | head -1):a.txt"
<<<<<<< side-a
AAA
=======
BBB
>>>>>>> side-b
```

The recipe's whole purpose is to run a gate inside that tree, so a shape-based fix produces a gate that passes against conflict markers — a false green in the one place the page exists to make trustworthy.

Both call sites now guard on the **exit status**. The probe refuses and tells the reader to resolve first; the identity test in the submodule-revert section degrades to the numstat form instead of reporting a false `DIVERGED`. The single surviving `head -1` is in the diff-inspection recipe, which genuinely wants the conflicted tree, and now states it is correct nowhere else on the page. Verified on both arms: a conflicting pair refuses, a clean pair proceeds and `commit-tree` accepts the oid — no false refusal.

## The root cause was the frame

The page divided its content into epistemic and mechanism sections and promised execution only for the mechanism half — "reasoning is not available for this half of the page". The one broken shell recipe sat in an *epistemic* section, exempted by that very wording. The frame decided what got executed and routed a runnable command to the reasoning-is-enough side, so patching the recipe alone would leave the next one exposed.

The rule is rescoped to **content**: every runnable command and every mechanism claim on the page is executed before publication, wherever it sits. The three `merge-tree` behaviours are pasted as terminal evidence rather than asserted, and the page now records that this correction was itself forced by a defect.

Two readability findings from the same review land with it: a symptom-indexed entry table, so a reader arriving with a problem reaches routing before epistemology; and a note that `PR_HEAD=$(git rev-parse HEAD)` assumes cwd is the PR checkout.

## A landing-order constraint and a product defect, both surfaced by this cutover

**`charly marketplace drift` is clean on `main`, and the landing order that keeps it that way.** Main's `plugins` gitlink (`396e4bfe`) lags the `plugins` repo tip (`aa80ca9f`) by exactly `plugins#174`, whose R4a task-target sweep landed as a projection whose authoring half is not on main. Measured in a throwaway `origin/main` checkout with `git submodule update --init`: exit 0, 400 artifacts matching. Measured with the submodules at their tips instead: exit 1, eight stale artifacts. Both readings are correct for their own tree; only the first one is `main`.

An earlier draft of this entry, and the first bodies of `#175`/`#58`, asserted the second reading as a fact about `main`. That was a wrong-tree claim of exactly the kind the page in this cutover exists to prevent — right measurement, wrong noun — and it is corrected here and in `plugins` commit `088f687` rather than silently dropped.

The consequence is a gate on `main`, not a preference: whichever superproject commit first advances the `plugins` gitlink past `396e4bfe` carries `#174`'s projection onto main without the source half that produces it, and turns main red. The authoring half is held by another session as `feat/r4a-residue-sweep-2` (`bb3ce657`), which carries the candy-source edits and the pointer advance in one commit so the inverted state closes atomically. This leg therefore lands after it, and pins both submodules only then.

**A non-existent `$TMPDIR` silently contaminates every charly measurement.** Out-of-process plugins are go-plugin servers that create their unix socket under `$TMPDIR`; with the directory missing they die before the handshake, and go-plugin's upstream client text (`Failed to read any lines from plugin's stdout`) names four causes — architecture, shared libraries, permissions, handshake negotiation — none of which is the real one. charly then warn-skips the affected `kind:` node and exits 0, so `box validate`, `marketplace generate/drift` and `docs generate` all report success against a model that lost content. This bit this cutover: the first round of gate figures was taken under a TMPDIR that did not exist and had to be discarded and re-measured. The bad text is upstream, so the fix is a charly-side preflight on `$TMPDIR` before launching a plugin — a Go change with a real gate, not foldable into a documentation-only cutover, and distinct from `#281`'s spec bump.

Documentation-only change class at `documentation reviewed`.

## What the lock change does, in one line

`AcquireFileLock` no longer writes `pid=%d` into every lock file. Nothing read it,
and a pid line in a lock file is the visual signature of a PIDFILE lock — a
mechanism these locks do not have, since the kernel releases an flock when the
holder dies. Presence proves nothing and absence proves nothing; `ps` is the only
discriminator. Full rationale in `spec`'s own entry.

The version sweep is routed to the **module-hygiene batch**, which already owns it:
its gate is the standalone `GOWORK=off` build across 91 modules, a different gate
from this cutover's bed, and folding a 95-file sweep into a two-line pin bump would

## The one exception, named so it is not read as forgotten

**`sdk/go.mod:15` requires `github.com/opencharly/spec v0.2026227.1854` with NO
`replace`.** It is the single case where the require string is load-bearing rather
than nominal: built standalone, `sdk` resolves spec from the proxy at that version,
now two releases behind (`v0.2026227.2226`, `v0.2026228.0002`).

It is **not touched here** because it is a different repository, and its bump belongs
to the `sdk` chain already in flight. Recorded rather than omitted, because a reader
who sees 94 modules left alone and one repo untouched should not have to guess which
was deliberate.

**Worth stating as its own lesson:** *"94 of 95 carry a replace"* and *"the require is
nominal"* are **not the same claim**. The 94 are nominal; the 95th is precisely the
one where the string selects code. A ratio that high invites treating the remainder
as rounding error, and the remainder was the only load-bearing case in the set.

# 2026.228.0223 — retention Unit A: keep_images counts images, and the ephemeral reaper stops reaping the wrong thing

Two members of the retention batch — *what charly's retention counts, and what it cannot
reach at all*.

**Every half of the reaper change is safe alone and unsafe in some combination with another
half.** The freshness bypass is safe only because identity is gated; the identity gate is
reachable only because the address form resolves without a project; that address form is safe
only because identity is checked *before* resolution. Three couplings, none of them local — which
is why this ships as one change and why **a partial fix here is worse than no fix**.

## Member 1 — `keep_images` budgets IMAGES, not tag rows

`keep_images: N` now keeps **the newest N distinct images, and at most N tags of each.**

`retentionRemovable` ranked by tag index, so one image wearing three tags consumed the whole
`keep_images: 3` budget and the 2nd and 3rd *distinct* images were pruned — measured live on
`fedora-nonfree` (id `e2efeb1c`).

**Direction matters, and this is the guard against a retraction I had to make:** the defect made
retention keep FEWER distinct images, so it **over**-pruned within a managed family. It could
never cause under-reclaim, and it is **not** an explanation for any observed disk shortfall. That
attribution was asserted once in this program and withdrawn; the retraction is more useful than
the finding.

Two ordinals are load-bearing and each alone regresses the other:

- tag-index alone is the over-prune above;
- image-rank alone reclaims **no tags at all** — a content-stable image rebuilt many times wears
  every CalVer tag it ever had at rank 0, so tag rows grow without bound.
  `TestPruneImagesByRetention_SharedID` caught exactly that when the first cut of this fix
  budgeted images only. **The proposed fix traded an over-prune for an unbounded leak, in the
  batch about retention.** The test was right and the design was incomplete; the test was not
  touched.

Reusing `N` on both axes is principled, not a dodge: distinct images bound **bytes**, tag rows
bound **metadata**. Worst case is `N × N` tag rows — quadratic in a small integer, on metadata —
while bytes stay linear in `N`. A second knob would let an operator tune a quantity that costs
nothing.

`keep_images: 0` still disables retention before any enumeration (`pruneImagesByRetention` returns
on `keepN <= 0`), covered by `TestPruneImagesByRetention_Disabled`.

## Member 2 — the ephemeral TTL reaper

### What was broken

The reaper is a systemd transient unit running `charly fleet del <entity> --assume-yes`, registered
per ephemeral deploy. It had **four independent defects**, each masking the next:

1. **Frozen worktree paths.** `registerTransientTimer` baked `os.Executable()` *and* `os.Getwd()`
   into a persistent unit. Both are correct at registration — the binary is R9-correct, and
   `--working-directory` was itself a deliberate fix — and both are worktree-scoped, so the
   rulebook's own "remove your worktree after the PR lands" disarmed every reaper it had
   registered. Observed: ten armed units, all `203/EXEC`, binary absent.
2. **The entity name is reused and stale timers stay armed**, because `EphemeralRuntime` records
   ONE `TimerUnit` and registration overwrites it — so every earlier timer became unreferenced and
   permanently un-cancellable.
3. **The bed deleted the reaper's state.** A bed session isolates ephemeral state into a per-run
   temp overlay (`MkdirTemp` + `CHARLY_DEPLOY_CONFIG`) and `RemoveAll`s it at teardown while
   leaving the timer armed — half of a two-part registration.
4. **Nested children were never torn down.** A pod bed's cleanup runs `charly remove --purge`,
   a container verb with no deploy-tree walk, so `check-sidecar-pod`'s ephemeral VM outlived every
   run — contradicting the bed's own authored comment that it is *"torn down as part of the bed's
   own cleanup"*.

**The near-miss.** Nine stale timers fired at 00:19:26 while a live incarnation held the entity
name. Each was about to `fleet del` it. **Only the missing executable stopped them.** So fixing the
path alone would have converted a silent leak into deletion of live work — and it would have looked
like a successful fix, because the reaper would finally have been running.

### What changed

- **Incarnation identity as a FLAG**, `--require-timer-unit=<unit>`, checked **before** resolution
  and **failing closed**: no recorded registration, or a superseded one, refuses and exits
  non-zero. It is a flag rather than an environment variable because the guarantee is enforced by
  the binary that RUNS: an older binary silently ignores an env var and reaps with no check, while
  an unknown flag is a parse error. Measured on an installed `2026.223.1347` binary —
  `fleet del … --require-timer-unit=x` exits 80 without entering the command body, while the same
  command without it parses and proceeds. **The flag is its own version gate.**
- **`CHARLY_SKIP_FRESHNESS_CHECK=1` scoped to the unit.** `fleet del` is correctly not
  freshness-safe, so an installed binary older than the source tree refuses to run — the normal
  state on a developer host. The bypass is safe only because of the identity gate above; that
  dependency is stated at the seam.
- **Cancel-at-registration**, so at most one timer per entity is ever armed. This removes the
  cross-run hazard *at its source*: a run deploying over a killed incarnation's name cancels that
  armed timer, so it never survives into the run it could damage. The gate stops a stale timer from
  ACTING; this stops it from EXISTING. **Both are kept** — `cancelTransientTimer` is best-effort,
  so a `systemctl` failure leaves a timer armed with no second chance, which is exactly what the
  gate refuses.
- **The bed cancels what it registered**, before removing the overlay, so a cancellation failure
  leaves the state intact and the timer still able to work. Scoped to the session's **own** overlay:
  a `charly-fleet-del-*` name-pattern match — the obvious implementation — would cancel a
  **concurrent bed's** reaper for a VM still in use.
- **The bed tears down nested children**, mirroring `d.ChildKeys` in reverse. An **addition**, not
  a verb swap: the root keeps `remove --purge`, the only path reaching `purgeDeployArtifacts`.

### `os.Executable()` is deliberately kept

Pointing the unit at an installed `charly` is the obvious answer to worktree deletion and is wrong
twice: `fleet del` is not freshness-safe, so an older installed binary refuses; and the identity
gate lives in the **reaping** binary, so an older one would reap with no check. *Safe because it
refuses* is worse than *safe because it works* when the registering binary is right there and
correct.

## Findings filed, not fixed here

**`fleet del` cannot purge.** Both reachers of `purgeDeployArtifacts` are gated on the flag
(`remove_orchestration.go:411,433`) and `candy/plugin-fleet` never sets it, so `fleet del` leaves
named volumes, gocryptfs volumes and `<name>-overlay` images behind. **Today `fleet del` and
`remove --purge` differ in what they destroy and nothing at the call sites says so** — that
asymmetry is the defect and the stranded VM was one symptom. Filing rather than fixing: it changes
a destructive verb's semantics with blast radius over every pod deploy, and this cutover's
single-bed gate cannot fail on it. **A fix whose blast radius exceeds its cutover's gate needs a
different gate.**

**A struct tag that describes a serialization no producer emits.** `FleetConfig.Fleet` is tagged
`yaml:"deploy"`, but `SaveFleetConfig` writes entity-name keys carrying node-form bodies and
`LoadFleetConfig` delegates to the unified loader rather than parsing YAML. So a hand-rolled
`yaml.Unmarshal` of any real overlay **succeeds and returns an empty map** — silently. Two readers
written here did exactly that, in one sitting, with the paired loader three functions above one of
them. The instances are fixed; **the invitation stands**, and anyone reaching for `FleetConfig` and
a `yaml.Unmarshal` reproduces it, because the type's own annotation tells them to.

## Measurement discipline this cutover paid for

**A correction is a new claim and carries the full risk of one.** Three of the failures below
were *fixes for earlier failures on this list*, and every one failed in the direction that does
not announce itself: the fix for over-matching under-matched; the guard against silent success
raced the thing it watched; the fix for stale branch names cited an immutable wrong object. Each
was made by someone who had just been burned by the thing they were correcting — which is exactly
when a positive control feels least necessary and is most needed. **This predicts the next failure
better than any individual row.**

Ten measurements returned plausible values about the wrong object, and one shipped. Nine rows —
the last covers two, a probe and the filter added to fix it:

| instrument | what it actually measured |
|---|---|
| `grep -rin warn` over a run dir | the word "warning" inside candy skill prose baked into an OCI label |
| a perturbation that deleted the ranking | orphaned its consumers → **compile** failure, not a test failure |
| `systemctl show` on a name from `list-units` | the `●` glyph, returning `Result=success` for nothing |
| `pgrep -f 'check run <bed>'` | **its own command line**, so the `until ! pgrep` loop could never exit |
| `yaml.Unmarshal` into `FleetConfig` | a shape no writer emits — **this one was in shipped code** |
| `git diff --name-only` across a gitlink bump | one filename standing for three commits over four files |
| `pgrep -x qemu-system-x86_64` | **nothing, ever** — `comm` is capped at 15 chars, so the name is stored `qemu-system-x86` and the pattern is structurally unmatchable |
| a monitor's own failure branch | a **race**: it sampled between the bed exiting and the recorder's 5s poll writing, and reported "no output — investigate" for a run that had passed |
| `git rev-parse HEAD^{tree}` at run time | **main's tree** — the change was uncommitted, so the SHA is immutable, precise, and names an object containing none of what the run proved |
| `pgrep -f "agent-name <x>"`, then a `/versions/` filter added to fix it | **its own argv, twice** — the added filter string was itself in the command line; a positive control on an impossible name returned 1, so liveness came out UNMEASURED rather than "all live" |

Rules extracted, in the form that survives inattention:

- **The axis is not `-f` vs `-x`: it is whether the identifying string lives in `argv` or in
  `comm`, and whether it FITS.** `-f` matches your own command line; `-x` matches a `comm`
  truncated to 15 characters, so any longer executable name can never match. *"Match the
  executable, not a substring"* was the advice that produced the second defect, and it is struck.
  **Better: ask the subsystem that OWNS the fact** — `virsh list`, `charly vm list` — rather than
  inferring it from the process table.
- **Immutability is not correctness.** A stable identifier fails silently *by construction*: the
  property that makes it trustworthy — it never changes — also means it never *shows* that it is
  wrong. A branch name at least goes stale visibly. "Cite something immutable" is incomplete
  without *immutable pointer to what*; for a run against an uncommitted tree, cite the resulting
  commit **plus the evidence the code did not change between run and commit**, which a reader can
  falsify.
- **When the searcher and the searched share a namespace, every filter you add is also a thing to
  be found.** More predicates do not escape it — each is new evidence in the haystack. The escape
  is a *different* namespace: `virsh list` over the process table, a PR's own statuses over
  `pgrep`. Ask the subsystem that owns the fact.
- **A new default is a claim, and needs a positive control BEFORE it becomes the default.**
  `pgrep -xc bash -> 9` is what isolates *the pattern cannot match* from *nothing is running*;
  without it, `0` is consistent with both.
- **`-f` over-matches and gets caught because the number looks odd; `-x` under-matches and returns
  the number you were hoping for.** A silent miss invites a second look; a confident negative
  closes the question. Prefer the failure mode you will notice.
- **A build failure is not a discriminating perturbation** — it proves the test cannot run, not
  that it can tell right from wrong. Perturb the decision, not the scaffolding.
- **A token search establishes absence-of-*mention*; only tracing the callee establishes
  absence-of-*path*.** Widening the scope is necessary and not sufficient.
- **Expand every changed gitlink into its own log, read it at the pin (`git show <pin>:<path>`,
  never the working tree), and trace each hit to a real call path.** A path-based blast-radius
  check answers `NONE` confidently and wrongly.
- **A test fixture that restates a serialization is a test of an assumption.** Go through the
  writer's counterpart, so a schema change breaks both sides together.
- **A comment describing a capability is not a claim that any particular caller reaches it.**
  `resolveDelNode`'s tree-absent fallback exists; the reaper did not qualify for it.
- **Establishing who owns a behaviour does not establish that the owner can perform it.** Two
  members were retracted for being *"X did not do Y"* where Y was never X's job — and one of those
  retractions was itself wrong, because the owner could not perform it either.

## Gate

Run against the code committed here (`spec 898d5fa0`, `sdk c1c41b06`). Run dir
`.check/check-sidecar-pod/2026.228.0221/`.

The run executed an **uncommitted** working tree, so the citation is the commit **plus falsifiable
evidence the code did not change between run and commit** — not a bare identifier:

    binary built                        04:20:46
    run started                         04:21:24   (run dir 2026.228.0221)
    every committed .go file's mtime   < 04:20:46  — checked file by file, none newer
    post-run edits to committed files   this CHANGELOG only

Every `.go` file here is byte-identical to what the tested binary was built from.

**This paragraph previously cited a tree SHA** captured with `git rev-parse HEAD^{tree}` at run
time — which returned MAIN's tree, because the change was uncommitted. See the instrument table
above: *immutability is not correctness*, and the justification "a tree SHA, not a branch name" was
the wrong reasoning, not merely the wrong value.

    charly check run check-sidecar-pod: PASS (steps=18)     summary.yml ok: true
    [cleanup-check-sidecar-pod-ephvm] PASS after 28.187s

    BASE 0   PEAK 1   FINAL 0          registration fired, this run cancelled
    running domains 0   armed timers 0   failed units 0

The domain count comes from `virsh list` / `charly vm list` — the subsystem that OWNS the fact —
never from the process table. Every instrument in the table below inferred; the only two that
never lied asked an owner.

**Two mechanisms, two independently observable effects, in one run.** Peak falling to 1 can only
be registration-time cancellation; final falling to 0 can only be teardown's. Before this change
the same run measured `PEAK 6 / FINAL 5` from a base of 3.

**The identity gate was proven live, and the proof arrived by accident.** Five stale timers
preserved as *evidence of the defect* reached their TTL during the session and ran against the
fixed binary:

    charly: error: command "fleet": ephemeral reaper "charly-fleet-del-…-1786835537" refusing to
    reap "vm:check-sidecar-pod.check-sidecar-pod-ephvm": no ephemeral registration recorded for
    this deployment — refusing to reap on an unverifiable identity

The whole design on the real path: the `vm:` address resolving with no project, the flag carrying
the incarnation, a real overlay read, a fail-closed refusal, and a **visible** failure naming its
reason. Pre-fix those same units exited `203/EXEC` saying nothing. The deliberate version of this
proof was judged unreachable — the gate only fires 30 minutes after registration, outside any bed
window — and the accidental one is stronger than a constructed fixture.

Per-package `GOWORK=off` build + vet + test green for `candy/plugin-clean`, `candy/plugin-fleet`
and `candy/plugin-check`; `gofmt` clean; `charly box validate` exit 0 at zero warnings, checked as

**Coverage fails without the change**, proven by perturbation at every seam: pre-fix tag ranking

afterwards"*; prefixing every registration fails the population-scoping assertion.

## Not covered

The bed's ephemeral VM is reaped by the bed's own teardown; the **abnormal-exit** path — a killed
bed — still depends on the TTL net, whose state now survives because the unit carries
`CHARLY_DEPLOY_CONFIG`. That path is not exercised by any bed and is not claimed as proven.

Whether a supervised bed should register a TTL net at all remains open and is not decided here.

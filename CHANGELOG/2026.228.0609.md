# 2026.228.0609 — five validation rules that a review round had to teach us, at their source

Five items, two candies. Each is a rule the `pr-validator` now performs; each exists because its
absence cost real rounds in the retention/keep_images program. The fifth arrived as a finding a
fresh validator routed to this PR as the owning source, and closing it needed the `charly` binary
changed, not just the page.

## 1. `plugins#178`'s prose lands at its SOURCE

`internals/skills/git-workflow/references/evidence-and-freshness.md` and
`multi-repo-coordination.md` are **projections** — both carry a `DO NOT EDIT` banner and are emitted
from this candy. `plugins#178` authored `+317/-33` and `+48/-2` directly into those artifacts, so
the next `charly marketplace generate` would have reverted every line while its diff looked clean.

The prose is re-homed into `candy/charly-internals/charly.yml` unchanged. **The transplant proves
itself**: regenerating from this candy reproduces `#178`'s two emitted files **byte-identically**,
verified with `diff -q` in both directions before anything was committed. That is the only check
that can confirm a re-homing is faithful — reading the prose confirms it is *good*, never that it
is *the same*.

`plugins#178` is closed in favour of this, with a comment saying why rather than silently.

## 2. Find the generated files FIRST

`git grep -lEi "DO[- ]NOT[- ]EDIT" -- <changed files>` is now the **first action of Phase 1**,
before any content is read. A hand-edit to a generated artifact is a defect in KIND regardless of
whether the prose is right, and one PR in this program hand-edited generated pages for **four
consecutive rounds**, each round improving text that regeneration would erase.

Three measured reasons the naive form misses it:

- **The banner is usually near the top, and a fixed window still fails.** Measured over `plugins` @
  `32f48d2`: **339 of 351 hits at line ≤ 15 (96.6%)**, three above line 100, **two of which are this
  spec quoting the banner in prose** — so exactly ONE genuinely deep carrier, at line 1214. Grep the
  whole file because the tail is real, not because the distribution is flat. Describing it as "24
  distinct positions" would be a UNION over the tree reported as a spread — the population/union
  error, committed in the sentence warning about it.
- **The two trees use OPPOSITE separators.** Measured at `plugins` @ `32f48d2` and `docs` @ `3d11170`:
  `plugins` 339 spaced / 4 hyphenated / 340 tolerant; `docs` 2 / 899 / 899. A hyphen-only matcher
  finds 4 of 340 in `plugins`; a space-only matcher finds 2 of 899 in `docs`. Hence `-i` and
  `[- ]`. The columns do not sum because `grep -l` unions files rather than partitioning them —
  3 carry both spellings, so `339 + 4 - 3 = 340`.
- **A targeted edit never renders the top of the file.** An `Edit` on a matched string, or a jump to
  a grep hit at line 240, never displays line 8 — the banner is invisible to the access pattern a
  targeted edit actually uses, which is why this must be a deliberate step rather than something a
  careful reader would notice.

**Triage the hits; do not tune the pattern — and this cutover's own PR is why.** Run against its
own change set, the grep flags BOTH files: the candy that defines the check and the CHANGELOG
describing it. Neither is generated; the grep cannot distinguish CARRYING a banner from MENTIONING
one, and it should not try.

Both obvious tightenings were measured and both are worse. A 20-line header window still flags a
CHANGELOG that quotes the banner in its opening paragraph. Requiring a comment-form line carrying
both *generated* and the phrase removes the false positives but **misses 2 of 336 real banners in
`plugins` and 6 of 897 in `docs`.**

**The two error directions are not symmetric.** A false positive costs one glance. A false negative
cost this program four consecutive rounds. A detector for an expensive, silent failure should be
tuned toward noise, and the instinct to make it precise is exactly wrong here — which is only
visible once you measure what precision costs.

## How to tell a carrier from a mentioner — delete it and regenerate

The rule as first written documented its own false positive and said only *triage the hits*, which
named the problem without closing it. The first attempt at a criterion — *regenerate and see what
moves* — was **unsound in two ways**, and the second is worse than the first.

**It depends on a second input nobody named.** Regeneration has two: the artifact and the SOURCE.
*"Read the ref, not the checkout"* governs the artifact axis only, so a validator can read the
correct artifact ref and still reach a false verdict by standing at the wrong source commit. The
same file, in sync, regenerated against a source one commit older, produced a full-file delete
(`0/-132`) — indistinguishable from a hand-edit. **A verdict that flips on which source commit you
stood at is not a property of the PR.**

**And it fails when everything is RIGHT, which is worse.** *"A carrier appears in `git status`; a
mentioner never does"* is false for an **in-sync** carrier — the normal state of a correct PR at
validation time. It does not move, so the rule concludes *not generated* about exactly the file it
exists to protect. My first failure needs a wrong source tree to fire; this one fires with the right
tree and a clean checkout.

**The sound test is DELETE-AND-REGENERATE**, because the real question is whether the generator
PRODUCES that path, not whether its bytes currently differ:

```
rm <file>; charly marketplace generate; test -f <file>
```

Measured both ways: an **in-sync** generated agent spec reappears byte-identically; an authored
CHANGELOG that merely quotes a banner stays deleted. Movement can still CONVICT — it moved, so a
source produces it — but **its absence proves nothing**, and the rule now says so with the three
states tabulated.

**The hand-edit signature is stated to its evidence.** An earlier draft claimed regeneration
*"reverts precisely"* and that *"the additions do not survive"*; the worked example is `0/-15`,
`0/-15`, `5/-20`, and **five additions survived in the third file**. The numbers were right and the
prose overshot them, in the same paragraph teaching people not to do that.

Two more corrections of the same kind. **Banner positions**: one tree carries the banner at **24
distinct line numbers, the furthest at 1214** — so the guidance is *grep the whole file*, and the
earlier enumeration of "1, 7, 8, 9, 10, 12" undersold its own case badly enough to invite a fixed
window. **The census** now cites the REF it was counted at rather than a date, and explains why its
columns do not sum: `grep -l` unions files rather than partitioning them, and 3 files carry both
spellings, so `339 + 4 - 3 = 340`. A careful reader had spent their time suspecting arithmetic
errors instead of reading the point.

## The procedure had to be runnable, not just sound

A sound criterion stated as an unrunnable procedure is not a rule. Four defects, all in the steps
rather than the reasoning:

**It was destructive and said nothing about it.** `rm <suspect-file>` as STEP ONE, executed
*before you read a single line of content*, in whatever checkout the reader is standing in — while
this same document says elsewhere that `rm` on a tracked file is destructive and that a scratch
worktree is the correct way to run any mutation test. **Both safeguards existed and neither was
where the step that needed them was.** The procedure now stands a scratch worktree, restores it,
and says why.

**It dropped one of the two generators.** An earlier revision offered `marketplace generate` *or*
`docs generate`; the rewrite kept only the first. `marketplace generate` does not emit the `docs`
tree, so every carrier there would answer *"not generated"* — **899 files, the larger of the two
corpora, eleven lines from the census that establishes exactly that.** Both generators now run
unconditionally.

**`test -f` cannot tell a mentioner from a crashed generator.** Both leave the file absent. The
generator's exit code is now classified before the file is read — the same absence-without-scope
trap this page warns about for `merge-base --is-ancestor`, reappearing in the step written to
replace a different unsound test.

**"The PR's own source head" had no resolution procedure.** Naming the axis fixed the previous
round's finding and left the reader unable to act on it: for a `plugins` or `docs` PR the emitting
source is a branch in the superproject, derivable from the artifact PR only if it happens to say so.
An ordered resolution is now given, with the requirement to STATE which was used — an input the
reader cannot resolve is as fatal as an input nobody named.

## And STEP ONE's own command could not reproduce this page's example

`git grep` does not cross a gitlink. Run from the superproject over `plugins/<path>`, STEP ONE
returns **zero hits** — not because the tree is clean, but because it never looked — and a zero-hit
result is indistinguishable from a clean tree, which is the precise silent-false-negative direction
the step exists to prevent. The command is now per-submodule (`git -C <sub> grep`) with paths
relative to that repository. **The `git -C` form was already stated elsewhere on this page, 288
lines away, and never applied here.**

That is the same shape as the two above: the knowledge was present in the document and absent from
the step. **A rule is only as good as the invocation printed next to it**, because that is what
gets run.

## Two rules the review rounds produced, generalised

**A claim-keyed sweep produces a candidate list, and the candidates still have to be read.** The
sharpest case is sweeping a claim you have just corrected: the correction quotes the old wording in
order to retract it, so **the sweep's hits include the fix**. Measured here — four hits for a
superseded rule across two CHANGELOGs, **three retractions and one live assertion**. A mechanical
pass would have deleted the three retractions, leaving a page that no longer states the wrong thing
and no longer records that it was wrong: clean-looking, and stripped of the history that stops the
claim returning. No pattern can separate *asserting X* from *saying X was wrong*, because they are
the same string.

Sweep across every **repo** the claim reached rather than the files a finding named. The live
assertion in that set was in a repository no finding mentioned, twenty lines above its own
correction, and surfaced only because the sweep covered the whole cutover.

**Put the safeguard where the reader acts, not where it is true.** This spec knew `rm` is
destructive, knew a scratch worktree is the right mutation harness, and knew an exit code must be
classified before absence is believed — and stated all three roughly 700 lines from the step that
did the deleting. The same page's `git -C <submodule> grep` form sat 288 lines from a command that
could not reproduce its own worked example without it.

**A reader executes the invocation printed next to the instruction**, so anything true elsewhere in
the document is operationally absent. The test for a rule is not *does the page contain the answer*
but *is the answer at the point of action* — which also predicts where the next defect will be.

## The fix rounds produced most of the remaining defects

Across three rounds the original prose came out clean and **four of the last five findings were
created by the round that fixed the previous ones.** One regression (a generator dropped during a
rewrite) and three defects born inside newly written material. The lesson is not to slow down; it is
that **the paragraphs least likely to have had the page's own checks run against them are the ones
just written to satisfy a finding.**

Three of this round's four are the same defect on a new axis:

- **`;` between the two generators discards the first one's status.** `false; true; rc=$?` is `0`;
  `false && true; rc=$?` is `1`. A crashed `marketplace generate` followed by a successful
  `docs generate` passed the guard, so `test -f` reported *"not generated"* for a real carrier —
  **the exact silent false negative the guard had just been added to prevent.** The correct `&&`
  form was ten lines away in the PR body.
- **The setup landed the PIN, not the PR head.** `git submodule update` checks out the source's
  pinned gitlink, typically several revisions behind the artifact PR — so the block would have
  deleted and tested the pin, and *"reappears byte-identically"* would have been measured against
  the wrong artifact. **Source-vs-artifact was solved on the source axis and reintroduced by the
  setup steps on the artifact axis.**
- **W0's exemption was narrower than the procedure it had to permit.** It allowed a *read-only*
  worktree *at the PR head*; the carrier test writes, runs two generators, and stands on the source
  head. Fixing the `rm`-safety gap created a rule conflict, so the exemption is widened rather than
  the procedure weakened. **A rule narrower than its own mandated step makes that step either
  unusable or a violation, and a reader facing that picks one silently.**

## The banner distribution, corrected against its own data

*"The banner is not reliably near the top at all"* is **refuted by the numbers offered to support
it**: 339 of 351 hits sit at line ≤ 15. The banner IS reliably near the top; what defeats a fixed
window is a **one-file tail** — and that is the stronger argument for grepping the whole file,
because it does not depend on the distribution being flat.

*"24 distinct line numbers"* was a **union over the tree presented as a spread**, which is the
population/union error stated two paragraphs below it. Two of the three deep hits are this spec
quoting the banner in prose, so the union was inflated by the document describing the problem. **A
count over a corpus is not a distribution, and it was the union that made the wrong conclusion look
supported.**

## The fifth finding is this entry's own lesson, unapplied

The sweep rules — the candidate-list principle and the retraction case — landed in
`references/evidence-and-freshness.md`, and **the acting step never cites that file.** A validator
sweeping works from checklist item 9 in the agent spec, which carries the gitlink form and the
`CHANGELOG/`-context clause and neither of the two rules. Positive control: the same spec DOES cite
`references/multi-repo-coordination.md`, so the mechanism exists and only this pointer was missing.

**This is the same shape as the `rm` safeguard 700 lines away, across a document boundary with no
pointer — which is strictly worse, because distance can be closed by scrolling and an uncited file
cannot be reached at all.** And it shipped in the commit that added *"put the safeguard where the
reader ACTS, not where it is true"*: **the generalisation was codified and not applied to the fix
beside it.** Fixed with a citation rather than by moving text, since the acting step should not grow.

Item 9's existing `CHANGELOG/`-context clause covers one slice — a hit in a prior release entry is
expected — but not the general case, where a **retraction in live prose** quotes the claim it
corrects and is indistinguishable by pattern from the assertion.

## Three ways to get one grep wrong, stated as a set

| getting it wrong | finds |
|---|---|
| wrong separator (hyphen-only) | 4 of 340 in `plugins` |
| wrong repo scope (superproject-relative across a gitlink) | **0** of 340 |
| wrong pathspec (`-- '*.md'`) | **0** of 4 in `sdk`, **0** of 8 in `spec` |

Each alone returns a plausible number and two return a clean tree, so the lesson is the **set**, not
three separate corrections: **a zero here means "I found nothing" and never "there is nothing"**
until all three are right.

## The ratio rule was filed against the wrong statistic

*"The ratio is the claim and the totals only date it"* is **true — of the top-clustering
statistic**: 338/350 and 339/351 at two refs one commit apart, 96.57% and 96.58%, stable to two
decimals while both totals moved. It is **false of the separator ratio it was attached to**, which
swung 24% (111.7:1 → 84.8:1) across that same single ref change.

So the separator claim is now stated as an ORDINAL one — spaced dominates `plugins`, hyphenated
dominates `docs` — and the ratio sentence moved to the measurement it holds for. **Deleting it would
have lost a correct idea because it was filed in the wrong place**, which is worse than the original
error.

The refinement exists because a one-hit discrepancy was not shrugged off: 350/338 against 351/339,
one ref apart, both correct — **and the extra hit is this cutover's own CHANGELOG**, the banner
*mention* its worked example uses to demonstrate a mentioner. **A discrepancy small enough to ignore
was exactly the size that carried the distinction.**

## 3. Read the ref, not the checkout

Five distinct instances in one session across three people. A working tree is not a commit: resolve
what you mean to inspect (`git -C <sub> show <sha>:<path>`, `git ls-tree <head> <sub>`) rather than
reading files on disk that may carry unmerged or uncommitted content.

The sharpest instance was a **byte-identity check that passed cleanly against a checkout holding
content that did not exist on `main`** — so the strongest available freshness check produced a
clean, meaningless result. **Byte-identity is unattributable unless you state which tree you
compared against.**

Its exit-code costume is now guarded explicitly: `merge-base --is-ancestor` returns **128** when the
objects are absent — which is what happens when a submodule ancestry check is run from the
superproject — and `128` is falsy under a bare `if`, so "objects not here" is indistinguishable from
"not an ancestor". **Capture `rc` and classify it: `0` ancestor, `1` not, anything else not a
verdict.**

## 4. The CHANGELOG placeholder can SURVIVE, not just collide

The four strict CalVer rules require a placeholder to be CalVer-shaped, self-consistent, and
non-colliding. **They therefore guarantee that a placeholder whose Phase-3 rename is SKIPPED merges
looking exactly like a properly stamped entry** — well-formed by construction, because the rules
demand it. `plugins` has no CI to catch it (`.github/workflows` empty; the same probe finds one in
`charly`, which is what makes that absence evidence rather than a failed lookup).

The obvious remedy — a self-announcing `CHANGELOG/UNSTAMPED-<slug>.md` — **fails the filename regex
by construction** and would be rejected before anything else was read, and the org PR template
independently instructs authors to use a CalVer placeholder. The shape cannot change per-leg: the
rules, the template and the Phase-3 step would all have to move in one cutover.

So the fix closes the hazard without moving any of them: **after tagging, Phase 3 verifies that every
`CHANGELOG/*.md` this merge added has a basename equal to the version just MINTED.** The existing
self-verify only runs if the rewrite is already happening, so it cannot fire when the rewrite never
happened; only a post-merge comparison against the minted version distinguishes a guessed date from
a minted one.

## 5. A published figure had to name its tree — and the tool had to stop naming the wrong one

The `pr-validator` that passed the projection leg routed a blocking finding back here. This page
published

```
marketplace drift: clean (400 artifact(s) match the committed tree)   exit 0
```

introduced by *"Both runs perturb a clean tree and are reverted immediately after"* — while ruling,
a few hundred lines above, that **a figure is publishable only with the tree identified: which
commit, which submodule shas, which working-tree state.** The block supplied one of the three, in
the example that ships with the rule. The validator re-derived the count independently: **400 was
correct and reproducible**, so the defect was provenance, never accuracy.

The sharper half is what made it a code change. The validator watched that exact line print `exit
0` beside a `git status --short` listing ` M candy/charly-internals/charly.yml` and ` M plugins` —
**`drift` reporting clean on a tree git called dirty**. So "a clean tree" was ambiguous between
git-clean and drift-clean: precisely the ambiguity the rule exists to kill, occurring inside the
rule's own worked example.

**The ambiguity was in the tool, not only in the label.** `drift()` builds its emissions map from
the sources ON DISK (`readKinds` walks `charly.yml` files) and compares them with the artifacts ON
DISK (`readOnDisk` is an `os.ReadFile`); the package contains no `os/exec` and never invokes git at
all. "Match the committed tree" is therefore a claim the command has no mechanism to establish —
true only by accident, on a tree that happens to be committed, and false in exactly the case that
matters. R4a decides the direction: the code held the intent (a working-tree gate is the useful
one — comparing against `HEAD` would go red on every correct-but-uncommitted regeneration), so the
prose moved. The success message, the Kong `--help` string, the file comment and the candy
`description:` now say what was compared, and name `task skills:drift` as the recipe that adds the
`git status --porcelain` half:

```
marketplace drift: clean (400 artifact(s) on disk match their sources; regeneration is a no-op)
```

Two adjacent claims in the same comments went with it, both measured false: `drift` is not "the CI
gate" — it runs in **no** workflow (`release-binary.yml` is the only one and never mentions it), so
it is red only for whoever runs it — and it is not "the docs:drift model", since that one is a
Taskfile recipe that *does* consult git.

The block itself is now a four-run TRANSCRIPT taken in one session at a named tree (superproject
commit, both submodule shas, `git status --porcelain` empty including untracked files, and the
elision stated), and it **publishes the disagreement instead of hiding it**: runs 3 and 4 print the
identical `clean` line from opposite git states. It also records the discriminator that tells you
whose half is outstanding — ` m plugins` is modified content inside the submodule, ` M plugins` is a
moved gitlink — measured both ways at that tree.

Coverage: `TestDriftCleanMessageNamesWhatItCompared` captures the printed line and asserts it names
both compared sides and claims nothing about commit state. It discriminates twice over — the
fixture is a `t.TempDir()` that is never `git init`'d, so a check that read git could not report
clean there at all, and restoring the old wording turns the test red (verified: FAIL on `match the
committed tree`, PASS on the new line).

Two rules survive the incident:

- **An adjective is not a tree.** "On a clean tree", "on main", "after a fresh run" all read as
  provenance and identify nothing; only a commit plus its submodule shas plus the working-tree
  state lets a reader falsify a figure.
- **When the ambiguous word is printed by the tool, prose cannot disambiguate it.** Careful text
  around a message that says *committed* while measuring *on disk* only teaches the reader that the
  discrepancy was intended. The message is the thing to fix — documenting around it is the R4a
  failure by name.

## Why these five are one cutover

They converge on one file and one reader. Every one is a rule the validator performs, four of the
five were learned in the same program, and each is the *procedural* form of a defect the others
would otherwise catch only after it landed — a generated-file edit, a claim about the wrong tree, a
date nobody minted. Splitting them would mean five rounds of the same reviewer reading the same
agent spec.

The fifth is the least separable of all: it is item 3's rule (*read the ref, not the checkout*)
failing on this page's own figure, repaired by item 1's rule (*fix it at the SOURCE*), and its
repair re-projects the very artifact items 1 and 2 are about. The `charly` change it required rides
in the same commit because the transcript quotes that binary's output — landing the prose without
it would publish a corrected label above an uncorrected message.

# 2026.229.0003 — the lint gate could not see formatting

`golangci-lint run ./...` reported `0 issues.` over a file `gofmt -l` rejected.

golangci-lint **v2 moved formatters out of `linters:` into their own top-level `formatters:` block**.
This config declares `default: standard` plus eleven quality linters and no `formatters:` block, so
formatting was never checked — by the linter, or by any CI step or taskfile, which run no separate
`gofmt`. A mis-formatted file could land with a green gate.

## Proof that the gate now discriminates

The clean tree still passes, and the same perturbation that previously produced `0 issues.` now fails:

```
CONTROL   tree as-is                          -> 0 issues.
MUTATION  a doubled space in a func declaration -> gofmt -l flags the file            
                                                 golangci-lint: 1 issues: * gofmt: 1
```

Before this change the mutation produced `0 issues.` — that is the whole defect.

## Zero churn

Measured before adding the block: `gofmt -l` returns **0 files** across `charly`, `sdk`, `spec` and
all 91 `candy/*` modules. So this only makes the gate able to fail; it repairs nothing and reformats
nothing.

## The claim that 91 modules "inherit this" was FALSE, and is now actually true

An earlier revision of this entry said: *"The 91 `candy/*` modules have no `.golangci.yml` of their own
and are linted through the workspace, so they inherit this once it lands."* **Both halves were wrong,
and neither was ever tested.** A validator measured it:

- `candy/plugin-check/.golangci.yml` **exists** — so "no `.golangci.yml` of their own" was false, and
  that module was the one the batch most needed to touch.
- golangci-lint discovers a config by walking **up** from the working directory, and
  `charly/.golangci.yml` is not an ancestor of `candy/<name>/`. From inside a candy module:
  `No config file detected`. There was no root config. They inherited **nothing**.
- A workspace run from the repo root reports `0 issues.` and **exit 7** — `directory prefix . does not
  contain modules listed in go.work`. It checks nothing at all.

So the batch gated **3 of 94 modules while claiming 94** — and the shortfall was concealed by a
sentence asserting coverage rather than declared as a gap. That is worse than the gap.

## The fix: one root config, not 91 copies

`.golangci.yml` at the superproject root. It governs **95** modules — the 91 `candy/*` plus the 4
`tools/*` nobody had enumerated. Verified: from `candy/plugin-fleet`, `golangci-lint config
path` resolves `../../.golangci.yml`, and a doubled-space defect there is caught (`gofmt: 1`) where
the same defect with no root config produces `0 issues.` `candy/plugin-check` keeps its own config —
the closest one wins — so its `formatters:` block is added there directly. A per-module copy would put
the identical block in 90+ places (R3).

## `default: none` was a SECOND inference from absence, and it silenced live findings

An earlier revision set `default: none`, reasoning that 91 modules with no config had "never been
linted" and that enabling linters would be an unmeasured blast radius. **That was false and untested.**
golangci-lint with NO config runs its default standard set — errcheck, govet, ineffassign, staticcheck,
unused. The candy modules were never un-linted. `default: none` therefore *removed* five linters:

```
candy/plugin-appium, same file, nothing else changed
  root config with `default: none`   ->  0 issues.
  no root config  (== main today)    ->  * errcheck: 3   (resp.Body.Close unchecked)
```

**This is the same error as the coverage claim above, in a new place.** That one inferred
"no config ⇒ inheritance"; this one inferred "no config ⇒ no linting". Both reasoned from absence and
neither measured. A validator caught both.

The config now says `default: standard` — what these modules already ran — so it **removes nothing**
and adds `gofmt`.

## The errcheck exclusions, stated plainly because they are a reduction

`default: standard` surfaced **5 findings across 3 modules** (`plugin-appium` ×3, `plugin-agentteams`,
`plugin-vnc`), every one the same idiom: an unchecked best-effort `Close` on a response body or read
handle. The root config now carries the **same `errcheck.exclude-functions` list that
`charly/.golangci.yml`, `sdk/.golangci.yml` and `spec/.golangci.yml` already carry** — verified
present in all three — which clears all five.

**This is a reduction against main's effective behaviour for candy modules, and it should be read as
one.** Two limits on it, both from a validator and neither obvious: `(io.Closer).Close` matches
INTERFACE receivers only, so a concrete `(*os.File).Close` still reports — "clears all five" is true
for candy and does not generalize (`tools/ledger-validate` is still red at `errcheck: 1`, though that
is an improvement on main's 4). And `plugin-vnc:687` is the one of the five with an error channel
actually available, where this codebase's own idiom is an explicit `_ =` discard rather than an
exclusion. The argument for it is consistency, not convenience: without it the root config would hold the
91 candy modules to a STRICTER errcheck than core, which is not a gate improvement but an
inconsistency that happens to fail. `(io.Closer).Close` is excluded project-wide by deliberate policy
with a written rationale in each config. If a reviewer prefers the five fixed in code instead, say so
— it is five lines and I will do it rather than argue.

```
regression sample, 12 modules  ->  0 red

```

**A measurement note, because it produced a false number first.** Sweeping all 91 modules in one pass
filled the sandbox's `/tmp` quota, and 10 modules then reported `no go files to analyze` — which reads
exactly like a real finding. `plugin-vm` has 71 Go files. Re-run individually against a root-fs cache,
they are green. Disk exhaustion is indistinguishable from a defect in that output.

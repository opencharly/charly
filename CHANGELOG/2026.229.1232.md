# 2026.229.1232 — ollama goes packaged with split GPU backends, and eight things that had to be true first

The headline is four strands: the `charly ollama` management CLI, an ollama candy that installs
from the distro package where one exists, the CUDA/ROCm backends split into their own opt-in
candies, and the rpm repo template gaining the ability to REPAIR a vendor that ships package
verification disabled.

The rest of this entry is what proving those four required. Each one was found by the previous
one — the packaged install needed a CachyOS build that ran its own scriptlets; that build's log
needed to be readable before its warnings could be counted; counting them needed a gate that
graded logs rather than exit codes; and that gate needed a module surface whose spec pins agreed
before anything would compile at all. None of it is incidental scope: every item below is
something the four strands could not be honestly verified without.

## The plugin-ollama management plugin (`candy/plugin-ollama/`)

A compiled-in `command:ollama` plugin (dual-placement, placement-agnostic) that owns
the entire `charly ollama` CLI — `list` / `ps` / `pull` / `rm` / `show` / `cp` /
`create` / `push` / `run` / `stop` / `version` — against a deployed Ollama server's
HTTP API, built on the official upstream Go client (`github.com/ollama/ollama/api`,
pinned `v0.32.14` in the candy's own go.mod). Self-contained (plain HTTP, no reverse
channel), so it works identically compiled-in or out-of-process. Endpoint resolution
is deliberately lightweight: `--server` flag > `OLLAMA_HOST` env >
`http://127.0.0.1:11434` — the flag is named `--server`, NOT `--host`, because the
charly-level Kong grammar already owns `--host` (SSH remote execution) for every
command. Full Modelfile authoring stays with the upstream CLI inside the deployment
(the candy's host alias); `create` covers the lightweight `--from` form.

Coverage: 19 test functions against an httptest fake Ollama server — every subcommand's
request body and output, endpoint precedence, error propagation, and the chat REPL.
`push` was the one subcommand of eleven shipping untested; it now asserts both its
output and its request body, so all eleven are covered.

## The ollama candy: packaged where possible, tarball where not

The candy installed the upstream release tarball unconditionally. Arch (and CachyOS)
package ollama in `extra`, tracking upstream closely — `0.32.14-1` landed the day
upstream tagged `v0.32.14` — so the candy now declares `distro.arch.package: [ollama]`
and the tarball step is skipped there.

**The skip is capability-gated, not distro-gated.** `distro:` package sections compile
into the plan at phase 1 and `plan:` steps at phase 3 (`BuildDeployPlan`), so on a
packaging distro `/usr/bin/ollama` already exists when the step runs, and the step
returns early on exactly that. A distro that gains an ollama package is picked up with
no edit. A distro-name filter was the obvious alternative and is not available: the
`exclude_distro:` modifier is read by the check runner (`sdk/kit/planrun.go`), never by
the build emitter, so it cannot gate a `run:` step at build time.

`OLLAMA_VERSION` keeps selecting the upstream release, and is now documented as
applying to the tarball path only — on Arch, pacman owns the version.

The three host-side `charly ollama` steps that prove the plugin end to end
(help dispatch, live `version` round-trip, `list`) moved OUT of the fedora bed and ONTO
this candy, where every composing box inherits them (R3). `${CHARLY_BIN}` is stamped
for any runtime check run, not only for bed members (`kit.StampCharlyBin`), so the
steps work wherever the candy is deployed. Both ollama beds are now plan-free.

## GPU backends as opt-in candies (`candy/ollama-cuda/`, `candy/ollama-rocm/`)

The upstream tarball is a 1.32 GiB download because it bundles every backend; Arch splits them,
and `ollama-cuda` / `ollama-rocm` DEPEND on `ollama` rather than conflicting with it,
dropping their backend into ollama's own `/usr/lib/ollama/` runner directory. That maps
exactly onto "GPU support is a box-level composition choice", so the backends are now
candies a box opts into:

| candy | backend | installed |
|---|---|---|
| `ollama` | CPU only | 66 MiB |
| `ollama-cuda` | `libggml-cuda.so` | +988 MiB |
| `ollama-rocm` | `libggml-hip.so` | +2.9 GiB |

A CPU consumer (`openclaw-desktop`) now installs 66 MiB (16 MiB download) where it
previously downloaded the whole 1.32 GiB archive.
Each backend candy asserts its library with a version-agnostic glob under
`/usr/lib/ollama/*/`, so a CUDA or ROCm version bump does not rot the check.
`ollama-rocm` is Arch-only by construction and says so: the base upstream tarball ships
no ROCm backend (upstream publishes it as a separate archive), so the candy would
install nothing on a tarball distro and its check would correctly fail rather than
pretend.

Three rounds of validation on this page shared one failure mode, worth naming because it is the
lesson rather than any single sentence: **each fix stopped at the SENTENCE boundary instead of the
CLAIM boundary.** The retraction deleted the sentence that cited a verification and left the same
claim standing one clause upstream. The size-accounting rewrite fixed the bullet and left the
preamble it had just falsified — "the one figure above is a COMPRESSED DOWNLOAD", when there are
three figures above and two are installed sizes. The remedy is to sweep the whole PARAGRAPH
against the new text, which is what the final round did: every figure on the page is now checked
against the axis the paragraph claims, and the axis no longer splits by position ("above"/"below")
but by which figure it is.

A cold reader of the projected page caught the corollary this narrative had left implicit:
BOTH backend candies package only on Arch, and off Arch they DIVERGE — `ollama-cuda`
degrades into an ASSERTION that the tarball's bundled CUDA is present, while `ollama-rocm`
has no tarball path at all. The page now states that, and stops calling its two size
bullets a "table" it does not contain.

The first attempt at that fix replaced a vague attribution with a WRONG one. It said
"`box/cachyos` for both, `box/fedora` for the CUDA assertion only", and a validator
falsified both halves: at the gitlinks this branch pins — which are those repositories'
`main` — NEITHER submodule composes EITHER backend candy; the strings do not occur in
either repository. The composition exists only on the unmerged `feat/ollama-plugin`
branches of `distro-fedora#18` and `distro-cachyos#15`, and the claim was checked against a
`box/fedora` working tree left on that branch rather than at the pin — the same
submodule-ref confusion that cost two bed runs earlier in this cutover.

So the enumeration is gone rather than corrected. Naming boxes on this page was the defect:
the list lives in the distro submodules, moves there, and any copy here is stale the moment
one of those PRs lands. What the page states now is the property that does not move — the
Arch-only rule — plus an instruction to read any submodule list through it.

## rpm repos can now force gpgcheck ON (`charly/charly.yml`)

The rpm `install_template` copies a vendor `.repo` file in verbatim and offered a
`gpgcheck:` knob that could only ever turn verification OFF — the guard tested for the
literal `false`, so `gpgcheck: true` was a silent no-op. Both `gpgcheck:` and the new
`repo_gpgcheck:` are now TRI-STATE: absent inherits the vendor's value (unchanged
behaviour, and `candy/nvidia` is the only candy in the tree that sets either), `false`
forces the check off, `true` forces it ON.

That closes a real hole. NVIDIA ships `nvidia-container-toolkit.repo` with
`gpgcheck=0` — the only repo in the tree that does — so its four packages, a container
runtime hook, were installing **unverified** in every Fedora GPU image, even though the
imported key was good and every package is validly signed by the primary key. No value
expressible in the candy could fix it until the knob became tri-state.

Two more defects in the same RUN, found by the same RCA and fixed here:

- **`candy/nvidia` no longer imports the key explicitly.** The repo file already
  declares it, so dnf5 imports it under `gpgcheck=1`. An explicit `rpm --import` of
  NVIDIA's published certificate emitted `Subkey 6ED91CA3AC1160CD is expired` on every
  single build, because that certificate carries a subkey that died 2021-06-16 and
  every NVIDIA copy still ships it. Nothing is trusted less — the packages are signed
  by the primary key and verify either way.
- **`candy/cuda` pinned a key URL NVIDIA had deleted.** `D42D0685.pub` 404s; the live
  `cuda-fedora43.repo` names `1940C73E.pub` ("Kitmaker (Fedora 43)"). Every GPU image
  build was emitting `import read failed(2)`, survivable only by accident because the
  `cuda-*` packages happened to resolve from fedora-multimedia, so that repo's
  `gpgcheck=1` never had to verify anything.

A cache-cold `nvidia` build now emits **zero warnings and zero errors**, where it
previously emitted two warnings, two errors, and installed four packages unverified.

The enforcement is GATED, not merely asserted: `nvidia-container-toolkit-gpgcheck-enforced`
reads the repo definition in the built image and requires `gpgcheck=1`. That is the one
observable that discriminates — a "the signing key is in the rpmdb" probe would not, because
the previous code imported the key explicitly via `rpm --import` while still installing
unverified under NVIDIA's shipped `gpgcheck=0`, so the key was present either way. What
changed is the repo's enforcement setting, so that is what the check asserts.

## CachyOS install scriptlets actually run (`charly/charly.yml`)

CachyOS ships pacman as a `-4` rebuild of the version Arch ships as `-2`, carrying a scriptlet
network-isolation patch Arch's does not have. In a rootless build container
`unshare(CLONE_NEWNET)` returns EPERM and that pacman ABORTS the scriptlet rather than running it
unisolated — so **46–51 scriptlets and hooks never ran in any CachyOS image charly has ever
built**: `ldconfig`, `systemd-hook` (34–37 invocations), `update-ca-trust`, `locale-gen`,
`fc-cache`, and `nvidia-ctk-cdi` on the GPU boxes. pacman treats a refused hook as non-fatal, so
every one of those builds reported success.

The fix is `DisableSandboxNetwork` in the image's own `/etc/pacman.conf`, set in the **cachyos
distro bootstrap** rather than as a box-level step, because a box-level `run:` reaches only the
baked LABEL and never the emitted RUN. The bootstrap block had to be restated in full: `bootstrap:`
REPLACES rather than deep-merges, and a partial override silently dropped `curl`,
`ca-certificates` and the pacman package cache mount.

Enabling the hooks immediately surfaced the next one — `nvidia-ctk-cdi` cannot enumerate devices
in a build container — which is masked in the same bootstrap rather than left for later.

Measured on a derived image: **refused 51 → 0, isolate-failures 59 → 0, hooks executed 11.** The
gate is `cachyos-pacman-sandbox-disabled` in the CachyOS submodule, which fails if the setting is
absent.

## Build logs stop being line-corrupted (`charly/host_build_cli.go`)

Build output was captured through a shared buffer that interleaved stdout and stderr mid-line.
Warnings were destroyed and, worse, INVENTED: fragments of two lines could combine into text that
matched a diagnostic pattern. stdout and stderr are now captured separately, so a line in the log
is a line the tool emitted. Everything downstream that counts diagnostics depends on this being
true first.

## Beds grade their logs, not just their exit codes (`candy/plugin-check`)

A bed reported `ok: true` over a step log carrying 56 error lines, because the runner graded exit
codes and nothing else. `bed_diagnostics.go` scans each step log, classifies diagnostic lines,
resolves them against a reviewed allowlist, and fails the step on any non-allowlisted error-tier
line under a zero exit code. Counts, the distinct shapes, and each allowlist entry's verbatim
justification are written into `summary.yml`, so an exemption is audited on every run rather than
reviewed once and forgotten.

The error-tier allowlist holds exactly ONE entry, and the invariant a test enforces is not
emptiness but CONDITIONALITY. It began empty on the premise that an `error:` line under a zero
exit code is a swallowed failure by construction. pacman falsifies that: its mirror fallback
prints one `error: failed retrieving file …` per unreachable mirror and then installs from the
next — observed live, three errors for libyuv followed by `installing libyuv...` in the same log.
So the entry is exempt ONLY when the same log proves that specific package recovered, and an
unrecovered retrieval error still fails the step. "That specific package" is load-bearing on two
axes, and the first attempt got both wrong in opposite directions: the capture was a lazy prefix
over a class containing `-`, so a `nvidia-container-toolkit` error captured `nvidia` and any
unrelated `installing nvidia...` discharged it (too LOOSE); and the recovery named only
`installing`, so a package that recovered into a `reinstalling` — 23 occurrences in this tree's
retained bed logs — failed a step for arriving (too TIGHT). The capture is now greedy, anchored by
the three trailing hyphen-separated fields of an Arch filename, and the recovery enumerates the
four alpm operations that end with the package installed, REMOVE being the one that does not. That keeps what emptiness protected — the gate
cannot be talked into tolerating an error — while letting it stop firing on a retry that worked. Cache hits and cache steps are counted in the same pass, because a
warm cache suppresses the very lines the gate looks for: "0 warnings" at 199/211 cache hits is not
the same claim as "0 warnings" at 82/195.

## One resolved-project resolution per status fan-out (`candy/plugin-substrate`)

The `check-pod` bed went red during this cutover's acceptance batch, and the failure was not in
the diff: its `charly status --json` probe was killed by the never-hang ceiling at exactly
2m0.003s. The same probe passes at 88s on an idle host, so the command sits close enough to the
ceiling that a concurrent six-bed roster pushes it over.

A CPU profile settled the cause, which is not what #208 guessed. It is not `ls-remote` per ref —
the run is compute-bound (35.9s user of 67s wall), and the profile is dominated by GC over YAML:
`resolveProjectEnvelope` accounts for 43% of samples because ONE `charly status` resolves the
whole project FOUR times. Two of those are in this package: the kubernetes and android status
collectors each call `fetchResolvedProject` independently, and both need the same envelope to
enumerate their deploy nodes.

The fan-out now resolves once and shares it. The memo is scoped to one fan-out via the context,
deliberately not to the process: a process-lifetime cache would be wrong for `charly mcp serve`
and the plugin servers, which keep a provider alive across requests and would then answer from a
project resolved before the user's last edit. A single-word `OpStatusCollect` off the wire
carries no memo and resolves directly.

Measured on this repo's own project, idle host: 4 resolutions -> 3, 19.7s -> 17.8s wall,
29.0s -> 25.2s user.

**This does not close #208.** The remaining two resolutions live in `candy/plugin-status`, and
sharing across that boundary needs a home in the sdk — the kernel/plugin boundary law forbids one
plugin importing another. Collapsing all four needs a memo on the host seam with real
invalidation semantics for long-lived processes, which is a design decision and its own cutover,
not a bolt-on here.

## A guard for this cutover's repeated failure — written, and WITHDRAWN before landing

`scripts/verify-claimed-changes.sh` was written to catch the class this entry's table documents,
and removed again before this PR landed. The reasoning is worth more than the script was.

It caught a real defect a diff review cannot see: a docs commit that reverted its own branch's work
to `main`, byte-identical, while its message described the fix. But it acquired three defects, two
found by reviewers:

1. **A parser bug that made its author's own verification vacuous.** Binding tested
   `[ "$base" = "origin/main" ]` as a proxy for "has base been bound yet"; a caller passing the
   literal default defeats it, so the second positional overwrote `base` and `head` stayed `HEAD`.
   The run cited as evidence had compared a branch against a detached checkout and printed CLEAN.
2. **Merge commits.** `git diff $c^ $c` on a merge is the FIRST-PARENT diff, so everything the
   other parent brought in reads as changed-then-undone. Fixed with `--no-merges`.
3. **Merge RESOLUTIONS, which sank it.** A conflict resolved in favour of the base leaves
   `head == base` — byte-indistinguishable from an edit-then-revert. This cutover's own catch-up
   merge with `main` produced **93 false positives**, every one a correct resolution taking main's
   newer `spec` pin.

The third is not a bug but the definition being wrong: "a path some commit edited that the net diff
no longer contains" genuinely describes both an accidental revert and a deliberate resolution, and
no flag separates them from the diff alone.

The script's own header stated the rule it then broke — *a check with false positives gets disabled
by whoever inherits it* — so shipping it would have been shipping the thing it warns against. It is
withdrawn, and `charly#338` records the full measurement so a second attempt starts from evidence.

What lands instead is the narrow half: `scripts/verify-changelog-h1.sh`, which fires only when a
CHANGELOG H1 names a CalVer DIFFERENT from its filename, and which an independent validator
mutation-tested against a live true positive on `plugins/main` — red on the real defect, green on
its fix. Its own first draft returned 35 hits where one was real; the narrowing is the whole value,
and it is the same lesson defect 3 teaches.

## A CHANGELOG H1 must name its own file, and now a script says so (`scripts/verify-changelog-h1.sh`)

`#332` records nine entries whose H1 carries the AUTHOR-time CalVer after a merge-time rename
(charly 1, sdk 6, spec 2). A tenth landed on `plugins/main` during this cutover, committed by the
validator that merged this cutover's own projection PR — which is what makes it worth a script
rather than a habit.

The mechanism is identical every time and is not carelessness. A merge-time stamp runs
`git mv CHANGELOG/<placeholder>.md CHANGELOG/$VER.md`, which STAGES a rename; edits the H1 in the
WORKING TREE; then commits without `-a`. The rename lands, the H1 edit does not, and
`git status --short` prints `RM` — a staged Rename plus an UNSTAGED Modification — where the `M`
is the half that gets missed. Self-verification with `head -1 <path>` then reads the working tree,
where the fix IS present, and confirms a commit that does not contain it. So the check must read
the OBJECT: `git show <ref>:<path>`, never `head -1 <path>`.

The check is deliberately NARROW: it fires only when an H1 names a CalVer DIFFERENT from its
filename. A first draft flagged anything not matching `# <CalVer> — <title>` and produced 35 hits
on `plugins/main` where ONE was real — 34 entries predate the convention. A check that cries wolf
34 times gets disabled by whoever inherits it, which is the same reasoning that put `--no-merges`
in `verify-claimed-changes.sh`.

Run across the four repos it reproduces `#332`'s hand-counted population exactly — charly 1,
spec 2, sdk 6 — which is the evidence that the narrowing did not also narrow away the defect.
charly's single instance (`CHANGELOG/2026.210.1559.md`, H1 naming `2026.210.1445`) is fixed here
so this repo passes its own guard; `sdk` and `spec` are separate repos and stay with `#332`.

## Eighteen green bed runs, and seven instances of one defect none of them caught

The most useful thing this cutover produced is not in the diff. Across three bed batches — six
disposable beds each, every run green, zero errors and zero warnings — SEVEN instances of a single
defect class sat in the tree, and not one was caught by a bed. Every one was caught by a reviewer
reading a committed object.

They are all the same shape: **a proxy standing in for the artifact.**

| the proxy consulted | instead of | what it hid |
|---|---|---|
| a working tree | `git show <sha>:<path>` | a CHANGELOG H1 fix reverted by a scoping dance, reported fixed twice |
| a submodule checkout on a feat branch | the pinned gitlink | a box-composition claim false at every landed state |
| a diffstat | the page content | a docs commit that reverted its own branch's work to `main` |
| a command's exit code | the resulting PR body | an edit whose replacement string never matched |
| a hand-typed number | the command's output | a `--stat` published as 31/81/12 against an actual 30/79/10 |
| a guard's own argument default | explicit refs | a parser that compared a branch to a detached HEAD and printed CLEAN |
| the line I had edited | the VALUE that had to change | `DOCS_REF` bumped at its assignment and missed at its assertion |

And then the correction to that last row, which is the eighth instance and the sharpest, because
it is the previous row's own lesson misapplied. Keying the sweep on the VALUE finds every
occurrence — right for a pin, WRONG for a citation. The short form `eb92dc24` appears eight times
in this tree: two are `DOCS_REF` pins that must track the gitlink, and three are records of a
MEASUREMENT taken at that ref (`candy/charly-internals/charly.yml`'s separator census, its
projection in `plugins/internals/agents/pr-validator.md`, and two CHANGELOG entries). Bumping a
citation fabricates a measurement that was never run, and unlike a wrong pin — which fails a bed —
nothing downstream can detect it; it simply reads as fact.

A THIRD variant of the same family, and it cost two findings in this cutover: **a measurement is
only as good as the TREE it runs in.** The direction test that decides regenerate-vs-record was run
twice from a working tree that already contained the answer — once against submodule checkouts
sitting on feat branches for a bed run (three box pages recorded as stale that do not exist at the
pinned gitlinks at all), and once against a plugins gitlink this branch itself bumps (a page
reported as ADDING a cell that a clean `main` regeneration REMOVES). Both were caught by a reviewer
re-measuring from clean `main`.

So the direction test needs its tree named alongside its verdict. "Regenerating adds it" is not a
property of the page; it is a property of the page AND the tree, and the tree that decides landing
is the one a clean checkout produces — never the one with the fix already in it.

The general form, which is the reviewer's and is sharper than the instance: **a sweep keyed on a
VALUE finds every SITE, but the obligation attaches to the MEANING at each site — track, or
preserve. Same string, opposite duties, and no gate can tell them apart, because the gate only
knows the string.** So a value-keyed sweep produces a CANDIDATE list, never an edit list.

The full-sha sweep used here reached only the two pins, which is luck rather than method: the
natural way to sweep a sha is the short form, and that reaches every site.

And the sharpest form of the risk is one hop further out. `candy/charly-internals/charly.yml`'s
census is the SOURCE of the projected census at `plugins/internals/agents/pr-validator.md:367`, so
bumping it would not merely record a measurement that was never taken — it would propagate that
fabrication into the validator spec that every future validator reads, where it would be indexed
as the authority on how a census is cited.

A SECOND class emerged alongside it, and the two are worth keeping apart because the fix differs.
The table above is *a sound check read against the wrong object*. The other is **a check that
could not have produced the verdict at all** — three of them here, all cited as passing evidence:

| the gate cited | why it could not go red |
|---|---|
| a Containerfile diff, to prove a candy edit reached no artifact | the box resolves that candy through a pinned `@github` ref, never the local tree — so it is byte-identical for ANY local candy change |
| `docs: DRIFT — 2 newly stale`, to prove a docs PR's inputs | produced by `scripts/drift-baseline.sh`, which exists only on the SOURCE branch and so never read the PR's landed tree |
| `task skills:drift`, to prove a `reference/candy/` page stale | that gate reports only `plugins/**`; `reference/candy/` is the one-hop chain read off the candy on disk |

Each was green, each looked true, and none was capable of the verdict claimed from it. The tell is
cheap and is the durable rule out of this cutover: **ask what mutation would make this gate go red,
and if you cannot name one, the gate is decoration.** That question is also what proves a check
worth keeping — `verify-changelog-h1.sh` survived precisely because an independent validator could
name the mutation and ran it against a live true positive.

A fourth instance of the same class is in the HARNESS rather than in this branch, and is filed as
`charly#340`: `charly check run <bed>` overrides the bed project's superproject to the local tree
and ignores the declared `:vTAG`, so a bed can never fail on an unresolvable `@github` candy pin.
Both ollama submodule PRs currently pin `candy/ollama-cuda` at tags where it does not exist, and
every bed passes.

The reason the proxy class is so durable is that every proxy is CHEAPER to consult than the
artifact and AGREES with it almost always. They diverge exactly when something has gone wrong — which is
precisely the moment you are consulting them. So the fix is not more care; it is a check that reads
the artifact, which is why this cutover ships two of them.

A corollary worth stating because it cost a round: `task docs:pin` compares `DOCS_REF` against the
COMMITTED gitlink, not the staged one, so it stays red until the bump and the pin land in the same
commit. Reading that red as "the bump did not work" is the same inference error as reading
`head -1` from a working tree.

## The `docs` gitlink, `DOCS_REF`, and a pin that was already adrift

Both projections landed first (`plugins#210` -> `b58510eb` -> `#211` -> `192f9d96`; `docs#82` ->
`6b7819c8`), so B6a step 5 bumps the two gitlinks here.

`DOCS_REF` moves with the docs gitlink, and it was ALREADY adrift before this cutover touched
anything — gitlink `e3e75081` against `DOCS_REF eb92dc24`. This change CURES that drift rather than
introducing it, which is a fact about attribution rather than a dismissal.

It appears TWICE in `candy/docs-site/charly.yml`, and the second occurrence is the one that bites:
line 44 is the `var:`, line 82 is a LITERAL inside a check step, because charly's check-step
substitution does not resolve a candy `var:` — it skips the step with "unresolved variables" while
the bed still reports PASS. A bump that updates the assignment and misses the assertion leaves the
guard checking the OLD sha while the clone layer fetches the new one. `task docs:pin` asserts both,
which is why it is the gate and a grep of line 44 is not.

The first attempt here did exactly that, and the guard caught it — a bed was already running that
would have cloned `6b7819c8` and asserted `eb92dc24`. The sweep had been keyed on the line I had in
mind rather than on the value that had to change everywhere.

## The spec pin moves in lockstep across every module

See the `fix(mods)!` commit. `task plugins:tidy` is removed in favour of `task mods:tidy`, whose
membership rule is "declares a local replace of sdk or spec" rather than a `candy/plugin-*`
directory prefix — the prefix assumption had left `candy/generate-packages` and both
`tools/golden-*` modules behind, two of which had been stale on `main` for weeks.
`TestSpecPinsMatchSDK` proves it.

## Project scope becomes a contract

`candy/plugin-mcp`'s `childCharlyEnv` and the CLI's literal env-name reads now go through
`spec.ChildProjectEnv` / `spec.ProjectDirEnv` / `spec.ProjectRepoEnv` (opencharly/spec#38,
opencharly/sdk#142). The Kong struct tags in `charly/main.go` stay literal because a Go struct tag
cannot reference a constant.

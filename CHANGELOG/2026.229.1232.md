# 2026.229.1232 — the ollama candy goes packaged, GPU backends split out, and rpm repos can finally force gpgcheck on

Four strands, one surface: the `charly ollama` management CLI, an ollama candy that
installs from the distro package where one exists, the CUDA/ROCm backends split into
their own opt-in candies, and the rpm repo template gaining the ability to REPAIR a
vendor that ships package verification disabled.

## The plugin-ollama management plugin (`candy/plugin-ollama/`)

A compiled-in `command:ollama` plugin (dual-placement, placement-agnostic) that owns
the entire `charly ollama` CLI — `list` / `ps` / `pull` / `rm` / `show` / `cp` /
`create` / `push` / `run` / `stop` / `version` — against a deployed Ollama server's
HTTP API, built on the official upstream Go client (`github.com/ollama/ollama/api`,
pinned `v0.32.14` in the candy's own go.mod). Self-contained (plain HTTP, no reverse
channel), so it works identically compiled-in or out-of-process. Endpoint resolution
is deliberately lightweight: `--server` flag > `OLLAMA_HOST` env >
`http://127.0.0.1:11434` — the flag is named `--server`, NOT `--host`, because the
charly-level Kong grammar already owns `--host` (SSH remote execution) for every
command. Full Modelfile authoring stays with the upstream CLI inside the deployment
(the candy's host alias); `create` covers the lightweight `--from` form.

Coverage: 19 test functions against an httptest fake Ollama server — every subcommand's
request body and output, endpoint precedence, error propagation, and the chat REPL.
`push` was the one subcommand of eleven shipping untested; it now asserts both its
output and its request body, so all eleven are covered.

## The ollama candy: packaged where possible, tarball where not

The candy installed the upstream release tarball unconditionally. Arch (and CachyOS)
package ollama in `extra`, tracking upstream closely — `0.32.14-1` landed the day
upstream tagged `v0.32.14` — so the candy now declares `distro.arch.package: [ollama]`
and the tarball step is skipped there.

**The skip is capability-gated, not distro-gated.** `distro:` package sections compile
into the plan at phase 1 and `plan:` steps at phase 3 (`BuildDeployPlan`), so on a
packaging distro `/usr/bin/ollama` already exists when the step runs, and the step
returns early on exactly that. A distro that gains an ollama package is picked up with
no edit. A distro-name filter was the obvious alternative and is not available: the
`exclude_distro:` modifier is read by the check runner (`sdk/kit/planrun.go`), never by
the build emitter, so it cannot gate a `run:` step at build time.

`OLLAMA_VERSION` keeps selecting the upstream release, and is now documented as
applying to the tarball path only — on Arch, pacman owns the version.

The three host-side `charly ollama` steps that prove the plugin end to end
(help dispatch, live `version` round-trip, `list`) moved OUT of the fedora bed and ONTO
this candy, where every composing box inherits them (R3). `${CHARLY_BIN}` is stamped
for any runtime check run, not only for bed members (`kit.StampCharlyBin`), so the
steps work wherever the candy is deployed. Both ollama beds are now plan-free.

## GPU backends as opt-in candies (`candy/ollama-cuda/`, `candy/ollama-rocm/`)

The upstream tarball is 1.36 GiB because it bundles every backend; Arch splits them,
and `ollama-cuda` / `ollama-rocm` DEPEND on `ollama` rather than conflicting with it,
dropping their backend into ollama's own `/usr/lib/ollama/` runner directory. That maps
exactly onto "GPU support is a box-level composition choice", so the backends are now
candies a box opts into:

| candy | backend | installed |
|---|---|---|
| `ollama` | CPU only | 66 MiB |
| `ollama-cuda` | `libggml-cuda.so` | +988 MiB |
| `ollama-rocm` | `libggml-hip.so` | +2.9 GiB |

A CPU consumer (`openclaw-desktop`) now pays 66 MiB where it used to pay 1.36 GiB.
Each backend candy asserts its library with a version-agnostic glob under
`/usr/lib/ollama/*/`, so a CUDA or ROCm version bump does not rot the check.
`ollama-rocm` is Arch-only by construction and says so: the base upstream tarball ships
no ROCm backend (upstream publishes it as a separate archive), so the candy would
install nothing on a tarball distro and its check would correctly fail rather than
pretend.

## rpm repos can now force gpgcheck ON (`charly/charly.yml`)

The rpm `install_template` copies a vendor `.repo` file in verbatim and offered a
`gpgcheck:` knob that could only ever turn verification OFF — the guard tested for the
literal `false`, so `gpgcheck: true` was a silent no-op. Both `gpgcheck:` and the new
`repo_gpgcheck:` are now TRI-STATE: absent inherits the vendor's value (unchanged
behaviour, and `candy/nvidia` is the only candy in the tree that sets either), `false`
forces the check off, `true` forces it ON.

That closes a real hole. NVIDIA ships `nvidia-container-toolkit.repo` with
`gpgcheck=0` — the only repo in the tree that does — so its four packages, a container
runtime hook, were installing **unverified** in every Fedora GPU image, even though the
imported key was good and every package is validly signed by the primary key. No value
expressible in the candy could fix it until the knob became tri-state.

Two more defects in the same RUN, found by the same RCA and fixed here:

- **`candy/nvidia` no longer imports the key explicitly.** The repo file already
  declares it, so dnf5 imports it under `gpgcheck=1`. An explicit `rpm --import` of
  NVIDIA's published certificate emitted `Subkey 6ED91CA3AC1160CD is expired` on every
  single build, because that certificate carries a subkey that died 2021-06-16 and
  every NVIDIA copy still ships it. Nothing is trusted less — the packages are signed
  by the primary key and verify either way.
- **`candy/cuda` pinned a key URL NVIDIA had deleted.** `D42D0685.pub` 404s; the live
  `cuda-fedora43.repo` names `1940C73E.pub` ("Kitmaker (Fedora 43)"). Every GPU image
  build was emitting `import read failed(2)`, survivable only by accident because the
  `cuda-*` packages happened to resolve from fedora-multimedia, so that repo's
  `gpgcheck=1` never had to verify anything.

A cache-cold `nvidia` build now emits **zero warnings and zero errors**, where it
previously emitted two warnings, two errors, and installed four packages unverified.

The enforcement is GATED, not merely asserted: `nvidia-container-toolkit-gpgcheck-enforced`
reads the repo definition in the built image and requires `gpgcheck=1`. That is the one
observable that discriminates — a "the signing key is in the rpmdb" probe would not, because
the previous code imported the key explicitly via `rpm --import` while still installing
unverified under NVIDIA's shipped `gpgcheck=0`, so the key was present either way. What
changed is the repo's enforcement setting, so that is what the check asserts.

## Also

`candy/plugin-docs/gen_skills.go` claimed the generator reads the plugins tree "at
whatever gitlink the superproject currently pins". It does not — `collectSkills` does a
filesystem `os.ReadDir`, so the WORKING TREE wins. The comment now says so, including
the operational consequence: check plugins out at the commit you intend to publish
before regenerating, or the drift gate goes red for a reason the diff does not explain.

## The `pkg/` submodules are gone; packaging is nFPM + per-distro repos

Phase 3 of the nFPM packaging cutover, and the one that removes the old path.
Phases 0a/0b landed the schema and the `sdk/packagekit` driver, Phase 1 the
release-binary workflow, Phase 2 the six per-distro repos. This lands the
superproject half: the `pkg/*` submodules and the `charly box pkg` verb are
deleted, and the packaging metadata moves into the charly candy.

### What is removed

- **The three `pkg/*` git submodules** — `pkg/arch` (PKGBUILD), `pkg/fedora`
  (spec), `pkg/debian` (debian/control) — plus `pkg/host-command-plugins.txt`,
  with their `.gitmodules` entries.
- **The `charly box pkg` command surface** and the `build:pkg` word behind it.
- **The localpkg source-build machinery** — `BuildLocalPkgOnHost`, the
  `localpkg:` candy map, and the `local_pkg` build vocabulary
  (`pkg_glob`/`source_sentinel`/`build_template`). The install half
  (`install_template`/`probe`/`download_template`) stays: deploys now DOWNLOAD
  the published package instead of building it from source.
- **`.github/workflows/release-packages.yml`** and `scripts/pkg-install-test.sh`,
  superseded by `release-binary.yml` and the distro repos' own workflows.
- **The `charly clean --makepkg` sweep**, which only ever cleaned `pkg/arch`.

### What replaces it

Package metadata is now ONE source: the `packaging:` section in
`candy/charly/charly.yml` — name, description, maintainer, per-format
depends/optdepends, and the named variants. The external
`charly generate-packages` plugin reads exactly that file and builds all five
Linux formats through nFPM; each distro repo assembles and signs its own
repository and publishes it to GitHub Pages.

The `download_template` URLs move from GitHub release attachments to the
per-distro repos, so `pacman -S charly` / `dnf install charly` /
`apt install charly` / `apk add charly` work for the first time.

### The package name changed

`opencharly-git` (Arch) and `opencharly` (rpm/deb) are both now **`charly`**,
matching the binary. Every bed assertion that probed the old names
(`pacman -Q opencharly-git`, `rpm -q opencharly`, `dpkg -s opencharly`) is
updated in the same change, across the main repo and the `box/*` submodules.

### Five new check beds

`check-alpine-repo`, `check-arch-repo`, `check-debian-repo`,
`check-ubuntu-repo`, `check-fedora-repo` — disposable fleets that prove the
REPO-BASED install end to end: add the published repo and its signing key,
install via the native package manager, assert `charly version` matches the
published CalVer, and assert the welded command plugins dispatch project-less
from `/tmp`.

These deliberately do NOT use the localpkg mechanism. The check-bed runner
auto-sets `--dev-local-pkg`, which forces the dev build path, so each bed uses
explicit `command:` steps against the real published repo instead — otherwise
the bed would prove the build path rather than the thing being shipped.

### A note on the Alpine bed, and what it cost to get right

`check-alpine-repo` is a `pod:` bed rather than a `vm:` one. The VM route was
attempted first and abandoned: Alpine cloud images run OpenRC, and the
cloud-init renderer emitted `systemctl enable --now sshd`, so the guest booted
and was simply never reachable.

Bringing that bed up surfaced **five** separate glibc/shadow-utils assumptions,
each invisible until a busybox base actually exercised it, and each only
discoverable after the previous one was fixed:

| # | assumption | where |
|---|---|---|
| 1 | `curl` exists | `sdk` bootstrap (go-task install) |
| 2 | `groupadd`/`useradd` exist | `sdk` bootstrap (user creation) |
| 3 | `/bin/bash` exists | `sdk` bootstrap (login shell) |
| 4 | the guest runs systemd | `sdk` cloud-init render |
| 5 | `bash` exists on a jump's far side | `spec` `wrapWithJump` |

The first four land in `sdk`; the fifth in `spec` (`v0.2026228.2`, pinned here).
None was caught by any existing bed, because every box in the fleet ran a glibc
base where all five assumptions hold.

## The Alpine leg, and five version checks that could not fail

The nFPM cutover's Alpine leg had no distro vocabulary, so `check-alpine-repo` could not
build. Fixing that exposed the more interesting finding: **all five distro beds' version
checks passed for reasons unrelated to what they claimed to prove.**

### The Alpine vocabulary did not exist

`charly/charly.yml`'s embedded build vocabulary defined five distros — arch, cachyos,
debian, fedora, ubuntu — and no alpine. So an Alpine box had no bootstrap command, no
cache mount, and no `apk` format with an install template. Added as a complete `alpine:`
entity with an `apk:` format (bootstrap `apk add --no-cache`, `/var/cache/apk` cache
mount, install template handling repo `key:`/`url:`, `local_pkg` install/download/probe,
uninstall template).

`candy/plugin-vm/build_defaults.yml` carried a second copy of the same distro vocabulary
with no drift test between them, so I initially copied the new entity into it as well — 41
lines into a second file, with a note that "the duplication itself is the real defect and is
not fixed here". That was the wrong call twice over: "not fixed here" is the deferral this
project does not permit, and the duplication turned out not to need syncing at all.

**Measuring the file's consumers settled it.** `build_defaults.yml` is embedded by
`vm_phaseA_shims.go` because the out-of-process plugin cannot reach core's `//go:embed`. It
has exactly ONE decoder (`unmarshalEmbeddedDefaults`), wired to exactly one seam
(`vmshared.UnmarshalEmbeddedDefaults`), called from exactly two places in
`sdk/vmshared/ovmf_paths.go`, which decode exactly two keys: `ovmf_paths` and
`ovmf_distro_aliases`. The file had **28 top-level keys and 1273 lines** — a near-complete
copy of `charly/charly.yml`. **26 of those keys were read by nothing**, including the entire
distro build vocabulary I had just added alpine to.

So the copy was not a vocabulary needing sync; it was dead data that *looked* like one, and
that appearance is the whole cost — a distro added to core reads as though it needs adding
here too, and adding it changes no behaviour whatsoever. The file is now **52 lines and 2
keys**, and `candy/plugin-vm/build_defaults_keys_test.go` fails if a third top-level key
reappears, with a second test as the presence control (the resolver panics on an empty table,
so trimming to zero keys must also fail).

One thing this does NOT fix, stated rather than implied: `ovmf_paths` and
`ovmf_distro_aliases` are top-level keys in the validated project schema
(`spec/schema/node.cue`), so a project may override them — but the plugin reads its own
embedded copy and therefore ignores such an override. That is a real gap between the schema's
promise and the plugin's behaviour, with its own root cause (an out-of-process plugin has no
route to project config here), and it is not something this cutover's change created or can
honestly close in passing.

### `alpine-repo-box` inherited the wrong package format

The box declared no `build:`, so it fell through to `defaults.build: [rpm]` — an **rpm**
primary format on an Alpine base. The package cascade matched the candy's `alpine:`
section and resolved `sudo` correctly; the rpm install template then did not exist in the
alpine distro, and the install was dropped with no diagnostic. It now declares
`build: [apk]`.

That silent drop is fixed in the sdk (see its entry for this CalVer); this repo's part is
the missing declaration.

### Why a check bed needs passwordless sudo

New `sudo-nopasswd` candy, composed into `alpine-repo-box`. A charly box runs as uid 1000
and `run_as:` on a check step is not honoured by the check executor, so a check that must
drive a native package manager **in-container** has no other elevation path. It installs
`sudo` declaratively through the new alpine `apk` format and writes
`/etc/sudoers.d/charly-user` at 0440, refusing to write anything if no uid-1000 account
exists — the same guard, and the same sudoers rule, the sshd candy already ships.

Its own check reads the file's mode *through* `sudo`, deliberately: `/etc/sudoers.d` is
0750 root:root, so uid 1000 cannot `stat` inside it, and routing the read through sudo
proves both halves at once — the drop-in is 0440 **and** the NOPASSWD rule actually
grants elevation. The first version of this check used a direct `stat` and failed with
`Permission denied`, which is correct Unix behaviour and told us nothing about sudo.

### The five version checks: what they claimed, and what they measured

Every distro bed carried the same claim in its description — *asserts `charly version`
equals the repo's published CalVer* — and the same shape:

```sh
test "$(charly version)" = "$(<package-manager query>)"
```

Three independent problems, none of which any run would have surfaced:

1. **No non-empty guards.** When both sides are empty, `test "" = ""` **passes**. The
   check reported success while measuring nothing. This was first found on the Alpine bed,
   proven in a live pod, and the identical shape was then found in the other four.
2. **`charly version` reads PATH**, which inside a check resolves to the check runner's
   own staged binary — not the binary the package installed. The check could pass with the
   package absent.
3. **Two of the queries reported the wrong thing entirely.** `dnf info charly` and
   `apt-cache policy charly` report the **available candidate**, not what is installed. A
   correct comparison against them is still not a statement about the installed package.

And the Alpine query was simply wrong about its tool: `apk info -v charly` prints the
package *description*, not `name-version-rN`, so its `sed` extracted the empty string —
which is how problem 1 stayed invisible.

All five now share one shape (R3), differing only in the query, with both values echoed
so a failure is diagnosable:

```sh
installed="$(/usr/bin/charly version)" &&
packaged="$(<query>)" &&
echo "installed=[$installed] packaged=[$packaged]" &&
test -n "$installed" && test -n "$packaged" &&
test "$installed" = "$packaged"
```

| distro | query, verified live |
|---|---|
| alpine | `apk list --installed charly \| sed -n 's/^charly-\([0-9][0-9.]*\) .*/\1/p'` |
| arch | `pacman -Q charly \| awk '{print $2}' \| cut -d- -f1` |
| fedora | `rpm -q charly \| sed -n 's/^charly-\([0-9][0-9.]*\)-.*/\1/p'` |
| debian, ubuntu | `dpkg-query -W charly \| awk '{print $2}'` |

Each query was measured against its **live published repo**, not reasoned about: all four
package managers installed charly from `opencharly.github.io/charly-<distro>` and every
one reported `2026.227.1426`, matching the packaged binary's own `charly version`. So the
published repos are sound and the versions do agree — the checks simply were not the thing
establishing it.

Two queries avoid `${...}` / `%{...}` on purpose (`dpkg-query -W … | awk` rather than
`-f='${Version}'`, `rpm -q | sed` rather than `--queryformat '%{VERSION}'`): a check
`command:` passes through charly's own `${VAR}` substitution, and while an unknown name is
left alone today, a brace-free form cannot collide with it at all.

### The update and install steps had the same weakness

`apk update`, `pacman -Sy` and `apt-get update` all exit 0 with a *warning* when a
configured repo is unreachable, so none of them could prove the charly repo resolved. Each
now additionally proves the package is visible from a repo that only the charly repo could
serve (`apk list charly` / `pacman -Si charly` / `apt-cache policy` showing a Candidate),
and each install step now asserts the package is **registered** afterwards (`apk info -e`
/ `pacman -Q` / `rpm -q` / `dpkg-query -W`) rather than trusting the installer's exit code
alone.

### An instrument worth recording, because it produced a false report

Probing whether the Alpine repo published an index, `curl` returned **404** for
`charly-alpine/amd64/APKINDEX.tar.gz` while `apk` in the same configuration installed the
package successfully. The contradiction was the instrument, not the repo: **apk appends
its own architecture** to the repository URL, so the index it actually fetches is
`charly-alpine/amd64/x86_64/APKINDEX.tar.gz`, which returns 200. Reported as "the repo
publishes no index", that 404 would have sent a fix at a repo that was working correctly.

### `charly candy add-apk`, and the three lists that had to agree

Non-blocking on its own — a candy author writes `distro: {alpine: {package: […]}}` by hand,
which is what this cutover's own candy does — but leaving the authoring CLI unable to name a
format the build vocabulary now supports is the kind of half-done cutover that reads as
intended. `charly candy add-apk <candy> <pkg…>` appends to `distro.alpine.package`.

Adding it surfaced the reason it would have been easy to get wrong: **which `add-<fmt>` verbs
exist was written down in three places** — the `sectionDistroPath` map, the `switch` in
`runCandyCLI`, and the `candyUsage` string — with nothing tying them together. A format added
to the map but not the switch would be silently undispatchable; added to the switch but not
the usage string, invisible. The map is now the single source: the dispatch looks the format
up rather than listing verbs, and the usage string is joined from the map's keys. Two further
enumerations were swept in the same change (the MCP mutating-tool allowlist, which gates
whether the verb is exposed at all, and the scaffold hint a new candy is created with).

Coverage: `TestAppendCandyPackages_Apk` fails without the map row;
`TestAddFormatVerbs_DerivedFromOneSource` asserts every mapped format is both dispatchable
and present in the usage string, with an unmapped `add-nope` as the presence control so the
assertion cannot be satisfied by accepting everything.

### The prose the emitter change falsified

The Containerfile emitter no longer names `bash`, so the per-verb emission table was wrong
in the candy source and in both of its projections. Fixed at the source and regenerated
through `charly marketplace generate` → `task docs:sync`; see the `plugins` and `docs`
entries for this CalVer.

**The regeneration had to be scoped, and the reason is worth recording.** Running it
wholesale modified 21 files in `plugins` and 41 in `docs`, and the extra ones were not drift
being tidied up — they were **reverts**, ~500 lines of prose that had legitimately landed in
those repos ahead of the superproject candy source that pins them (the ordering this project
works under: the projection merges first). Regenerating from a superproject tree that lacks
the pending source drags the projection backwards, and the diff looks identical to a
legitimate update. This change therefore keeps only the projections of the three candy files
it edited — five files per repo — and every deleted line in them is one it deliberately
replaced, audited line by line.

Two further details worth noting:

- The `cmd` row was stale in a **second, independent** way — it described ANSI-C `$'...'`
  quoting where the emitter has been using a heredoc. Correcting only the `bash` half would
  have left the row self-contradictory, which is worse than uniformly wrong: half of it would
  still have read as authoritative.
- The `charly candy add-rpm`/`add-deb`/`add-pac`/`add-aur` doc rows were checked against the
  CLI rather than swept as format lists. They enumerate **commands** — the same tokens
  answering a different question — so they were only updated once `add-apk` actually existed.

### The four VM beds could not have passed either, for two more reasons

Running them surfaced two defects the Alpine bed had already taught, plus one that is not
this cutover's to fix.

**No root escalation.** Every root-requiring step ran as the cloud-image's uid-1000 user and
failed on contact: `Permission denied` writing `/etc/yum.repos.d/charly.repo` and
`/etc/pacman.conf`, `pacman-key needs to be run as root`, `dnf`/`pacman`/`apt-get` refusing
outright. The bed's own preamble documents the intended mechanism — *"provide passwordless
sudo for the check runner's `ssh vm sudo bash -s` root escalation. The default distro
cloud-image user has passwordless sudo via cloud-init"* — so the intent was recorded and the
implementation simply absent. Every such step is now escalated, and the six that redirect a
shell into `/etc` go through `sudo tee` / `sudo gpg -o`, since `sudo` on the command does
nothing for a redirect the *calling* shell performs.

**A 90-second kill-switch.** `sdk/kit/runner.go`'s `ProbeNeverHang` SIGKILLs any step running
past `runnerProbeNeverHangFallback` (90s) unless the step declares `timeout:`. Installing
charly pulls ~190 packages (podman, qemu, libvirt, gnupg, tailscale), which on a 2-vCPU VM
crosses it: fedora's `dnf install` died at ~2m with `signal: killed` and nothing naming a
deadline. Thirteen package-manager steps across the five beds now declare `timeout: 10m` —
the mechanism's own parameter, which the function honours explicitly ("a longer
author-declared timeout: is honored over the floor so a slow probe is never cut short"), not
a workaround.

What made this costly to diagnose is worth recording: **arch passed while fedora was killed**,
and two beds differing only in package manager invites a distro-specific theory — repo
layout, signing, cloud image — when the real variable is elapsed time against a shared floor.
`pacman -S` fits under 90s; `dnf install` does not.

### Debian and Ubuntu never booted: `firmware: bios` under a UEFI cloud image

`debian-repo-vm` and `ubuntu-repo-vm` declared `firmware: bios`, and the Debian 13 generic
and Ubuntu noble cloud images are UEFI-oriented. The domain started, the port forward
accepted TCP, and `sshd` never answered — `Connection timed out during banner exchange` —
so the driver waited on a guest that had written 196 KB and was not going to boot. The repo's
own working templates already had the answer: `box/debian` and `box/ubuntu` both use
`firmware: uefi-insecure`, and both new templates now match them. Fedora and Arch legitimately
run under `bios` (as `box/fedora` does), which is exactly why only two of the four hung.

#### The wrong diagnosis this replaces, because the error is worth more than the fix

I first called this a **VM image-cache concurrency race** — four beds launched together,
"only three base images materialized", `vm-create` reporting PASS over an unmaterialized
disk — and started running the beds sequentially to get around it. Every load-bearing part of
that was false:

- **The image cache was never involved.** All four bases resolved to four distinct
  content-addressed entries; I counted three because the fourth (fedora's) had been cached in
  July and I was implicitly counting only *today's* mtimes. A fetch that legitimately hit a
  warm cache looked identical to a fetch that never happened.
- **A 196 KB disk is not an empty disk.** Every built disk is a 1.2 MB qcow2 overlay backed by
  the cached base; the deployed disk grows only as the *guest writes*. So 2.1 GB meant "booted
  and installed 190 packages", and 196 KB meant "did not boot" — a symptom of the real defect,
  which I read as its cause.
- **`qemu-img info` returning nothing did not mean a corrupt image.** It could not take a lock
  because the VM was running and holding the disk. The files were valid qcow2 all along
  (`QFI\373`).
- **And the sequential run disproved the concurrency theory rather than working around it** —
  debian stalled there too, identically. The evidence that the theory was wrong was in the
  first result the workaround produced, and running sequentially is what would have kept it
  hidden if the run had happened to pass.

The generalizable part: **a fix that avoids a failure also stops you learning what it was.**
Three of the four false beliefs above were disproven by a single measurement I could have made
first — reading the built disk's backing file. The beds are proven concurrently.

## Codifying six findings into the skills that own them, and one skill that told you to edit a generated file

Documentation-only. Six findings from the nFPM Alpine cutover existed only in a session
transcript and an operator's private memory, which is a knowledge leak: every other
contributor — and every fresh validator or teammate, which never reads that memory —
re-hits the same wall and re-derives the same fix. Each is now in the committed skill that
owns it, edited at the **candy source** and regenerated.

### `/charly-internals:skills` — step 1 told you to edit the artifact

The worst of the six, because it manufactures the error it should prevent. "How to Update"
opened with:

> 1. Edit the skill file at `plugins/<plugin>/skills/<skill-name>/SKILL.md`

Most of that corpus is a PROJECTION carrying a DO-NOT-EDIT banner. Following step 1 gets
your work reverted by the next regeneration, silently and without a conflict. It now says
to edit the candy's `skill:` entity and regenerate, with `git grep -l 'DO[- ]NOT[- ]EDIT'`
as the discriminator — and the caveat that the grep cannot tell a file that *carries* a
banner from one that *mentions* it, so its hits are triaged rather than trusted (agent
definitions under `plugins/<plugin>/agents/` really are hand-authored).

It also gains **"Regenerate ONLY the projections of the sources you edited"**, because a
projection merges *before* the superproject source that pins it. Prose can therefore be
correct and landed in `plugins`/`docs` while its candy source is still in flight, and
regenerating from a tree that lacks that source drags the projection backwards. Measured:
a wholesale regeneration touched 21 files in `plugins` and 41 in `docs` when three candy
sources had changed, and the extras were ~500 lines of reverts — 317 from one git-workflow
reference, 107 from the `pr-validator` spec. The section gives the audit
(`git diff --numstat`, then read every deleted line) and names the reading that ships the
revert: "it was probably just stale".

### `/charly-vm:vm` — the firmware matrix was wrong about two distros

The BIOS/UEFI decision matrix listed **Ubuntu Cloud and Debian Cloud** under `bios`.
`debian-13-generic-amd64.qcow2` does not boot that way: the bed stalled twice under `bios`
and passed (`check-debian-repo` PASS, steps=9) under `uefi-insecure` with nothing else
changed. The repo's own `box/debian` and `box/ubuntu` templates already pinned
`uefi-insecure`, so the skill disagreed with the working configs next to it. Corrected as a
per-image property rather than a global preference — `bios` still holds for Arch, Fedora and
CentOS, and `box/fedora` runs it today.

Also added: **the signature of a firmware mismatch**, because it looks like anything but
firmware. The domain reports `running`, the port forward accepts TCP (qemu user-net binds it
before the guest listens), `sshd` never answers (`timed out during banner exchange` /
`kex_exchange_identification: Connection reset by peer`), the console is silent, and the
deploy step waits forever. The probe is the deployed disk's growth read **twice** — a booted
guest's mtime advances, a guest that never booted stays frozen — with the two traps that cost
hours: size alone cannot separate them (every deployed disk is a small overlay backed by the
cached base, so it grows only as the guest writes), and `qemu-img info` failing with
`Failed to get shared "write" lock` means the VM is holding its disk, not that the image is
corrupt.

### `/charly-check:check` — three additions to the authoring gotchas

Gotcha 10 already said to verify "can I sudo?" rather than a root-only file bit, and I
rediscovered that the hard way by authoring a `stat` on `/etc/sudoers.d/charly-user` — the
skill had it and I had not loaded it (R0). Extended rather than duplicated:

- **The same applies to a `vm:` bed**, where steps run as the cloud image's default user;
  `pacman-key needs to be run as root` and `Permission denied` on `/etc/pacman.conf` are
  this, not a repo or signing problem.
- **`sudo` on the command does not cover a shell redirect** — `sudo echo … > /etc/…` and
  `sudo cat > /etc/… <<'EOF'` both redirect as uid 1000. Use `sudo tee` / `sudo gpg -o`.
- **Where `sudo` comes from differs by substrate**: a cloud-image VM has it via cloud-init;
  a container box must install it and write its own drop-in.

**New gotcha 13 — a step is SIGKILLed at 90s unless it declares `timeout:`.** Installing
charly from a published repo pulls ~190 packages, so on 2 vCPUs `dnf install` does not finish
inside the floor while `pacman -S` does — one bed green, one "killed", which invites a
distro-specific theory when the variable is elapsed time against a shared bound. `#Op` has
`timeout?: #Duration` and `ProbeNeverHang` honours a longer authored value, so declaring it
is using the mechanism's parameter.

**New gotcha 14 — a check must be able to FAIL for the reason it names.** Four ways a step
passed while measuring nothing: `test "$(a)" = "$(b)"` with both sides empty; `apk update` /
`apt-get update` / `pacman -Sy` exiting 0 on an unreachable repo; an installer's exit code
mistaken for registration; and `<cmd>` on PATH resolving to the check runner's own staged
binary rather than the packaged one. Plus: query the installed package, not the available
candidate, and prefer brace-free extraction since a check `command:` passes through charly's
own `${VAR}` substitution.

### `/charly-build:generate` — an unrenderable install is loud

The emission pipeline now documents that resolved-but-unrenderable packages hard-error rather
than vanishing, with the two authoring consequences that produced the original bug: a box
declaring no `build:` inherits `defaults.build:` (an Alpine-based box silently took `[rpm]`),
and `buildkit.TemplateFuncs` is the complete set, so a template calling anything else fails
at render time.

### Scope note

`vm/skills/vm/SKILL.md`'s projection is deliberately NOT regenerated here. Its regenerated
output would also delete 15 lines of landed `distro:`-inference prose whose candy source is
still in flight — exactly the hazard documented above. The candy source is the authority and
carries the correction; the projection catches up when regenerated on a tree that has every
source. Three projections whose full output is revert-free (one deleted line, the one
replaced) ship here.


### The Ubuntu leg, and why it was never firmware

`check-ubuntu-repo` was left open by the previous entry with its measurements and no cause. It
now **PASSES (steps=9)**, and the cause was in charly's cloud-init renderer, not the bed.

`sshUnitForDistro` and `composePackages` key on the **explicit** `source.distro` field, which
`effectiveDistro` infers for `arch`/`alpine` but never for `debian`/`ubuntu`. Both new VM
entities omitted it, so the renderer emitted the Arch package name `openssh` (which apt cannot
locate) and `systemctl enable --now sshd` (a unit Ubuntu does not have) — and since `bootcmd`
deliberately masks `ssh.socket` until cloud-init finishes, Ubuntu's socket-activated sshd was
masked and never restarted. The guest booted fully and served nothing.

Both entities now set `distro:` explicitly, with a comment saying why it is load-bearing rather
than decorative, and the sdk gained a fallback to the other unit name so omitting it can never
brick SSH again (see the sdk entry for this CalVer).

**Four wrong theories preceded the right one, and the pattern in them is worth more than the
fix.** Firmware (`bios` → `uefi-insecure`) was real for Debian but not Ubuntu, which failed
under both. A concurrency race in the image cache was fabricated from a miscount. A 196 KB disk
looked like an unmaterialized image and was an unwritten overlay. `qemu-img info` returning
nothing looked like corruption and was a lock held by the running guest. Every one was a
structural theory built without reading the artifact the guest was actually given — and the
rendered `seed.iso` user-data, extracted in one command, contained the answer in plain text the
whole time.

### Codified in `/charly-internals:vm-spec` too

The skill already warned that `base_user:` steers rendering and that an Alpine image with a

artifact-first diagnostic (extract `seed.iso`, read `user-data`) rather than a code-path

## OpenRC becomes a first-class init system; the distro guesswork is gone

### OpenRC, beside systemd and supervisord

`openrc:` is now an `init:` entity in the embedded vocabulary, a peer of `systemd:` and
`supervisord:` — same contract, same fields, no special-casing anywhere in Go.

Declared in the vocabulary rather than in code, because a vocabulary entry bakes its whole
contract into the `ai.opencharly.init_def` label and so resolves at runtime with **no Go change
at all**. The alternative was the `wellKnownInitDefs` fallback table — which this same cutover
DELETES, two sections below, precisely because it could never answer for a third init system:
it was triplicated across `sdk/kit`, `plugin-pod` and `plugin-deploy-pod` and frozen at
supervisord + systemd. Its own comment said to declare new init systems in the vocabulary
instead, which is what openrc does.

What it declares: `model: file_copy` (each service is its own `/etc/init.d` script, like
systemd's units — not supervisord's single concatenated config), the install step (with the
`chmod 0755` that OpenRC silently requires — a non-executable file in `/etc/init.d` is the
classic "service does not exist"), `rc-update add … default` to enable, `rc-service` as the
management tool with `<service> <action>` ordering (the inverse of systemctl's, which is why
the action cannot be hardcoded around one tool), and a service template using
`supervisor=supervise-daemon` so OpenRC has the restart semantics systemd expresses with
`Restart=` — the default start-stop-daemon path starts a service and forgets it.

Before this, the only OpenRC support anywhere was a hardcoded `if distro == "alpine"` in the
cloud-init renderer that enabled sshd in a *guest*; a container box on an Alpine base could
not declare `service:` entries at all.

### The distro guesswork is deleted

See the spec and sdk entries for this CalVer. In this repo:

- **Presence is enforced in the kind's own plugin.** `candy/plugin-substrate/validate_vm.go`'s
  vm `OpValidate` capability now requires `source.distro` on the distro-bearing source arms
  (`cloud_image`, `bootstrap`) and rejects an id outside the generated vocabulary. That is
  where this repo already documents concreteness as belonging: the host's value gate is
  closedness-only **by design**, and a kernel-side branch encoding which fields a kind needs
  was overruled by the boundary law once already. The check mirrors the PCI-hostdev one
  beside it — the same "Go distinguishes absent from empty where non-concrete CUE cannot"
  shape. Presence controls included: the `bootc` and `disk` arms carry no distro and must not
  be asked for one.
- Every `cloud_image` source in this repo and its box submodules states `distro:` explicitly.

### What is NOT proven yet, and what blocks it

**One cause gates four things in this tree, not just the test suite.** Measured:

| command | exit | blocked by |
|---|---|---|
| `go test ./...` (in `charly/`) | 4 failures | loading the pinned repos |
| `charly marketplace generate` | 1 | same |
| `charly docs generate` | 1 | same |
| the check beds | — | same (they load the project) |

So the `plugins/` and `docs/` projections of the candy edits in this cutover cannot be
regenerated until the pins move; the candy sources are the committed truth in the meantime. This
is worth stating precisely because "4 test failures" reads as a test-only problem, and the
projection chain is the part that silently stays stale.

**The 4 failures are all the same external cause:** the
pinned remote copies of `opencharly/distro-arch` (at `v2026.200.2132` and `v2026.204.1300`)
and `opencharly/distro-fedora` (at `v2026.216.0232`) carry `cloud_image` sources without
`distro:`, so loading them now fails validation. Those repos are the `box/arch` and
`box/fedora` submodules; both carry the fix in this tree and are committed here, but a pin can
only move to a tag that exists. The order is producer-before-consumer: those two land and are
tagged, then the `@github` pins in `charly.yml` and `box/cachyos/charly.yml` bump, and the
suite goes green.

This is stated rather than worked around. The alternative — a migration that fills the field
by inferring it from the image URL — was written and deleted: it is the same guess in a new
location, and the point of this cutover is that nothing infers a distro from anything.

The affected set is enumerated rather than assumed. Every cached pinned repo was parsed for
`cloud_image` sources lacking `distro:`, because the obvious instrument — grepping for
`distro:` — cannot answer the question: that key also appears in candy package sections, so
`distro-arch` grepped as covered while the validator rejects it. Against the parsed answer:

| pinned repo | entities missing `distro:` |
|---|---|
| `distro-arch` (both pins) | `arch` |
| `distro-fedora` | `fedora-vm`, `web-vm` |
| `distro-cachyos`, `distro-debian`, `distro-ubuntu` | none — already clean |

So the pin bump touches three pin sites in two repos (`charly.yml` for arch + fedora,
`box/cachyos/charly.yml` for arch), and the two box repos in flight cover every gap. All 13
`cloud_image` VMs in this tree declare `distro:`.

**OpenRC is schema-valid and vocabulary-complete but not yet bed-proven.** No existing box
composes `service:` entries on an Alpine base, so nothing exercises the new init contract end
to end. It needs an Alpine box with a service and a bed; that is the next unit, and until it
runs, the entity's runtime behaviour is unverified.

### OpenRC's shipped template is now pinned by a test

`TestEmbeddedVocab_OpenRCIsAFirstClassInit` (in `charly/`, where the vocabulary is embedded)
asserts openrc declares the same management surface systemd and supervisord do, and then
**renders the shipped `service_template`** and checks the result is a valid OpenRC script:
`#!/sbin/openrc-run`, `supervise-daemon`, a `depend()` block, the authored exec, exported env —
and that it contains **no** systemd syntax (`[Unit]`, `ExecStart=`, `systemctl`), which is the
failure mode if the template were adapted from its neighbour.

This gap was real: the existing render tests in `candy/plugin-init` use LOCAL template
constants, so nothing exercised the templates this binary actually ships. It matters most for
OpenRC because OpenRC silently ignores a malformed or non-executable `/etc/init.d` file — it
presents as "service does not exist", not as a parse error.

Properties are asserted rather than a golden string, so a legitimate template edit does not have
to be re-baselined. Perturbation-checked: changing `command_args=` to `ExecStart=` fails with
`rendered openrc script contains systemd syntax "ExecStart="`.

### A "compatibility wrapper" that was test scaffolding mislabelled as production

`ociEmitStep` sat in `charly/oci_step_emit.go` described as "a Go-object-typed compatibility
wrapper existing unit tests drive directly". It has **zero production callers** — all ~8 are in
`_test.go` files.

The cost was not the function; it was that **three production comments described the production
chain as ending in it** (`build_overlay.go` twice, `tasks.go` once). Production actually runs
`HostBuild("step-emit","oci-emit-step")` → `stepEmitOCIEmitStep` → `dispatchOCIStep`. Reading
those comments is what makes a test helper look like a live path — and a "compatibility wrapper"
in production is exactly the shape a legacy sweep should stop on.

It moves to `charly/oci_step_emit_helper_test.go`, where its status is legible, and the three
comments now name `dispatchOCIStep`. Nothing about behaviour changes: it converted concrete
`spec.InstallStep`/`InstallPlan` values into the wire views the production caller already sends
and forwarded through the identical seam. Not deleted, because it is not a parallel
implementation (R3) — just no longer shelved among production code.

### What closedness does NOT catch, documented at the source

A fresh validator, reviewing `distro-fedora#19`, ran the mutation I had not: **`distro: debian` on
a Fedora cloud image validates cleanly, exit 0.** Closedness rejects a misspelled id
(`distro: redhat` fails on a CUE `_|_`) but cannot express "matches the image this URL points at",
and no gate in charly does. The value is a human check against the URL, every time.

`/charly-internals:vm-spec` now says so beside the trap it already documented, because the
misreading this field invites is treating a green `charly box validate` as proof the distro is
*correct* rather than merely *spelled like a real distro*.

**The projection of that edit is not in this commit, and the reason is the chain itself:**
`charly marketplace generate` and `task docs:sync` both hard-fail while the pinned copies of
`distro-arch` / `distro-fedora` lack `distro:` — the same failure blocking the test suite. So the
candy source carries the text and the `plugins`/`docs` pages catch up once those two land and the
pins bump.

Worth recording how that nearly went unnoticed: the first regeneration attempt produced **no
changed files**, which reads exactly like "already up to date". It was a skipped run — `generate`
had exited non-zero on a freshness check. Absence of output from a generator is not evidence it
had nothing to do; the exit code is.

### A cold image store silently skipped the tag alias, and `charly box pull` exited 0 anyway

`check-arch-vm` failed at `deploy-add` with podman's `ghcr.io/opencharly/arch-builder: image not
known` — roughly a thousand log lines after `build:ensure` had reported a successful local build.
The two facts that look contradictory are the whole bug: the build DID succeed, and it tagged
`ghcr.io/opencharly/arch-builder:2026.229.1423`; the requested **bare** ref was never created.

`ensureProjectRef` resolved the ref the build would produce BEFORE running the build, and every
resolver for it bottoms out in `ResolveShellImageRef` with an empty tag — which **reads the local
image store** (empty tag → `ResolveNewestLocalCalVer`). On a cold store there is nothing to read,
so it degraded to the bare `<registry>/<name>`: byte-identical to the requested ref. The alias
guard was `produced != image`, so it concluded no alias was needed and skipped silently — no
error, no warning, exit 0, and a ref that does not exist.

That ordering also explains why this was invisible: the failing run's own build seeded the store,
so every later run resolved the CalVer tag, short-circuited at `present`, and passed. The bug
reproduced only against a fresh store — the first-run path.

The fix inverts the order. `aliasBuiltImageOntoRequestedRef` takes the produced-ref resolve as a
**callback** so it cannot run before the build, and it checks the real post-condition — does the
requested ref resolve locally now — instead of comparing ref strings. A resolve that comes back
empty or equal to the request is now a hard error naming both refs, not a silent skip: the caller
runs with `--pull=never` and cannot proceed without that ref, so a warning would only relocate the
failure to a message naming neither the build nor the alias. The remote leg
(`ensureRemoteRef`) had no alias at all after its cached-source build and now shares the same
helper (R3).

#### Proof: A/B/A on three cold leaves

A throwaway one-layer box was used so nothing shared had to be removed to get a cold store — a
peer was active on the same host, and `charly clean`'s image pruning is machine-wide. Each run
requested the bare ref for a leaf with no local CalVer:

```
# with the fix
ensure-image: pulling ghcr.io/opencharly/coldleaf-probe3
ensure-image: pull ghcr.io/opencharly/coldleaf-probe3 failed: exit status 125
ensure-image: building coldleaf-probe3 locally
ensure-image: tagged ghcr.io/opencharly/coldleaf-probe3:2026.229.1456 as ghcr.io/opencharly/coldleaf-probe3
→ podman image exists ghcr.io/opencharly/coldleaf-probe3: PRESENT

# with the pre-fix semantics restored, on a fresh cold leaf
ensure-image: pulling ghcr.io/opencharly/coldleaf-probe2
ensure-image: pull ghcr.io/opencharly/coldleaf-probe2 failed: exit status 125
ensure-image: building coldleaf-probe2 locally
→ no "tagged" line, no warning, exit 0
→ podman image exists ghcr.io/opencharly/coldleaf-probe2: ABSENT
```

`candy/plugin-build/ensure_alias_test.go` pins it. The tests drive the produced-ref resolve
through a callback whose answer differs between the cold- and warm-store cases, because that is
the only way to exercise an ORDERING defect — a test passing the produced ref in as a plain
string cannot tell the two orders apart. Restoring the pre-fix silent skip fails exactly the two
rejection tests; `TestAliasBuiltImage_ShortNameNeedsNoAlias` is the presence control and passes
either way, so an implementation that rejected every input could not satisfy the suite.

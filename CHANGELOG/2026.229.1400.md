# 2026.229.1400 — OpenRC becomes a first-class init system; the distro guesswork is gone

Placeholder CalVer (the pr-validator finalizes it at merge). Chosen after `2026.229.1158`,
with no filename or tag collision.

## OpenRC, beside systemd and supervisord

`openrc:` is now an `init:` entity in the embedded vocabulary, a peer of `systemd:` and
`supervisord:` — same contract, same fields, no special-casing anywhere in Go.

Declared in the vocabulary rather than in code because that is the documented extension point:
`candy/plugin-pod`'s `wellKnownInitDefs` is a frozen legacy fallback for images built before
the `ai.opencharly.init_def` label existed, and its own comment says to declare new init
systems in the vocabulary instead — a vocabulary entry bakes its whole contract into that
label, so it resolves at runtime with **no Go change at all**.

What it declares: `model: file_copy` (each service is its own `/etc/init.d` script, like
systemd's units — not supervisord's single concatenated config), the install step (with the
`chmod 0755` that OpenRC silently requires — a non-executable file in `/etc/init.d` is the
classic "service does not exist"), `rc-update add … default` to enable, `rc-service` as the
management tool with `<service> <action>` ordering (the inverse of systemctl's, which is why
the action cannot be hardcoded around one tool), and a service template using
`supervisor=supervise-daemon` so OpenRC has the restart semantics systemd expresses with
`Restart=` — the default start-stop-daemon path starts a service and forgets it.

Before this, the only OpenRC support anywhere was a hardcoded `if distro == "alpine"` in the
cloud-init renderer that enabled sshd in a *guest*; a container box on an Alpine base could
not declare `service:` entries at all.

## The distro guesswork is deleted

See the spec and sdk entries for this CalVer. In this repo:

- **Presence is enforced in the kind's own plugin.** `candy/plugin-substrate/validate_vm.go`'s
  vm `OpValidate` capability now requires `source.distro` on the distro-bearing source arms
  (`cloud_image`, `bootstrap`) and rejects an id outside the generated vocabulary. That is
  where this repo already documents concreteness as belonging: the host's value gate is
  closedness-only **by design**, and a kernel-side branch encoding which fields a kind needs
  was overruled by the boundary law once already. The check mirrors the PCI-hostdev one
  beside it — the same "Go distinguishes absent from empty where non-concrete CUE cannot"
  shape. Presence controls included: the `bootc` and `disk` arms carry no distro and must not
  be asked for one.
- Every `cloud_image` source in this repo and its box submodules states `distro:` explicitly.

## What is NOT proven yet, and what blocks it

**The root `charly` test suite has 4 failures, and every one is the same external cause:** the
pinned remote copies of `opencharly/distro-arch` (at `v2026.200.2132` and `v2026.204.1300`)
and `opencharly/distro-fedora` (at `v2026.216.0232`) carry `cloud_image` sources without
`distro:`, so loading them now fails validation. Those repos are the `box/arch` and
`box/fedora` submodules; both carry the fix in this tree and are committed here, but a pin can
only move to a tag that exists. The order is producer-before-consumer: those two land and are
tagged, then the `@github` pins in `charly.yml` and `box/cachyos/charly.yml` bump, and the
suite goes green.

This is stated rather than worked around. The alternative — a migration that fills the field
by inferring it from the image URL — was written and deleted: it is the same guess in a new
location, and the point of this cutover is that nothing infers a distro from anything.

**OpenRC is schema-valid and vocabulary-complete but not yet bed-proven.** No existing box
composes `service:` entries on an Alpine base, so nothing exercises the new init contract end
to end. It needs an Alpine box with a service and a bed; that is the next unit, and until it
runs, the entity's runtime behaviour is unverified.

## OpenRC's shipped template is now pinned by a test

`TestEmbeddedVocab_OpenRCIsAFirstClassInit` (in `charly/`, where the vocabulary is embedded)
asserts openrc declares the same management surface systemd and supervisord do, and then
**renders the shipped `service_template`** and checks the result is a valid OpenRC script:
`#!/sbin/openrc-run`, `supervise-daemon`, a `depend()` block, the authored exec, exported env —
and that it contains **no** systemd syntax (`[Unit]`, `ExecStart=`, `systemctl`), which is the
failure mode if the template were adapted from its neighbour.

This gap was real: the existing render tests in `candy/plugin-init` use LOCAL template
constants, so nothing exercised the templates this binary actually ships. It matters most for
OpenRC because OpenRC silently ignores a malformed or non-executable `/etc/init.d` file — it
presents as "service does not exist", not as a parse error.

Properties are asserted rather than a golden string, so a legitimate template edit does not have
to be re-baselined. Perturbation-checked: changing `command_args=` to `ExecStart=` fails with
`rendered openrc script contains systemd syntax "ExecStart="`.

## A "compatibility wrapper" that was test scaffolding mislabelled as production

`ociEmitStep` sat in `charly/oci_step_emit.go` described as "a Go-object-typed compatibility
wrapper existing unit tests drive directly". It has **zero production callers** — all ~8 are in
`_test.go` files.

The cost was not the function; it was that **three production comments described the production
chain as ending in it** (`build_overlay.go` twice, `tasks.go` once). Production actually runs
`HostBuild("step-emit","oci-emit-step")` → `stepEmitOCIEmitStep` → `dispatchOCIStep`. Reading
those comments is what makes a test helper look like a live path — and a "compatibility wrapper"
in production is exactly the shape a legacy sweep should stop on.

It moves to `charly/oci_step_emit_helper_test.go`, where its status is legible, and the three
comments now name `dispatchOCIStep`. Nothing about behaviour changes: it converted concrete
`spec.InstallStep`/`InstallPlan` values into the wire views the production caller already sends
and forwarded through the identical seam. Not deleted, because it is not a parallel
implementation (R3) — just no longer shelved among production code.

## What closedness does NOT catch, documented at the source

A fresh validator, reviewing `distro-fedora#19`, ran the mutation I had not: **`distro: debian` on
a Fedora cloud image validates cleanly, exit 0.** Closedness rejects a misspelled id
(`distro: redhat` fails on a CUE `_|_`) but cannot express "matches the image this URL points at",
and no gate in charly does. The value is a human check against the URL, every time.

`/charly-internals:vm-spec` now says so beside the trap it already documented, because the
misreading this field invites is treating a green `charly box validate` as proof the distro is
*correct* rather than merely *spelled like a real distro*.

**The projection of that edit is not in this commit, and the reason is the chain itself:**
`charly marketplace generate` and `task docs:sync` both hard-fail while the pinned copies of
`distro-arch` / `distro-fedora` lack `distro:` — the same failure blocking the test suite. So the
candy source carries the text and the `plugins`/`docs` pages catch up once those two land and the
pins bump.

Worth recording how that nearly went unnoticed: the first regeneration attempt produced **no
changed files**, which reads exactly like "already up to date". It was a skipped run — `generate`
had exited non-zero on a freshness check. Absence of output from a generator is not evidence it
had nothing to do; the exit code is.

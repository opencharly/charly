# 2026.230.0717 — the generate-packages shim, and two north-star claims that did not survive measurement

Closes the last open unit of the nFPM packaging cutover: the superproject's declaration of
the out-of-tree `charly generate-packages` command plugin. Phase 3's own deliverables were
already on `main`; this is the remainder.

## The shim

`candy/generate-packages/` — a thin re-export module (charly.yml + `cmd/serve` + go.mod +
go.sum) whose only Go content hands the external module's provider to `sdk.Main`. It pins
`github.com/opencharly/plugin-generate-packages/candy/generate-packages v0.2026230.708`,
the Go-module tag minted by `opencharly/plugin-generate-packages#3` (merged `38565a61`).

Declaring it is what makes the verb resolvable from a charly CHECKOUT: the prescan walks the
project's `discover:` paths, finds `plugin.providers`, and registers the word; the host then
builds this directory through its OWN go.mod — `source:` is identity metadata, never a fetch.

## Two north-star claims, corrected by measurement

`PROGRAM/nfpm-packaging-north-star.md` recorded a diagnosis that was actionable and wrong.
Both corrections are measured, not argued:

1. **The Go-module tag must be SUBDIRECTORY-PREFIXED.** The module lives at
   `candy/generate-packages/`, so Go resolves versions from
   `candy/generate-packages/v0.<YYYYDDD>.<HHMM>`. The prescribed bare root tag "mirroring
   sdk's scheme" would never have been consulted — sdk is a repo-ROOT module, which is why
   the bare form works there. Go names the ref itself:

   ```
   $ go list -m .../candy/generate-packages@v0.2026227.1233
   go: invalid version: unknown revision candy/generate-packages/v0.2026227.1233
   ```

   Confirmed end-to-end: the shim now resolves and builds against the real tag
   `v0.2026230.708`, which only works because the tag carries the subdirectory prefix.

2. **The shim was never blocked on that tag.** The module already resolved via
   pseudo-version (`@latest` -> `v0.0.0-20260815123931-cf852b9ad3b6`), so the recorded claim
   that a missing tag makes the word "appear in the grammar then fail at dispatch" did not
   hold. The tag supplies release identity, not resolvability — a smaller claim than the one
   on record.

## Two environment traps that make a test lie, codified

Both cost real time here and neither is visible as a code defect. Added to
`/charly-internals:go` "Environment constraints":

- **A long `TMPDIR` breaks go-plugin tests, intermittently near the limit.** go-plugin serves
  each plugin over a UNIX socket at `$TMPDIR/plugin<random digits>`, and `sun_path` caps the
  whole path at 107 bytes — leaving `$TMPDIR` a little under 90. Over budget, `bind` returns
  `invalid argument` and the loader reports `Unrecognized remote plugin message`, blaming
  architecture, libraries, or permissions — none of which is the cause.

  The digit count varies, so the boundary is fuzzy and a path near it fails intermittently:
  the same directory passes, then fails, unchanged. Measured across six runs per length: 79
  and 90 always pass, 93 always fails, 91–92 give both. That intermittency is the operationally
  important half — it is what makes the failure read as a flake.

  This interacts with the existing `GOTMPDIR=~/.cache/go-tmp` advice: a deep per-session
  scratch path satisfies the quota rule and violates this one. They are separate variables —
  `GOTMPDIR` may stay long, since Go's build work needs no socket.

- **`CHARLY_PLUGIN_DIR` prepends; it never replaces.** `bakedPluginDirs()` returns it when set
  and then ALWAYS appends the FHS path, so pointing it at an empty directory masks nothing.

  **The masking is per WORD, not per machine.** `resolveCommandPluginBinary` returns on a baked
  hit before the project loads, so a BAKED word resolves to the baked binary and its project
  declaration is never consulted — while an unbaked word falls through to the project scan
  normally. `charly examplecommand hello world` prints `hello world` from the project candy
  even where the charly package is installed, because `examplecommand` is not baked.

  So the testing consequence is narrow: for a word that IS baked, `charly <word> --help` cannot
  distinguish "my project declares this" from "the installed package provides it". A mount
  namespace settles it — `bwrap --dev-bind / / --tmpfs /usr/lib/charly/plugins ./bin/charly
  <word>`, run with and without the project candy. That instrument is a workaround for a real
  product gap: `CHARLY_PLUGIN_DIR` can only prepend, so charly offers no supported way to
  resolve as-if-unpackaged.

  The code comments asserting the env var was "a true override" are corrected at both sites in
  `charly/plugin_loader.go`.

## Coverage

`charly/generate_packages_shim_test.go` — three assertions, each keyed to a way the shim
rots silently, and each proven to discriminate by perturbation:

| perturbation | failing assertions |
|---|---|
| control (unperturbed) | 0 |
| shim absent | 3 |
| provider word drifted | 1 |
| re-export import removed | 1 |
| go.mod require dropped | 1 |

The import assertion reads parsed IMPORT SPECS rather than file text. The first version used
`strings.Contains` and did **not** fail when the import was deleted — the module path also
appears in the file's own doc comment. That version was a guard that could not fail; the
perturbation table is what caught it.

commits already landed on `plugins/main` — their charly-side source sits in the unmerged
`charly#289` / `charly#297`. Measured: a one-section source edit produced a 21-file

edit lands here; the projection follows once those legs merge, and is owned by them rather

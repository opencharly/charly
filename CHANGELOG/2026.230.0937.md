# 2026.230.0937 — two verification gaps closed

Both were found while landing the generate-packages shim and its prose sweep, disclosed there,
and left unfixed. Neither is fixed by being written down.

## `CHARLY_PLUGIN_ONLY=1` — resolve as-if-unpackaged

`bakedPluginDirs` is a SEARCH PATH, and `resolveCommandPluginBinary` returns on the first baked
hit **before the project is loaded at all**. So on a host with the charly package installed, a
word baked into `/usr/lib/charly/plugins` masks the project's own declaration of that word:
`charly <word> --help` cannot tell "my project declares this" from "the installed package
provides it", and a regression in the project path is invisible.

`CHARLY_PLUGIN_DIR` cannot express this — it PREPENDS, so the FHS path stays on the search
whatever it is set to. The only previous way to observe the project path was to mask the
directory with a mount namespace (`bwrap --dev-bind / / --tmpfs /usr/lib/charly/plugins`), which
needs a host tool, cannot run in a unit test, and is a workaround for a missing capability.

`CHARLY_PLUGIN_ONLY=1` drops the FHS path, making the search exactly `$CHARLY_PLUGIN_DIR` (or
empty when unset). Measured, on this host, with the package installed:

```
charly generate-packages                       -> the plugin's own Kong flags   (baked hit)
CHARLY_PLUGIN_ONLY=1 charly generate-packages  -> the plugin's own Kong flags   (project path)
CHARLY_PLUGIN_ONLY=1, shim candy REMOVED       -> charly: error: unexpected argument
```

The third row is the discriminator: without the flag, removing the shim still resolves via the
baked plugin, so only the flag makes the project path observable.

**The FHS path is still appended by default, deliberately** — a deployed image's in-container
charly must find what the package baked there. And the flag is an EXACT `"1"` match: `true`,
`yes`, ` 1` and `01` all leave the FHS path in place, so a typo fails closed rather than
silently hiding a container's own plugins.

## The claim this change falsified, swept

`charly/plugin_loader.go`'s `bakedPluginDir` comment said *"bakedPluginDirs always appends this
FHS path, so setting the env var cannot HIDE a plugin baked here. Masking a baked word for a test
needs an environment without the file, not an env var."* That wording landed with the shim
cutover, correcting an earlier "true override" claim — and this change makes both halves false
thirty lines below it, in a file it already edits. The new test file masks a baked word for a
test **using an env var**.

Swept with it: `/charly-internals:go` carried the same two claims plus a published
`bwrap --tmpfs` recipe as the way to exercise a baked word's project declaration. The recipe is
now `CHARLY_PLUGIN_ONLY=1 ./bin/charly <word>` — no host tool, and it runs in a unit test.

The keys that would have caught this are not provenance keys; they are **the claims the diff
invalidates**. Nothing in the sweep method looks for those, which is the same gap that produced
two findings on the prose-sweep cutover.

## `ci.yml` — the repo now runs its own tests

`release-binary.yml` was the only workflow. It builds the binary and asserts `charly version`,
so a compile break is caught and **a failing test is not**. Nothing ran `go test`, so a red suite
on `main` would sit unnoticed until someone happened to run it locally — and local runs are
where environment noise lives: a long `$TMPDIR` breaks every go-plugin test with a misleading
handshake error, and uninitialized submodules break the fixture tests. Both cost real
investigation time here, and both produced a false "main is red" reading.

The job checks out submodules recursively, pins a short `TMPDIR` (`sun_path` caps the plugin
socket path at 107 bytes), runs `go test ./charly/...`, and fails on `gofmt -l`.

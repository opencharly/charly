# 2026.231.0110 — `charly box load`: image delivery into a pod's nested store (Factory unit 5)


## Why

A Factory incident spike is one disposable candybox running its own containers, and that
only holds if the spike's controller uses the pod's OWN podman rather than the host's —
bind the host socket in and every spawned Worker lands in the host store, beside PROD's
containers, with no boundary left to license the spike's autonomy. Images therefore have
to reach the NESTED store. A registry hop cannot do it (the spawn images are private), so
delivery is local — and charly had no verb for it. The only path was a hand-run
`podman save | podman --remote --url … load` pipeline: a manual container-engine command
against a charly-managed deploy, which R4 forbids outright. The missing capability was
the bug.

## What landed

**`charly box load <target> <image> [--as] [--socket] [--instance]`** — the container-venue
twin of `charly vm cp-box`, in `candy/plugin-box`. It resolves the running container the
way `charly shell`/`charly cp` do, and streams the image through the venue's own podman
API socket.

**`candy/nested-podman-socket`** — the prerequisite, and the mechanism unit 1 lost. The
containment spike proved a controller running on a nested socket, but its bed was
throwaway and the mechanism went with it: `podman system service` appeared nowhere in the
tree afterwards, so the finding was unreproducible. It is now a candy: a supervisord
`exec:` entry running `podman system service` at uid 1000, plus the `/run/user/1000`
named volume it needs. Deliberately separate from `container-nesting` — nesting supplies
podman, this supplies its API endpoint, and the nine boxes composing nesting do not want
a podman service.

**One delivery path instead of four (R3).** There were three copies of the `save | load`
pipe and a fourth was about to land. They are now one primitive and one orchestrator:

- `spec/container.StreamLoad` — the tarball-free pipe. `TransferImage` and
  `kit.TransferToRootful` are callers.
- `sdk/deploykit.TransferImageToVenue` — the venue-generic verified transfer: the
  idempotency skip that fires only on a VERIFIED-intact image, the torn-overlay probe,
  the drop-and-re-stream recovery, the post-load tag. Lifted out of the VM path, which
  was its only home. `vm cp-box` and `box load` are both bindings; a third venue costs a
  constructor.

Deleted with it: `streamLoadAndTag`, `podmanCmd`, `guestHasImage`, `guestImageCorrupt`,
`removeGuestImages`, the unused `osExecCommand` test seam, the now-dead `deployShellQuote`
alias, and `hostImageExists` (a duplicate of `container.LocalImageExists`).

## Defects found and fixed along the way

**`vm cp-box`'s short-name support never worked.** `candy/plugin-vm` shadowed the working
`container.ResolveNewestLocalCalVer` with a local stub returning `""`, so a bare box name
always fell through to "not found". Its comment justified this with "the plugin has no
direct store access", which is false — `spec/container` is importable from plugins. The
stub is deleted; both verbs now resolve through the STRICT `ResolveBuiltImageRef`, which
refuses to elect an image older than the newest local build. Delivering a stale artifact
is the wrong-artifact class `charly check box` refuses to certify, and it is harder to
notice here: the load succeeds and the venue simply runs the wrong image.

**`candy/plugin-box` declared a word that does not exist and omitted six that do.** The
`providers:` list carried `pkg` (long gone) and was missing
`pull`/`build`/`labels`/`merge`/`reconcile`/`feature`; the description and package doc
enumerated the same wrong set. Because the docs generator reads that list, six CLI
reference pages had never been generated at all — fixing it emits `build`, `labels`,
`load`, `merge`, `pull` and `reconcile`, and drops the stale `pkg` page.

**A candy example that cannot work.** `candy/charly-image` documented `security.mounts:`
where the schema field is `mount:` — copy it and `charly box validate` rejects it. Wrong
in the source and both projections; fixed at the source.

## Also: the CLI reference pages for a word served by two candies

Three defects on one page class, all of which passed every gate because the page existed
and the build was green.

- **The frontmatter `description:` named one owner of two.** It is also the search-result
  text, so it is read BEFORE the body — which contradicted it two lines down. Naming
  either owner alone is the same defect, so a fix that swapped which one it named would
  have looked like a cure while preserving it.
- **The fact table repeated `Served by` / `Placement` / `Version` per owner with no
  grouping.** Both `Placement` values may coincide, but the versions do not, so three of
  six rows could not be attributed to a candy at all. Now keyed by owner; single-owner
  pages keep the plain field names.
- **`podmanCmd(rootless)`** was named in `candy/charly-internals` as the helper that keeps
  the load, integrity probe and tag addressing one store. This cutover DELETES it; the
  field is `deploykit.ImageVenue.PodmanCmd`. A reader following the old name finds nothing.

The first two had NO test coverage — the emitter that silently overwrote a page (56
emitted, 55 written, exit 0) was never covered either. `gen_cli_test.go` now asserts all
three surfaces, and each was proved by perturbation rather than assumed: reverting the
description to `owners[0].Name` fails the multi-owner test, and reverting the fact table
to unkeyed field names fails it too. The single-owner case is asserted separately, so the
multi-owner cure cannot leak into the common page.

## Proof

`check-boxload-pod` — PASS, 13 steps. The two checks carrying the claim,
`boxload-deliver` and `boxload-present-in-nested-store`, pass on BOTH the initial and the
fresh-rebuild live legs (36 steps: 31 passed, 0 failed). The presence assertion queries
the NESTED socket rather than running `podman images` in the container, so it fails if the
image is ever delivered to the wrong store.

Coverage discriminates, proven by perturbation rather than asserted: removing `load` from
`boxCommandWords` makes the verb error with `unexpected argument load`, failing
`boxload-deliver`; unwiring the pipe in `StreamLoad` fails `TestStreamLoad_PipesPayload`.
The transfer path had no test coverage at all before this change.

## RDD

The throwaway spike proved the socket mechanism before any of the above was written, and
killed one candidate: a tmpfs at `/run/user/1000` is impossible, because podman's
`--tmpfs` rejects `uid=`/`gid=`. It also closed the open risk in the named-volume
approach by showing the build-time seed survives into the image. The spike is deleted; a
claim-keyed grep for its identifiers returns nothing.

## The projection window — structural, and it bit this cutover

`plugins` main carries prose in `internals/agents/pr-validator.md` and two `git-workflow`
references that `charly` main cannot reproduce. The candy entities ARE present in
`charly` main — they are simply SHORTER there, because the longer text is sourced from
`charly#289`, still unlanded. So `charly marketplace generate` run from `charly` main
TRUNCATES those three files, correctly, by 661 lines net. (An earlier draft said the
sources were "absent" and that regeneration "deletes" the prose; both overstated what was
measured — the distinction is truncation-from-a-shorter-source, not a missing source.)

This is **by construction, not a slip by anyone.** The ordering law is that a projection
merges before the source that pins it — a pin needs a merged target, and `docs/main` must
be a fixed point over landed inputs. The unavoidable consequence is a window in which
`plugins/main` carries prose `charly/main` cannot regenerate. It opens when the first
projection leg merges and closes when the source lands. (An earlier draft of this entry
called it "a leg that merged ahead of its source", which reads as a process failure and
sends a reader hunting a culprit who does not exist; corrected here.)

**The window is not singular.** The number of open windows equals the number of
superproject legs that have not landed — at least three concurrently while this cutover
was in flight, each invisible from inside the others. Nothing in `marketplace generate`
can detect it: it faithfully emits what the source it was given projects.

So the defence is procedural, and this cutover follows it: regenerate from your OWN source
tree, never from `charly/main`, and **scope the byte-identity assertion to the files your
PR touches**. Accordingly this cutover restored the three files above to exactly what
`plugins` main has, and changed nothing about them; a `marketplace drift` run flags them
until the owning leg lands, and that signal is the window, not a regression here.

One correction to an earlier draft of this entry, from the `plugins#189` validator and
against this cutover's interest:

- **This cutover does NOT close that window.** The prose in question is sourced from
  `charly#289`, a different leg — landing THIS one changes nothing about it. The earlier
  wording implied otherwise.
A third correction, to the rule as this entry first stated it: a clean whole-tree
assertion is NOT impossible while a window is open. Your OWN window is harmless —
regenerating from your own source reproduces exactly what you landed. Only a FOREIGN
leg's projection beneath you can be reverted, so the unscoped check stays available, and
strictly stronger, until another leg lands into your base.

**And a gate hole worth naming, because it is structural:** `marketplace drift` cannot
distinguish "the open window" from "someone hand-edited a projection" — the mandated
landing order guarantees it is red during every multi-repo landing, which is exactly when
it would matter.

## Also landed: `charly check stop <bed>`

Ruled BLOCKING for this cutover by the operator, so it ships here rather than batching.

There was no charly verb that stops a running bed. `charly check` offered
`box|live|feature|run|sync-credential|scope|last-tag|self-evaluate|list|report|note|list-agent`
and no `stop`. The only way to stop one was to kill the process, and the reachable form
of that is `pkill -x charly` — which matches `comm` exactly and is blind to cwd, session,
systemd scope and cgroup. On a host running more than one session it cannot stop your bed
without stopping everyone's, and today it terminated two unrelated R10 runs mid-flight.
The session that ran it verified `drivers: 0` and read that as local success, when it had
measured the whole machine.

R4 names the shape: a capability no charly verb expresses is a charly GAP, and the gap
manufactures the workaround.

`charly check stop <bed>` scopes by LOCK HOLDER. A bed run holds an flock on
`.check/<bed>/.lock` for its lifetime, so asking the kernel who holds that file
(`proc.PIDsHoldingPath`, spec) identifies this bed's runner and nothing else. SIGTERM
first so the runner's shutdown hooks run; SIGKILL only after `--grace` seconds, and only
against whoever is STILL holding — re-derived, never the original list, since an exited
PID can be reused. A bed with no run in flight is a success, not an error.

It deliberately does NOT tear down the bed's target: that would make "stop" silently
destructive, and the deploy is often the thing worth inspecting — the same reason a
FAILED bed leaves its target up. It names the scoped verbs instead.

Live proof, with third-party controls that make it meaningful — the host was concurrently
running another session's three bed runners:

```
before: 380586 fedora-repo | 380588 debian-repo | 380589 ubuntu-repo | 403509 boxload | 403510 check-pod
        charly check stop check-boxload-pod
after:  380586 fedora-repo | 380588 debian-repo | 380589 ubuntu-repo | 403510 check-pod
```

Exactly one process stopped — the lock holder. Four survived, three of them belonging to
another session. That is precisely the damage `pkill -x charly` caused.

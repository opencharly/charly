# 2026.231.0714 — chrome candy: skip google-chrome-stable's `%post` scriptlet on Fedora

The `google-chrome-stable` RPM's `%post` scriptlet runs `rpm --import` to install
Google's signing key while dnf still holds the transaction lock. The import fails
with `error: can't create transaction lock on /usr/lib/sysimage/rpm/.rpm.lock` and
`error: /tmp/google.sig.*: key N import failed.` — the package itself installs
correctly and the build completes and tags the image, but the error lines trip the
charly build gate (`errors_fatal: true`), failing every Fedora bed that composes the
chrome candy (`check-cross-pod-cdp`'s `image-build-chrome` step).

The fix is a one-line dnf option on the candy's `distro.fedora:` block:

```yaml
fedora:
    package:
        - vulkan-loader
        - mesa-dri-drivers
        - cups-libs
        - iproute
        - google-chrome-stable
    option:
        - "--setopt=tsflags=noscripts"
    repo:
        - name: google-chrome
          url: "https://dl.google.com/linux/chrome/rpm/stable/x86_64"
          gpgkey: "https://dl.google.com/linux/linux_signing_key.pub"
```

`tsflags=noscripts` skips the package's scriptlets during the transaction, so the
`%post` `rpm --import` never races dnf's lock. The key is still installed by the
`repo:` block's `gpgkey:` (dnf imports it at repo-add time, outside the transaction),
so package verification is unaffected.

Verified three ways:

- **RDD (podman, disposable):** a baseline `dnf install google-chrome-stable`
  reproduced the exact error lines; the same install with
  `--setopt=tsflags=noscripts` produced zero error lines, `Complete!`, and both
  `/usr/bin/google-chrome-stable` and `/usr/share/applications/google-chrome.desktop`
  present.
- **Schema:** `charly box validate` exits 0 with zero warnings — the `option:` field
  is the existing `#DistroPackages.option` schema surface, not a new field.
- **Emission:** the generated `chrome-headless` Containerfile renders
  `dnf install -y --setopt=tsflags=noscripts --enable-repo="google-chrome"`.

The authoritative R10 for this candy change is the consuming image's build — the
`check-cross-pod-cdp` bed in `box/fedora` — which runs against this tag once the
fedora submodule reconciles to it (B6 step 4).

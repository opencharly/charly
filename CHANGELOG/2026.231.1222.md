# 2026.231.1222 — bed diagnostics: exempt pip's resolver-conflict notice when the install completes

The bed-diagnostics gate (`candy/plugin-check/bed_diagnostics.go`) scans every step log
for `error:`/`warning:` lines and fails the step on any non-allowlisted error-tier line
(`errors_fatal: true`). pip's dependency resolver prints this notice when the environment
ALREADY carries packages that conflict with the install's requirements:

```
ERROR: pip's dependency resolver does not currently take into account all the packages
that are installed. This behaviour is the source of the following dependency conflicts.
```

…then installs anyway and exits 0. The notice is a description of the environment, not a
swallowed failure — but the `severity-prefix` recognizer matches the `ERROR:` prefix, so
every image build that runs pip against a pre-populated environment failed its step. This
surfaced live in `box/fedora`'s `check-jupyter-ml-pod` bed (2026.231.0749): vllm's pinned
requirements vs the pixi.toml loose pins produced the notice, the install completed
(`Successfully installed SecretStorage-3.5.0 … fastmcp-3.4.7 …`), the build tagged the
image — and the gate failed the step anyway.

## The fix

A conditional error-tier allowance `pip-resolver-conflict-recovered`, following the
`pacman-mirror-retrieval-recovered` precedent: the line is exempt ONLY when the same step
log proves the install completed (`Successfully installed …`). If pip never reports
success, the entry does not claim the line and the step still fails — the error tier keeps
its teeth.

The allowance's Match is anchored to the exact fixed pip sentence (never a broad shape),
and its RecoveredBy is pip's own success line for the same invocation. Because the notice
names no package, there is no token to tie the recovery to — so `allowanceRecovered` now
treats the `%s` subject-tie as OPTIONAL: an entry whose RecoveredBy carries `%s` keeps the
token-tied form (pacman), and one that omits it uses the recovery pattern as-is, still
conditional on the same step log proving the operation recovered. The step boundary is the
tie: a step log is one pip invocation.

## Verification

- **Unit:** `TestPipResolverConflictAllowanceIsConditional` drives the entry three ways —
  the notice + `Successfully installed …` is exempt; the notice alone is fatal; an
  unrelated `ERROR:` line is NOT discharged by a pip success. The existing
  `TestErrorTierEntriesAreConditional` / `TestConditionalErrorFailsWithoutRecovery` /
  `TestAllowlistEntriesAreWellFormed` all still pass, so the pacman entry's token-tied
  behavior is unchanged.
- **R10:** the authoritative gate is the consuming image's build — `check-jupyter-ml-pod`
  in `box/fedora`, the exact bed that failed at 2026.231.0749. The stale image +
  build-cache layers were purged (`charly clean --invalidate '*jupyter-ml*'` +
  `charly clean --deep`) so the fresh build reproduces the notice. Result:
  `[image-build] PASS after 8m40.729s [allowlisted=1 cache=27/279]`, summary reports
  `errors: 0, warnings: 0, allowlisted: 1` with `allowlisted: pip-resolver-conflict-recovered`,
  and the bed passed all 13 steps (exit 0).

# 2026.232.0001 — fix the org-wide auto-merge workflow

The `auto-merge` workflow (`.github/workflows/auto-merge.yml`, byte-identical across
all 14 opencharly repos) had never succeeded once. Four defects, each fatal:

1. **No `actions/checkout`.** The `workflow_run` trigger checks out nothing, but
   `gh pr merge` resolves the repository through a local git repo and runs
   `git status` against it — every merge died with
   `failed to run git: fatal: not a git repository`. (Observed live in run
   3235221669.)
2. **Tag computed from a future SHA.** The tag was derived with
   `git log -1 "$MS"` on the merge commit SHA, which does not exist in the local
   clone at tag time — the tag POST 422'd with an empty version.
3. **No wait for pending checks.** The gate exited 1 the moment any check was
   still `in_progress`, so a validator still running (or any other pending check)
   aborted the run instead of waiting.
4. **No CHANGELOG placeholder finalization.** The old evaluator model did the
   merge-time `git mv` + H1 rewrite of the author's placeholder
   `CHANGELOG/<calver>.md`; the workflow never carried that step, so the
   changelog filename/H1 and the release tag could disagree.

## The fix

- `actions/checkout@v7` with `fetch-depth: 0` so `gh pr merge` has a git repo.
- Tag version computed from the merge commit's committer date via the GitHub API
  (`gh api /repos/$REPO/commits/$MS --jq '.commit.committer.date'`), never from a
  local `git log` on a SHA the clone does not have.
- `wait_all_settled()` polls both check-runs and commit statuses until **every**
  check has completed (180 × 5s), then `verify_all_green()` accepts only
  `success`/`skipped`/`neutral` — the auto-merge runs only once ALL status checks
  are green, never on a still-pending or failed head.
- Rulebook merge-time CHANGELOG finalization (same-repo PRs only, best-effort):
  the placeholder is `git mv`'d to the merge stamp and its H1 rewritten, pushed,
  and the new head re-validated before the merge — so the changelog filename/H1
  and the release tag always agree. The rename is staged as `git add <new>` and
  committed without a pathspec so the deletion side of the `git mv` is not
  dropped.
- Idempotent tag creation via a shared `ensure_tag` helper (a tag that already
  exists is reported, never re-created) used by both the already-closed and
  post-merge paths so the two cannot drift.

## Additional fixes from the fresh-validator review

The fix PRs were independently reviewed by the `pr-validator` agent, which found
four more defects in the first fix draft:

1. **Commit-status `error` state accepted as green.** `verify_all_green()` only
   rejected `state == "failure"`, but GitHub's combined commit-status state can
   also be `"error"` — a red head could merge. The gate now rejects any state
   other than `"success"`.
2. **Re-entrancy.** The CHANGELOG-finalization push re-triggers the validator,
   which re-triggers this workflow; overlapping runs could rename the CHANGELOG
   repeatedly and one run could merge a head another run was still re-validating.
   A `concurrency:` group keyed on the PR head branch serializes runs for the
   same PR (a new run queues, never cancels), so only one auto-merge run is ever
   active per PR — the re-triggered run starts only after the active run has
   merged/closed the PR. Finalization is additionally narrowed to files the PR
   added (`A`-status in the diff), never a pre-existing or modified CHANGELOG
   file.
3. **Direct-squash fallback bypassed the atomic re-check.** The fallback merged
   without GitHub's branch-protection re-check, so a head that changed after the
   green verdict could land. The fallback is removed: enabling auto-merge is the
   only merge path, and a failure fails the run loudly with the PR left open.
4. **Duplicated tag-creation block.** The already-closed and post-merge paths
   each carried a copy of the tag logic; extracted into the shared `ensure_tag`
   helper above.

The workflow logic was proven against a stub `gh` before landing: all-green
merge+tag, pending-then-green wait, failed-check abort (exit 1, no merge),
already-closed idempotent tag, same-repo CHANGELOG finalize (rename commit with
the old placeholder deleted), merge-fail fallback, and placeholder-already-at-stamp
skip — each asserted on the observed behavior.

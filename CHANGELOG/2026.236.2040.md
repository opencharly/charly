# 2026.236.2040 — feat: unified pac install body (one body, both venues) + arch key FILE + spec#50 pins

## Summary

R3 cutover (spec#50 + sdk#165): the pac `phase.install` cell was TWO hand-maintained copies (host + container) that drifted — the host cell was bare `pacman -Syu ...` with no repo/key handling (`check-cachyos-vm` `target not found: charly`, the charly#401 bug class), and the keyserver-fingerprint key form failed inside the VM guest (`gpg: keyserver receive failed`). The rpm host cell had the identical drift (charly#396).

This change:
1. **ONE venue-agnostic `install` body** for pac (repo setup + key import + package install, `&& \` continuations valid in plain shell AND a Dockerfile RUN). `spec.FormatPhaseTemplate` applies the venue wrapper (`RUN {{cacheMounts}}` for container, verbatim for host). The host/container cells are DELETED (R5).
2. **Key FILE mechanism**: a repo `key:` that is an http(s) URL is a published key FILE (`charly.gpg`) — `curl` + `pacman-key --add` + lsign by extracted fingerprint (via `gpg --batch --show-keys --with-colons`), the deterministic keyserver-free mechanism deb/fedora/alpine already use. A bare fingerprint falls back to `pacman-key --recv-keys` (the `hasPrefix` branch, sdk#165).
3. The charly candy's arch repo entry points at the published `charly.gpg` (fingerprint 978DFF…) instead of the keyserver fingerprint.
4. `candy/plugin-distro`'s self-contained schema (`#DsPhaseTemplates`) gains the `install` cell to match spec#50; `cue:gen` regenerated the params.
5. New diagnostic allowance `pacman-hook-failed-mkinitcpio-recovered`: the guest-side pacman kernel-install hook wraps the allowlisted chroot autodetect failure and reports `error: command failed to execute correctly` — CONDITIONAL on `Initcpio image generation successful`, the same recovery as the mkinitcpio allowance.
6. spec pins bumped to v0.2026232.521-0.20260824192047-0c29ab15816d (spec#50) and sdk to v0.2026236.1958 (sdk#165) in charly + the three out-of-process plugin go.mods.

# 2026.237.1408 — feat: pluginsgen resolves the compiled-in module path from the plugin source: field (the plugin mechanism cutover, part 1)

## Summary

The plugin mechanism cutover, part 1 (the candy de-submodule cutover Phase 2): **`pluginsgen` now resolves each compiled-in plugin's Go module path from the candy's `plugin.source:` field** — the module path of record — falling back to `candy/<name>/go.mod` only when source is absent or `builtin`.

Why: the RDD bed (Phase 2a) proved charly builds with an out-of-tree compiled plugin at the standalone module path `github.com/opencharly/plugin-port/candy/plugin-port` — but pluginsgen today reads `candy/<name>/go.mod` unconditionally, which fails with `open ../candy/<name>/go.mod: no such file or directory` the moment a plugin candy moves to its standalone repo. `source:` is already the module path of record in 90/92 plugin candies; making pluginsgen source-driven means Phase 2c (the 93-repo move) only rewrites the `source:` fields, with zero pluginsgen change at move time.

**No behavior change in the current in-repo state** — the generated `plugins_generated.go` + `go.work` stay byte-identical for all 64 compiled plugins (the reproducibility gate proves it).

# 2026.240.1432 — fix(plugin): make an unresolved plugin word name its cause

## Summary

An unresolved plugin verb reported only the word:

```
no provider registered for plugin verb "wl"
```

**Four distinct situations reach that line and were indistinguishable:**

1. a project candy declares the word, but perf-scoping never loaded it,
2. the word is in a `.providers` manifest whose binary is missing,
3. the word is in no manifest on the search path,
4. the search path itself is empty (`$CHARLY_PLUGIN_ONLY=1`, no `$CHARLY_PLUGIN_DIR`).

Every fact needed to tell them apart is known at that moment and was thrown away: the search path
`bakedPluginDirs()` actually walked, the manifests found in each directory and the words they
declared, and whether a candy declaring the word was dropped by `pluginProvidesReferencedWord`'s
perf-scoping.

The message also **actively misled**. "No provider registered" reads as *the plugin is broken*, when
the usual cause is *charly never looked where the plugin is* or *charly decided not to load it* —
opposite problems with opposite fixes.

`explainUnresolvedPluginWord` now renders the search path in order with the `word -> binary` pairs
found in each directory, then names the cause and the fix. The perf-scoping skip records which candy
declared what (`recordScopedOutPlugin`), because that skip is **silent by design** — it is the
normal, correct case — and so was the one cause the old message hid most completely.

Before / after, both rendered from the real code:

```
no provider registered for plugin verb "wl"

  ── after ──
no provider registered for plugin verb "wl"
  searched (in order):
    /tmp/TestZZShowDiag2717103737/001  verb:cdp -> plugin-cdp
  cause: verb:wl is declared by no .providers manifest on that path, and no project candy
         declares it either.
  fix: for a host-built verb plugin, set $CHARLY_PLUGIN_DIR to a directory holding the provider
       binary beside a <binary>.providers manifest listing verb:wl

  ── and for the cause the old message hid completely ──
no provider registered for plugin verb "wl"
  cause: the project candy "plugin-wl" declares verb:wl, but it was not loaded — nothing in the
         resolved work referenced that word (perf-scoping).
  fix: reference the word from the plan being run, or add the candy to the bed's add_candy: so the
       check runner passes it as an extra candy ref
```

**No behaviour change.** An unresolved word is still `StatusFail`, which is correct: a bed asserting
a plugin verb that never registered must go red, never fake-green.

**Why this was worth fixing.** Diagnosing exactly this on a live bed cost an eight-step RCA and four
wrong hypotheses before a control experiment (publishing the *unmodified* upstream plugin, which
failed identically and so exonerated the change) isolated it. The control cost almost nothing and
should have been step one — the message is what made step one non-obvious.

## Placement

The diagnostic reads the loader's own search path and skip state, so it lives in `plugin_loader.go`
— already `KERNEL_MANIFEST.md`'s *"THE plugin-loading mechanism"* (clause M) — rather than as a new
kernel file. A new file would need its own manifest adjudication, and `TestKernelManifestBidirectional`
correctly blocked the first attempt at one; the fix was cohesion, not a manifest row.

Each case produces the **same string** without this change, so each fails on the old behaviour. The
second test is the one that pins the actual defect: it asserts the four causes do not render
identically — indistinguishability *is* the bug, so it is asserted directly rather than implied.
Cases also carry `deny` assertions, so a message that names the *wrong* cause fails too.

## Also in this change: four pre-existing lint issues

The commit gate lints the whole touched module, and `refs_sweep_test.go` carried three unchecked
`os.WriteFile`/`os.MkdirAll` returns plus a staticcheck `S1011` append-loop. They are untouched by
this work but block **any** commit to the module, so R2 puts them in this tree rather than a
follow-up.

The unchecked writes were not cosmetic: they build the fixture that *is* the test's precondition, so
a silently failed write would leave the walker an empty tree and pass the test for the wrong reason.
They now route through the package's existing `mustWrite` helper — reused, not re-declared (the
first attempt added a second copy and `typecheck` caught the collision).

## Not covered

- **Correction to an earlier revision of this body.** It claimed the command-word dispatch path
  "has the same four-causes-in-one shape" and deferred it as a "one-line follow-up". That was
  asserted, not checked, and it is **wrong** — so there is no batch to route it to, and nothing
  deferred.

  Checked: `connectBakedPlugin` has exactly two call sites (`provider_checkenv.go:77`, the verb
  dispatch this PR fixes, and `plugin_loader.go:558` inside `connectPluginByWordRef`). The
  command path resolves through `connectPluginByWordRef`, which returns a bare `(nil, false)` and
  emits **no message at all** — its callers own the error, and they already name the specific
  missing candy rather than a generic one:

  ```
  check_venue_resolve.go:33   "check-resolve: plugin-check (verb:check-resolve) not registered —
                               charly built without the plugin-check candy"
  host_build_pod_lifecycle_dispatch.go:103
                              "resource arbiter (verb:arbiter) not registered — charly built
                               without candy/plugin-preempt"
  deploy_target_dispatch.go:28
                              "command:fleet provider not loaded (candy/plugin-fleet must be
                               compiled in via compiled_plugins:)"
  ```

  So the command path has no single indistinguishable-message site to fix. Pushing the diagnostic
  into `connectPluginByWordRef` itself was considered and rejected: it is also called
  **speculatively**, where a miss is the normal, correct outcome, so emitting a cause there would
  print a diagnostic for non-failures.
- A related defect found while establishing the init behaviour for the bed fixture, **not** fixed
  here: when the resolved init's `depends_candy` is absent from a project's scanned set,
  `deploykit.InjectInitDependsCandy` correctly declines to inject but says nothing, so the build
  succeeds and stamps `init=supervisord` onto an image with no supervisord binary — failing only at
  `charly start`. Same "mechanism knows why it is declining and discards it" shape as this change.
  Tracked as batch **B9 — init `depends_candy` unsatisfiable is silent**.

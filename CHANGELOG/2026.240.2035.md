# 2026.240.2035 — test(vocab): the install_template guard moves to the repo that owns the files

## Summary

A guard that had stopped running gets relocated to the repo that owns the data it guards.

`candy/plugin-migrate` carried `TestEmbeddedVocabHasNoInstallTemplate` — the regression guard
for the `install_template` → `phase.install.container` cutover, asserting charly's embedded
build vocabulary carries no residual **format/builder-level** `install_template:`. It read
`../../charly/charly.yml`, a path that resolved only while that plugin was a directory
**inside this repo**.

## RCA

The de-submodule (`plugin-migrate` c1b8b56, *"remove the stray charly submodule; fetch charly at
CI time into a temp checkout"*) removed the submodule but did not repoint the test. That alone
would be a loud failure — except for the second half:

```
$ ls .github/workflows/          # in plugin-migrate
deploy.yml  pr-validator.yml  tag-on-merge.yml

$ grep -n 'go test' .github/workflows/*.yml
(no matches)
```

`deploy.yml` clones charly to `/tmp/charly` to build the **binary** and then runs
`charly box validate`. It never runs `go test`, so the module's own suite is not a CI gate
there — and the dangling guard was not failing, it was **never executing**. Confirmed by a
control on pristine `main`:

```
$ git clone --depth 1 …/plugin-migrate.git ; cd candy/plugin-migrate ; go test ./...
--- FAIL: TestEmbeddedVocabHasNoInstallTemplate (0.00s)
    read ../../charly/charly.yml: no such file or directory
```

A guard that cannot run is worse than no guard: it reads as coverage.

## Why here, and why shape-scoped

The guard needs **both** the reshaper (plugin-migrate) and the data (charly); neither repo had
both, which is what let it rot. Asserting the invariant **directly**, where the data lives,
needs neither the reshaper nor a cross-repo checkout — so it cannot rot the same way again.

The check walks the YAML shape rather than grepping, because `install_template:` also appears
legitimately at two unrelated paths:

```
$ grep -c install_template charly/charly.yml
12
```

All twelve are `format.<fmt>.local_pkg.install_template` or `distro.bootloader.install_template`
— different fields that were never part of the cutover. A text search would flag every one.

those, a finder that silently matched nothing would pass exactly as it does now.

## A second commit: the CI timeout this PR ran into

Adding a 0.4s test to `charly/charly` made the **package** exceed `go test`'s 10-minute default:

```
panic: test timed out after 10m0s
  running tests:
    TestCandyCutoverSweep_AllRemotePinsResolve (7m1s)
```

`main` is green at the exact commit this branched from, so the trigger really was this PR — but
the cause is not. `TestCandyCutoverSweep_AllRemotePinsResolve` resolves every unique
`@github.com/opencharly/...` pin in the tree through the canonical loader path. The candy
cutover left **226** of them, and it resolved them **sequentially**: on a cold CI cache that is
226 network round trips, 7m01s of the package's 10-minute budget. The package therefore ran
with essentially no headroom, and the next test added to it — of any size — would tip it.

A warm cache hides this completely (**0.04s** locally), which is why it surfaced as an unrelated
PR's CI failure rather than as that test's own.

Re-running and hoping is the R4-forbidden move, and raising the timeout only moves the ceiling.
The fix is to stop making 226 sequential round trips: deduplicate first, then resolve through a
bounded pool of 12 workers — enough to overlap network latency, not so many as to open 226
sockets at a remote we do not own.

Measured on a **genuinely cold** cache (`CHARLY_REPO_CACHE` pointed at an empty directory, so
the developer's real 2.3G cache was never touched):

```
$ env CHARLY_REPO_CACHE=/tmp/coldrepos go test . -run TestCandyCutoverSweep_AllRemotePinsResolve
ok      github.com/opencharly/charly/charly     31.575s
```

**31.6s, down from the 7m01s CI measured sequentially.** The assertions are unchanged: every pin
still resolves at its pinned tag through the same loader call, and failures are still collected
and reported together.

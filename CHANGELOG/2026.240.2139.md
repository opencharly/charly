# 2026.240.2139 — docs(skills): audit skill DELIVERY, not just content (the corpus can be valid and never load)

## Summary

`/charly-internals:skills` covered when and how to *write* skills, but never how
to check that the corpus actually *reaches* the agent. That gap hid a real
failure: `opencharly/opencharly` declared three plugins in `enabledPlugins` and
loaded **zero** of their skills, so every row of its R0 dispatcher pointed at
something no session could load (opencharly/opencharly#30).

Enablement and installation are separate halves of the harness contract.
`enabledPlugins` flips the first; skills load only when the harness *also* holds
an install record scoped to the current project. The umbrella's records were
bound to a different project, with `installPath`s that no longer existed — and
the marketplace, the manifest, and every `SKILL.md` frontmatter were valid the
whole time. Nothing in the corpus was wrong; it simply never arrived.

`claude plugin list` makes the failure worse rather than surfacing it: it reads
enablement from `settings.json` and prints `Status: ✔ enabled` regardless of
whether the install record resolves, so the obvious diagnostic *confirms* a
corpus that is not loading.

Added a section to the `skills` skill giving:

- the failure mode, stated so it is recognisable before it costs a session;
- the only probe that is real evidence — a fresh session's own answer;
- the fix that writes both halves (`claude plugin install … --scope project`),
  and why hand-editing the settings JSON reproduces the same half-state;
- the warning that this **presents as a badly written dispatcher row**, so the
  tempting fix is to rewrite the row and leave the real defect in place;
- a scoping note: enabling image/pod plugins in a repo that runs no boxes also
  drags in their pod-provided MCP servers, which then log connection failures
  for boxes never meant to be running there.

Source-only change to `candy/charly-internals/charly.yml`. The corresponding
corpus artifact (`internals/skills/skills/SKILL.md`) regenerates in
`opencharly/marketplace` once this merges and charly tags — see Follow-up.

## Rulebook compliance

- **R1 — RCA every anomaly.** The section exists *because* an anomaly was
  root-caused rather than worked around; the operational insight is fed back
  into the skill that owns skill maintenance, which is what R1 asks for.
- **R3 — No duplication.** The knowledge lands in exactly one skill — `skills`,
  whose stated remit is "feeding back operational insights, or auditing skill
  coverage". No other skill documents plugin loading, so nothing is forked.
- **R4 — No workarounds.** Documents the fix that writes both halves of the
  contract and explicitly rules out hand-editing the settings JSON.
- **R5 — Delete legacy completely.** Pure addition; no superseded guidance left
  behind, and no stale wording elsewhere describes plugin loading.
- **R6 — Git safety.** `gh pr list` preflight across every affected repo before
  branching; a dirty sibling checkout on another contributor's branch was left
  untouched and a fresh clone used instead. `fix/` branch, no force-push, no
  hook bypass, no direct push to `main`.
- **R7 / R10 — Prove the gate, not the plan.** `task skills:drift` pasted above,
  run on the final committed tree, with the generated artifact inspected rather
  than assumed.
- **SDD.** Source-of-truth edit in the candy's `skill:` entity; the generated
  `SKILL.md` is a projection and was never hand-edited — the `DO NOT EDIT`
  banner on the artifact is respected.

# 2026.241.0018 — build: pick up the plugin-box bake_plugin dedupe fix

## Summary

Picks up `opencharly/plugin-box#3`, which made the `bake_plugin` dedupe **symmetric**.

`validateRemoteCandies` compares every remote candy against every other, so it visits a clashing
pair twice — `(A,B)` and `(B,A)` — but the bake relationship is one-directional: only the
**baking** repo holds the sibling carrying the ref. Testing one direction let the mirrored visit
through, so every baked plugin reported the identical conflict twice, in opposite orders.

Bumps the compiled `plugin-box` module to `v0.2026241.5`.

## How tested

```
$ go test . -count=1
ok  github.com/opencharly/charly/charly  78.656s

$ golangci-lint run
0 issues.
```

**The fix is verified present in the built binary, not merely in `go.mod`** — `plugin-box` is a
`compiled_plugins:` entry, so a stale build would silently keep the old rule:

```
$ strings bin/charly | grep -c reportRemoteNameConflicts
2
```

That is the function the fix extracted; it is absent from the previous build.

## Honest scope: this does NOT yet clear the conflicts downstream

Measured on `distro-cachyos` with this binary, the four `plugin-mcp`/`plugin-record` conflicts
**still report**. So the symmetric dedupe is necessary but not sufficient here, and I am not
claiming otherwise.

The likely reason, offered as a hypothesis rather than a finding: the dedupe needs the *baking
sibling* (`charly/candy/charly-mcp`, which carries the `bake_plugin:` ref) to be present in the
scanned candy set. In that project `charly` itself does not resolve —

```
candy "charly-marketplace" candy: unknown candy "github.com/opencharly/charly"
```

— because `candy/charly-marketplace` references the charly **repo root** (`@github.com/opencharly/
charly:vTAG`) rather than a candy inside it. If charly's candies only partially load, the phantom
`plugin-mcp` provider appears without the sibling that would dedupe it. Both the marketplace's
canonical copy of that candy and `distro-cachyos`'s use the same repo-root form, so this is a
question about that candy's intended shape, not a local mistake — which is why I have not changed
it here.

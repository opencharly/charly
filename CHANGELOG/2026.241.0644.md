# 2026.241.0644 — fix(refs): charly box validate exits 0 — advance stale pins, repoint bare-name candies

## Summary

**`charly box validate` exits 0 on this branch. On `origin/main` it reports 33 errors.**

This supersedes #436, which was closed with the right objection: that PR advanced four pin
bumps while **parking** 18 remaining `remote candy name conflict` errors, and B14(b)/B5 do not
allow parking a surviving error class. This branch **fixes that class** rather than parking it —
there are no surviving validation errors left to defer. Nothing here is routed to a batch.

That gate blocks more than itself: `charly box build` validates the **whole project** before
building any box, so every one of those errors aborts **every bed run in this repo**. Concretely,
`check-dsh-pod` died during image-build without ever reaching the dsh box:

```

                 box "check-k8s-deploy-app": candy resolution error: unknown candy "check-keepalive"
                 box "agentteams-worker": candy resolution error: unknown candy "agentteams-openclaw"
                 box "agentteams-manager": candy resolution error: unknown candy "agentteams-openclaw"
charly subcommand exited 1
```

With validation clean, charly's R10 beds are runnable again.

## Three groups of stale refs

**1. Four pod pins predating their own repointing** — their bare-name deps resolve to nothing:

```
pod-agentteams-manager  depends: agentteams-cli, agentteams-openclaw
pod-agentteams-worker   depends: agentteams-cli, agentteams-openclaw
pod-github-runner       depends: container-nesting
pod-versatiles-frontend depends: versatiles-style, versatiles-fonts, maplibre-versatiles-styler
```

**2. The five distro imports, pinned at v2026.226–229 tags.** This is the root of all 16
`remote candy name conflict` errors. Those tags predate the candy cutover, and fetching one
materialises its **own nested `box/*` submodules**, which reference charly at `v2026.201.0706` and
`v2026.227.0914` — trees that still carry `candy/plugin-cdp`, `plugin-dbus`, `plugin-mcp`,
`plugin-record`, `plugin-wl`, `plugin-vnc` and `plugin-example-*` **inline**. Those inline candies
then collide with the standalone repos of the same names.

I found this by instrumenting the conflict rule to print the provider's source directory, after
two cheaper hypotheses failed:

```
DBGC key="…/charly/candy/plugin-cdp"  src="…/repos/…/charly@v2026.201.0706/candy/plugin-cdp"
DBGC key="…/charly/candy/plugin-dbus" src="…/repos/…/charly@v2026.227.0914/candy/plugin-dbus"
```

**Advancing charly's own `box/*` gitlinks changed nothing** — measured, 18 → 18. The old distro
trees arrive through the `@github` **import** refs, not through the submodule checkouts. That
measurement is why this PR moves the imports and leaves the gitlinks alone.

**3. Five candies still referenced by bare name** after being de-submoduled, so they resolved to
nothing: `check-keepalive`, `check-group-layer`, `check-structkind-layer`,
`check-substrate-layer`, `check-builder-npm` — each repointed at its standalone repo.

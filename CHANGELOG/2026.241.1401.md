# 2026.241.1401 — feat: fold charly-dev into the project manifest and drop the binary sync

## Summary of changes

Phase D.3 of the candy de-submodule cutover: `charly-dev` moves out of `candy/charly-dev/` into
the project manifest, and the hand-maintained second copy of the charly binary goes with it.

**`charly-dev` cannot become a standalone repo, and its own description already said so:** its
`copy: bin/charly` step reads a locally built, **gitignored** binary, so a remote fetch "would have
no binary to copy and is not a valid use". It is inherently checkout-bound.

But it does not need a candy **directory** either. A candy takes its **declaring file's** directory
as `SourceDir` (`loader_threaded.go:395`), so declaring it in `charly.yml` resolves
`copy: bin/charly` against the **repo root** — exactly where `task build:binary` already writes the
binary.

### What that makes redundant

`candy/charly-dev/` held three things: the manifest (moved), a `.gitignore`, and **a second copy of
the charly binary** that existed only so a candy-dir-relative path could find it.
`taskfiles/Build.yml` maintained that copy by hand after every build:

```diff
-      # …so the sync target is candy/charly-dev/bin.
-      - cp bin/charly candy/charly-dev/bin/charly
```

One binary, one path, no sync step to forget. This is the R3 case in its most literal form: two
copies of the same artifact, kept in step by hand.

### A finding worth recording: the corpus has a THIRD input path

While verifying the skill fix I regenerated the corpus and found it **unchanged**, despite my edit
being present in `candy/charly/charly.yml`. Chasing that down produced something bigger than a
mis-attribution.

First I assumed `layer-charly` was the source and overrode it to a local checkout carrying the fix.
The corpus still did not move. So I isolated the two input paths directly — regenerate with
`candy/charly` **removed** from `--root` entirely:

```
$ rm -rf <root>/candy/charly
$ charly marketplace generate --root <root> --out <tmp>
$ ls <tmp>/tools/skills/charly/SKILL.md
… exists, and still carries "Two independent paths need to stay in sync"
```

The skill survives without `candy/charly`, so it is generated from the **refs closure** — and the
cache says where from: **22 repos in the closure, pinned at tags, each vendor a whole charly
checkout** containing `candy/charly/charly.yml`:

```
$ ls -d ~/.cache/charly/repos/github.com/opencharly/*@v*/charly/candy/charly | wc -l
22
   layer-agentteams@v2026.238.2102      layer-android-sdk@v2026.238.2102
   layer-asciinema@v2026.238.2226       layer-language-runtimes@v2026.238.2140   …
```

That is a **third input path**, and a worse one than the one this cutover set out to remove. The
known problem was a single hand-written CI pin that could freeze skill content. This is ~22
independent charly checkouts, each frozen at whatever ref its submodule points at (day 238 and
older), any of which can supply a skill to the published corpus.

**Consequences, stated plainly:**

- This PR's edit to `candy/charly/charly.yml` is correct for the in-repo file but **does not reach
  users**. I am not claiming otherwise.
- Deleting `candy/charly` later will **not** move the corpus — which de-risks that step, but only
  because the content is coming from somewhere worse.
- Phase C's `--refs`-only generation would **not** fix this: the vendored checkouts are inside the
  refs closure, not behind `--root`.

The real fix is for the generator to refuse to descend into a vendored `charly/` checkout inside a
referenced repo. That is a generator change and belongs to the generator's repo, not to this
charly-side relocation, so it is **routed to a named batch, not parked**:

> **`opencharly/plugin-marketplace#7` — _batch: the corpus has a third input path — 22 refs-closure
> repos vendor a whole charly checkout_**

That issue carries the full evidence (the three isolation steps, the 22 pinned repos, and the
concrete consequence: the published `tools/skills/charly/SKILL.md` still instructs readers to `cp`
into a directory that no longer exists), plus the proposed fix and a gate that would fail generation
when two sources supply the same entity name at different content — which today is only an advisory
`Note: … shadows …`.

# 2026.241.1418 — feat: move the generate-packages shim out of candy/ into tools/

## Summary of changes

Phase D of the candy de-submodule cutover. `candy/generate-packages` is **not a deployable candy**:
it is a thin **re-export shim** (a `go.mod` plus a `cmd/serve` main) whose only job is to make
`charly generate-packages` resolvable from a **checkout**. It moves to `tools/`, where the rest of
charly's dev tooling lives, and `charly.yml`'s `discover:` gains `tools/` so the project
fall-through can still find it.

**`candy/` now holds only the `charly` meta-candy.**

## Why it is moved and not deleted

The plan proposed deleting the shim and teaching command-plugin resolution to fetch a **remote**
plugin ref instead. I probed that before writing any code, and it is the wrong trade.

**First, a remote ref does not register a command word at all:**

```
$ cat charly.yml                 # a project whose ONLY reference is the remote pin
  candy:
    - '@github.com/opencharly/plugin-generate-packages/candy/generate-packages:v2026.240.0203'

$ charly generate-packages --help
exit 80 — the generic `charly <command>` usage; the word is not in the grammar
```

**Second, making it register one means putting a network fetch in CLI startup.** The registration
happens in `prescanDeclaredPluginWords`, which runs on **every** charly invocation, *before* the CLI
grammar exists, and is deliberately local-only — its own contract says *"Best-effort: any I/O or
parse error on a single file is skipped, never fatal — a malformed candy must not break `charly
status` / `charly box validate` repo-wide."*

Trading a four-file shim for a network round-trip in CLI startup — with new latency, offline, and
failure-mode behaviour on every command — is not a simplification. The shim is the cheaper design,
and the plan's premise that it is cruft does not survive contact with what it costs to remove.

What the shim genuinely was, is **in the wrong directory**. That is what this PR fixes.

## Why `tools/` and not a new `plugins/`

Concrete, not aesthetic: **`tools/*/go.mod` is already in `lockstepModules`' glob and in
`mods:tidy`'s sweep**, so the shim keeps its contract-pin coverage across the move. A new directory
would have silently dropped it out of both — which is exactly the blind spot
`gomod_canonical_test.go`'s own comment records having been found broken three times:

> *"The glob is deliberately NOT `candy/plugin-*`: that shape misses `candy/generate-packages` … and
> all three were found broken by exactly that blind spot."*

Moving into a glob that already covers the file is how the move avoids repeating that.

### One observation I chased down and dismissed as my own artifact

The first post-move run printed `Downloading github.com/opencharly/plugin-substrate:main…` — a
**mutable** ref fetch, which would be a pin-discipline defect. It is not one:

- charly declares **zero** version-less `@github` refs
  (`grep -rhoE "@github\.com/opencharly/[^']+" --include='*.yml' . | grep -vE ':v[0-9]'` → 0);
- a pre-move `origin/main` worktree showed no such line — but it ran **second**, against the cache
  my run had just warmed;
- re-running my branch with the cache warm shows no download either.

Ordering artifact, not a behaviour change. Reported here because the raw output looks like a defect
and I would rather show the elimination than quietly drop the line.

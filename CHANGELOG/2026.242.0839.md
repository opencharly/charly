# 2026.242.0839 — fix(distro): pacman-key --init before the arch/cachyos bootstrap upgrade

## Summary

A **cold** arch-base image build emits two error lines that fail charly's own build-diagnostic gate. A **warm** build of the same tree passes. That difference is the whole bug: the failure is cache-dependent and time-triggered, so it lands on a fresh store (CI, a new machine, a wiped cache) and hides everywhere else.

```
==> ERROR: There is no secret key available to sign with.
==> Use 'pacman-key --init' to generate a default secret key.
error: command failed to execute correctly
```

**Cause.** The pristine `quay.io/archlinux/archlinux` base ships a populated keyring but **no local secret key**. Verified directly against the pinned base:

```
$ podman run --rm quay.io/archlinux/archlinux:base-20260719.0.558306 sh -c \
    'gpg --homedir /etc/pacman.d/gnupg --list-secret-keys; \
     pacman-key --init >/dev/null 2>&1; \
     gpg --homedir /etc/pacman.d/gnupg --list-secret-keys'
--- secret keys in the pristine base ---
gpg: WARNING: unsafe permissions on homedir '/etc/pacman.d/gnupg'
--- after pacman-key --init ---
sec   rsa4096 2026-08-30 [SC]
      A71C5A91D6A786B3FED4FC9ACC8A36AB86AEDE0D
uid           [ultimate] Pacman Keyring Master Key <pacman@localhost>
```

The list is empty before `--init` and holds the master key after. So once the pinned base tag ages far enough that the repos carry a newer `archlinux-keyring`, the bootstrap `-Syu` upgrades that package, and its post-transaction hook tries to sign with a local key that does not exist yet. This is why the bug appears on its own over time with no change to charly: it is a function of how stale the pinned base is relative to the repos.

pacman treats the refused hook as non-fatal, so the image still builds and is tagged — but the lines are real output, so `scanStepDiagnostics` fails the step.

**Fix the hook, do not allowlist its error.** `pacman-key --init` is idempotent and creates exactly the key the hook wants. This mirrors the existing cachyos bootstrap, which masks the `nvidia-ctk-cdi` hook with an empty override rather than tolerating its `error: command failed to execute correctly` line — same class of problem, same resolution. Allowlisting was the alternative and it is worse here: the second line is pacman's fully generic hook-failure line, so an entry claiming it would have to be conditional on something unrelated to it, and would mask real hook failures.

Applied to **both** bootstraps. `cachyos` sets `inherits: arch` but overrides `bootstrap:` wholesale rather than deep-merging (the block's own comment says so), so fixing arch alone would not reach it.

## How tested

Two cold builds of the same project from a **wiped** container store, one per binary. Store isolation via `CONTAINERS_STORAGE_CONF` with its own graphroot, wiped between runs, so both are genuinely cold — a warm store cannot reproduce this at all.

**Before** — `charly` at `origin/main`, cold store (`check-punktfunk-pod` image-build):

```
  'no secret key available' lines:         1
  'command failed to execute correctly':   1
  --- Building arch.arch ---
[image-build] FAIL after 3m17.966s: image-build exited 0 but its log carries
  2 error line(s); first at line 187: ==> ERROR: There is no secret key available to sign with.
```

Note `exited 0` — the build itself succeeded; only the diagnostic gate failed it.

**After** — this branch's binary, store wiped again, same project, same cold path:

```
  'no secret key available' lines:         0
  'command failed to execute correctly':   0
  arch stages built:                       2   (arch.arch, arch.arch-builder)
Successfully tagged ghcr.io/opencharly/punktfunk-host:2026.242.0823
```

The fix reaching the generated Containerfile:

```
$ grep -m1 -o 'pacman-key --init && pacman -Syu --noconfirm[^\\]*' coldfix.log
pacman-key --init && pacman -Syu --noconfirm curl ca-certificates && ...
```

Build of the binary under test:

```
$ task build:binary
task: [build:binary] mv bin/.charly.next bin/charly
exit=0
```

**The cachyos path, exercised in the same cold build.** The earlier note said only "arch stages built: 2", which under-reported the run: the cold build contains four stages, and `cachyos` is one of them.

```
$ grep -n 'Building ' coldfix.log
3:--- Building arch.arch ---
244:--- Building arch.arch-builder ---
1000:--- Building cachyos ---
1272:--- Building punktfunk-host ---
```

Inside the `cachyos` stage (starting line 1000), its own bootstrap RUN carries the change — this is the cachyos `install_cmd`, not the inherited arch one:

```
1007:[2/2] STEP 2/22: RUN --mount=type=cache,...,sharing=locked     pacman-key --init &&
  (grep -q '^DisableSandboxNetwork' /etc/pacman.conf || sed -i '/^\[options\]/a
  DisableSandboxNetwork' /etc/pacman.conf) && mkdir -p /etc/pacman.d/hooks &&
  : > /etc/pacman.d/hooks/nvidia-ctk-cdi.hook && pacman -Syu --noconfirm --needed
  curl ca-certificates && ...
```

The trigger condition is present in that stage — it does upgrade the keyring package, which is what makes the hook fire — and the errors are gone:

```
$ sed -n '1000,1271p' coldfix.log > cachyos-stage.log     # the cachyos stage only
  'no secret key':                        0
  'command failed to execute correctly':  0
  archlinux-keyring mentions in stage:    2
[2/2] COMMIT ghcr.io/opencharly/cachyos:2026.242.0823
Successfully tagged ghcr.io/opencharly/cachyos:2026.242.0823
```

So both changed branches executed live on a wiped store, each with the keyring upgrade actually occurring.

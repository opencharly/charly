# 2026.242.0913 — fix(provider): fail fast on a hung plugin-to-plugin call — bound the broker InvokeProvider

## Summary

The broker's `InvokeProvider` — the leg a plugin uses to call **another plugin** — ran with whatever context the caller passed back, and that context carries no deadline of its own. So a peer that never answers (the fleet-del teardown deadlock: a plugin waiting on a peer that is itself waiting) blocked the goroutine in `futex_wait` forever.

`invokeTyped` already bounds the **host→plugin** leg (#468). This adds the same guard to the **plugin→plugin** leg, reusing the same `defaultPluginInvokeTimeout` var rather than introducing a second timeout, and only when the caller supplied no deadline:

```go
if _, ok := ctx.Deadline(); !ok {
    var cancel context.CancelFunc
    ctx, cancel = context.WithTimeout(ctx, defaultPluginInvokeTimeout)
    defer cancel()
}
```

**Correction to the previous body.** It credited the live stall's root cause to `sdk#190`. That PR is now **closed**, superseded by `opencharly/sdk#191` (same fix, corrected commit message). This PR does not depend on either: the two bound different calls — sdk bounds the *engine command* `RemoveImagesByReference` runs, this bounds the *broker invoke*. Both were unbounded; neither subsumes the other.

# 2026.242.1114 — ci: run golangci-lint, matching the local pre-commit gate

## Summary

First instance of the `go-ci-lint-parity` batch (opencharly/charly#464).

No opencharly repo runs `golangci-lint` in CI. The only enforcement is `.claude/hooks/pre-commit-gate.sh`, which runs it **locally** at commit time — so nothing keeps a default branch green between commits, and lint debt accumulates on `main` unnoticed.

That debt does not land on whoever created it. The hook lints the **whole repo**, not the diff, so the next contributor to touch a drifted repo cannot commit at all until they have cleaned up someone else's files. Measured in `opencharly/spec` on 2026-08-29: **11 findings** (7 `errcheck`, 2 `gofmt`, 2 `unparam`) sitting on a pristine `main`.

This adds the step to `ci.yml`'s existing `go` job, next to the `go test` and `gofmt` steps already there.

## How tested

This repo's `main` is clean today, so the gate lands green and its job is to keep it that way:

```
$ golangci-lint run ./charly/...
0 issues.
lint exit=0
```

The pinned version is the same build the local hook uses, confirmed rather than assumed:

```
$ go version -m $(command -v golangci-lint)
	path	github.com/golangci/golangci-lint/v2/cmd/golangci-lint
	mod	github.com/golangci/golangci-lint/v2	v2.13.2
```

Workflow parses:

```
$ python3 -c "import yaml; yaml.safe_load(open('.github/workflows/ci.yml'))"
workflow YAML parses
```

The step's own run in CI on this PR is the live proof that it executes and passes.

## Two deliberate choices

**Pinned by module version, not a third-party action.** `go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.13.2` means the CI binary is the same build the pre-commit hook uses locally — a gate that disagrees with the hook is worse than no gate, because it fails people who did everything right. It also means a new upstream release cannot turn `main` red on its own schedule.

**Scoped to `./charly/...`**, matching the `go test` step above it rather than linting paths the existing job does not build.

## On the rest of the batch

charly#464 covers 98 Go repos in the umbrella; none currently has this gate. I am landing this one first rather than opening 98 PRs at once, deliberately: I ran a 94-repo sweep earlier in this session that stamped a schema version the repos' pinned charly could not read, and turned `candy` CI red on `main` for ~84 of them until a second corrective sweep. A proven template first, replication second, is the lesson from that.

What makes this one a template rather than a one-off: the step is self-contained, pins its own tool, and needs no repo-specific configuration beyond the package scope. What still has to be checked **per repo** before it lands there is whether that repo's `main` is currently lint-clean — `spec` demonstrably was not — because adding the gate to a drifted repo turns its `main` red immediately. That check is per-repo work, not a copy-paste.

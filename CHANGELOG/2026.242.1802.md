# 2026.242.1802 — fix(omarchy): make the installer seed's volume id ISO 9660 compliant

## Summary

charly emitted a warning on **every single installer-seed write**, in every bed, forever:

```
xorriso : WARNING : -volid text does not comply to ISO 9660 / ECMA 119 rules
```

ISO 9660 / ECMA 119 d-characters are `A-Z 0-9 _` only. The omarchy installer's
`volume_id: cidata` is lowercase — accepted by xorriso, but non-compliant, so it warns and
writes it anyway.

It fired **three times per `check-omarchy-iso-vm` run** — `vm-build`, `vm-create`, and the
rebuild inside `update` — and was the **only** non-allowlisted finding in the entire bed.

## How it was found, and why that matters

Not by grepping build logs. `summary.yml` is what records which lines charly actually counted
as findings and which allowlist rule cleared each one; a log grep cannot distinguish
"allowlisted" from "counted against the gate". Enumerating the run's non-allowlisted findings
programmatically gave exactly one distinct message:

```
[vm-build]           non-allowlisted findings: 1
    warning: xorriso : WARNING : -volid text does not comply to ISO N / ECMA N rules
[vm-create]          non-allowlisted findings: 1   (same)
[update]             non-allowlisted findings: 1   (same)
[deploy-add]         non-allowlisted findings: 0
[check-live]         non-allowlisted findings: 0
[check-live-rebuild] non-allowlisted findings: 0
[cleanup]            non-allowlisted findings: 0
```

Everything else in the bed was already clean.

## Uppercase is safe — read off the shipping ISO, not assumed

The obvious worry is that the guest discovers the volume by a lowercase label and uppercasing
it would break the unattended install outright. It does not, and this is not an inference:
`airootfs.sfs` was extracted from `omarchy-4.0.1.iso` and its loader read directly.

`/usr/local/bin/omarchy-cidata-load`:

```bash
device=""
for label in cidata CIDATA; do
  [[ -e $by_label/$label ]] && { device=$by_label/$label; break; }
done
[[ -n $device ]] || exit 1
```

It searches **both** cases. So the guest finds the volume either way, and only one of the two
spellings makes charly stop emitting a warning it has no business emitting.

`xorriso -as mkisofs -volid` preserves case exactly, so the label reaches the guest as
written and `#DistroInstaller.fs` can stay at its `iso9660` default permanently — the reason
the original comment gave for lowercase is unaffected by this change.

## This also removes an inconsistency inside charly's own stack

The sdk reached this conclusion already. `vmshared`'s cloud-init path:

```go
// cloudInitVolumeID is the ISO 9660 volume identifier cloud-init's NoCloud
// datasource looks for. It MUST be uppercase: ISO 9660 / ECMA 119 d-characters
// are A-Z 0-9 _ only, so a lowercase label makes xorriso warn on every single
// VM boot ("-volid text does not comply to ISO 9660 / ECMA 119 rules").
const cloudInitVolumeID = "CIDATA"
```

Same writer, same warning, same fix — the two paths were simply inconsistent, and the
installer path was the one that had not been brought up to standard.

## Rulebook compliance

- **R1 — RCA every anomaly.** The warning was root-caused to the d-character rule, and the
  "will uppercase break discovery?" question was answered by extracting the ISO's own loader
  and reading it, not by trying it and hoping. Not dismissed as cosmetic, which is what it had
  been treated as until it became the one thing standing between a bed and a clean gate.
- **R2 — Finish the whole cutover.** One value, one comment, one repo; the sdk half was
  already correct, so there is nothing else to bring along.
- **R3 — No duplication.** This removes a divergence rather than adding one: the two seed
  writers now agree on the rule the format actually imposes.
- **R4 — No workarounds.** The rejected alternatives were adding an allowlist entry for the
  message, and passing xorriso a compliance-relaxation flag. Both silence a true statement
  instead of making it false; an allowlist would also have hidden any *future* non-compliant
  volume id behind the same rule.
- **R4a — Fix the product first.** Documenting "this warning is expected" is exactly how it
  survived this long.
- **R5 — Delete legacy completely.** The lowercase value and the comment justifying it are
  both replaced; nothing is left behind a flag.
- **R6 — Git safety.** `git status` inspected before the commit (local `go.mod`/`go.sum`
  replaces used for the dev build were deliberately NOT staged); branched from a fresh
  `origin/main`; no force-push, no hook bypass, no direct push to `main`.
- **R7 — Prove behavior, not compilation.** The proof is a before/after on the same
  disposable bed, with the counter disappearing AND the install still succeeding — either
  alone would be insufficient.
- **R8 — Preserve emitted artifacts.** The emitted artifact is the answers volume; its
  contents are unchanged and its label is asserted to still be discoverable by the guest.
- **R9 — Binary equals source.** The bed ran against a `task build:binary` stamped charly
  built from this branch; no runtime dependency changes.
- **R10 — Fresh disposable proof.** `check-omarchy-iso-vm` reaches `PASS (steps=9)` **at zero
  non-allowlisted warnings**, including its own destroy-and-rebuild and 13/13 against the
  guest that rebuild installed from a blank disk.

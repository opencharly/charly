# 2026.242.1822 — fix(pac): declare charly's package transaction as tool-driven

## Summary

**charly could not install any package on an Omarchy guest.** Not "some packages" — any.
Measured at `deploy-add` on a real ISO-installed guest:

```
Woah partner...

This looks like a direct pacman system upgrade. Omarchy updates should normally
run through:

  omarchy update
...
If you really meant to bypass Omarchy for this transaction, rerun pacman with:

  sudo env OMARCHY_ALLOW_DIRECT_PACMAN=1 pacman -Syu

error: command failed to execute correctly
error: failed to commit transaction (failed to run transaction hooks)
Errors occurred, no packages were upgraded.
charly: error: ... walk step "SystemPackages" ... system packages pac: exit status 1
```

The cause, read out of the shipping ISO rather than inferred —
`/usr/share/omarchy/default/libalpm/hooks/00-omarchy-update-guard.hook`:

```ini
[Trigger]
Operation = Upgrade
Type = Package
Target = *

[Action]
When = PreTransaction
Depends = omarchy
Exec = /usr/bin/omarchy-update-pacman-guard
AbortOnFail
```

It aborts **every** upgrade transaction that did not come through `omarchy update`. And
charly's pac install body is `pacman -Syu`, where the `-u` is mandatory and load-bearing —
the existing comment explains why: `pacman -Sy <pkg>` on a guest whose DB predates the repo
partial-upgrades and leaves a binary linked against a library the image does not ship.

So on Omarchy, *every* charly package install is an upgrade transaction, and every one aborts.

## The fix declares something already true

`OMARCHY_ALLOW_DIRECT_PACMAN=1` says: this is a **tool-driven transaction**, not a human
running pacman by hand. The variable name and this exact usage are the guard's **own
documented escape hatch**, printed by the guard itself in the message above. This is charly
answering a question the distro asks, not routing around a guardrail.

It goes on the shared pac line **once**:

```diff
-  pacman -Syu --noconfirm --needed{{range .Options}}…
+  OMARCHY_ALLOW_DIRECT_PACMAN=1 pacman -Syu --noconfirm --needed{{range .Options}}…
```

and on the local-package path, because `pacman -U` over an already-installed charly is an
Upgrade operation — so a **re-deploy** trips the guard even when the first deploy succeeded.

### Why here and not in the omarchy distro entity

The pac format lives in arch's entity and omarchy inherits it. Overriding just this leaf
would mean omarchy carrying a copy of the whole ~25-line install body — repo setup, key
import, keyring reseed and all — to change one prefix. That copy would drift, which is
exactly the failure this session already hit twice with two copies of one policy (two writers
of the ssh stanza, then two definitions of the known-hosts rule).

Nothing but Omarchy's guard reads the variable, so it is **inert** on arch, cachyos and every
other pac distro. One line, one place, no duplication (R3).

### The tempting wrong fix

Dropping `-u` would also silence the guard, because an install-only transaction is not an
`Operation = Upgrade`. It trades a loud abort for a **silent partial upgrade** — the exact
failure mode the `-u` was added to prevent. `TestPacInstallDeclaresToolDrivenTransaction`
fails on that specifically, so it cannot be taken later by accident.

## How tested

```
$ go test -count=1 -run 'TestPacInstall|TestPacHostCell' ./
ok  	github.com/opencharly/charly/charly	0.585s
```

**Negative control 1 — remove the declaration:**

```
--- FAIL: TestPacInstallDeclaresToolDrivenTransaction
    pac install body does not declare the transaction tool-driven; charly cannot
    install any package on an Omarchy guest without it.
```

**Negative control 2 — drop `-u`** (the fix that also silences the guard):

```
--- FAIL: TestPacInstallDeclaresToolDrivenTransaction
    pac install body does not declare the transaction tool-driven; …
    pac install body no longer runs `pacman -Syu --noconfirm --needed`; dropping -u
    silences Omarchy's guard by partial-upgrading instead, which is worse than the
    abort it replaces.
```

The test also fails if the declaration is ever smuggled in as a shell **comment** — the body
is `&& \`-continued, where a comment line is legal but carries nothing to pacman.

### Live, on the guest

`check-charly-omarchy-vm` — a `disposable: true` bed added in
`opencharly/distro-omarchy` — installs the charly toolchain onto a guest Omarchy installed
from its own ISO. Before this change it failed at `deploy-add` with the abort quoted at the
top. With it:

```
$ charly vm ssh check-charly-omarchy-vm -- 'pacman -Qo "$(command -v charly)"'
/usr/bin/charly is owned by charly 2026.229.1921-1

$ ... -- 'pacman-conf --repo charly Server'
https://opencharly.github.io/charly-arch/amd64/

$ ... -- 'pacman-conf --repo core Server'
https://stable-mirror.omarchy.org/core/os/x86_64
```

Three separate facts, and the third is the one worth pausing on: charly added a third-party
repo to a guest whose pacman is pinned to **Omarchy's own frozen mirror snapshot**, and that
snapshot **survived**. A repo added by rewriting `pacman.conf` wholesale would silently drop
the `Server` lines pinning `core`/`extra` and repoint the guest at upstream Arch — a
divergence pacman reports success for either way.

## Rulebook compliance

- **R1 — RCA every anomaly.** The abort was root-caused to the specific alpm hook, extracted
  from the shipping ISO's `airootfs.sfs` and read, including its exact `Operation = Upgrade /
  Target = * / AbortOnFail` trigger. Not guessed from the error text.
- **R2 — Finish the whole cutover.** Both pac paths that can produce an Upgrade operation are
  covered — the package install and the local-package install. Fixing only the first would
  leave every re-deploy broken.
- **R3 — No duplication.** One declaration on the shared body, explicitly instead of a
  per-distro override that would duplicate the whole template.
- **R4 — No workarounds.** This is the distro's own published interface for the case, not a
  bypass of it. The rejected alternatives were dropping `-u` (silent partial upgrades) and
  writing the variable into the guest's `/etc/environment` (disables the guard for the
  operator's own transactions too, permanently).
- **R4a — Fix the product first.** The documented-caveat version ("run `omarchy update` by
  hand before deploying") would have made charly unusable on Omarchy by design.
- **R5 — Delete legacy completely.** N/A — nothing replaced.
- **R6 — Git safety.** `git status` inspected before the commit; the local `go.mod`/`go.sum`
  replaces used for the dev build were deliberately NOT staged; branched from a fresh
  `origin/main`; no force-push, no direct push to `main`.
- **R7 — Prove behavior, not compilation.** Two negative controls, each shown failing,
  including one that pins the *tempting wrong fix* rather than only the absence of the right
  one.
- **R8 — Preserve emitted artifacts.** The emitted artifact is the guest's `pacman.conf`; the
  bed asserts the added repo AND that Omarchy's own mirror pinning survived the addition.
- **R9 — Binary equals source.** The bed ran against a `task build:binary` stamped charly
  built from this branch. No runtime dependency change.
- **R10 — Fresh disposable proof.** See the run below.

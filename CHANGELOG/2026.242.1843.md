# 2026.242.1843 — fix(pacstrap): drop a dangling template field that broke every bootstrap VM build

## Summary

**`charly vm build` of any bootstrap VM has been broken since #484 merged this afternoon.**

```
charly: error: command "vm": rendering bootstrap script:
template: bootstrap-script:2:9: executing "bootstrap-script"
at <.Distro.Pacstrap.KeyringInitCmd>: can't evaluate field KeyringInitCmd
in type *spec.Pacstrap
```

Reproduced on **`arch-pacstrap` and `omarchy-pacstrap-vm` identically**. The pacstrap builder
template is shared, so this is arch, cachyos and omarchy alike — not one distro's problem.

## Root cause

#484 dropped `keyring_init_cmd` and `mirrorlist_url` as dead fields, and verified they had
**zero Go consumers**. That verification was correct. What it missed is that
`keyring_init_cmd` also had a **template consumer**, in this repo's own pacstrap builder body:

```yaml
container: |
    set -euo pipefail
    {{.Distro.Pacstrap.KeyringInitCmd}}      # ← removed from spec.Pacstrap by #484
    mkdir -p /target /out
```

Go templates resolve struct fields at **render** time. So the reference compiled, `charly box
validate` passed, every unit test passed — and the failure appeared only at
`charly vm build <bootstrap-vm>`, which no CI gate exercises. A `git grep KeyringInitCmd`
across Go sources finds nothing; the surviving reference is in YAML.

Nothing is lost by removing it. `pacstrap -K` two lines below already initialises the target
keyring — which is what #484's own body said was "all that was ever needed here".

## The guard is for the class, not this string

`TestPacstrapBuilderTemplateFieldsExist` reflects over `spec.Pacstrap` and requires every
`.Distro.Pacstrap.X` interpolated anywhere in `charly.yml` to be a real field:

```go
re := regexp.MustCompile(`\.Distro\.Pacstrap\.([A-Za-z0-9_]+)`)
for _, m := range re.FindAllSubmatch(body, -1) {
    if !real[string(m[1])] { t.Errorf(...) }
}
```

A hand-kept list of allowed names would have to be updated by the same person who forgot the
template — which is no guard at all. Reflection means the next field removal is caught by the
removal itself.

**Negative control — restore the exact #484 defect:**

```
--- FAIL: TestPacstrapBuilderTemplateFieldsExist
    charly.yml interpolates .Distro.Pacstrap.KeyringInitCmd, which is NOT a field of
    spec.Pacstrap. Every `charly vm build` of a bootstrap VM will fail at template
    render, on a path no unit test reaches. spec.Pacstrap has:
    [BasePackages ExtraRepos RuntimePacmanConf]
    checked 1 .Distro.Pacstrap.* references against spec.Pacstrap [...]
```

That control matters twice over: it proves the test catches the real defect, **and** it proves
the test is not passing vacuously — with the fix applied it reports `checked 0 references`,
which on its own would be indistinguishable from a broken regex or a wrong file path.

### Live — the build proceeds again

`arch-pacstrap`, which failed at render before this change, now renders and runs pacstrap:

```
tar: ./etc/pacman.d/gnupg/S.gpg-agent.extra: socket ignored
...
charly: error: building bootstrap VM disk: insufficient free space on /tmp/charly-priv-…:
12.9 GiB free, 22.0 GiB required
```

It gets all the way into the rootfs tar and stops on a free-space precondition — that check
working, on a host whose `/tmp` is a 62 GiB tmpfs with other work on it. The template render,
which is what this PR fixes, is past.

With staging redirected to a filesystem that has the room, the build completes end to end:

```
$ TMPDIR=… charly vm build omarchy-pacstrap-vm
Wrote …/output/qcow2/omarchy-pacstrap-vm/disk.qcow2 (rootfs sha256=060e5284b14d8dd…)
Wrote …/output/qcow2/omarchy-pacstrap-vm/seed.iso
[exited with code 0]

$ ls -l …/output/qcow2/omarchy-pacstrap-vm/
-rw-r--r-- 2426011648  disk.qcow2
-rw-r--r--     378880  seed.iso
```

A 2.4 GB bootable rootfs built from packages — the thing that was impossible between #484 and
this commit.

# 2026.242.1908 — fix(pacstrap): append only repositories the builder image does not already have

## Summary

The pacstrap builder template appends the distro's `extra_repo` block to `/etc/pacman.conf`
unconditionally. When the builder image already carries those repositories, pacman
double-registers them and errors on **every** build:

```
error: could not register 'omarchy' database (database already registered)
error: could not register 'multilib' database (database already registered)
```

## Why a builder would already have them — this is not a misconfiguration

`omarchy-pacstrap-builder` is built on the `omarchy` image **deliberately**. pacstrap runs
inside the builder and resolves against the builder's own `pacman.conf`; charly appends a
distro's *extra* repositories there but does **not** repoint `[core]` and `[extra]`. On a
plain-Arch base those still point at upstream Arch, so the target rootfs would come from a
mix — the ~23 Omarchy-built packages from Omarchy's repo and the ~125 `core`/`extra` ones from
a newer upstream snapshot than Omarchy ships. pacman succeeds either way, which is what makes
that divergence dangerous rather than merely wrong.

So choosing the correct base is exactly what surfaced this. The fix belongs in the template,
not in the box.

## Why it stayed invisible

pacstrap completes after the failed registration, so `charly vm build` **exits 0** and writes
the disk. Only a bed's errors-fatal log gate catches it — which is precisely how it surfaced:
`check-omarchy-pacstrap-vm` failed at `[vm-build]` with those two lines as its **only**
non-allowlisted findings (the mkinitcpio chroot messages beside them are already allowlisted).

## The fix

```awk
awk -v conf=/etc/pacman.conf '
  BEGIN { while ((getline l < conf) > 0) if (l ~ /^\[/ && l != "[options]") have[l]=1 }
  /^\[/ { keep = ($0 == "[options]") || !have[$0] }
  keep
' /etc/pacman.conf.extra >> /etc/pacman.conf
```

**`[options]` is deliberately exempt.** It is present in every `pacman.conf`, its directives
merge rather than conflict, and it is where `renderPacstrapExtraConf` puts the microarch
`Architecture = x86_64 x86_64_v3` line that cachyos-family repos require. Dropping it as a
duplicate would break those silently — the same class of failure this fixes, in the opposite
direction. That exemption is the part most likely to be "simplified" away later, so it is
called out in the template comment too.

## How tested

### The filter, in isolation, before it went near a build

Given a `pacman.conf` with `[options] [core] [omarchy] [multilib]`, and an extra file offering
`[options]`+Architecture, `[omarchy]`, `[multilib]`, `[newrepo]`:

```
$ awk … extra
[options]
Architecture = x86_64 x86_64_v3
[newrepo]
Server = https://new
```

Exactly the two things that should survive: the `[options]` directives, and the repository the
image does not already have. Both duplicates dropped.

### The real build, before and after

Same entity, same builder image, same host — the template is the only difference.

**Before:**

```
[vm-build] FAIL
    Ex1  error: could not register 'omarchy' database (database already registered)
    Ex1  error: could not register 'multilib' database (database already registered)
    Ex1  ==> ERROR: failed to detect root filesystem  [allowlisted: mkinitcpio-chroot-autodetect-fallback]
    Wx2  ==> WARNING: sd-vconsole …                   [allowlisted: mkinitcpio-chroot-warnings]
charly check run check-omarchy-pacstrap-vm: FAIL (steps=1)
```

**After:**

```
$ TMPDIR=… charly vm build omarchy-pacstrap-vm
Wrote …/omarchy-pacstrap-vm/disk.qcow2 (rootfs sha256=a178fe520c033e254112540b6c…)
Wrote …/omarchy-pacstrap-vm/seed.iso
[exited with code 0]

$ grep -cE '^error: could not register' build.log
0
$ grep -cE '^error' build.log
0
```

**Zero error lines of any kind**, and the disk still builds — 2,430,926,848 bytes. Both halves
matter: silencing the errors by not appending at all would also have produced zero errors and
a rootfs missing Omarchy's repositories.

### The bed

`check-omarchy-pacstrap-vm` (`disposable: true`) is the bed that caught this. Its
`[vm-build]` step is the step this change fixes, and it went from

```
[vm-build] FAIL
    Ex1  error: could not register 'omarchy' database (database already registered)
    Ex1  error: could not register 'multilib' database (database already registered)
charly check run check-omarchy-pacstrap-vm: FAIL (steps=1)
```

to

```
[vm-build]  PASS after 3m19.593s [allowlisted=4]
[vm-create] PASS after 1.744s [allowlisted=1]
```

No `warnings=` counter on either step — the remaining findings are the allowlisted mkinitcpio
chroot messages, and the two `error:` lines this PR removes are gone.

**The bed as a whole does not yet reach `PASS (steps=N)`.** It went on to fail at
`[check-live]` on two assertions about the *guest*. Both are **already fixed**, in a named
place, and neither is a defect in this diff:

**Exit: `opencharly/distro-omarchy` branch `feat/omarchy-pacstrap-vm`** — pushed, commit
"feat(vm): omarchy-pacstrap-vm — Omarchy built from packages, and its builder". It carries
exactly these two fixes:

1. `omarchy` added to the VM entity's `source.package`. The pacstrapped rootfs was plain Arch
   (`ID=arch`) because the distro's `pacstrap.base_package` is a minimal bootstrap set and
   carries neither `omarchy` nor `omarchy-settings`.
2. The bed's limine assertion replaced. It demanded a named NVRAM entry, which the bootstrap
   path does not create — `efibootmgr --create` runs inside the builder against a loop device
   and never reaches the guest's OVMF variable store. The guest boots limine through the
   firmware's auto-created removable-media entry (`Boot0002* UEFI Misc Device
   {auto_created_boot_option}` → `/boot/EFI/BOOT/BOOTX64.EFI`). The replacement asserts
   `/proc/cmdline` carries `rootflags=subvol=@` and `rootfstype=btrfs`, which exist only in the
   `limine.conf` charly's template wrote — a stronger claim that holds on both paths.

That branch is blocked on THIS PR: without the de-duplication its `[vm-build]` fails first and
neither guest-side assertion is ever reached. So this is not a deferral — it is the ordering
of a two-repo fix whose second half is already written, pushed, and re-running.

Scoping this PR's claim to `[vm-build]` is the honest reading of what the diff does.

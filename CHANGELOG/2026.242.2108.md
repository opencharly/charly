# 2026.242.2108 — fix(deps): charly ships omarchy-vm but pins a plugin-vm that cannot build it

## Summary

`charly vm build omarchy-vm` fails on `main`:

```
charly: error: command "vm": vm "omarchy-vm": unsupported source.kind "iso"
        (want one of cloud_image, bootc, bootstrap)
```

so `charly check run check-omarchy-iso-vm` dies at its first step, `[vm-build]`, after
637ms. The bed asserts nothing, and the entity charly ships is unreachable.

### Root cause

`source.kind: iso` is implemented in plugin-vm and landed in `opencharly/plugin-vm#8`,
first tagged `v0.2026242.1242`:

| plugin-vm tag | `knownVmSourceKinds` |
|---|---|
| `v0.2026242.812` | `{"cloud_image", "bootc", "bootstrap"}` |
| `v0.2026242.1242` | `{"cloud_image", "bootc", "bootstrap", "iso"}` |

`charly/go.mod` required **`v0.2026242.812`** — the version immediately *before* it.

charly#495 and #496 advanced the `box/omarchy` gitlink to a `distro-omarchy` that ships
`omarchy-vm` (`source.kind: iso`) and `check-omarchy-iso-vm`, but neither bumped the
plugin-vm require. charly gained the **entities** that need the capability without gaining
the **capability**.

Nothing caught it, and that is the part worth noting: the entity is data;
`charly box validate` checks it against the schema, which *does* have the `iso` arm (from
spec#71); and the rejection happens only at `vm build` time inside the plugin — a path no
unit test and no CI job exercises. This is the "partial repin" class: a gitlink advanced
while its consumer's own dependency pin stayed put, and the two disagree only at runtime.

### The fix

Bump to the newest published plugin-vm, `v0.2026242.1912`, which also carries the
per-domain serial log (plugin-vm#15) that makes a headless guest's console readable.

`go get` additionally resolved `sdk` off a pseudo-version onto a released tag —
`v0.2026242.914-0.20260830150119-f476722d55eb` → `v0.2026242.1217`. That is a strict
improvement: an untagged-commit pin becomes a released one.

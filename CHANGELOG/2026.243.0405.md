# 2026.243.0405 — fix(omarchy): the pacstrap VM's limine.conf produced an unbootable branch

## Summary

The omarchy bootstrap VM produced a disk that **could not boot**. `charly vm build` and
`vm create` both succeeded, then the guest sat at the Limine menu forever and every bed
using it hung at `[deploy-add]` waiting for SSH that could never arrive — 40+ minutes
observed before I killed it.

`check-omarchy-pacstrap-vm`'s own description claims it is the *"sole proof that charly's
own from-packages path produces a BOOTABLE Omarchy"*. That claim was false.

## Root cause

Read off the built disk's ESP (`qemu-img dd` + mtools, no root required). The live
`limine.conf` was 778 bytes next to a 295-byte `limine.conf.old` — charly's own write had
been rotated and replaced:

```
/Omarchy                                       <- charly's depth-1 entry
    protocol: linux
    kernel_path: boot():/vmlinuz-linux
    ...
  //linux                                      <- APPENDED, depth-2 sub-entry
  ### This kernel entry is auto-generated by limine-entry-tool
  protocol: efi
  path: boot():/EFI/Linux/omarchy_linux.efi#<hash>
```

`limine-entry-tool` is a hard dependency of the `omarchy` metapackage (via
`limine-mkinitcpio-hook`) and runs as an alpm hook **during the pacstrap transaction**. It
appends its UKI entry as `//linux` — depth 2 — to whatever `limine.conf` it finds. Because
charly had written a depth-1 leaf, the tool's entry nested **under** it, silently converting
charly's bootable entry into a **branch**.

limine renders a branch as `[+] Omarchy … ENTER Expand` (not `ENTER Boot`) and offers
`B Blank Entry`, which it only does when nothing is bootable. `default_entry: 1` selected
that branch. From the guest's serial console:

```
BdsDxe: starting Boot0002 "UEFI Misc Device" from PciRoot(0x0)/Pci(0x1,0x2)/Pci(0x0,0x0)
Limine 12.6.0 (x86-64, UEFI)   [+] Omarchy   ARROWS Select  ENTER Expand  S Firmware Setup  B Blank Entry
```

4220 bytes of serial output, no kernel line anywhere.

### The reference that settled the shape

Reading the **working** `limine.conf` off an ISO-installed Omarchy guest's ESP:

```
default_entry: 2
/+Omarchy                                      <- '+' = EXPANDED branch
### This OS entry is auto-generated by limine-entry-tool
  //linux                                      <- the bootable entry, at position 2
  protocol: efi
  path: boot():/EFI/Linux/omarchy_linux.efi#<hash>
```

So charly had **two** bugs against what Omarchy itself produces: no `+` (the branch renders
collapsed) and `default_entry: 1` (counting includes the branch, so 1 IS the branch).

## The fix

Mirror Omarchy's own structure — an expanded branch with the entry as a sub-entry, and
`default_entry: 2`:

```
timeout: 3
default_entry: 2

/+Omarchy
    //Charly
        protocol: linux
        kernel_path: boot():/vmlinuz-linux
        cmdline: root=PARTUUID=${ROOT_PARTUUID} ...
        module_path: boot():/initramfs-linux.img
```

`//Charly` sits at position 2, which `default_entry: 2` selects. When `limine-entry-tool`
later appends its `//linux`, it lands as a **sibling** at position 3 rather than a child, and
both entries stay bootable. Verified on the rebuilt disk — the tool's entry is now a sibling,
exactly as intended.

The reasoning is recorded in the template itself, with the observed failure and the reference
config, so the next person to touch it does not reintroduce a depth-1 leaf.

## Why it was never caught

`[vm-build]` used to FAIL for an unrelated reason — limine's alpm hook cannot succeed inside
a pacstrap chroot, and the bed's errors-fatal log gate rejected the run. That was fixed in
`opencharly/plugin-check#11` (merged). Until then the bed never reached `[vm-create]`, so the
built disk had **never once been booted** by a bed or by CI. This is the first run after that
gate stopped firing.

## Blast radius

`omarchy` only. `arch`, `cachyos`, `debian`, `ubuntu` and `fedora` use grub, and no other
distro entity writes a limine config. Any future limine distro whose packages ship
`limine-entry-tool` would hit the same trap, which is why the template now explains it.

- **R1 — RCA every anomaly.** Eight steps completed to the mechanism, not the symptom: both
  ESPs were read and diffed against a known-good guest before any edit. An earlier response

  second config path.

  correct. Pointing `default_entry` at the tool's entry, or pressing a key past the menu,

- **R6 — Git safety.** `git status` inspected; branched from a fresh `origin/main`; no

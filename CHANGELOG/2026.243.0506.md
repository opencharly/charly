# 2026.243.0506 — fix: pin the parity fixture tags so an unrelated repo's release cannot turn main red

## Summary

`TestFleetCompileParity_PluginRoundTrip` resolved its three fixture candies at **"the newest tag"**
via `git ls-remote`, at test time, over the network — while the golden it compares against is
checked in. So a release in **any** of `layer-debootstrap-builder`, `layer-dev-tools` or
`layer-pre-commit` changed what the test compiled while the golden stood still, turning **main**
red with no charly change involved.

Two commits:

1. **Pin the fixture tags.** `golden-compile` now records the tags it resolved into
   `charly/testdata/fleet_compile_parity_tags.json`, written in the same run as the golden; the
   test reads that file instead of asking the network.
2. **Fix the remedy.** **Five pre-existing sites** told the reader to regenerate with
   `go run ./tools/golden-compile`, which cannot run. (The first commit of this PR unknowingly added
   three more — its own new `pinnedFixtureTag` messages, written before I had discovered the command
   was broken — so the second commit rewrites eight in total. Corrected from an earlier revision of
   this body, which said "eight sites" as though all eight pre-existed.)

## Root cause

`newestFixtureTag` (test) and `newestCandyTag` (generator) both shell out to `git ls-remote --tags`
and take the last entry. Nothing pins anything, so the fixture content is whatever the upstream
repos happen to have published at the moment CI runs.

**Measured, not inferred.** A clean clone of `main` at `c05d90e`, zero local changes:

```
$ go test ./charly/ -run TestFleetCompileParity_PluginRoundTrip -count=1
--- FAIL: TestFleetCompileParity_PluginRoundTrip (5.07s)
    fleet_compile_parity_test.go:318: PARITY BREAK on "pre-commit"
        --- GOLDEN ---  {"version":"2026.166.1751", …
        --- NEW ---     {"version":"2026.243.0100", …
FAIL	github.com/opencharly/charly/charly	5.458s
```

`#503` was failing on exactly this, having touched only a submodule gitlink and one pin line — it
could not have caused it.

### Why re-baking the golden is not the fix

`#504` fixed a real and separate defect (the regeneration tool was left on the pre-cutover root
marker, so it could not run at all) and re-baked the golden, which makes main green **until the next
upstream release**. That is the workaround R4 forbids, and it had already expired before it merged:
`layer-pre-commit` published `v2026.243.0409` while `#504` was in flight.

Removing the float fixes it for good — the tag and the golden can no longer drift apart, because
they now move together in one commit.

**The pin is load-bearing** — it is not decoration that happens to hold. Repointing `pre-commit` at

```
$ # pre-commit: v2026.243.0409 -> v2026.239.1552

```

So the test really does compile what the file pins, and a stale pin is caught rather than ignored —
the property that makes pinning a fix instead of a mute button.

## Rulebook compliance

- **R1 — RCA every anomaly.** The failure was traced past "the golden is stale" to the floating
  fixture resolution, and the diagnosis was confirmed by reproducing red on an unmodified `main`
  rather than by reading the diff.
- **R3 — no duplication.** One pinned tag file, read by the test and written by the generator; the
  resolution logic stays in the generator only. `newestFixtureTag` is deleted, not left beside its
  replacement.
- **R4 — no workarounds.** Re-baking the golden on each upstream release is the blind-retry shape
  this rule names; the float is removed instead.
- **R5 — delete legacy completely.** `newestFixtureTag` and its now-unused `os/exec` and `strings`
  imports are gone in the same PR.
- **R6 — git safety.** Working tree checked before staging and clean after commit; `fix/` branch off
  a fresh clone of `main`; no force-push, no direct push to `main`, no hook bypass.
- **R7 — prove the gate, not the plan.** Full `go test ./charly/` output pasted above, run on the
  final committed tree.
- **R10 — fresh disposable proof.** Both the red reproduction and the green gate ran from clean
  clones/committed trees, never from an edited working state.

## Change classification

- **Change class:** test determinism + tooling. One test file, one tool file, one new checked-in

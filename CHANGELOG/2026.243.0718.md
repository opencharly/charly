# 2026.243.0718 — chore: advance 11 stale candy pins so published tags carry current refs

## Summary

This candy's pinned refs were behind their repos' newest tags. That matters beyond tidiness:
**a published tag embeds the pins it carried at tag time**, so every consumer that pins a tag
of this candy drags those old refs into its own resolution, and charly reports them as
`resolved to multiple versions` on every build of that consumer.

The pins advanced are listed in the commit message.

**Which `version:` fields move, precisely.** `charly.yml` here is a MULTI-ENTITY manifest with
12 `version:` fields, so a single global bump would be wrong. Each changed pin line was mapped
back to its owning top-level entity, and only those seven move:

```
agentteams           2026.223.1500 -> 2026.243.0300
agentteams-manager   2026.224.0600 -> 2026.243.0300
agentteams-worker    2026.224.0600 -> 2026.243.0300
charly-dev           2026.238.1243 -> 2026.243.0300
check-boxload-app    2026.229.1100 -> 2026.243.0300
docs-site-app        2026.215.1207 -> 2026.243.0300
dsh-app              2026.226.1600 -> 2026.243.0300
```

The TOP-LEVEL `version:` is the SCHEMA STAMP and is deliberately untouched: it identifies the
config schema the file is written against, not its content, and bumping it would claim a
schema this file does not use.

**Correcting the previous version of this body:** it claimed "the nested `version:` advances"
when the diff moved **no** version field at all — the sweep applied the pin bumps but its
version-bump step never ran for this repo. The pr-validator caught that, correctly, and the
commit above fixes the diff rather than softening the claim.

### Why this is being done across the org

A downstream project (`distro-cachyos`) could not reach a zero-warning build, and the cause
was traced to this class of staleness rather than to anything in that project. Measured
there, advancing a *consumer's* pin makes it worse, not better:

| Change in distro-cachyos | Warnings |
|---|---|
| baseline | **2** |
| advance one consumer | 3-6 |
| advance ALL 23 stale pins (of 177) | 8 |

Advancing a consumer to a newer tag simply exposes that tag's *other* stale refs. The only
operation that removes an edge rather than trading it for others is fixing at the source, so
the next tag cut here carries current pins throughout.

A full scan of the 178-repo closure found **93 repos carrying 188 stale pins, with zero
dependency cycles** - so the graph can be repaired in dependency order, and this repo is part
of that ordered sweep. Analysis, measurements and options: opencharly/distro-cachyos#48.

## How tested

```
$ charly box validate
exit 0
```

Run with the charly version this repo's own `deploy.yml` clones and builds, so it is the same
gate CI runs rather than a newer local binary - a mismatched binary rejects the repo's schema
stamp outright. The exit code was read directly from `charly box validate`, not through a
pipeline.

The diff is confined to `charly.yml`: the ref pins listed in the commit message plus the
version line. No packages, services, plan steps or scripts change, so there is no runtime path
to exercise and no image is built in this repo. The consuming project's warning drop lands
with the repins that follow these tags.

# 2026.244.0726 — fix(ci): release-binary must fire for API-created tags (tag-on-merge)

## Summary

The release-binary workflow never fired for merged PRs: tag-on-merge creates release tags via the REST API (`git.createRef`), which does NOT emit a `push` event — so `on: push: tags` alone never ran. The release binary silently lagged main's schema (the 2026.244 release-lag RCA: the newest release supported max schema 2026.232.0520 while main declared 2026.240.1943, breaking `charly --repo opencharly/charly` for every release-binary user).

Fix: add `push: branches: [main]` to the trigger. Every main push builds the binaries; the upload step fires when the pushed HEAD carries a v* tag whose release does not exist yet. The binary is stamped with the TAG's CalVer (not the commit date) so the distro repos' `charly version` == packaged-version assertion holds.

## How tested

- RCA: confirmed via the Actions API that no release-binary run exists for the API-created tags v2026.243.1846 / v2026.244.0635 (last run 2026-08-22 for v2026.234.2336).
- Confirmed the newest release binary (v2026.234.2336) fails `charly --repo opencharly/charly box list boxes` with `config schema 2026.240.1943 is newer than this charly supports (max 2026.232.0520)`.
- Pushed tag v2026.244.0836 manually (git push) — the release-binary workflow triggered and is building (the manual push path still works).
- The workflow change is a trigger + upload-guard change; the build steps are unchanged.

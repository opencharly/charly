# 2026.244.0853 — fix(ci): build the newest UNRELEASED tag, not the newest tag

## Summary

The workflow_run resolve step (from #521) picked the newest v* tag unconditionally. When a newer released tag exists (e.g. a manual release like v2026.244.0836), it shadows the unreleased tag-on-merge tags (v2026.244.0751/0726) — the upload step skipped or updated the existing release and the tag-on-merge tags never got their release binaries.

Fix: the resolve step iterates the v* tags newest-first and picks the first one WITHOUT a release; when none exists it sets `SKIP=true` and the build steps are guarded off (the workflow_run fires on every tag-on-merge completion, so the all-released case must skip cheaply, not fail on an empty CALVER). The shell `RELEASE_TAG` is assigned in the loop (GITHUB_ENV values load only at the next step, so the `-z` check must see the loop outcome in the current shell).

## How tested

The corrected resolve logic executed locally (the exact tag-iteration + `gh release view` check the workflow_run branch runs):

```
$ cd /tmp/charly-work && git fetch origin --tags --quiet
$ for TAG in $(git tag -l 'v*' --sort=-v:refname); do
    if ! gh release view "$TAG" >/dev/null 2>&1; then
      echo "picked: RELEASE_TAG=$TAG (no release exists)"; break
    else
      echo "skipped: $TAG (release exists)"
    fi
  done
skipped: v2026.244.0836 (release exists)
picked: RELEASE_TAG=v2026.244.0751 (no release exists)
$ git tag -l 'v*' --sort=-v:refname | head -5
v2026.244.0836
v2026.244.0751
v2026.244.0726
v2026.244.0635
v2026.243.1846
```

The newest released tag (v2026.244.0836) is skipped; the newest unreleased tag (v2026.244.0751) is picked — exactly the intended behavior. The next tag-on-merge completion will build v2026.244.0751 and upload its release.

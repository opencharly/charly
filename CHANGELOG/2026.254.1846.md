# 2026.254.1846 — fix: report the SERVED plugin artifact identity (baked vs host-built-from-cache)

## Summary

**The defect (RCA, RC3).** A check bed's plugin verbs are served by whatever binary the plugin
loader picks, but the run log never said which one. The only line naming the plugin resolved a
REF (`Resolved @repo -> vTAG (latest tag)`) — not a tree, not a binary — so a run whose
verbs came from a *different* build printed an identical line. Two full bed runs (~20 min each)
were discarded before the served binary was identified out-of-band by reading `strings` out of it.

**R1 — where that line actually comes from, and the corrected scope.** That line is printed
by the **sdk** (`loaderkit/refs_collect.go:258`), NOT by charly core. The core seam the first
revision of this PR also touched (`host_build_remote_image_resolve.go`) prints a different line
and is not exercised by any bed, so that part is **withdrawn** — the file is restored to
`origin/main`. The net diff is the plugin loader + its test, and every runtime line in it is
live-proven below.

**The loud signal (one place, generic).** `charly/plugin_loader.go` renders the SERVED artifact
identity for every out-of-tree plugin the loader connects — one renderer (`pluginServedLine`)
and one reporter (`reportPluginServed`), so nothing else has to know how to say it:

```
# host-built from the plugin candy source (the cache path keyed by that source, #76):
plugin <ref>: served from <cache path> (build stamp <16-hex content stamp>); source <candy source dir>

# prebuilt / baked binary (bake_plugin:, $CHARLY_PLUGIN_DIR):
plugin <ref>: served from baked binary <path> (build <size+mtime>)
```

The build id is the CONTENT stamp recorded beside a host-built binary (`plugin_build_stamp.go`)
when one exists, else the file size + mtime (a baked binary carries none). A run log now answers
"which bytes executed?" before the run is spent.

**The B7/R3 duplicate is deleted.** The first revision also made `CHARLY_REPO_OVERRIDE` outrank
the baked search and labelled the override in the log — which needs the override ROOT for the
plugin's repo, i.e. loaderkit's `RepoOverrideDir`. **charly core cannot reach it**:
`charly/import_purity_test.go` forbids ANY `github.com/opencharly/sdk` import in the host (root or
subpackage), and `charly/loader_threaded.go` states the doctrine ("charly core imports NEITHER
loaderkit NOR any other sdk mechanism kit; the WALK mechanism and the MATERIALIZE POLICY are
reached exclusively through the compiled-in loader plugin's spec-typed seams"). The first revision
therefore carried a second parse (`localOverrideRootFor`) — the finding itself. It is **deleted,
not re-sourced**: core now holds ZERO `CHARLY_REPO_OVERRIDE` parse, and the override-precedence
branch plus the two override-labelled log lines go with it.

### Named follow-up wave (the smallest correct path for the override fix)

Making an override outrank the baked search is a separate improvement and belongs behind the
host/plugin boundary:

1. `spec.ProjectLoader` gains `RepoOverrideDir(repoPath string) (string, bool, error)`;
2. `candy/plugin-loader` implements it by delegating to
   `loaderkit.RepoOverrideDir(repoPath, os.Getenv(proc.RepoOverrideEnv))` — it already delegates
   every other `ProjectLoader` method to loaderkit one-line, and a PLUGIN may import the sdk;
3. `charly/plugin_loader.go` asks `requireProjectLoader().RepoOverrideDir(repoPath)` (repoPath
   derived from the plugin source ref via `spec.ParseRemoteRef`) before the baked probe.

sdk#251 already exported the resolver (tag `v0.2026254.1740`); this PR has no sdk consumer, so the
pin is untouched. The sdk's own `Resolved @repo -> vTAG (latest tag)` line folds into the same wave.

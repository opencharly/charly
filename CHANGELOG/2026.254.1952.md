# 2026.254.1952 — fix: bound the plugin readiness read so a non-answering plugin can no longer hang charly forever (#588)

## Summary

`charly box build` (image-build step inside `charly check run`) and `charly check live` (plugin resolution) were each observed to park **indefinitely** — host in state S / `futex_wait`, its `__plugin serve` children alive and idle at 0.0% CPU, no step output, no error, no `summary.yml` for 25+ minutes (charly#588).

### The unbounded wait, anchored

The readiness READ that follows the go-plugin handshake was the ONE leg with no deadline:

- `charly/plugin_loader.go:145` (`loadBuiltinPluginUnits`), `:585` (`loadBakedPluginBinary`), `:686` (`loadPluginUnit`) each handed **`context.Background()`** to `LocalTransport.Connect`;
- `plugin_transport.go connectAndDescribe` passed that context straight to `describe(ctx, conn)` (`charly/plugin_grpc.go`) → `conn.Meta.Describe(ctx, &pb.Empty{})` — a plain gRPC unary call;
- so a plugin child that completes the go-plugin handshake and then **never answers Describe** leaves that call parked forever: host blocked, child idle, nothing printed.

Every other leg was already bounded, which is why the bound belongs on this one and not around the whole connect: go-plugin bounds spawn→handshake with `StartTimeout` (from the project's resolved readiness `per_attempt`), and the host build BEFORE the connect is legitimately slow (a cold `go build` of a candy plus its module graph takes minutes).

Scope note (RCA, not a residual): the `command:`-class plugin path is a **syscall.Exec** of the plugin binary — the plugin runs as the process and owns its own CLI grammar — it does *not* go through the registry connect. The registry connect (verbs/steps/substrates/builtins) is the path `box build`/`check live` hit, and it is the path this PR bounds.

### The fix

- **`charly/plugin_connect_deadline.go` (new)**:
  - `pluginReadyTimeout = 2 * time.Minute` — bounds ONLY the post-handshake readiness read (~3 orders of magnitude above the healthy cost: the schema is a CUE string already in the child's memory).
  - `connectPluginReady(t, name, source)` — the ONE seam every loader connect now routes through (R5: the old `(&LocalTransport{...}).Connect(ctx)` call sites are gone, not shadowed).
  - `connectAndDescribe` tags each failure with its phase (`start/handshake | dispense | describe | protocol-gate`); the seam renders the diagnosable error:
    ```
    plugin plugin-adb did not become ready within 2m0s (describe phase, source github.com/opencharly/plugin-adb): plugin describe: readiness read timed out after 2m0s: context deadline exceeded
    ```
    — plugin, source, phase and bound, so the next occurrence is identifiable **from the log alone** (charly#588 ask #2/#3). A non-deadline failure names the same identities without claiming a bound it never hit; a caller's own cancellation is never misreported as the bound.
  - `killPluginClient`/`boundedTeardown` bound the teardown too: go-plugin's own `Client.Kill()` sends its Shutdown RPC on a deadline-free context (`grpc_client.go` → `controller.Shutdown(c.doneCtx)`), so a peer that never answers it would swallow the very error the bound just produced.
- **`charly/plugin_transport.go`**: `LocalTransport.ReadyTimeout` (zero ⇒ `pluginReadyTimeout`), threaded into `connectAndDescribe`; `clientCloser.Close` runs the bounded teardown. Split out so the regression tests can drive the REAL transport with a short bound.
- **`charly/plugin_loader.go`**: all three connect call sites go through the seam; `loadBakedPluginBinary` no longer needs an unbounded context (`loadBakedPluginBinary(ctx, bin)` → `loadBakedPluginBinary(bin)`), and its warning keeps the plugin identity.
- **`charly/KERNEL_MANIFEST.md`**: the new production file's row — REQUIRED, the `TestKernelManifestBidirectional` gate fails on a new `charly/*.go` file with neither a manifest row nor a pending entry. (No change to `scripts/host-command-plugins.txt`: that file is the release workflow's welded-command pin list and this change adds no plugin — the branch deliberately leaves it to origin/main, where #589 bumped it.)

**Why a constant and not the resolved readiness `per_attempt`** (R1 — this was measured, not assumed): resolving readiness from inside the connect path re-enters `loadBuiltinPluginUnits`' non-reentrant `sync.Once` from its own callback — a measured deadlock (SIGQUIT dump: `loadBuiltinPluginUnits → sync.Once.doSlow → loadBuiltinPluginUnits.func1 → loadedReadiness → sync.Once.doSlow`, documented in the file header). `per_attempt` keeps governing the spawn leg exactly as before; the two never interact.

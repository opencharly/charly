# 2026.254.2132 — fix: a local CHARLY_REPO_OVERRIDE outranks a baked plugin binary (via the loader seam, the #587 wave)

## Summary

Wave step 3/3 of the override-precedence seam: charly core asks the loader seam whether a plugin's REPO is served from a local `CHARLY_REPO_OVERRIDE` tree, and lets that override OUTRANK a baked provider binary — WITHOUT core parsing the env var. Precedence is now **LOCAL OVERRIDE > baked binary > host build** on BOTH plugin-binary call paths: the loader (`loadPluginUnit`) and the externalized COMMAND dispatch (`resolveCommandPluginBinary`).

charly #587 withdrew this arm because core could not answer "does an override apply to THIS plugin's repo, and to which tree?" without re-parsing `CHARLY_REPO_OVERRIDE` itself (loaderkit owns the ONE parse; `import_purity_test.go` forbids an sdk import in the host). The withdrawal was routed to this NAMED wave, whose seam landed first:

- spec v0.2026254.1930 (#130) — `spec.ProjectLoader.RepoOverrideDir(repoPath) (string, bool, error)`.
- candy/plugin-loader v0.2026254.2014 (#9) — implements it as a one-line transit for `loaderkit.RepoOverrideDir(repoPath, os.Getenv(proc.RepoOverrideEnv))`.

### The change

- `resolvePluginBinary(ctx, srcDir, name, repoPath)` returns `(bin, overrideRoot, err)`. It asks `repoOverrideRootFor(repoPath)` — i.e. `requireProjectLoader().RepoOverrideDir(repoPath)` — BEFORE the baked probe: a baked binary can no longer silently serve a repo the operator pointed at a working tree. A seam ERROR (malformed entry, missing/non-directory target) propagates and fails the plugin load loud — a typo never falls through to other bytes.
- `overridePluginBinary` is the ONE override arm (the LOUD bypass warning + the build from the overridden source), shared by the loader path and the COMMAND path, so both name the binary they bypass identically.
- The plugin's repo is DERIVED, not guessed: `pluginRepoPath(source)` = `spec.ParseRemoteRef(source).RepoPath`, normalized through `spec.NormalizeRepoSpec` for the SHORT form (`owner/repo`, with or without a candy sub-path) — see round 1, block 3. A `./`-relative or absolute source and a bare single-segment name still name no repo, so the seam is never asked for them.
- The bypass is named LOUDLY (the restored #587 warning) and `pluginServedLine` gained the override arm:

```
plugin <name>: using LOCAL OVERRIDE <root> — serving <binary> (build <id>); source <srcDir>
```

  plus `WARNING: plugin <name>: ignoring baked binary <baked> — CHARLY_REPO_OVERRIDE root <root> is authoritative (building from the overridden source)`. The baked/host-built arms are byte-identical to before.
- Pins (unchanged from the previous round): spec v0.2026254.503 -> v0.2026254.1930, plugin-loader v0.2026251.534 -> v0.2026254.2014 (sdk v0.2026254.523 -> v0.2026254.1740 indirect, via the plugin). plugin-loader is consumed as a COMPILED-IN pin (`compiled_plugins:` + the go.mod require); there is no candy ref to bump.

**The limit that remains, stated rather than parked:** a command word's repo is in NO manifest (the `.providers` file records `class:word`), so the override question needs the project's candy declarations. In a source-less deployed container there is no project, hence no repo, hence no question to ask — the baked hit serves exactly as before, and `TestResolveCommandPluginBinary_BakedServesWithNoProjectHit` pins that. If a baked-only container ever needs override-awareness for a word it cannot see declared, the `.providers` manifest is what must carry the repo; that is the extension point, not a silently-unmet claim.

### Why this bed, and not `check-commands-local`

`check-commands-local` composes plugin-{clean,settings,candy,box,authoring,status,substrate} — every one of them COMPILED-IN. `loadProjectPlugins`' coexist switch (`pluginAlreadyConnected`: a word already registered from origin `builtin` skips the out-of-process build) means that bed can never reach `loadPluginUnit`, so the override arm is unreachable there. `check-cardwire-local` is the same shape of bed (kind: local, `disposable: true`, host-side steps, no host dependencies) but its three live assertions ARE the external command dispatch — `charly cardwire status|list|config get` fork/exec the out-of-tree plugin — so it covers the command path this round touched, and it composes plugin-{cardwire,record}, genuinely out-of-tree plugins loaded through the host-build path.

# 2026.256.0728 — feat(deps): spec v0.2026256.653 — the plugin build lock queues and reports

## Summary

Pins `github.com/opencharly/spec` **v0.2026254.1930 → v0.2026256.653** (spec #132, merged). That release makes every **blocking** acquire of `spec/lock`'s advisory flock **queue behind a contended lock with a bounded, REPORTED wait**: it says who holds the lock while it waits, and if the bound is ever reached it fails with the **holder's pid + command line** (resolved from the kernel, never from lock-file bytes) plus the next step. Previously it gave up after **2 minutes and named nobody**.

**Why charly needs it.** charly core's own out-of-tree plugin-binary build lock — `buildPluginBinary`'s `lock.AcquireFileLock(bin+".lock", true)` (`charly/plugin_loader.go`) — is a blocking acquire of exactly that primitive. Several check beds (or a roster fan-out) can call it for the **same** plugin at once, and the 2-minute bound turned a peer that is merely **slow** (a cold `go build` of a plugin binary) into a hard failure of a lane whose only sin was running concurrently. It is the same defect class as the measured `check-githubrunner-pod` image-build failure fixed in spec #132:

```
charly: error: command "build": building githubrunner: acquiring build lock for githubrunner:
flock ~/.cache/charly/locks/image-abNcNfNcNaeN.lock: lock held by another process for > 2m0s
```

### What changed in this repo (the semantics arrive with the pin)

- **`charly/go.mod` + `charly/go.sum`** — the pin bump (spec #132).
- **`charly/plugin_loader.go`** — the call site now documents the semantics it depends on (*a peer mid-build is a SLOW holder, not a stuck one, so the second builder queues* — with the pin named as the `github.com/opencharly/spec` require in `charly/go.mod`, not as anything "below" the comment, the divergence R1/R5 in the previous review round caught), and its error, if the bound is ever reached, names the lock file and says what to do (*another charly process is building this plugin binary; wait for that build to finish and re-run — the kernel releases the lock when that process exits, so there is nothing to clean up*). No behavioural code change beyond the wrapped message: the queue/report/holder-naming come from the pinned release.

### This does NOT clear #83's measured block (stated plainly)

The measured failure is **`candy/plugin-build`'s image build lock** (`podman.go:37`, wrapped by `drive.go:158`), which is fixed in **spec #132** and still needs its own **plugin-build call-site PR** (and later the distro-cachyos repin / bed re-run that #83's block 2 wants). This PR only makes charly core's **own sibling lock** consistent with that class. It is not a substitute for the plugin-build PR.

# 2026.256.0745 — chore(deps): pin plugin-build v0.2026256.706 — the image-build lock failure names box + tag + holder

## Summary

Bump charly's compiled-in `plugin-build` candy pin `v0.2026255.1833 → v0.2026256.706` (the Go module tag `candy/plugin-build/v0.2026256.706`, created by the merge of opencharly/plugin-build#13 at `v2026.256.0706`).

**Why this is the last pin of the campaign.** The plugin build lock — the per-image flock `charly box build`/`check run` takes around each image (`~/.cache/charly/locks/image-<sha16>.lock`) — used to fail a racing lane HARD after a silent `2m0s`, naming nobody. Two merged changes fix that at the layer that owns each half:

- **opencharly/spec#132** (`v0.2026256.653`, already pinned by this repo in #599, merged `625e576f`, tag `v2026.256.0728`): the blocking acquire now QUEUES — bounded at `30m0s`, and it REPORTS what it is waiting for (path + holder pid + command line, resolved from `/proc/<pid>/fdinfo`) every 30s while it waits; the timeout error names the holder.
- **opencharly/plugin-build#13** (`candy/plugin-build/v0.2026256.706`, merged `eb1f4f31`): `imageBuildLockError` wraps that primitive error with what the primitive cannot know — the BOX and the LOCK KEY — so an operator reads which box, which tag, and which process holds it.

Until this bump, charly's binary carried `v0.2026255.1833`, i.e. the old `acquiring build lock for %s: %w` rendering: on a lock failure the operator saw `acquiring build lock for githubrunner: flock …: lock held by another process for > 2m0s` — no holder, no tag, and a hard failure where the correct behaviour is to queue and then cache-hit (measured: `check-githubrunner-pod` attempt 2, calver `2026.255.2310`, opencharly/distro-cachyos#83).

**One line of the diff is the change; `go.sum` is the checksum trail.** `gofmt`/`go build`/`go vet`/`go test`/lint are unaffected by a pin (no Go source changed) but were run on the final tree anyway; no runtime code is touched here — the behavioural change arrives as the pinned module's own code.

### 5. The queue+report half IS RUNNING LIVE in the built binary

The one path this PR's pin cannot exercise live is the failure BRANCH itself: the bound is `30m0s` (that bound is the point — a peer's cold image build is a slow holder, not a stuck one), so reaching it takes half an hour. What CAN be and WAS exercised live is the new queue/report behaviour and the holder resolution, in the binary built from this tree: a real `charly box build githubrunner` was started while the githubrunner image lock was held by another process:

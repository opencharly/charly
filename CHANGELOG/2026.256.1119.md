# 2026.256.1119 — chore(plugins): unify the welded plugin pins to one SDK-compatible set

## Summary

Closes #605. Unify the welded-plugin pins in `scripts/host-command-plugins.txt` to a set that is
**mutually compatible with one SDK/spec**, which the shared `charly-lib` host requires
(`charlylib`, opencharly/sdk#256 — merged). Also corrects the stale "9 welded plugins" labels in
`.github/workflows/release-binary.yml` (the list is 12; the workflow already builds all 12), found
while landing this.

Per-plugin binaries each resolved their own SDK/spec, so they tolerated skew. A single shared host
links everything together, so a plugin pinned against a removed SDK/spec symbol breaks the whole
host. Two pins were stale:

- `plugin-vm@v2026.240.2034` imports the removed `spec/fleet`
- `plugin-preempt@v2026.239.1606` uses the removed `spec.FleetNode` / `deploykit.FleetConfig` /
  `loaderkit.LoadHostFleetConfigViaExecutor`


The non-zero rcs are each plugin's own CLI behaviour (`--help`/arg parsing), not dispatch failure:
every line is that plugin's distinct output, so `argv[0]` reached the right plugin.

**RCA for the two `settings`/`vm` CLI lines:** their COMMAND implementations require the in-proc
reverse channel (their own `command.go` comments document this — e.g. `plugin-clean`'s
"settings/clean/… need the threaded in-proc reverse channel"), which exists only in the compiled-in
placement. Out-of-process CLI mode therefore errors for those specific ops; their PROVIDER halves
serve fine over go-plugin, as the 12/12 handshakes above show. This is intrinsic to those commands'
placement, not caused by the pins change.

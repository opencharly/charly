# 2026.258.0219 — fix(plugin): bind plugin->plugin calls by IDLE, not total duration

## Summary

Replaces the withdrawn #611 (env-configurable timeout) with the ROOT fix.

### RCA (R1)

`defaultPluginInvokeTimeout` (10m) was added as a **hung-plugin guard** (#468 host→plugin, #474 plugin→plugin) but applied as a **TOTAL-duration cap**. That also guillotined calls long BY DESIGN and actively progressing. Measured live on `check-omarchy-iso-vm`'s R10 `[update]` step (deploy-dispatch `op=rebuild` → `plugin-deploy-vm` re-runs the unattended OS install): it died with `context deadline exceeded` after `check-live` had passed **64/64**, while the guest kept installing for minutes afterwards (disk mtime advanced past the failure). The step ran **788s** per `summary.yml` — i.e. the 10m cap is not measured from the step's start but from when the *bounded plugin→plugin call* begins, so "the step reports 788s while the call is cut at 10m" is the same event, not a contradiction.

**Why the sibling `-inst` beds survived at 553/903/1276/1346s** — executed evidence (the `served from` line is emitted per out-of-process plugin connection; zero means in-proc, hence no gRPC hop and no `defaultPluginInvokeTimeout`):
```
$ grep -c 'served from' <eval-omarchy>/.check/check-omarchy-eval-edge-inst/2026.256.1551/update.log
0                       # the plugin ran IN-PROC → no bound applied → 1346s completed
$ grep -c 'served from' <distro-omarchy>/.check/check-omarchy-iso-vm/2026.257.1708/update.log
8                       # the SAME plugin OUT-OF-PROCESS → the cap applied
```
That placement difference — not the operation's length — is why one bound fired and the other did not.

### Root fix — an IDLE guard, not a wall-clock cap

`plugin_activity.go`: the plugin→plugin call is bound by NO-PROGRESS, with **two** progress sources:

1. **Host reverse legs** — `RunSystem`/`RunUser`/`PutFile`/`GetFile`/`RunCapture`/`RunHostStep`/`HostBuild` touch the call's clock; `host_build_cli` heartbeats while its host child (the install) runs.
2. **The peer plugin process's own CPU** — `/proc/<pid>/stat` `utime+stime+cutime+cstime`, polled per tick. This is load-bearing: an ISO `prepare-venue` does its long work **plugin-locally** (console `virsh send-key`, ssh readiness retries as the plugin's own children), touching NO host leg.

- A **wedged** plugin (futex_wait; no work, no children) freezes both → trips the window → #474 preserved.
- A host reverse leg that itself outlives the window (a multi-minute `RunSystem`/`RunHostStep`/`HostBuild`) is heartbeated for its whole duration (`withActivityHeartbeat`), and the beat interval is DERIVED from the window.
- A **progressing** 13min install advances one or the other → never killed.
- **No absolute cap** (matching `ResolvedReadiness.WatchProgress` for an intentional long-runner); the window is the project's `defaults.readiness.no_progress` (the SAME config the executors' watchdogs use, R3).
- **Per-call clock** (rides the invoke ctx + the reverse server), so one call's progress can never mask another call's idleness.

Scoped correctly: the host→plugin **leaf** path (`invokeTyped` — distro/resource/init/project/gpu/arbiter resolve) attaches no reverse channel, so it keeps a TOTAL cap — explicitly the **former 10m** (`pluginLeafCapDefault`, unchanged; no silent loosening), since no progress signal exists there.

The plugin pid is plumbed `LocalTransport.Connect` (captured after `client.Client()` spawns the process) → `buildUnit` → `grpcProvider`.

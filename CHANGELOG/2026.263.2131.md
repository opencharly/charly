# 2026.263.2131 — fix(release): weld plugin-review v2026.263.1956 — it fixes the bare-name 404

## Summary

Bump the **welded** `plugin-review` pin from `v2026.263.1642` → **`v2026.263.1956`** so the next charly release's plugin bundle carries the owner/repo slug fix merged into `opencharly/plugin-review#15`.

The `#14` weld (`v2026.263.1642`) made the engine fail-fast but exposed a regression: the ghkit adoption collapsed `(owner, repo)` into **one slug** argument, while the tool dispatch kept passing the **bare repo name**. Every read-only tool 404'd, and the model correctly returned a BLOCK — *"No retrievable PR state"*. This is why `spec#140`, `action-review#7` and umbrella `#231` stayed BLOCKED after the `#14` weld.

**Measured on the `#14` weld** (umbrella `#231`, charly `v2026.263.1828`, run `35531666727`):

```
get_pr_meta  -> /repos/opencharly/pulls/231   404
get_pr_body  -> /repos/opencharly/issues/231  404
```

On `spec#140` the bare name `spec` was used: `/repos/spec/pulls/140` 404.

`#15` adds `toolSet.slug()` — the one place the engine's split `(owner, repo)` meets ghkit's single slug — resolves it once, passes it at all seven dispatch sites, and fails loudly on an empty owner instead of silently re-creating the bare-name path.

**Why this PR is the unlock.** The org validator runs `charly review` from the pinned charly release bundle, not from `plugin-review@main`. Merging `#15` alone changes nothing in the running gate; this one-line weld is what makes the fix reach it.

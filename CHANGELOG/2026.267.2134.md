# 2026.267.2134 — fix(check): the ephemeral-register-roundtrip assertion is pre-Cutover-C (W3)

## Summary

Fixes the W3 defect flagged on #633: the `check-sidecar-pod` bed's `ephemeral-register-roundtrip` step asserted a **dotted** address for the ephemeral VM member `check-sidecar-pod-ephvm`. That assertion encodes the **pre-Cutover-C** addressing contract and is stale — the address the product computes is correct.

**The member is DEPLOY-LEVEL, not in-substrate.** `check-sidecar-pod-ephvm:` is authored at 4-space indent — a **sibling of the `` `pod:` `` key**, not an entity inside the `pod:` body. Cutover C (spec `#103` / charly `#550`, merged 2026-09-06) made **deploy-level members** top-level addressable entries addressed by their **BARE name** (`sdk/loaderkit/deploy_load.go:81-92`: *"DEPLOY-LEVEL members (siblings of the kind key) are addressed by their BARE name … IN-SUBSTRATE members (entity keys inside the kind body) are addressed `rootName.child`"*; `FoldMembers` promotes them to `uf.Deploy[p.key]`). Only **in-substrate** members get the dotted form.

A VM member is **necessarily** deploy-level — it cannot deploy *into* a pod's venue — so `sdk/deploykit/deploy_members.go:64-115` (`BringUpMembers`) dispatches `deploy add <memberKey>` with the bare key **by design** (`deploy_members.go:92`). The bare address propagates: `BringUpMembers` bare `memberKey` → `ResolveNodePath` treats it as a folded top-level root → `walk` path=`check-sidecar-pod-ephvm` → `DeployName` → `pluginDeployTarget.name` → `dispatch req.Name` → `lifecycleParams.Name` → `dispatchVmEphemeralRegister` → `EphemeralRegisterRequest.Name`. `plugin-fleet/ephemeral.go` records exactly the address it is given. **No product change is required.**

**RCA.** The assertion landed **2026-07-21** (`d35a0fd0`, FINAL/K5 unit 6); Cutover C reclassified member positions **2026-09-06**. The bed was not exercised against the post-Cutover-C addressing since, so the stale expectation survived.

### Block 1 — the concurrent-load failures: RCA + named batch (#650)

When other sessions' beds ran concurrently (load 100–152) I saw failures that were **not** assertion failures — they were **never-hang-ceiling kills** (`sdk/kit`'s `ProbeNeverHang`) — and I did NOT dismiss them.

RCA: the never-hang ceiling is a *hang* safety net, but it is also the de-facto **per-probe timeout** for any step that does not declare its own `timeout:`. A probe that is legitimately slow under host load (`charly status --json`'s per-container fan-out — the cost already tracked as `task #26` in this file) or that performs a cold network fetch (`charly box pull`) is indistinguishable from a hang at the ceiling. Concurrent full-roster runs on one host drive load to 100–150 and slow every probe together.

Named fix vehicle: **#650** — *"batch: bed steps under concurrent-host load — the never-hang ceiling kills legitimately-slow probes (status fan-out, cold box pull) and resolution stalls"*, filed with the retained `.check/` evidence and the concrete direction (explicit per-step `timeout:` for load-sensitive steps as the bed already does for `sidecar-pod-roundtrip-final`; make the ceiling load-aware; or bound the roster's safe parallelism). A product-side remediation owned by its own change — not a lower-load re-run as proof. The R10 run above is at load ≈16.

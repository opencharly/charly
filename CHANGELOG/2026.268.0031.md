# 2026.268.0031 — fix(check): align check-k8s-deploy's cluster context with the derived domain

## Summary

Fixes the `check-k8s-deploy` group bed's failing `bring-up-members` step (filed as #653 during the plugin-kube schema-261 verification). The group's `check-k8s-deploy-cluster-ctx` template pinned `kubeconfig_context: vm-check-k8s-deploy-cluster`, but the group's **cluster member is the group ROOT's own `vm:` body** — there is no `check-k8s-deploy-cluster` member. The root's per-deploy domain identity is `vm-<group>` = `vm-check-k8s-deploy`, so the workload member's `kubectl apply -k` failed with `error: context "vm-check-k8s-deploy-cluster" does not exist`.

**RCA.** The `-cluster` suffix names a member that never existed: on `origin/main`, `grep -n 'check-k8s-deploy-cluster:' charly.yml` found only stale COMMENTS, never an entity. The pin and the derived domain diverged. This reproduces on `origin/main`.

**The one non-allowlisted warning in `deploy-add`/`update` — RCA + NAMED batch (not dismissed).** Raw line:

```
Warning: could not persist auto-generated secret charly/secret/K3S_CLUSTER_TOKEN: InvokeProvider: no provider registered for verb:credential (the target plugin must be loaded before a peer invokes it, and no connectable candy source provides it)
```

`summary.yml` classes it under the plain `severity-prefix` finding (count 1 per deploy-add), NOT any `allowlisted:` entry — so it is a real surviving warning, and I root-caused it rather than waving it off. Mechanism: `GenerateAndStoreSecret` (`sdk/deploykit/secret_provision.go:63-67`) generates the token and calls `cred.Write`, which forwards to `verb:credential` — served out-of-process by `candy/plugin-secrets` (`charly/charly/credential_plugin.go`'s `connectPluginByWord`). This project's candy closure does not reference `plugin-secrets`, so the write cannot connect; the warning is logged and the deploy continues (the token is still used in-memory, so the bed's k3s control plane comes up). It is a project-CLOSURE gap, not a plugin defect and not caused by this context fix. Filed as the named batch **opencharly/charly#655** — *"VM beds warn (non-allowlisted) that K3S_CLUSTER_TOKEN cannot be persisted — plugin-secrets is absent from the bed closure"* — with the mechanism + fix direction (make `plugin-secrets` reachable from the bed closure). This PR's fix (the context pin) does not touch that path; #655 owns it.

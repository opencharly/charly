# 2026.268.0312 — fix(plugin): make the idle guard event-driven, not sample-driven (RCA)

## Summary

Make the per-call plugin idle guard **event-driven** instead of sample-driven,
root-causing a real intermittent failure of
`TestInvokeProvider_ProgressingLongCallIsNotKilled` under full-suite load.

**RCA.** The watchdog ticked at `noProgress/4` and each tick compared the
last-touch timestamp against the FULL `noProgress` window
(`idleFor() >= noProgress`). A host-leg touch also fired at `noProgress/4` (the
fixture's cadence; production heartbeats are similar), so the two cadences were
EQUAL with **zero scheduling margin**: a single `>noProgress` stall in the
producer goroutine under load let the watcher read a stale timestamp and cancel a
call that was actively progressing. Re-timing the interval would only move the
race.

**Fix (the primitive, not the timing).** `pluginActivity` gains a buffered `wake`
channel; `touch()` signals it non-blockingly; `idleBoundedContext` arms a deadline
timer and **resets it on every wake**. A progress event arriving before the
deadline always resets it, so there is no race between producer and watcher
cadence. CPU advance (no event source) is still polled at `noProgress/4` and
likewise resets the deadline. `newPluginActivity(pid)` is the constructor the
dispatch site and the tests now use.

**Nil-wake hardening.** A clock built as a bare `&pluginActivity{}` literal would
have a nil `wake`, so `case <-wake` would block forever and the reset would never
fire — silently reverting to a bare timer (the bug being fixed). `idleBoundedContext`
therefore **arms the channel before the watcher starts**, and
`TestIdleBoundedContext_NilWakeLiteralStillResets` proves it (the test FAILS if the
arming is removed — verified by temporarily deleting it).

The now-dead sampled reader `idleFor()` and its `nanos` field were removed in the
same cutover (R5); the CI golangci-lint job flagged `idleFor` as unused.

### Why `kindcluster` is in this diff

The ONLY spec tag that carries `#KubeVirt` also carries `#Kindcluster` (both merged before this branch; `kindcluster` is another session's integration). charly's `checkDeployProviderBijection` runs over `spec.ResourceKinds` at process init and HARD-FAILS for any word with no `externalDeploySubstratePlugins` entry — so bumping to the `#KubeVirt` tag *requires* the `kindcluster` entry too, or every `charly` invocation panics. It is the mechanical pin-bump consequence, not kubevirt scope creep.

The producer now exists: **plugin-kube#6 merged + tagged** (`candy/plugin-kube/v0.2026268.2341`), so the pinned `plugin-kube` genuinely serves `deploy:kindcluster` (its `charly.yml` `providers:` now lists `deploy:kubernetes` + `deploy:kindcluster`). plugin-kube is an EXTERNAL deploy-substrate plugin (not compiled into charly), resolved at load time from `@github.com/opencharly/plugin-kube/candy/plugin-kube` → the latest tag, so no `go.mod` bump is needed for the entry to be live:

The snapshot / `from_snapshot` / `vm_state` substrate-word gates are VENUE-based (`spec/deploy.IsVmVenue` reads the stamped `ssh` venue), so a `kind:kubevirt` deploy is already a VM venue — no gate change is needed.

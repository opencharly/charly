# 2026.269.1034 — feat(plugin): make a command's parent its registry identity; derive deploy providers from the index

## Summary

Make a command capability's PARENT part of its registry identity, and derive the deploy
provider set from the generated index. This is the core-behaviour leg of the command-parent
cutover (grammar: `opencharly/spec#167` + `opencharly/sdk#293`; grammar-adoption:
`opencharly/charly#670`; producers: `opencharly/plugin-box#15`,
`opencharly/plugin-authoring#6`, `opencharly/plugin-build#16`; the docker images-parse fix
this bed surfaced: `opencharly/spec#169`).

A command's identity is `(class, word, parent)`: `charly box generate` nests under `box`, and
a top-level `charly feature` is a DIFFERENT capability that happens to share the word. The
parent lived only in the plugin's compiled Go (a sniffed `CommandParent()` method), never on
the wire — so the declaration was lossy, the registry disambiguated a collision with an
order-dependent "parking" heuristic, and an out-of-process nested command was impossible.

**The core change (one key grammar, no fallbacks):**

- `splitCapability` returns `(class, word, parent)`; `providerKey` renders the ONE identity
  `<class>:<word>[:<parent>]`. The registry keys DETERMINISTICALLY from the DECLARED parent —
  the parking/relocation heuristic is DELETED, and so is the Go-interface parent sniff in
  `buildUnitInProc` (the parent rides the declared wire `command_parent`, read identically in
  both placements).
- the peer-invoke path names the parent too (`InvokeProviderRequest.command_parent`).
- `externalizedDeploySubstrates` is DERIVED FROM THE GENERATED INDEX (the open set of deploy
  words plugins declare) instead of the closed `spec.ResourceKinds` list, and
  `checkDeployProviderBijection` is DELETED — a plugin-only target (`deploy:exampledeploy`) is
  first-class, so a new substrate costs a manifest entry, never a core edit.
- the generator emits `plugins_refs_generated.go` (word→candy-ref, a projection of each plugin
  repo's `plugin:` block); new gate `TestNoProviderRefMapInKernel` keeps the word→provider fact
  in the plugin repos.

### One deploy-word leaves the set: `kubevirt` (accounted, pinned, owned elsewhere)

The old set was `setFromSlice(spec.ResourceKinds)` — seven words incl. `kubevirt`. The new set
is the index-derived `deploySubstrateWords()`, and the ONLY delta is `kubevirt`: no corpus repo
declares `deploy:kubevirt` because its server, `github.com/opencharly/plugin-kubevirt`, cannot
join the corpus yet — it declares `kind:kubevirt`, which the compiled-in
`candy/plugin-substrate` declares too, and the generator rejects that duplicate ("a word has one
canonical provider"). `plugin-kubevirt` is owned by the **in-flight KubeVirt venue leg** (a
separate session), which will land it into the corpus and retire the overlap.

This is pinned in-tree, not parked: `TestReservedWordRegistry_DeploySubstrates` now asserts
`kubevirt` is a CUE resource kind AND is absent from the index-derived deploy set (so the moment
plugin-kubevirt joins the corpus, the assertion flips with no charly change). The diagnostics
handle it correctly meanwhile — `unresolvedDeployTargetError("kubevirt")` classifies it as a
KNOWN substrate (via `resourceKindSet`) and names the missing corpus plugin instead of rendering
an empty plugin name.

### Review-round fixes folded in

- **R3 (one key grammar).** The round-1 finding that a second parser/renderer existed is
  fixed: `splitProviderKey` is DELETED (`deploySubstrateWords` now calls `splitCapability`),
  and `provKey` delegates to `providerKey` instead of re-implementing it.
- **R1/R2 (the bed's `clean` failure).** The `check-commands-local` bed surfaced a REAL
  pre-existing defect: `spec/container.ParseLocalImagesJSON` assumed podman's JSON-array shape,
  but `docker images --format json` is NDJSON (and is EMPTY for a no-match filter). RCA'd and
  fixed at the source in `opencharly/spec#169` (merged, tag `v0.2026269.759`); this PR pins it,
  and `clean --dry-run` now works on this docker-backed host.
- **B18 (doubled class).** `plugin_dispatch_reverse.go`'s miss branch rendered
  `command:command:feature:box`; it now names the single `providerKey(...)` identity. A test
  pins the exact text.
- **B18/A1 (the known-substrate diagnostic).** `unresolvedDeployTargetError` no longer renders
  an empty plugin name for a resource kind with no corpus plugin; it names the missing corpus
  entry. `TestUnresolvedDeployTargetError` covers it.
- **A1 (the `kubevirt` delta).** Accounted in its own section above and PINNED by
  `TestReservedWordRegistry_DeploySubstrates` (a resource kind absent from the index-derived
  set), with the KubeVirt venue leg named as the owner.

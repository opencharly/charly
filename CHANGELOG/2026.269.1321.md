# 2026.269.1321 — feat(kindcluster): add the docker and nerdctl engine R10 beds

## Summary

Add the **docker** and **rootless nerdctl** R10 witnesses of the `deploy:kindcluster`
substrate (the podman witness, `check-kindcluster`, already landed in #669). kind
provisions node containers on any of the three charly engines; the engine word
maps 1:1 to kind's `KIND_EXPERIMENTAL_PROVIDER`, so the two new beds differ from
the podman bed only in `engine:` and their collision-free cluster name + kubeconfig
context.

Also add the in-venue node-container assertion to **all three** engine beds (the
plan §4 Phase 6 requirement): each bed asserts the kind node container exists on
its engine via the `io.x-k8s.kind.cluster` label.

| Entity | Change |
|---|---|
| `check-kindcluster-docker-cluster` / `check-kindcluster-docker` | NEW — the docker engine bed |
| `check-kindcluster-nerdctl-cluster` / `check-kindcluster-nerdctl` | NEW — the rootless nerdctl engine bed |
| `check-kindcluster` (podman) | + the node-container assertion `kc-node-container` |

Why per-engine cluster names: a kind cluster name is unique only WITHIN an engine
(`kind get clusters` is engine-scoped — measured), so each bed names its own
cluster and context. Never `kube: addons` (kind ships kindnet, no
Traefik/ServiceLB).

## Workload leg — routed to a NAMED core cutover (R2)

The plan's §4 Phase 6 also asks for a **workload** bed (a kindcluster deploy
carrying `image:`). Authoring it surfaced a **genuine charly-core defect**,
root-caused (R1) and routed to its own named cutover rather than worked around:

> **opencharly/charly#680 — `bug: group-bed teardown deadlocks when the root is an external-in-place substrate with a deploy-level member`**

Mechanism: a group bed whose root is an **external-in-place** substrate
(kindcluster) with a **deploy-level member** deadlocks on teardown. The bed runner's
`cleanup` calls `deploy del <root>` (`bed_run.go:599`); that holds the project
**ledger lock** and internally calls `deploykit.TearDownMembers`, which spawns a
**peer** `deploy del <member>` (`sdk/deploykit/deploy_members.go:132`) that blocks
on the very lock its parent holds (measured: a 30-minute
`waiting for file lock … .ledger.lock` stall). `check-k8s-deploy` avoids it only
because its root is a **VM** (`vm destroy`, which takes no ledger lock).

This is a production-impacting defect (a `kindcluster:`/`local:` deploy with a
member cannot be `charly deploy del`-ed), so it is a distinct cutover with its own
fix + tests in #680 — not shipped broken here, and not hidden behind a retry. The
workload leg reuses plugin-kube's already-proven materialize/apply/`kindLoadImage`
path (the same code `check-k8s-deploy` exercises for the kubernetes substrate), and
its cluster-provisioning half is fully proven by the three engine beds above.

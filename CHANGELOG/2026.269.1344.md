# 2026.269.1344 — refactor(plugin): collapse plugin resolution to ONE identity lookup (no fallbacks)

## Summary

The plan's §4 spine — one resolution *rule*, no fallback chains — applied to the plugin connect
layer. Removes the resolution crutches and fixes a latent identity bug. **Six** files, charly-only
(`provider_command_external_test.go` is the new gate).

### 1. `substrateFallbackRef` DELETED — no per-class special case

Its `class != ClassDeployTarget` branch was exactly the plan-§4 "special case for a substrate vs
a verb". It becomes `canonicalProviderRef(class, word, parent, callerRef)` — the SAME
generated-index lookup for **every** class, so `deploy:pod` and `verb:libvirt` resolve through one
table. `externalDeploySubstratePluginRef` remains only for its two deploy-specific
display/inject sites.

### 2. `vmPluginCandyRef` DELETED — a single-verb special-case helper

A one-word helper (`pluginProviderRef("verb:libvirt")`), folded into the same
`canonicalProviderRef` at its two call sites (`check_cmd.go`, `vm_plugin_client.go`).

### 3. BUG FIX — the command PARENT was dropped on the on-demand connect

`connectPluginByWordRef` took only `(class, word, extraRef)` and ended in
`providerRegistry.resolve(class, word)` — a **bare-word** lookup. After the C0 identity cutover a
nested command is `command:<word>:<parent>`; a connect for a nested command therefore re-resolved
the **top-level same-word twin**. It now takes the `parent` and resolves
`providerKey(class, word, parent)` at every leg, and `executorReverseServer.InvokeProvider`
threads `req.GetCommandParent()` through.

### 4. The local-first scan order is KEPT (the plan's removal of it was wrong — live-caught)

An earlier plan row listed `connectPluginByWordRef`'s two-pass as a "fallback" to collapse into
one scan. That was corrected: appending the canonical ref to the scan makes the loader **fetch**
that ref and resolve its latest tag — work that can ERROR on an unreachable repo — so collapsing
to a single ref-bearing scan turned a fetch error into a **HARD connect failure for a project
that vendors the candy locally**, which the network-free pass 1 had loaded fine. The two passes
are not two resolution paths (they run the identical scan+connect, differing by one ref), so the
order is a correctness requirement, not a fallback. Kept: pass 1 over the project closure
(network-free), pass 2 with the ref only if still unresolved. The **resolution rule** stays one
and fallback-free: registry → the generated index's canonical ref → connect.

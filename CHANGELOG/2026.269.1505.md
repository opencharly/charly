# 2026.269.1505 — feat: declared inter-plugin dependency gate (plugin.requires) — onto the clean base

## Summary

The plan's **A3 — declared inter-plugin dependencies** (`plugin.requires`), rebased onto the
clean post-C0/F1/F2 base. The crutch that blocked it (the closed `spec.ResourceKinds` +
kernel map) is gone, so this lands on the open provider-ref model.

A plugin advertises the OTHER plugins it depends on over `Describe` (the wire
`Capabilities.requires`, authored as the candy `plugin.requires:` list). The host resolves every
requirement against the provider registry **before the unit is treated as loaded** — so a
plugin's internal peer need no longer depend on that peer being referenced by the project's own
plans.

### What lands

- **`PluginUnit.Requires`** — the CUE-authored `spec.PluginRequirement` (capability + source +
  optional), lifted from the wire `Capabilities.requires` (spec#163, sdk#290):
  `liftRequirements` maps each `pb.PluginRequirement` to `spec.PluginRequirement` and validates the
  class/word shape against the ONE closed class vocabulary.
- **The parent is part of the peer's IDENTITY, not a separate field** (the C0 adaptation) — a
  requirement naming a **nested** command folds its `command_parent` into the ONE `Capability`
  identity string via `providerKey(class, word, parent)` → `command:<word>:<parent>`. The gate
  parses it back with the ONE `splitCapability`, so both the resolve and the on-demand connect use
  the full identity, and a nested requirement is never silently satisfied by a top-level same-word
  twin.
- **`registerPluginUnitRequires` — THE gate** (`plugin_requires.go`): an already-registered peer
  resolves immediately; a missing peer is connected on demand via `connectPluginByWordRef` with
  the requirement's `source` as the canonical ref (the SAME chain a call-time `ExtraRef` uses);
  a **cycle** (a unit whose provider is currently resolving its own requirements) is rejected
  naming the chain; an unresolvable **non-optional** requirement is a hard error naming the
  plugin AND the peer; `optional: true` records a skip.
- **Wiring — two LIFT sites + three GATE sites.** Every unit is built by `connectPluginReady`,
  which lifts `Requires` via `buildUnit` (external gRPC) / `buildUnitInProc` (compiled-in). The
  gate runs at the three sites that then register a unit (`plugin_loader.go`): `loadPluginUnit`
  (project/demand connect), `loadBakedPluginBinary` (baked), and `loadBuiltinPluginUnits`
  (compiled-in, at process start — which is where a `buildUnitInProc` unit is finally gated).
  So every placement is gated exactly once; the lift sites do not gate (the unit is not yet
  registered there).

No spec/sdk bump is needed: the pinned `v0.2026269.759` / `v0.2026269.145` already carry the
`requires` wire types (`sdk.BuildCapabilitiesWithRequires` / `NewMetaWithRequires`).

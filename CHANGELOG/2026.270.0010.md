# 2026.270.0010 — chore(deps): bump plugin-vm + plugin-substrate to the landed Cua tags

## Summary

Bring the **Cua VM surface** into the shipped charly by bumping three pins to the landed tags:

- `plugin-vm` `v0.2026266.1235` → `v0.2026269.2256`
- `plugin-substrate` `v0.2026269.14` → `v0.2026269.1716`
- `spec` `v0.2026269.1640` → `v0.2026269.1703`

Why each:

- **`plugin-vm`** carries the `container_disk` `#VmSource` build engine (pull a bootable guest disk out of an OCI artifact — plugin-vm#43, v2026.269.1932), the containerDisk produce/publish surface (`charly vm build --container-disk --push`, same tag; `charly vm retag --push`, v2026.269.2025), and `charly vm bake --container-disk --push` (plugin-vm#50, v2026.269.2256 — the in-guest candy bake a Cua Fleet image needs). charly's pin (`v0.2026266.1235`) predated all of them, so the whole surface existed only on a `go mod edit -replace` dev build.
- **`plugin-substrate`** carries the `container_disk` distro-presence rule (plugin-substrate#20, v2026.269.1716); the pinned `v0.2026269.14` predated it.
- **`spec`** `v0.2026269.1640` → `v0.2026269.1703` is a **fix**, not currency: spec 1640's `WaitForCloudInit` polls `sudo cloud-init status` — a **password-prompting** sudo. On a guest without passwordless sudo (exactly a Cua Fleet / KubeVirt containerDisk, whose cloud-init is disabled) that poll **hangs 30 minutes**. spec#175 (v0.2026269.1703) reads the status unprivileged first with a `sudo -n` fallback; its own comment names this case: *"the check-cua-container-disk-vm bed hung 30m on 'cloud-init did not settle'"*. `v0.2026269.1703` is the highest spec tag below the C7 checkstep change (v0.2026269.2150) that the released sdk compiles against.

`go mod tidy` changed exactly these three `require`s (+ the matching `go.sum` lines); no other plugin pins move. The three `tools/*` modules that carry the shared sdk/spec pins are then aligned with `charly task mods-tidy` (they must match `charly/go.mod` — `tools/gomod-canonical`'s `TestContractPinsMatchShared`).

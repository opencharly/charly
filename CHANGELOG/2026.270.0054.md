Deliver the Phase 5 **`kind-host`** profile (a `kind: local` template composing
`layer-kind` — the kind binary + the per-engine `kind-engine-prepare` preconditions —

### The corrected shape (and the RCA it fixes)

An earlier revision of this bed composed the `layer-kind` **candy** onto a `vm:` bed via
`add_candy:`, and its comment claimed a nested `local:` would route the candy's
`SystemPackagesStep` through the **host-engine** leg. That claim is **false**, and the
earlier RCA was wrong: a `local:` node placed UNDER a `vm:` node deploys INTO the guest
via `kit.NestedExecutor` (tree position, no `host:` field) — the eval-vm doc comment's
canonical pattern, shipped as box/arch's `check-arch-vm -> arch-host`. `SystemPackagesStep`
runs on the VENUE (the guest), never the host. The `add_candy:` bed also only exercised
the candy and duplicated the profile's candy list (R3).

The bed is now:

```yaml
kind-host:
    local:
        candy: ['@github.com/opencharly/layer-kind:v2026.269.1131']
        install_opts: {allow_repo_changes: true, allow_root_tasks: true}
check-kind-host-vm:
    vm:
        from: eval-vm
        disposable: true
        cpu: 2
        ram: 2G
        lifecycle: dev
    check-kind-host-member:          # nested local node → guest via kit.NestedExecutor
        local:
            from: kind-host
            plan: [ … the toolchain check … ]
```

The member's own plan carries the deterministic check (mirror `check-group-member`): a
composed candy's `plan:` never reaches a deploy-scope check runner for a non-image
deploy, so the check must be authored on the member node. This exercises the `kind-host`
profile end to end, off the operator's workstation.

# 2026.277.0159 — chore(deps)!: adopt spec v0.2026276.1636 — the workflow provider class + typed ExtraCandyRef

## Summary

Adopt the `spec` contract module at **`v0.2026276.1636`** in `charly` — the first range that carries
both the `workflow` provider class and spec#188's typed `ExtraCandyRef` — together with the `sdk` and
compiled-in plugin candies its module graph requires, and adapt charly's `ExtraCandyRef` plumbing to
the typed `{Ref, Scope}` shape that range introduces.

**Why this target.** `spec.ProviderClasses` is a compiled-in closed vocabulary
(`spec/vocab_gen.go`, generated from `#ProviderClassNames` in the schema). `workflow` first appears at
`v0.2026276.0`; charly pinned `v0.2026272.1512`, which does not carry it, so any candy declaring a
`workflow:<word>` provider is rejected outright at `charly box validate` and no bed that composes it
can load. The same bump is a strict superset of `v0.2026273.203`, the typed-ref release that the
`extra_candy_refs` consumers need, so **one** charly head closes both classes.

| pinned module | from | to | why it must move |
|---|---|---|---|
| `github.com/opencharly/spec` | `v0.2026272.1512` | `v0.2026276.1636` | the `workflow` class + typed refs |
| `github.com/opencharly/sdk` | `v0.2026272.1813` | `v0.2026276.1822` | its own `spec` require |
| `.../plugin-build/candy/plugin-build` | `v0.2026272.2040` | `v0.2026276.438` | compiled-in candy; its go.mod requires the contract |
| `.../plugin-fleet/candy/plugin-fleet` | `v0.2026272.2039` | `v0.2026276.1113` | same |
| `.../plugin-installstep/candy/plugin-installstep` | `v0.2026272.244` | `v0.2026276.1353` | same |

Every one of those already had a published tag carrying the adaptation, so **no upstream plugin repo
needs a code change** — this is a lockstep version move, not a fan-out of five fixes.

**The source adaptation.** `spec.ExtraCandyRef` is a typed `{Ref, Scope}` pair, not a bare string. The
upstream doc comment states the reason verbatim — `spec/cue_types_gen.go:2860`, generated from
`schema/buildwire.cue:13`:

```
// #ExtraCandyRef is a candy ref collected IN ADDITION to the closure, together with the
// composition SCOPE that named it. The scope travels WITH the ref so the version arbiter never
// has to GUESS it — a flat [...string] lost the origin and a constant label then collapsed every
// composition into one scope (opencharly/charly#739). Mirrors spec.ExtraCandyRef.
type ExtraCandyRef struct {
	Ref string `yaml:"ref,omitempty" json:"ref"`

	Scope string `yaml:"scope,omitempty" json:"scope,omitempty"`
}
```

So the scope is semantically load-bearing, and it must be the ref's **origin**, not a constant. A
provider ref resolved for a word belongs to no box and therefore carries an **empty** scope; an
authored `add_candy` ref is **box-scoped**:

| file | change |
|---|---|
| `charly/build_overlay.go` | `collectOverlayCandies` returns `[]spec.ExtraCandyRef`, scoping each authored candy to its box via `spec.ScopedExtraCandyRefs(spec.BoxScope(box), …)` |
| `charly/builder_venue.go` | `ExtraCandyRefs []spec.ExtraCandyRef` |
| `charly/check_cmd.go` | a provider ref is `spec.ExtraCandyRef{Ref: ref}` — no box scope |
| `charly/plugin_loader.go` | `deployNodePluginContext` returns `[]spec.ExtraCandyRef` (authored refs box-scoped, provider refs unscoped); `loadDeployPlugins` takes `[]spec.ExtraCandyRef` |
| `charly/host_build_buildengine.go` | threads the typed refs through the build request |
| `charly/host_build_deploy_plugins_connect.go` | same, box-scoping the deploy's own authored refs |
| `charly/host_build_buildengine_test.go`, `charly/refs_test.go` | the same at the test seam |

**The coupled sibling.** charly's own `ci.yml` runs every `tools/*` module, and
`tools/gomod-canonical`'s `TestContractPinsMatchShared` binds those lockstep modules to
`charly/go.mod`'s contract pins. Bumping charly alone leaves them behind and turns the repo's own CI
red. Fixed with the canonical mechanism, `charly task mods-tidy` (its own `check` step proves it) —
not a hand-edit.

Refs `opencharly/charly#632`.

.build/overlay-check-pod-overlay` — so the message's own parenthetical ("the peer runs no host work") is
false in this log. The same starvation class is already documented in this repo for a *test*:
`CHANGELOG/2026.269.2034`, `TestIdleBoundedContext_NilWakeLiteralStillResets` — *"on a loaded host …
that goroutine can be starved past [the window], so the window expires and the test false-fails a call
that is plainly progressing."*

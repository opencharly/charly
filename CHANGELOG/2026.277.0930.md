# 2026.277.0930 — fix(check): carry a verb's CapturedValue through every dispatch path + pin plugin-command/task (workflow-IR W7)

## Summary

The **charly leg (W7)** of the CUE-first workflow-IR wave, tracked in **opencharly/charly#758**. Two things land together, because the second is only provable through the first: the **fix that makes a check verb's captured value survive dispatch**, and the **pin bump to the two producers this wave already merged**.

### 1. The fix — a verb's `CapturedValue` reached the ledger as `""` on every dispatch path

A host-coupled check verb returns `spec.CheckVerbResult` — `Status`, `Message`, and the optional `CapturedValue` the verb stashed while making its judgement. charly's own `spec.CheckResult` carries those three plus `Op`, the resolved verb word, and the timing. **Four** separate dispatch paths each hand-built that literal with `Op`/`Verb`/`Status`/`Message` only, so a producer's capture — the entire reason the field exists, and the only thing `charly task --output` prints — was dropped on every one of them:

| path | site |
|---|---|
| `kitVerbAdapter.RunVerb` | `charly/check_kit_adapter.go:84` |
| `hostVerbResolver.RunVerb`, in-proc branch | `charly/planrun_adapter.go:156` |
| `hostVerbResolver.runPluginVerb`, generic `plugin:` fall-through | `charly/provider_checkenv.go:147` |
| `executorReverseServer.InvokeProvider` | `charly/plugin_dispatch_reverse.go:236` |

There is now **one** conversion, `checkResultFromVerb` (new file `charly/checkverb_result.go`), and all four call it (R3 — one declaration per behaviour; R2 — the same-mechanism siblings are fixed in the same cutover, not one at a time).

The conversion states **no capture policy of its own**: it copies whatever the verb stashed, and leaving it empty for a verdict that captured nothing stays the producer's decision (a FAIL/SKIP arm leaves it empty on purpose — a failed step's output was never vouched for). The `omitempty` tag on `spec.CheckResult` keeps a captureless result byte-identical to the pre-extension wire. The caller passes `verb` rather than the function deriving it, because the word belongs to the dispatch path, not the verdict: an in-proc verb walks under its `Reserved()` word, while the generic `plugin:` fall-through reports `"plugin"`.

**This is what made the wave's own bed step red.** `task-output-captured` — the `check-task` step that reads a task's stdout back through `charly task --output` — could never pass while the value was being discarded here.

The fix is a de-duplication, so the sweep that matters is: *does any hand-built `CheckResult` literal survive that would still drop a verb verdict's capture?*

The surviving literals fall into three groups, and none of them can drop a verb verdict's capture:

- `checkrun.go:46`, `:50`, `:54` — the `passf`/`failf`/`skipf` message-only helpers. They build a result from a format string with no `CheckVerbResult` behind them at all, so there is nothing to lose.
- `checkrun_act.go:81`, `planrun_adapter.go:138`, `:142`, `provider_checkenv.go:164` — zero-values, used as a not-found sentinel or as the starting point for a result the caller then fills in.
- `provider_checkenv.go:72` — the synthetic pre-dispatch result, built as `spec.CheckResult{Verb: "plugin"}` and completed by three `StatusFail` returns (an unresolved word, a `plugin_input` marshal error, and an authored-input validation failure), **all of them before any verb runs**. No verb verdict exists on that path, so there is no capture to drop.

`provider_checkenv.go:164` deserves its own note, because it *is* a real dispatch path and it does *not* go through the new function: `invokeVerbProvider` fills `res` from the `ops.OpRun` **wire** result, and that wire form (`pluginCheckResult`) is deliberately `status` + `message` only — the protocol carries no captured value at all. `CapturedValue` is a contract of the `CheckVerbResult` seam (the in-proc kit verbs and the reverse-channel broker), and every path that reaches *that* seam now goes through `checkResultFromVerb`.

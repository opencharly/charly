# 2026.278.0531 — fix(charly): end the plugin idle guard's false kills and deliver the kill's evidence (#699)

## Summary

The plugin **no-progress watchdog killed provider calls that were plainly making progress**, and
the measurement it was supposed to leave behind never reached the caller. This fixes the guard,
makes its kill message actually carry the evidence, and names the process tree it saw.

**Six defects, every one of them measured — three of the six were found only by running this
change's own R10 bed.** They are listed here in full, then root-caused one by one under
*Root cause (R1)* below.

- **Defect 1 — the kill fired on calls that were progressing.** The guard's CPU progress source read
  **only the peer plugin process's own** `/proc/<pid>/stat` counters. `cutime`/`cstime` aggregate a
  descendant's CPU **only after that descendant has been reaped** — so a peer that forks a long-lived
  CPU-active child and blocks in `wait()` reports a **frozen** tick count for that child's entire
  life. That is exactly the shape of a deploy plugin while its overlay/engine children run.
  Reproduced deterministically with **no bed and no host load** — the identical failure on every
  run of it, nothing else on the box (two retained: `/tmp/699-r10/parent-repro.txt`,
  `parent-repro2.txt`).
- **Defect 2 — the kill fired on the FIRST unconfirmed expiry.** A coalesced `touch()` burst can drop
  its one token, and a `select` picks at random among ready cases, so `case <-timer.C` can win the
  race while an unread progress event sits in the channel.
- **Defect 3 — the sentinel asserted a cause it could not prove**, which sent a week of investigation
  after a trigger that did **not** survive the solo reproductions.
- **Defect 4 — the report was thrown away on the way to the caller** (found by this change's first R10
  bed, which came back RED carrying the new sentinel text and **no report at all**):
  `pluginInvokeErr` re-wrapped the bare sentinel, so the report the watchdog had built was discarded.
  The instrumentation never reached the bed — a conclusion with no evidence, which is the defect #699
  *is*, reproduced by the fix for it, and invisible to `errors.Is`, so nothing caught it.
- **Defect 5 — the tests this change adds orphaned their own CPU burners** (found while gating that
  bed): they pinned the host above the idle level the bed requires. The report this branch adds warns
  that *"a starved host … reads this way"* — the suite was manufacturing the starved host, so the bed
  could have gone red for a reason with nothing to do with the guard.
- **Defect 6 — the one host reverse leg that was not heartbeated** (found by this change's second R10
  bed, the one run on this branch's own fixed tree — the deepest defect of the set): the guard was
  watching a clock that a legitimately long call *cannot* advance. A peer plugin parked in its own
  `exec.InvokeProvider` callback makes no CPU and no reverse leg while the **host** serves its
  request, so a call the host was burning ~1.4 cores on read as "the peer runs no host work".
  `InvokeProvider` was the one host reverse leg not wrapped in `withActivityHeartbeatErr`. Fixed, and
  pinned by a test that reds in 0.24 s without the fix.

**The previous head's review (`charly/pr-validator`, BLOCK) raised three findings, every one of them
R1 (B5) — comments asserting behaviour the code did not have, plus one reset nobody had proven. All
three are fixed in the push on this head, in ONE commit, and each fix is pinned by a test that
**FAILS when that fix is reverted** (section 9 below):**

- the `case <-cpu.C` arm passed a **nil** wake channel to `observe` while its comment claimed the
  call drained a pending host-leg token — and `observe`'s own doc, two functions up in the same
  file, said a nil channel never fires in a `select`. The drain was a no-op, so the comment asserted
  a safety property the call did not provide. The **live** channel is now passed, so the drain is
  real and the comment describes what the code does;
- `procTreeProcs`' doc said the walk was "breadth-first" where the LIFO stack is **depth-first
  pre-order**. The doc now says so and the variable is named `stack`;
- `reset()` is now invoked from the **expiry path itself**, a call the previous code never made from
  the timer arm, and no pasted test exercised it. It is now the package-level `resetDeadline`, whose
  drain is a `select`-with-default — a bare `<-timer.C` there would block **forever** and wedge the
  watcher — and both timer states are pinned by tests.

This change is the fix for **opencharly/charly#699** (`no-progress-guard`), and it is the blocker
for the `#762` bed roster.

## Root cause (R1) — six defects, all measured

### Defect 1 — the CPU source cannot see a peer's work that lives in a child

`cpu()` called `procCPUTicks(pid)` = `utime + stime + cutime + cstime` **of the peer process
alone**. A shell parked in `wait()` accrues no `utime`/`stime` of its own, and its child's CPU is
not folded into `cutime` until the child is reaped. Measured further: the peer's own count is
genuinely **0** — and `procCPUTicks` returns the same `0` for "frozen" and for
"error / unreadable", so the guard **cannot tell them apart**.

Verbatim, on the **parent production code** (`9cd960ea`), with no bed and no host load — the new
test compiled against the parent's `plugin_activity.go` and run 8 times:


Repeated with nothing else running: the identical FAIL on every run, never a pass — the assertion
that reds is the new test's, on the parent's own code (two retained: `parent-repro.txt`,
`parent-repro2.txt`). Deterministic, with nothing on the box.

### Defect 2 — the kill fired on the FIRST unconfirmed expiry

`touch()` is a **non-blocking depth-1 send**, so a coalesced burst collapses to one token that can
be **dropped** when the buffer is already full; and Go's `select` picks **at random among ready
cases**, so `case <-timer.C` can win the race while an unread progress event sits in the channel.
The CPU source is also *sampled*, so its last observation can lag. The doc comment above the
`wake` field claimed a progress event "always resets" the deadline and that there is "therefore NO
race" — true of the **event** path, false of the **expiry** path.

### Defect 3 — the sentinel asserted a cause it could not prove

The error text ended `(hung plugin — the peer runs no host work)`. That is a conclusion, not a
measurement, and it sent a week of investigation after the wrong mechanism (the issue title's
"under concurrent image builds" trigger, which did **not** survive the solo reproductions).

### Defect 4 — the report was thrown away on the way to the caller (found by the R10 bed)

The watchdog cancels with the report wrapped around the sentinel:

```go
cancel(fmt.Errorf("%w: %s", errPluginCallIdle, a.stallReport(noProgress)))
```

but `pluginInvokeErr` re-wrapped the **bare** sentinel, discarding it:

```go
if errors.Is(context.Cause(ctx), errPluginCallIdle) {
    return fmt.Errorf("%s: %w", what, errPluginCallIdle)   // <- the report dies here
}
```

Type-checks identically, satisfies `errors.Is` identically — and silently deletes the evidence. The
first R10 run of this change reproduced it verbatim, at the same step and the same line as the
second one would (`2026.278.0153/update.log:39`):

```
charly: error: command "deploy": deploy-dispatch add: deploy plugin: deploy-dispatch add: prepare venue: InvokeProvider deploy:pod op=prepare-venue: InvokeProvider: plugin call made no host-visible progress within the no-progress window (no host reverse leg and no CPU advance from the peer process or any of its live descendants)
```

That is the new sentinel and nothing else. No report.

### Defect 5 — the test suite orphaned its own CPU burners (found while gating the bed)

The tests this change adds fork a CPU-burning **grandchild** (`sh -c '…' & wait`) and then
reaped only the **direct child** with `cmd.Process.Kill()`. Reparented to the init process,
the grandchild spins at 100% of a core until its loop ends — minutes — invisible to the test
that made it.

Measured two ways. **Reproducibly**, with the checker this change adds (its output is pasted in
section 4 below): under the **old** kill style two of those tests leave **2 orphans reparented to
`ppid=566`**, and under the new helper the same two tests leave **0**. **Live**, while waiting on
this very bed, the same shape was seen with `ps` as **three** reparented burners (`ppid=566` is this
host's user manager, so their parents were already gone) at ~99% of a core each — enough to pin
loadavg above the idle-host level the bed requires. A single burner of exactly that shape, started
and then orphaned on this host, reads verbatim:

guard, and the report would have blamed the host. Test hygiene is load-bearing evidence here.

And the missing datum — **the host's own CPU**, which the guard never measures — taken live by a
sampler reading `utime`/`stime` from `/proc/<pid>/stat` of every `charly` and `__plugin serve`
process at a 5 s cadence (`/tmp/699-cpu.sh`, log retained at `/tmp/699-cpu.log`). During the resolve


So the host was busy for the whole window that the guard read as "the peer runs no host work" — and
that sampler is the one thing the guard's own report cannot show, which is why the report says what
it *measured* (`host reverse legs`, `CPU advances`, the peer tree at the kill) rather than asserting
a cause.

**The mechanism.** A peer plugin's own `exec.InvokeProvider` callback asks the HOST to perform a
provider call on its behalf, and the host serves it on `executorReverseServer.InvokeProvider`. While
the host serves it the CALLER is parked in that callback — no CPU, no children — and the served work
produces **no reverse leg on the caller's clock either**, because it runs entirely host-side: for
`build:generate op=resolve` the target is compiled-in (plugin-build is not served at all —
`grep -c 'plugin plugin-build'` = **0** in the run above, so `providerPid` → 0) and its whole host-FS
prep (`host_prep.go`: `cleanStaleBuildDirs`, `writeContextIgnore`, `createRemoteCandyCopies`, and the
container image-store listing) makes **zero** `ex.` calls. So both of the clock's sources are blind
for exactly as long as the host works hardest — 90 s of the host at ~1.3 cores, then killed as "the
peer runs no host work".

The clock it fires on is the CALLER's: `plugin_dispatch_reverse.go` threads it onto the nested channel
(`inv.InvokeWithExecutor(withPluginActivity(ctx, activity), …)`), and the nested server is built with
`activity: pluginActivityFrom(ctx)` (`plugin_grpc.go:422`) — so `s.activity` inside the handler **is**
the clock that fired, which is why the report names the caller's peer.

`HostBuild` and every executor leg already wrap their blocking work in
`withActivityHeartbeatErr(s.activity, …)`; `startPluginActivityHeartbeat`'s own doc states the
invariant — *"host_build_cli and the host reverse legs wrap their blocking work with this so the work
being ALIVE is forward progress for its whole (possibly ~13min) duration"*. **`InvokeProvider` was
the one host reverse leg that did not**, and the overlay resolve is precisely the caller that needs
it.

**The fix** — heartbeat the served dispatch, mirroring `HostBuild`:

```go
func (s *executorReverseServer) InvokeProvider(ctx context.Context, req *pb.InvokeProviderRequest) (*pb.InvokeReply, error) {
	var reply *pb.InvokeReply
	err := withActivityHeartbeatErr(s.activity, func() error {
		var serr error
		reply, serr = s.invokeProvider(ctx, req)
		return serr
	})
	return reply, err
}
```

This **does not widen the guard**: the served call keeps its own `idleBoundedContext`
(`invokeProvider`), so a genuinely hung target still fails fast on that clock and its error propagates
through the wrapper and stops the heartbeat. The two halves are now pinned side by side in
`plugin_dispatch_reverse_timeout_test.go` — the pre-existing `TestInvokeProvider_FailsFastOnHungPeer`
(a hung target must still be killed) and the new
`TestInvokeProvider_ServedHostWorkHeartbeatsTheCallerClock` (a served, leg-free host-side call must
not be).

One design note, because it is the difference between a test and a **vacuous** test: the new guard's
caller is a **REAL live process** parked in its callback (`sleep 30`, its own process group), and its
clock is *watched* by `idleBoundedContext`. The first version built the clock as
`newPluginActivity(0)` and passed the full duration even with the heartbeat removed — a clock nobody
watches cannot kill anything, so it proved nothing. A pid-0 clock would also have been ambiguous
against the *in-proc* target's own idle bound (below). With the real, watched caller clock, the test
can only pass if the served dispatch itself supplies the progress event.

## What changed

**1. `procTree` — the CPU source is now the peer's whole LIVE process tree.**
Every process contributes `utime+stime+cutime+cstime`, so the sum is **monotone**: a reaped
descendant's ticks move out of its own counters and into its parent's `cutime`, which is itself
summed. A **zombie is summed but not counted as live**, so the sum cannot dip at a child's exit
and hide a real advance. `/proc` unreadable degrades to the root-only reader rather than to a
false kill.

**2. `observe` — one progress measurement, and no kill on an unconfirmed expiry.**
It drains a pending host-leg token (counting it) or compares the tree CPU against the high-water
mark. On expiry it re-measures **both** sources and cancels only when **neither** has anything.

**3. `errPluginCallIdle` + `stallReport` — the kill carries the measurement, and names the tree.**
`procTreeProcs` is now the **one** tree walker: `procTree` sums what it returns and the report
renders it, so the two can never describe different trees. Every kill appends:

```
peer pid=%d; over the call: host reverse legs=%d (last %s), CPU advances=%d (last %s);
peer tree at kill: %d live process(es) summing %d ticks (root-only reader %d): <pid(state,comm), …>;
window=%s. A starved host, a double-forked descendant and a genuinely wedged peer all read this
way — if the tree shows live processes, re-run on an idle host before reading it as a hang
```

The member list is what makes it decisive: a sleeping parent waiting on a running child (the
guard's **own covered case**) is then distinguishable from a reparented — double-forked — worker
that is simply absent, or a `D`-state I/O wait the guard cannot help at all. `pid<=0`, an
unreadable `/proc` and a walkable-but-empty tree are three different facts and read as three
different sentences.

**4. `pluginInvokeErr` propagates the CAUSE**, so the sentinel **and** its report reach the caller.
`errors.Is(err, errPluginCallIdle)` still holds, because the cause wraps the sentinel.

**5. `startInOwnGroup` — the tests kill the peer's whole process group**, not just the peer.
The child is started with `Setpgid: true` and the cleanup SIGKILLs `-pgid`: the only handle that
still reaches a grandchild the peer has already forked. `-pgid` names exactly that child's tree —
never the test binary's own group. All five spawn sites go through the one helper (R3).

**6. `executorReverseServer.InvokeProvider` heartbeats the CALLER's clock while it serves the call.**
The served body is split out to `invokeProvider` so the wrapper can hold `withActivityHeartbeatErr`
around it — the same shape `HostBuild` already uses for the builds it runs on a plugin's behalf, and
the invariant `startPluginActivityHeartbeat`'s doc states. The served call keeps its own
`idleBoundedContext`, so a wedged target still fails fast on its own clock (defect 6, above).

**7. The review-fix commit — the guard's own claims made true (see section 9).** The `case <-cpu.C`
arm now passes the **live** `wake` channel, so the drain its comment claimed is real; `procTreeProcs`'
doc names the **depth-first pre-order** walk its LIFO stack performs (the variable is `stack`, not
`queue`); and the reset is the package-level `resetDeadline`, whose drain is a `select`-with-default
so it cannot block on the expiry path it is now called from. No behaviour is widened: the changed call
only adds progress signal, and the rest is naming what the code already did.

### 9. The previous head's review findings — all three fixed in ONE commit, each pinned by a test

The fresh `charly/pr-validator` BLOCKED the previous head (`40209961`) on three findings, all of them

commit carries all three — nothing was deferred, nothing was argued — and the whole of the code

**Finding 1 — the `case <-cpu.C` arm's comment claimed a drain the call could not perform.** It
passed `nil`, and `observe`'s own doc two functions up said plainly that a nil channel never fires in


Draining there is **strictly conservative** — it counts a touch that really happened, so it can only
ever prevent a kill, never cause one — and `observe`'s doc is corrected to match (a nil channel stays
legal for a caller with no event source; the watcher now passes one at **both** of its call sites).

depends on — `TestObserve_PendingLegEventAtExpiryIsProgress` proves `observe` **does** drain a
pending token when given the live channel, which is exactly what the nil call site could not do.

# 2026.279.1154 — ci: run charly's workflows on the org's self-hosted runners

## Summary

`opencharly/charly` ran its three workflows on GitHub-hosted `ubuntu-latest`, even though the org runs **8 self-hosted runners** (`charly-githubrunner-no-1..8`, label `opencharly`) that its own required `charly/pr-validator` already uses. A hosted run does not merely run slower — it can sit **queued indefinitely**, and that reds the required check on a green PR.

Measured today on `#803` (head `4ceb294c`): `ci` run `37367043549` stayed `queued` for **>15 minutes and never started**. The org-required `validate / validate` gate waits for the head's check-runs to settle, then fails at 600 s:

```
2026-10-05T20:13:02.3941025Z go -> queued/null
2026-10-05T20:13:02.4144017Z ##[error]could not confirm this head is green: still in flight after 600s — go
2026-10-05T20:13:02.4176046Z ##[error]Process completed with exit code 1.
```

So the PR was BLOCKED with diff green, `golangci-lint` green and review verdict **PASS** — the failure lived in the runner queue, not in the change.

This PR moves all three workflows to the org's self-hosted fleet:

```
ci.yml             go               runs-on: ${{ vars.CI_RUNNER_LABEL || 'ubuntu-latest' }}
release-binary.yml build            runs-on: ${{ vars.CI_RUNNER_LABEL || 'ubuntu-latest' }}
tag-on-merge.yml   wait-for-merge   runs-on: ${{ vars.CI_RUNNER_LABEL || 'ubuntu-latest' }}
```

`tag-on-merge.yml`'s second job is a reusable-workflow call (`uses: opencharly/.github/.github/workflows/tag-on-merge.yml@main`) and carries no `runs-on`, so `wait-for-merge` is the file's only one. Nothing else changes: no step, `uses`, trigger, permission or script is touched.

The label comes from a variable, mirroring the org's existing convention (`vars.REVIEW_RUNNER_LABEL` is how `pr-validator` selects its runner), with the hosted runner as the fallback — so an unset variable degrades to exactly today's behaviour rather than breaking CI.

Refs #806.

**The first `go` run on this head exposed a real fleet defect, and it is now fixed.** The job landed correctly on the pool (`labels: ["opencharly"]`, assigned `charly-githubrunner-no-2` in **6 s** — against `>15 min` of no assignment on the hosted pool for `#803`), then failed:


Root cause (measured in the running container, not inferred): the runner image carried Arch's `coreutils`, which ships **no `hostname(1)`** (``hostname` is `inetutils`'s). charly's venue-descriptor tests shell out to `hostname`, so the red is in the **image**, not in this workflow diff.

1. Rebuilt the image from `distro-cachyos` `main` (`a9afa6b1`, which carries `pod-github-runner:v2026.279.0028` → the merged `inetutils` fix, `pod-github-runner#8`) — built `ghcr.io/opencharly/githubrunner:2026.279.1036`.
2. Redeployed all eight `charly-githubrunner-no-{1..8}` onto that image (`charly --repo opencharly/distro-cachyos config githubrunner -i no-N --tag 2026.279.1036` + `systemctl --user restart`).

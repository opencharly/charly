# 2026.279.1234 — fix(check): declare the missing step budgets in the check-sidecar-pod bed

## Summary

The `check-sidecar-pod` bed's six unbudgeted `${CHARLY_BIN}` check steps declare an explicit `timeout: 300s`. Nothing else changes: no plan step, `id`, command or assertion is touched, and `charly box validate` is clean.

The bed's plan is 13 steps — 7 `check:` and 6 `run:`. A check-live pass dispatches the 7 `check:` steps and skips the 6 `run:` ones ("skipped — verify-only mode (mutating step)"). **All 7 `check:` steps invoke `${CHARLY_BIN}`**, so each pays charly's own project evaluation before it does its own work; six of the seven declared no `timeout:` and therefore inherited the runner's per-attempt never-hang floor. That is the defect this PR fixes: a step whose *legitimate* cost sits next to the floor is killed non-deterministically.

The measured cost of such a step on this host is **94.9 s** (see §3), against the floor that killed it. The new budget makes the never-hang bound resolve to the authored value + 30 s (330 s, `sdk/kit`'s `ProbeNeverHang` honours a longer authored value) instead of the floor — the mechanism's own parameter, and `charly#650`'s recorded direction #1: *"give load-sensitive bed steps an explicit `timeout:` (the bed already does this for `sidecar-pod-roundtrip-final` at 300s)"*.

> Killed at the 120s per-attempt ceiling under the full 28-bed roster (~30-40 containers resident; `charly status` fans out per-container), while green solo. 300s covers the measured worst case (2m0s kill point) with honest headroom. The underlying status fan-out COST is a separate concern, tracked as task #26 — this budget buys the bed correctness, it does not excuse the cost.

*(That block is `charly#650`'s own record of the failure class, quoted so the precedent is visible rather than paraphrased.)*

### 3. What the step actually costs — measured on this host

The step is `charly shell check-sidecar-pod -c "echo shell-roundtrip-ok"`, timed directly against a live deploy (not inferred from `charly box validate`), at three contention levels:

```
=== S0 idle  loadavg=5.79 7.57 24.12
    step rc=0 elapsed=94.9s
=== S1 load~120  loadavg=80.18 28.65 30.34
    step rc=0 elapsed=1112.7s
    loadavg after: 125.47 122.80 96.43
=== S2 load~120 + 120s cap  loadavg=115.19 118.33 96.78
    step rc=KILLED elapsed=120.3s   (KILLED == the original failure mode)
```

`S2` is the original failure reproduced on demand: the same step, the same cap, killed at the cap. So the load response and the kill mechanism are both established by measurement rather than by argument.

**Under a real roster, on this host.** `S1` is a synthetic worst case (120 busy loops on 16 cores — 7.5× CPU oversubscription, *all-runnable*, which is harsher than a roster of mostly-waiting containers). The roster's own signature was measured directly, by accident, when a peer session's roster was live while this bed's deploy was being built — and the very same bed's own operation pays exactly that cost:

```
START host nproc=16 loadavg=96.56 106.36 65.83
SETUP  charly deploy add check-sidecar-pod  rc=0 elapsed=512.8s
```

`charly deploy add check-sidecar-pod` costs **160 s** unloaded (its own `deploy-add` phase, both runs above) and **512.8 s** at loadavg **96.56** — a **3.2×** inflation on **one** of the bed's operations. Exactly two things follow, and no more:

- The roster band inflates this bed's work by roughly 3.2× **on the operation that was measured**. That is a *proxy* for the step's own cost, not a measurement of it — and this PR does not use it as one.
- The roster's load is *not* CPU starvation: had ~100 loadavg meant the CPU pressure of the `S1` synthetic, that same `deploy add` would have paid its ~95 s project evaluation at the `S1` rate and could not have finished in 512.8 s. `S1` is therefore an upper bound for an artificial regime, not a prediction for the roster's.

**What this budget covers, and what it does not — stated plainly.** It covers the **quiet-host regime, and only that regime**. That is the regime run `1503` actually failed in: the step's measured cost is `94.9 s`, against the `120 s` floor that killed it — it was sitting **1.27×** under a ceiling it had to clear, so ordinary variance crossed the floor. The new authored `300s` (resolving to a `330 s` bound) puts that quiet-host cost at a **3.5×** margin instead of `1.27×`. That is the defect, and that is what this fixes.

It does **not** claim roster coverage. An earlier revision of this body did, and that claim was wrong, on the body's own numbers: (i) the roster-regime cost of *this step* was never established — the direct attempt returned a null result (`§3`, below), so the only roster figure in hand is a `deploy add` proxy for a different operation; and (ii) computed from that proxy the claim would read `330 s / (94.9 s × 3.2) ≈ 1.09×`, which is **tighter** than the `1.27×` margin that already proved insufficient. A margin *below* the one that failed cannot be coverage, whatever its provenance. Roster-regime robustness for this step is therefore **routed, not claimed**: it is `charly#650`'s recorded direction #1, and the underlying COST — charly evaluating its own 609-candy project inside every bed step — is filed as `opencharly/sdk#319` and `opencharly/charly#650`. `S1` (1112.7 s) exceeds the 330 s bound and always will; a per-step budget cannot buy that off, and this one does not pretend to.

**A second, independent measurement under a live roster — attempted, and reported as the null result it is.** A 45-minute window was opened on this host to time the step at the moment a real roster is running: the bed's deploy was built up, then `/proc/loadavg` was polled every 20 s for `load1 >= 80`. **No roster started inside the window** — the wait expired on `=== R load1=2.11 loadavg=2.11 2.07 3.67`, with `load1` still falling (4.24 → 2.11). The step was timed anyway at that quiet load, and the capped run is a second clean measurement of the same regime as `S0`:

```
step uncapped  rc=0 elapsed=176.1s   <- EXCLUDED, see below
step @120s cap rc=0 elapsed=100.7s   NOT killed
```

`100.7 s` against `S0`'s `94.9 s` is ~6% apart and consistent with the **1.27×**-under-the-floor margin this PR fixes.

The uncapped run (`176.1 s`) is **excluded, and used nowhere in this PR**: my own `git worktree add` (a ~570-file checkout) and a `git merge` of `origin/main` ran inside its window, and a step whose cost is charly evaluating the whole 609-candy corpus is exactly what a fresh checkout perturbs. It is recorded because omitting it silently would have hidden a 1.86× spread that the two clean runs do not show.

So the roster-regime cost of **this step** is established by neither this attempt nor the `deploy add` proxy; it remains unmeasured, and the budget above claims nothing from it. This attempt is recorded as the null result it is rather than dressed up as the roster run it never was.

### 4. Mechanism (why the step is CPU-bound, not waiting)

```
$ timeout 45 ./bin/charly shell check-sidecar-pod -c "echo shell-roundtrip-ok"; kill -QUIT <pid>   # goroutine dump
goroutine 1 gp=… m=nil [runnable]:
cuelang.org/go@v0.16.1/internal/core/adt.(*overlayContext).cloneVertex … overlay.go:285
  ← doDisjunct … disjunct2.go:592 ← crossProduct …:413 ← processDisjunctions …:309
  ← adt.(*Vertex).unify → completeAllArcs → unify → … → overlay.cloneRoot
```

Exactly one busy goroutine, CPU-bound in CUE disjunction/overlay expansion — the project evaluation, not an I/O wait, a lock, or a plugin wait. Ruled out by measurement: stale plugin locks (`flock -n` FREE on every sampled lock; 0 lock files touched in 2 h; `/proc/locks` = 63); plugin-spawn fan-out (3 hosts served); stdin/TTY (every variant exits 124); `.check/` fixture poisoning (0 `charly.yml` under `.check/`).

This is what makes the cost *load-sensitive and structural at once*: it is pure CPU (so a roster's CPU pressure multiplies it, `§3`) and it is paid by every one of the seven steps (so it is not one step's accident). The cost itself — `charly` evaluating its own 609-candy project before a bed step does any work — stays filed as `opencharly/sdk#319` and `opencharly/charly#650`; a bed budget does not fix it and does not pretend to.

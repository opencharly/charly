# 2026.281.0855 — fix(tools): adopt the shared sdk pin in every tools module (unblocks main's red TestContractPinsMatchShared, charly#836)

## Summary

`main` is red in `charly`, and this is the repair. `tools/gomod-canonical`'s
`TestContractPinsMatchShared` compares every lockstep in-repo module against the shared sdk pin, and
three `tools/*` modules were still on the old one:

```
$ git checkout origin/main -- tools/generate-packages/go.mod tools/generate-packages/go.sum \
                             tools/golden-cloudinit/go.mod tools/golden-cloudinit/go.sum \
                             tools/golden-compile/go.mod tools/golden-compile/go.sum
$ cd tools/gomod-canonical && GOWORK=off GOTMPDIR=~/.cache/go-tmp go test -count=1 -v ./...

    gomod_canonical_test.go:117: ../../tools/generate-packages/go.mod: requires sdk v0.2026280.1251, but the shared sdk pin is v0.2026280.2133 - run `charly task mods-tidy`
    gomod_canonical_test.go:117: ../../tools/golden-compile/go.mod: requires sdk v0.2026280.1251, but the shared sdk pin is v0.2026280.2133 - run `charly task mods-tidy`
```

That is the **complete** output of the failing assertion, not an excerpt: it names two modules
although three carried the stale pin. The third's invisibility is measured, and it is a second
coverage gap in the same test (the first being the cache, which is the gate PR's subject):

```
$ sed -n '14p' tools/gomod-canonical/gomod_canonical_test.go
var contractRequireRe = regexp.MustCompile(`(?m)^\s*github\.com/opencharly/(sdk|spec)\s+(v\S+)`)
$ git show origin/main:tools/golden-cloudinit/go.mod | grep -nE "opencharly/(sdk|spec)"
5:require github.com/opencharly/sdk v0.2026280.1251
18:	github.com/opencharly/spec v0.2026280.1255 // indirect
$ printf 'require github.com/opencharly/sdk v0.2026280.1251\n' > /tmp/oneline.go.mod
$ printf 'require (\n\tgithub.com/opencharly/sdk v0.2026280.1251\n)\n' > /tmp/block.go.mod
$ grep -cE '^[[:space:]]*github\.com/opencharly/(sdk|spec)[[:space:]]+(v[^[:space:]]+)' /tmp/oneline.go.mod
0
$ grep -cE '^[[:space:]]*github\.com/opencharly/(sdk|spec)[[:space:]]+(v[^[:space:]]+)' /tmp/block.go.mod
1
```

`golden-cloudinit`'s **sdk** require is the SINGLE-LINE form (`require github.com/opencharly/sdk v…`),
which the anchored regex cannot match, while its **spec** require sits in a parenthesized block, which
it matches — so the module IS in `lockstepModules(t)`'s compared set (its spec pin was compared and
matched) but its stale **sdk** pin was never read. Two stale pins were therefore reported and three
were repaired: `charly task mods-tidy` rewrites the pins wholesale and its own `check` step asserts
every lockstep module, which is why the task found the third and the assertion did not.

`main`'s own `ci.yml` confesses the state, verbatim, directly above the step that reports it:
*"TestContractPinsMatchShared was already FAILING on `main` (the `tools/*` modules sat on an older
sdk/spec pin than charly/go.mod) and no CI job ran it. This step runs every tools module, so the gate
can no longer rot silently — the same class of hole the golangci-lint step above closes."* The step is
newer than the drift, which is why a run-level conclusion on `main` can read green while this
assertion is red — and why **every PR that folds `main` in fails `go` and cannot arm** until the
artefacts are fixed (`charly#830` is the instance in hand; `charly#836` is the row).

The fix is the one the test names, run through the repo's own task — no hand-pin:

```
$ ./bin/charly task mods-tidy
task mods-tidy: 2 step(s), 0 failed
  [pass] run — adopt the shared pins and tidy every lockstep module
      exit=0
  [pass] check — every lockstep module now carries the shared pins
      exit=0
```

Diff: `tools/generate-packages`, `tools/golden-cloudinit` and `tools/golden-compile` — `go.mod` +
`go.sum` each — moving `github.com/opencharly/sdk` from `v0.2026280.1251` to the shared
`v0.2026280.2133` (the value `charly/go.mod` already carried). Nothing else changes, and no pin moves
anywhere but to the already-shared value: the task's own `check` step asserts exactly that.

## Summary

**This is the critical path.** Six PRs are red on `latest=failure` because of this one bed step, and
a red required bed blocks: `charly#823`, `charly#828`, `plugin-check#89`, `plugin-clean#12`,
`plugin-deploy-pod#30`, `spec#205`. Review the assertion change below carefully rather than skimming
it — the diff is one step, but it is the difference between a gate that measures the code and a gate
that measures upstream's release clock.

The step `box-reconcile-remote-cached` asserted `stdout contains 'already reconciled'` from
`charly box reconcile --remote --dry-run`. That string is printed **only** when `len(rewrites) == 0`
(`plugin-box`'s `reconcile.go:146-150`), and every pin's comparison target is *the newest remote tag
at the instant of the run* (`reconcileTargetVersion(remote=true) -> refs.GitLatestTag`, `:170-180`);
`--dry-run` suppresses the write, never the comparison. So the assertion held only in the window
between a full pin sync and the next upstream landing — three independent measurements saw
**17 → 9 → 18** rewritable pins across consecutive runs, with tags minted *during* the bed. The step's
own text states a different, stable purpose: it exists to exercise the **cached, disk-persisted**
`LatestTag` path (the retired raw per-process `ls-remote` reintroduced a 90-94 concurrent fanout).

So the assertion now measures that stable property, and reports drift instead of denying it:

```
first=$(${CHARLY_BIN} box reconcile --remote --dry-run 2>&1)
second=$(${CHARLY_BIN} box reconcile --remote --dry-run 2>&1)
# the persisted cache must serve the SECOND --remote run (the regression probe)
printf '%s' "$second" | grep -q 'fetching git metadata' && { echo "...re-probed instead of serving the persisted cache"; exit 1; }
# the two runs must agree once the one-off warm-up chatter is stripped (reconcile is idempotent)
report() { printf '%s\n' "$1" | grep -vE '^charly: (fetching git metadata|git metadata cached)'; }
test "$(report "$first")" = "$(report "$second")"
# the report must still be one of the two known shapes — drift is PRINTED, not asserted absent
printf '%s\n' "$first" | grep -qE '^already reconciled|^would rewrite [0-9]+ pin\(s\):'
echo BOX-RECONCILE-CACHED-OK
```

`stdout: contains BOX-RECONCILE-CACHED-OK` is the assertion. Nothing else in the file changes.

Also in this diff, the correction of the invalidated claim wherever it lived on the surfaces this
repo owns: the step's `check:` text now states the churn-stable property it asserts, and says
explicitly that a stale pin is a report this step prints rather than a red gate (the previous text
("a stale repo would print 'would rewrite', so the assertion fails if …") described the old,
unsatisfiable-by-construction assertion). The generated `check` skill body carries the same
correction through the Lead's routing (`layer-charly-check`'s `check-skill` entity), not from here.

### 3. The removed assertion tested upstream state, not a defect — and the new one still catches the regression it exists for

**What the removed assertion actually tested.** `stdout contains 'already reconciled'` held only when
`len(rewrites) == 0` (plugin-box `reconcile.go:146-150`) over targets resolved to *the newest remote
tag at the instant of the run*. It therefore failed whenever any repo in the closure had published a
tag — measured by three agents independently as `17 → 9 → 18` rewritable pins across consecutive
runs, with tags minted *during* the bed — and by this PR's own `D1 → D2` datum above (`18 → 20`). It
failed on **upstream state, not on a defect**.

**What the new assertion tests.** That the persisted cache serves the SECOND `--remote` run (a
re-probe is the regression the step exists for), that the two runs agree, and that the report is one
of the two known shapes — i.e. the same regression class is caught deterministically, and drift is
*printed* rather than denied.

**The mutation, on the product's own surface** (`charly cache clear`, a sanctioned verb; no persistent
global bypass is left behind). The step's own shell logic, run three ways:

```
$ bash /tmp/t4-mutation.sh
=== ARM 1 — cache warm (the live step): must be GREEN
BOX-RECONCILE-CACHED-OK
arm1 exit=0
=== ARM 2 — MUTATION: drop the cache BETWEEN the two runs, so the second re-probes
box reconcile --remote re-probed the remote instead of serving the persisted cache
```

ARM 2 is the arm that matters: with the cache dropped between the two runs the second run re-probes,
the new check fires with its exact message and the step **exits 1**. So the check is NARROWED to the
property it was written for (the cached path is used) — it does not stop failing where it should —
while the property it cannot control (upstream's release clock) is reported instead of gated.

# 2026.281.1057 — chore(distros)!: roll box/cachyos to the newest released tag

## Summary

Policy B makes **charly's own `box/<distro>` gitlinks the source of truth** that the umbrella's `distro-*` pins follow, so a distro release can only reach the umbrella after charly rolls. `box/cachyos` was still at `a9afa6b` — the pre-M4 tip — and that is what kept this cutover's M4 step and its refs repoint out of the umbrella's view. This PR rolls it.

- `box/cachyos`: `a9afa6b` → **`673b1b6`**, the commit `distro-cachyos v2026.281.1001` points at. That tag carries M4's deletion of the three openclaw boxes, their beds and the `openclaw-desktop` skill, plus this cutover's refs repoint — so rolling here is what lets the umbrella, and then the marketplace corpus, see the CachyOS family without the retired openclaw content.

**Gitlink only.** No submodule content is touched and no nested checkout is created; the change is written to the index as a gitlink and nothing else in the tree moves.

**Why only `box/cachyos`:** policy B is a **consistency** rule — every `distro-*` pin equals charly's own `box/*` gitlink — not a "newest tag" rule. This cutover needs CachyOS, and rolling the other distros would be unrelated drift inside a pinning PR.

**Named follow-up in the same cutover:** `./charly/bin/charly task sync` in the umbrella propagates this into its `distro-*` pins, and `charly task verify` is then the pinning gate (it has **no CI gate**, so it is run by hand).

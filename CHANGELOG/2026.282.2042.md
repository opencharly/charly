# 2026.282.2042 — feat(pluginsgen): let --dev-plugin reach an OUT-OF-PROCESS plugin — every deploy-substrate change was unprovable against its own head (charly#835)

## Summary

`--dev-plugin` is the **documented** dev-loop bridge: it "builds a compiled-in plugin FROM A LOCAL CHECKOUT instead of its pinned module-proxy tag, so a bed run on this binary exercises the plugin's UNMERGED source". It refused every plugin not in `compiled_plugins:` — so **every out-of-process plugin's change was unprovable at review time by construction** (`charly#835`). That is not a deferral an author could choose otherwise; it is the absence of a mechanism, and it has already left `plugin-box#26` stuck on exactly this for rounds.

```console
$ ./scripts/bootstrap-charly.sh --dev-plugin plugin-deploy-pod=<checkout>     # before this PR
pluginsgen: -dev-plugin plugin-deploy-pod: not in the compiled_plugins: list of charly/charly.yml
            — only a plugin this build COMPILES IN can be re-pointed at a local checkout
exit status 1
```

## What the receiving side already had

`plugin_loader.go:743-778` already serves an out-of-process plugin's REPO from a local override tree, and `:216 buildPluginBinary(ctx, srcDir, name)` already builds one from a source dir. **The host could build and serve from a checkout; the flag simply had no way to hand it one.** `resolveDevPlugins`' single membership test was the entire limitation.

## What changes

- **`charly/internal/pluginsgen/main.go`** — `resolveDevPlugins` drops the `compiled_plugins:` membership requirement and keeps every other validation, including the one that matters: that the checkout really *is* that plugin's module (`candy/<name>/go.mod` declaring `github.com/opencharly/<name>/candy/<name>`).
- **The dev override reaches run time through the route that already exists.** For a compiled-in plugin `go.work.dev` works because the *build* reads it; an out-of-process plugin is built by the **host at run time**, and the seam that serves it is `spec.ProjectLoader.RepoOverrideDir`, whose ONE implementation lives in `plugin-loader`'s own repository and parses `CHARLY_REPO_OVERRIDE`. A generated file cannot reach it; **the env var is the only channel both sides share**, which is this issue's option 3 — name the ONE sanctioned route and make it work.
- **`charly/main.go`** — seeds that variable from the generated entries, **after** the `.env` load and **only when it is unset**, so an operator's own value always wins. A build artefact must never silently displace a value a person set deliberately.
- **The tracked artefact carries no dev state.** `plugins_generated.go` declares the var **empty and never varying**; the values ride `charly/plugins_dev_generated.go`, written only in a dev build, **gitignored**, assigning from an `init`. The first cut wrote them into the tracked file and the bootstrap's generated-clean guard refused the build — **correctly**, because it is derived from tracked inputs and had drifted.

# 2026.287.1934 — fix(plugin-loader): a plugin-vs-plugin CUE def-name collision is a load ERROR (#770)

## Summary

Fixes opencharly/charly#770 (`C3 — the loader's parallel paths must bypass the one
desugar/validate step`). Two plugins whose served CUE schemas each declare the same `#Def` used to
splice SILENTLY: CUE **unifies** same-name definitions across sources in one package, so
`registerPluginUnitSchema` returned nil, the merged def carried BOTH plugins' fields, and every
plugin sharing that def then rejected its own authored `plugin_input`. `registerPluginUnitSchema` is
now THE def-name collision gate.

**The gate is keyed on DECLARATION IDENTITY, never on a CUE value comparison** (RDD spike, ledger
§2 C3 — two plugins declaring one CUE def name must make the loader ERROR instead of unifying). The
spike's answer, recorded in the code comment on `pluginSchemaSet`, is a negative one that changed the
HOW: a "is this merge a no-op?" test built on `cue.Value.Equals`/`Subsume` is UNSOUND, because
`_`/disjunction normalization is not idempotent — unifying plugin-matching's own
`(#MatchingMatcher | [...#MatchingMatcher])` with ITSELF is already not `Equals`-equal and yields a
strictly LOOSER value. So the gate collects each served source's top-level def names and errors when
a name is already owned by a unit with a **different registry identity** (its declared capability
words), naming both plugins and the def:

- `charly/plugin_loader.go` — `pluginSchemaSet` gains `defOwners` (def name → the one declaring unit:
  identity + display name) and `srcSeen` (exact source strings already spliced);
  `unitSchemaIdentity`; `topLevelDefNames`; the STANDALONE-compile precondition and the collision gate
  in `registerPluginUnitSchema`. An exact-source replay (the builtin gate re-run from a cleared state,
  the embedded-defaults path) stays idempotent and is neither re-appended nor re-indexed.
- `charly/registry_testsupport_test.go` — `snapshotProviderState` restores the new state, and its doc
  no longer claims the `sources` slice grows monotonically on every run (a replay no longer appends).
- `charly/provider_checkenv_schema_gate_test.go` — that test hand-rolls a state clear to reproduce the
  "fresh container" state, so it clears/restores the new state with the rest; without it the gate saw
  a stale owner with no prior value.
- `charly/plugin_schema_collision_test.go` — the acceptance tests (new file).

**R1 — an anomaly surfaced and was root-caused before remediation.** The first full `go test ./...`
run FAILED 75 tests on the first version of this gate. RCA named two independent mechanisms, both
mine: (1) the value-based "no-op merge" allowance above was unsound; (2) my declarer index could go
stale against `unified`/`sources`, so the gate fired on a *replay of a plugin's own schema* rather
than on a collision. Both are fixed in this commit; the redesign is what the tests below pin, and the
suite was re-measured green.

Deliberate non-goal, documented in the code: a plugin re-declaring a def the BASE already declares is
not gated, because a plugin schema must be SELF-CONTAINED (it may reference no base def), so a
host-side WIRE twin is a structural necessity of that contract — `spec/schema/tunnel.cue` documents
the live instance (`#TunnelConfig`/`#TunnelPort`, deliberately twinned in
`candy/plugin-tunnel/schema/tunnel.cue`), and a value-based allowance for it is provably unsound.
`TestPluginSchemaBaseDefTwinAccepted` pins that.

**What the diff does, and what it does not.**

- **The URL**: the mirror's dated directory → its rolling one. The directory it leaves
  (`v20261001.604814`) still answers **HTTP 200 today** — the fuse has not blown yet. The directory this issue
  was filed against, same shape one rotation back, answers **HTTP 404**; that is the whole defect.
- **The checksum**: the six static `value:` lines are deleted, `checksum.type: sha256` is kept.
- **Untouched**: no other entity in the file. In particular the two Fedora cloud-image blocks
  (`charly.yml:79`, `charly.yml:3187`) keep their static digests, which is correct — those are immutable
  release paths, not a rotating mirror.
- **No comment is added to the six blocks.** The changed unit is byte-identical six times over, and neither of
  the two Arch cloud-image entities in the org that already work annotates its URL line. The rationale for the
  form lives here and on `#844` rather than six times in the file.

**Why the URL change alone is not the durable form — the value has to go with it.** The resolve order is in the
SDK module the core pins, not in this repository's own Go:


`value` wins; the sidecar is consulted **only** when it is empty. A rolling URL carrying a static digest
therefore never consults the sidecar, and the digest becomes the next fuse: on a host with a cold vm-image
cache the download fails `checksum mismatch` (`kit/http_fetch.go:134`) at the mirror's next rotation, while a
warm host silently keeps serving the previous image. The rolling URL is durable *only* with the value dropped,
which is what this diff does.

**The maintainer brief on this PR (comment `6120212047`) asked for one of two things, and this is the first
one.** It reads: *"the fix needs to keep the integrity check: either `latest` with the sidecar genuinely fetched
and verified at resolve time (and then the sidecar path is part of the fix and must be shown working), or
`latest` with the digest updated in the same change that rotates it."* The second arm does not exist for a
rolling URL — nothing rotates it in-tree — so the first arm is the one to satisfy. Its premise is now measured
rather than argued: the brief recorded that it *"could not find that resolution in charly's source"* after
searching `charly/charly/**.go`. **It is not in that search path; it is in the pinned SDK module**
(`github.com/opencharly/sdk`, an indirect requirement at `charly/go.mod:107`), the authoring reference states
the contract in one line — *"integrity-checks it via sha256 (sidecar auto-resolved when `checksum.value` is
empty)"*, the `vms-catalog` skill's `source.kind: cloud_image` section — and the mirror serves the sidecar
(measured below). The resolution exists; the search was in the wrong repository.

**And the form is already the org's spelling for this exact URL**: `distro-cachyos/charly.yml:336-342`
(`punktfunk-vm`) and `charly-arch/charly.yml:26-33` (`arch-repo-vm`) both name `images/latest/…` today, the
first with `checksum: {type: sha256}` and no value. This diff converges charly's six onto that one spelling
(R2/R5) — which is what `#844` asks for.

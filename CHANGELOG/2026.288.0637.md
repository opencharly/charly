**⚑ And leg 10, core's half of the same cutover — the build selector is RETIRED.** The image builder
is BuildKit, which is not a container engine and can never be a member of the closed `#EngineName`
vocabulary, so the contract carries no builder selector at all and **every consumer reads the RUN
engine**. Two core files:

1. **`charly/dispatch_build_ensure.go`** — `BuildEngine` dropped from the `spec.BuildEnsureRequest`
   literal, and the now-unused `buildEngine` parameter dropped from `dispatchBuildEnsure`, with both
   call sites updated (`plugin_executor_reverse.go`) — both always passed `""`, so no caller ever
   supplied one.
2. **`charly/runtime_config_test.go`** — the retirement's rule is the contract's own: with
   `ResolvedRuntime.BuildEngine → .RunEngine` and `EngineConfig.Build` gone, across 15 tests.

**Two distinctions the migration had to get right, and both were caught by running it rather than by
reading it:**

- **A retired CONFIG KEY is inert; a retired ENV VAR is not read at all.** The contract pins that an
  existing `engine.build:` in `~/.config/charly/config.yml` must not fail the load (so an upgrade does
  not break a user's boot), while `CHARLY_BUILD_ENGINE` no longer appears in `spec/hostenv` at all. So
  tests must clear the **live** var (`CHARLY_ENGINE_ROOTFUL`) where they were clearing the retired one
  — otherwise they leak ambient config.
- **`TestResolveRuntime_MixedEngines` is CONVERTED, not deleted.** Its pair-claim is exactly what the
  migration retired — its own doc comment said *"it fails if resolution ever collapses the two onto
  one engine"* — but its other half, *a non-podman run engine resolves `RunMode` to `direct` because
  quadlet requires `RunEngine==podman`*, is live behaviour the retirement never touched. It is now
  `TestResolveRuntime_DockerRunEngineResolvesDirect`, with the retired claim removed and the surviving
  coverage kept. The removal itself is pinned in the contract
  (`spec/hostenv/retired_build_selector_test.go`), with its own positive control.

**And a second defect of my own, which the suite could NOT have found — the round-2 fix.** The blanket
substitution above copied the removed `BuildEngine` assertion's *text* rather than replacing it, leaving
**two consecutive copies of the same guard** in `TestResolveRuntime_Defaults`. It is fixed in `2d7da8cd`
by deleting the second copy — and the reason it survived a green suite is the point: **a duplicate guard
is GREEN.** Both copies pass, and `golangci-lint`'s `dupl` checker is conventionally excluded from
`_test.go`, so the only control with reach is **reading the substitution's output as a DIFF rather than
as a result** — a substitution produces plausible code, and plausibility is not correctness. Swept that
way over the whole file, this was the only *adjacent* duplicate; the other 22 repeated 3-line blocks are
legitimate per-test setup idioms that recur across functions by design. The contrast with the sibling
defect below is the lesson: that one *failed*, so the suite caught it.

**A defect of my own, found by the suite rather than by review:** a blanket substitution made
`TestResolveRuntime_InvalidEngine` set *and then clear* the same variable — the clear existed to null
the *other* engine var, now retired — silently removing the invalid value the test was testing. It
failed with `expected error for invalid engine`; the collision was removed. A textual swap cannot know
which of two identically-named references is a set and which is a clear.

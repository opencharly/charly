# 2026.293.1326 — fix(plugin): make the host-to-plugin call bounds configurable

## Summary

Makes the two host→plugin call bounds operator-configurable instead of hard-coded.

A host→plugin leaf call is bounded by `pluginLeafCapDefault` (10m) and, on the readiness path, by the `no_progress` idle watchdog. Neither can see work happening **outside the plugin's own process tree** — and an image build's work happens in buildkitd. A healthy multi-arch build was therefore killed at ten minutes with `context canceled` in buildkitd and `signal: killed` in buildctl, while charly itself exited 1 and every earlier attribution (CDN, base digest, registry mirror) sent me the wrong way.

Two knobs, both defaulted to the shipped values so nothing changes unless an operator opts in:

| variable | meaning |
|---|---|
| `CHARLY_PLUGIN_LEAF_CAP` | total-duration bound for one host→plugin call (default `10m`) |
| `CHARLY_PLUGIN_NO_PROGRESS` | no-host-visible-progress window (default: the readiness config) |

`applyCallBoundEnv(getenv)` owns the parsing and `init()` wires `os.Getenv`, so the parsing is testable and
the consumer path is provably wired. A **malformed non-empty value now says so** on stderr and keeps the
default, instead of being silently discarded — a typo'd deployment (`CHARLY_PLUGIN_LEAF_CAP=120x`) is no
longer indistinguishable from never setting it.

`origin/main` was merged in during this round: the conflicts were **only** the two module files, and main
already carries the mirror dependencies this branch had bumped by hand (main's `plugin-build` is
`v0.2026293.926`, *newer* than the `v0.2026293.443` this branch pinned), so main's `go.mod`/`go.sum` were
taken whole and the branch's own pin commit is superseded. The three "pin" lines the earlier body listed are
therefore **not part of this diff** any more.

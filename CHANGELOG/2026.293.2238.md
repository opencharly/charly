# 2026.293.2238 — fix(cli): serve the WELDED command words a package install already has

## Summary

`charly secrets` — and `mcp`, `udev`, `review`, `pipeline` — answered with a **usage error and
exit 80** on a dev/worktree build, while the same binary installed from a package serves them.
Every documented credential read-back in the org (`charly secrets get charly/secret …`) was
therefore broken exactly where an operator proves things: on a locally built binary.

### The mechanism, measured

Those words are **WELDED** command plugins. `scripts/host-command-plugins.txt` is their single
source; every native package bakes them beside the binary at `/usr/lib/charly/plugins`, and a
baked `.providers` manifest is what puts a word in the CLI grammar
(`plugin_loader.go` → `bakedPluginDirs` / `discoverBakedPluginWords`). A binary that is not
installed at `/usr/bin` or `/usr/local/bin` skips the FHS path entirely
(`packagedInstallDirs`), and a project need not declare such a word — on a package install it
is served with no project at all — so **neither grammar leg fired** and the word was not a
command.

This is **not** a compiled-plugin gap, and the issue I filed (#995) suggested the wrong fix.
Measured on a throwaway worktree: adding `plugin-secrets` to `compiled_plugins:` **and**
pinning its go.mod require builds and generates cleanly, and still leaves the verb
unregistered — because `plugin-secrets` advertises `verb:credential` only and says so
explicitly: `command:secrets` is deliberately absent from `Describe` and is served by
`syscall.Exec`-ing the plugin binary in CLI mode. Compiling it in would mean reversing that
design and re-linking `go-keyring` into core.

### The fix — same source, same resolution path

- **`internal/pluginsgen`** reads `scripts/host-command-plugins.txt`, takes each welded
  plugin's command word from its OWN manifest in the generated corpus index, and emits
  `weldedCommandRefs` (word → pinned candy ref) into `plugins_refs_generated.go`. One
  generator, one source, no hand-written list. A welded plugin *missing from the corpus*, or
  *declaring no command word*, is a hard generation error rather than a silent gap.
- **`registerWeldedCommandWords()`** seeds the grammar after `discoverBakedPluginWords()`.
  Every welded word gets its grammar entry; a word a compiled-in provider also serves
  (`clean`, `vm`, `doctor`, …) is **shadowed at dispatch** — `providerRegistry` is consulted
  before the welded source fallback, so that provider wins and the word is never served
  twice. (The first revision of this body said such words were *skipped* by
  `collectExternalCommandPlugins`; that was wrong, measured against the builder, and is
  corrected here and in the code comment.)
- **`resolveCommandPluginBinary`** grows a welded leg between the baked probe and the
  project-scan error arm: it host-builds the plugin from the pinned ref through the **same**
  `ScanAllCandyWithConfigOpts(ExtraCandyRefs)` → `findCommandPluginCandy` →
  `resolvePluginBinary` path a project-declared word uses. Only the ref's *source* differs —
  it is not a second resolution path. It is taken before the error arm so a project this
  binary cannot load cannot take a welded command away.

**Visible consequence, worth signing off on:** a dev/worktree `charly --help` (and the
reflected MCP tool surface) now lists the welded words a package install already serves.
That is the installed-package CLI contract, reached from a source build.

### What the live verification actually covers

Three of the twelve welded words were exercised against the real plugin resolver, each
host-built from its generated ref on first use:

```
secrets  → `charly secrets list charly/secret`  EXIT=0, and `secrets get … WEBUI_ADMIN_PASSWORD`
           returned the real stored 32-hex value
udev     → `charly udev --help`     EXIT=0, usage printed (plugin built from its ref)
review   → `charly review --help`   EXIT=0, usage printed (plugin built from its ref)
```

The other nine pins are **not** claimed to be built here. What is asserted for them is the
generated index itself, and that assertion now genuinely reads its source: the test parses
`scripts/host-command-plugins.txt` into `<plugin>@<pin>` and compares every welded ref's tag
against it, so a stale or hand-edited tag fails. (An earlier revision's test merely asserted
"some non-empty tag" while claiming otherwise; `49eb7181` fixes that — the claim was the
defect, not the code.) The pin set being stale *by design* is a separate, filed concern
(#1001).

### Review fixes in `066fe33a` and `48b07376`

- The test's final block could not fire: `d.word != word` had already been established false by
  the entry check, so "compiled-in provider does not own the word" was unreachable and proved
  nothing. Replaced with the property that *can* break — every word a compiled-in provider owns
  **before** the seed still resolves to that same provider **after** it (a seeded word that stole
  the resolution, or an owner that vanished, both fail).
- The "skipped by `collectExternalCommandPlugins`" claim (comment + body) was wrong and is now
  "shadowed at dispatch", which is what the code does.
- `48b07376` reconciles the last divergence: the welded-leg comment claimed an unloadable
  project could not take a welded word away, while `buildWeldedCommandPlugin` returns the
  `LoadConfig` error on exactly that input. The behaviour is right; the comment now describes
  it (before the *candy-scan* error arm, still project-dependent for its config).

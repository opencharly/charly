# 2026.294.0012 — fix(plugin): raise the leaf cap to a bound a cold build can meet, and name it when it fires

## Summary

`pluginLeafCapDefault` was **10 minutes**, applied as a TOTAL-duration bound to every
host→plugin **LEAF** call — one that attaches no reverse channel, so the host has no
progress signal to guard on. The longest legitimate leaf is exactly the work that bound
kills: a cold image build.

**Measured** while building the Open Web UI image on a refreshed CachyOS base digest:
`box build openwebui` (multi-hundred-MB base pull + full package install + a pixi/pip app
layer) died **twice** at the cap, surfacing as:

```
charly: error: command "build": building openwebui: buildctl build …: signal: killed
level=error msg="/moby.buildkit.v1.Control/Solve returned error: rpc error: code = Canceled
  desc = mount callback failed …: failed to record upperdir changes (close error: failed to
  close tar writer: context canceled)"
```

…and the same build completed with `CHARLY_PLUGIN_LEAF_CAP=120m`. Nothing in either message
named a time bound, which is why it read as a crash before the constant was found in the
source.

### Two changes

**1. The default is 2h** (`pluginLeafCapDefault`). Long enough for a cold multi-stage build
or a full assembled bed with its rebuild legs; still finite, so a wedged plugin fails rather
than wedging the host — the #474 guarantee the 10m bound carried is preserved, just at a
scale that does not break the normal case. The precise **IDLE** guard
(`pluginInvokeNoProgress`) is unchanged and still owns the plugin→plugin path, which *does*
have a progress signal to watch; a leaf does not, which is why its guard has to be a generous
total bound rather than a tight one.

**2. The expiry identifies itself.** `leafCapErr` wraps with a new `errPluginLeafCap` sentinel
when the total bound is what fired, naming both the duration and the knob:

```
host->plugin build after 2h0m0s: plugin leaf cap exceeded (a host→plugin leaf call has no
host-visible progress to guard on, so the total-duration bound is the only guard; raise it
with CHARLY_PLUGIN_LEAF_CAP): context deadline exceeded
```

The underlying error keeps its identity (`errors.Is(err, context.DeadlineExceeded)` still
holds), so existing callers and tests are not silently retyped — and an **uncapped** call is
never rewritten, so the wrapper cannot claim a bound nobody applied.

## Change classification

**Runtime (core plugin-call bound + error contract) + tests.** No schema or wire-type change.
Confidence: **analysed on a live system**. The core gate is green on the final tree and the
disposable bed passed, but the NEW code path — `leafCapErr`'s wrap branch — did **not** fire
live: every leaf in that bed was short, and the measured before/after *raised* the cap rather
than expiring it. So the wrapper's naming behaviour is covered by tests (direct, and through
`invokeTyped` with a blocking provider) rather than by a live expiry, and the tier says so.

Why a live expiry was not produced: the bound only fires on a host→plugin **leaf**, and every
leaf reachable on demand here finishes in milliseconds — `box list boxes`, `box generate`,
`box validate` and `charly cmd` all completed under a `CHARLY_PLUGIN_LEAF_CAP=1s` bound because
they dispatch through the reverse-channel (idle-bounded) path, not the leaf path. The leaves
that DO expire are the long internal ones inside a build, which is exactly what the 10m value
was killing.

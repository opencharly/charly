# 2026.294.0913 — fix(plugin): give a non-interactive command its host reverse channel

## Summary

`charly pipeline run <entity>` could not reach ANY workflow engine for a plugin-provided
front-end. **The mechanism was the dispatch leg, not resolution** — and the `--dry-run` control
is what localised it: resolution + validation + lowering need no host and passed (`rc=0`), only
the dispatch failed.

**Mechanism (with `file:line`), two halves of one seam.**

1. **The dispatch lane was chosen by PLACEMENT, not by the declared contract.**
   `charly/provider_command_external.go:271` (`dispatchCommand`) sent a compiled-in command to an
   in-process `Invoke(OpRun)` and an out-of-process one *always* to
   `dispatchExternalCommand` → `syscall.Exec` (`:362`, `:367`). `syscall.Exec` **replaces the
   charly process**, so the plugin ran its own CLI face with no host in the address space at all
   (the front-end plugin's own `cli.go:288` — `runCLI(args, nil)`) and every
   `InvokeProvider("workflow", ...)` was structurally unreachable: `cli.go:112` `no host executor`.
   The spec already defines the right discriminator and charly had never read it —
   `ProvidedCapability.interactive`: *"a command DECLARING this keeps the process-replacing exec
   lane; every non-interactive command dispatches through the broker-backed Invoke(OpRun) path so
   it behaves identically compiled-in and runtime-loaded."*
2. **A baked plugin's `kind:` word never reached the parse-time kind set.**
   `charly/plugin_loader.go:529` (`discoverBakedPluginWords`) registered a baked plugin's
   `command:`/`verb:` words and recorded its binary for every class, but never called
   `registerDeclaredKind`, so `spec.Threaded.Kinds` (which `loaderkit.classifyKind` reads) lacked
   the word and a valid `pipeline:` entity was rejected with `no kind discriminator — none of its
   keys ("pipeline") is a recognized kind`; `connectDeclaredKindPlugins` then had no baked leg and
   reported `did not register during load` for a plugin the image already serves.

**Root fix.**

- `dispatchCommand` now decides the lane from the DECLARED flag: a command declaring `interactive`
  keeps the exec lane, every other command dispatches through its provider — in-proc via
  `hostInProcCtx()`, out-of-process via the new `grpcProvider.InvokeWithHostReverse`
  (`charly/plugin_grpc.go:422`), which stands up a **venue-less** host reverse channel. Both
  entry points now share ONE broker construction (`charly/plugin_grpc.go:432`) so the placements
  cannot drift.
- `capMeta.interactive` (`charly/plugin_provider_common.go:58`, populated at `:175` from the wire
  capability) — the decision is data-driven, never inferred from plugin Go, and identical in
  either placement.
- `charly/plugin_loader.go:529` threads the baked `kind:` word via `registerDeclaredKind`; the
  connect pre-pass gained the baked leg (`charly/plugin_prescan.go:249`), reusing the existing
  `connectBakedPlugin` (the one `connectPluginByWordRef` already opens with) — no second mechanism.
- Two supporting seams the change needs to be honest rather than a silent substitute:
  `errNoVenue` + `executorReverseServer.venue()` (`charly/plugin_executor_reverse.go:53`, `:65`)
  answer a venue op on a venue-less channel **by name** instead of dereferencing a nil executor
  inside the host process; and `charly/plugin_transport.go:114` forwards a plugin child's
  stdout/stderr instead of discarding them (go-plugin defaults both to `io.Discard`), without which
  `charly pipeline run --dry-run` would have gone from printing its dry-run line to printing
  nothing.

No fallback path hides a missing executor: an unresolvable word still reaches the exec lane, and a
venue op on the new channel is a named error.

    between, instead of as a chain — and the decisive mistake was measuring "welded" with

# 2026.294.1108 — fix(spec): embed the spec whose #PipelineArms carries `lanes`

## Summary

**The kernel's authored schema is a MODULE, not a file in this repo — so the `spec` pin in
`charly/go.mod` IS the schema the binary enforces.** `charly/cue_schema.go` compiles
`sharedCueSchema` from `sdkschema.FS` (`github.com/opencharly/spec/schema`, concatenated through
`spec/schemaconcat.ConcatSchema`), and that value gates every authored plugin-kind body
(`plugin_loader.go`'s splice) and every structural-kind value (`provider_kind_invoke.go`). The pin
sat on `v0.2026289.611`, which predates `#PipelineArms.lanes`, so a `lanes:` step was refused at the
CUE gate before any engine could be reached:

```
validation error: node "lane-probe": pipeline: steps.1.lanes: field not allowed
```

**Root fix: bump `github.com/opencharly/spec` to `v0.2026294.929`** — the tag that carries
`lanes?: string & !=""` beside `for_each`, with the companions it already shared (`item_var`,
`index_var`, `batch_size`, `steps`).

Two derived artifacts move with it, and each is a tracked input to a repo control:

- `charly/go.sum` — the module hash; the superseded version's two lines are pruned by
  `go mod tidy`, which is the tidy state this tree now carries.
- `tools/generate-packages`, `tools/golden-cloudinit`, `tools/golden-compile` — the lockstep
  `tools/*` modules. `tools/gomod-canonical`'s `TestContractPinsMatchShared` anchors both contract
  pins on `charly/go.mod` and failed on this tree until the repo's own `charly task mods-tidy`
  adopted the shared pin. That task is the remedy the failing assertion names, so it is what ran —
  no hand-edited pin.

No Go source changed: the schema is the single source (SDD) and the Go types for `#PipelineArms`
are generated inside the `spec` module, so the binary picks the arm up by recompiling against the
new pin.

**Scope, stated plainly: this closes the SCHEMA gate only.** `lanes:` is still refused one layer
further in — by `sdk/workflowkit.ValidatePipeline` inside the front-end, `plugin-pipeline`, which
pins `sdk v0.2026293.2302` and so has no `lanes` in its `execArms`. That is leg 4 of the chain in
`opencharly/plugin-pipeline#43`, and the measurement is in the evidence below: after this change the
CUE gate stops refusing the field, and the refusal moves to the front-end's own gate. Measured, not
diagnosed — and not worked around here.

**Round 1's review found a third changed file, and it was mine to remove.** My first build in this
worktree rewrote `go.work.sum`, dropping the `buger/jsonparser` and `plugin-candy` entries and adding
a `go-localereader` one; I committed it and called it "derived from `charly/go.mod`". The review is
right that the pin cannot explain that — `spec`'s `/go.mod` hash is byte-identical across

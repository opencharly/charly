## The one anomaly, with its RCA

The first control-arm attempt invoked the worktree's binary with `-C /tmp/charly-pinctrl` and
was REFUSED by the freshness guard (exit 1), not by the pin gate:

```
  running:        /home/atrawog/Sync/Atrapub/mo/dsh/opencharly/.worktrees/distro-pin-wave/charly/bin/charly
  binary mtime:   2026-10-21T17:24:07+02:00
  newer source:   charly/update_deploy_dispatch.go
  source mtime:   2026-10-21T17:39:33+02:00
  source root:    /tmp/charly-pinctrl

The source tree has been edited since this binary was built.
```

RCA: the guard compares the invoked binary's mtime with the newest source mtime under the
project dir; a freshly added worktree has current mtimes, so ANY prebuilt binary reads as
stale by construction. That is the guard doing its job (R9: a stale binary must not run), not
a product defect — and the remedy is NOT the `CHARLY_SKIP_FRESHNESS_CHECK` bypass, which this
body's runs never used. The fix is to make the guard's premise true: the same-HEAD binary was
placed at `/tmp/charly-pinctrl/bin/charly`, and both arms then ran and reported as pasted
above. Missed control: none in the product; my first arm attempt simply did not account for a
mechanical guard whose message named its own remedy.

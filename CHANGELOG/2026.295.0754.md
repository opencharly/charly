# 2026.295.0754 — fix(deps): weld plugin-migrate v0.2026294.1337 so charly migrate emits a loadable pipeline

Head `114b2a49fb9c6f3ec7debe61a2c67547970bb7e3` (branch `feat/plugin-migrate-2026.294.1337`).

## Summary

`charly`'s Go module graph pinned the `plugin-migrate` module at `v0.2026280.2238` — two releases behind the reshape that makes `charly migrate`'s OWN output loadable (`plugin-migrate#22` → `v2026.294.0359`, `#24` → `v2026.294.1337`). `charly migrate` dispatches its `pipeline-lobster-syntax` op to that COMPILED-IN plugin, so no released `charly` could reach the fix: the file it wrote failed its own loader, and every consumer running the shipped command inherited the defect (`opencharly/eval-omarchy#91` carries the consumer side).

| part | before | after | why it moves here |
|---|---|---|---|
| the `plugin-migrate` module pin | `v0.2026280.2238` | `v0.2026294.1337` | the reshape itself; the tag is fetched and re-resolved in How tested |
| `charly/go.sum` | 2 lines | 2 lines | the tag's content hash — its `/go.mod` hash is byte-identical to the old one, so the dependency SET did not change |
| `check-migrate-local` + its fixture | — | new bed | no bed in this repo drove `charly migrate`, so the pin's only observable — the document it emits — had no witness |

**Why `v0.2026294.1337` and not a later tag.** It IS the last Go tag on the repository: the only two `2026.294` Go tags are `.359` and `.1337`, and `.1337` is the tip. `main` (`fd9ab28`) is that tag plus exactly one CHANGELOG commit, so `main`'s code and the release are the same code — and a pin must name a TAG, never a branch, so the release is the only correct value. The Go module tags live under the plugin's `candy/plugin-migrate` prefix and are a different namespace from the repository's release tags (`v2026.294.1337`); the `require` line names the module tag, which is what `go.sum` records. The tag's tree is identical to the tree the validator PASSed on `plugin-migrate#24` (`8bebf7e`), so what lands here is the reviewed code.

**What the bump does not drag in, measured rather than assumed.** The tag requires `sdk v0.2026270.1147` and `spec v0.2026270.938` — both OLDER than this repo's `v0.2026294.1520` / `v0.2026294.929` — so MVS keeps charly's newer pins and raises nothing: `go mod tidy` moves exactly one `go.mod` line and two `go.sum` lines, `go.work` does not move (its `go` directive follows `go.mod`, which is unchanged), and the reshape's non-stdlib imports are `gopkg.in/yaml.v3` alone. There is no companion transitive, toolchain, or second pin to carry — unlike `#1017`, whose sdk raise moved grpc and dragged a Go fix with it. This is a ONE-part cutover, and the pin is the whole of the module change.

**The emitted shape, named.** The same fixture through the two binaries, every clause of the reshape's output (each count re-derived in How tested):

| clause | pre-bump (`.2238`) | post-bump (`.1337`) |
|---|---|---|
| lifted-verb step | `plan:` whose element is `- agent:` — bare step-level sugar, no intent | `- run: assess` with `agent:` as its SIBLING |
| the pipeline's arg | `args: pr:` carrying `type: string` (not allowed by `#TaskParamSpec`) | `args: prs:` carrying `description:` only |
| retired `concurrency: {lanes: N}` | flattened into the inert entity `config: {lanes: 16}` | the pooled fan-out ARM: `id: lane`, `lanes:`, `batch_size: 16`, `item_var: pr`, nested `steps:` |
| the per-lane `$pr` | left unbound | rebound to the lane item as `$pr.stdout` |
| `box validate` on the emitted document | `rc=1`, `plan[0] has no intent keyword (run/check/agent-run/agent-check/include)` | `rc=0`, `box validate: OK` |

**What this does NOT unblock, and the order that does.** On `eval-omarchy`'s tree the next named defect is that repo's OWN pin, not the reshape: `pipeline: entity has no stages`, raised by `plugin-pipeline:v2026.272.0332` — the retired executor, whose `OpValidate` still demands `stages:`. Moving that pin is a second leg, in that repo, and is not folded in here. Moving it to the newest released `plugin-pipeline` (`v2026.294.2124`) clears exactly that error and exposes two more, both already tracked: the newest `plugin-pipeline` tag AND its `main` still weld `sdk v0.2026294.1003`, which predates the `${env.NAME}`-in-a-`when:` fix (`sdk v0.2026294.1431`; `opencharly/plugin-pipeline#55`), and one `$report.` reference that `sdk#443` REFUSED by design so the consumer must author the value at its leaf. Because of that, `eval-omarchy`'s three skill bodies stay UNMOVED here: its manifest still does not load, and extracting bodies into a tree `box validate` refuses is the dual state this migration programme exists to remove. `opencharly/eval-omarchy#91` gets a STATUS with these measurements before this push.

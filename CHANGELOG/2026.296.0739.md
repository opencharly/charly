# 2026.296.0739 — chore(deps): adopt plugin-task v0.2026296.641 (the `task:` hop carries the nested run's report)

## Summary

The compiled-in `plugin-task` require moves to the release that carries the `task:` hop fix.

- `charly/go.mod` — `github.com/opencharly/plugin-task/candy/plugin-task` moves from `v0.2026288.804` to `v0.2026296.641`.
- `charly/go.sum` — the two hashes for that module move with it. Nothing else in the module graph moves.

`plugin-task` is compiled into the charly binary (`charly/charly.yml` lists it among the compiled plugin words), so the pinned module version **is** the behaviour of `charly task`. The previous release's `task:` hop composed its answer from the wrapped run's **counts** alone — `ran N task(s), M step(s) failed` — so a caller that composed a declared task through `task:` could see that the nested run passed but never **what it reported**: the wrapped verb's own counts, its per-pin states, its producer-first leg order. The verdict crossed the seam; the evidence did not. The new release carries the nested steps' own messages, so the nested run's own report crosses the hop too.

The upstream fix is **opencharly/plugin-task#36** (squash `81ce09a`; root tag `v2026.296.0641`, module tag `candy/plugin-task/v0.2026296.641`). The consumer of that fix inside the org is the umbrella's `pins` task, which composes the `git-submodules` verb through `task:`; the umbrella's leg lands after this one, because the umbrella's binary is built from this repo's pin.

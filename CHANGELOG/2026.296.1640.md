# 2026.296.1640 — fix(deploy): connect the substrate deploy provider at the resolution boundary

## Summary

Fixes opencharly/charly#1038: `charly deploy add <new-name>` failed at target resolution with
`target "pod" is a known substrate but its deploy provider is not connected`, while
`charly config` on the same binary served the same substrate.

The resolution boundary now connects the deploy provider for the resolved substrate before its
registry lookup (`ResolveTarget` → `ensureDeployProviderConnected`). That helper is the ONE
connect step (R2): `dispatchLifecycleTarget`'s separate `connectPluginByWord` call is deleted, and
`deployNodePluginContext` no longer injects the canonical substrate ref — the second connect path
that only fired when the deploy NAME already resolved to a node, which is exactly why a new name
failed. `loadDeployPlugins` still loads the plugins a deploy's PLAN and `add_candy:` list
reference.

Verified mechanism on the pre-fix tree:
- `charly/unified_targets.go:524` `ResolveTarget` did a bare
  `providerRegistry.ResolveDeploy(node.Target)` with no lazy connect.
- `charly/plugin_loader.go:1071` `deployNodePluginContext` resolved `name` → node and returned
  `(nil,nil)` for a new name, so `loadDeployPlugins` had no substrate ref to connect.
- `charly/pod_lifecycle_verb.go:49` called `connectPluginByWord(ClassDeployTarget, …)`
  explicitly, which is why `config` worked on the same binary.

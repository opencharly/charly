# 2026.296.1951 — chore(deps): adopt plugin-task v0.2026296.1911 (the bump advances an unmaterialized pin in the index)

Closes #1044

## Summary

Head `3b213c98984661157fbf1d096cb528b77619dd07` — 2 files changed, 3 insertions(+), 3 deletions(-).

`plugin-task` is compiled into the charly binary, so the pinned module version IS the behaviour of `charly task` — and of the `git-submodules` verb that `charly task sync` runs.

The pinned version could not advance a pin whose path has **no checkout**: the bump failed loud, and it blamed a **roll** it had not made — *"'src' did not roll, so its gitlinks are stale"* — for a source that had no tree at all. That is why every pin wave over the umbrella's light tree had to materialize the full set first, and why the umbrella states that cost in three places.

This adopts the release that fixes it: a path with no checkout is advanced **IN THE INDEX** — a leaf to the tip its remote serves for its `branch=`, an edge to the twin the source's tree records — while a path WITH a checkout is still rolled in that checkout, so the two keep agreeing. It still refuses, **by name**, every path it cannot advance: a sync over a tree it could not fully advance must never report success.

`charly/go.mod:141` moves `github.com/opencharly/plugin-task/candy/plugin-task` from `v0.2026296.641` to `v0.2026296.1911`; `charly/go.sum` moves the two matching hashes with it. No other requirement moves, and the pin is stated once: `charly/charly.yml` names the compiled-in plugin **word** (`plugin-task`), never a version.

**What this change does not do.** It does not change a line of product code — the behaviour is the module's, and the module is upstream (opencharly/plugin-task#41, squash `1d8342fc`, root tag `v2026.296.1911`, module tag `candy/plugin-task/v0.2026296.1911`). It does not touch the umbrella's guidance; the umbrella's leg follows this one, because the umbrella's binary is built from this repo's pin.

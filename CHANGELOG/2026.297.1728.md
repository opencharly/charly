Two changes, one gate, one PR — and they are one scope, not two cutovers: the second is a **prerequisite of the first's gate**, because the gate the bump's class demands was already red on `origin/main` (the evidence is pasted below).

**1. The task runner's third bucket reaches the product.** `plugin-task` is compiled into the charly binary, so the pinned module version IS the behaviour of `charly task` — and of the `git-submodules` verb that `charly task sync` runs.

At the pinned version the task runner counts **steps** and **failures** only. A step that ran nothing is neither: it is not a failure, so it is counted among the N steps, and it is not disclosed. A green task line can therefore read *"26 step(s), 0 failed"* over a run in which six comparisons never happened. The org already owns the vocabulary for exactly this state — `sdk.CheckSkippedExitCode = 3` ("the phase RAN NOTHING — neither a pass nor a failure") — and the check runner honours it. The task runner had no equivalent.

This adopts the release that adds it. Two merged releases carry it: opencharly/plugin-task#45 (squash `7e26679`, root tag `v2026.297.1509`, module tag `candy/plugin-task/v0.2026297.1509`) adds the third bucket — the headline becomes `task %s: %d step(s), %d failed, %d skipped`, the hop's aggregate `ran %d task(s), %d step(s) failed, %d skipped` is kept as the prefix whenever a step ran nothing, the JSON report carries `"skipped"`, and the exit status is untouched (a skip is not a failure) — and opencharly/plugin-task#46 (squash `c24c743d`, root tag `v2026.297.1542`, module tag `candy/plugin-task/v0.2026297.1542`) carries the stderr-capture fix that #45's PASS asked for.

`charly/go.mod:141` moves `github.com/opencharly/plugin-task/candy/plugin-task` from `v0.2026296.2153` to `v0.2026297.1542`. `charly/go.sum` moves with it, derived by `go mod tidy`: the two superseded pairs (`v0.2026296.1911`, `v0.2026296.2153`) go and the one live pair (`v0.2026297.1542`) arrives. The `v0.2026296.1911` pair was **already stale on this tree** — #1050 added the `2153` pair without tidying — so the tidy also restores the invariant this repo's own precedent (#1045) holds: exactly ONE plugin-task version in `charly/go.sum`.

**No cascade.** The two versions' own `candy/plugin-task/go.mod` are byte-identical in their requirements (`sdk v0.2026276.1822`, `spec v0.2026276.1636`), so this is a single-module bump with no `sdk`/`spec` move behind it. The pin is stated once: `charly/charly.yml` names the compiled-in plugin **word** (`plugin-task`), never a version.

**2. The containerd provider path is cut over to the renamed plugin repo.** The out-of-tree engine plugin was renamed when the engine word changed (the engine word is `containerd`; the retired `nerdctl` spelling is only the CLI binary), and its module path moved with it. Three surfaces in this repo still named the pre-rename path:

| surface | what it is |
|---|---|
| `charly/plugin_corpus.txt` | the corpus entry for the plugin repo — the list pluginsgen walks to learn which plugin serves which word |
| `charly/plugins_refs_generated.go` | the generated word→provider index: the three containerd words still pointed at the pre-rename module path |
| `charly/engine_word_cutover_test.go` | the guardrail's canonical ref — the constant the index must equal |

The index is a **projection** of the corpus's live word→provider map: pluginsgen fetches each corpus repo at its default branch — deliberately, because the word→ref FACT lives in the plugin repos — and records where each word is served (`internal/pluginsgen/main.go`, `collectWordRefs`). A projection does not follow its source by itself, so the index was re-projected with the **same** pluginsgen invocation the build uses (`scripts/bootstrap-charly.sh`). The corpus entry and the guardrail's constant follow the rename; regenerating the index is the replacement for the three generated keys.

This is also what the repo's own gate demands. `TestPluginsRefsIndexSound` compares the committed index against what the corpus serves **right now**, and its own failure message says *"the index is FALSE; regenerate and commit it"*. The gate had gone red for every checkout of this repo — including a fresh clone of `main` — because the corpus moved after the index was last committed. The build's `scripts/check-generated-clean.sh` deliberately classifies this file as `upstream` and **restores** the tracked copy, so a build never leaves the tree carrying a fresh projection: the remedy is a commit here.

**What this change does not do.** It changes no line of product logic of its own — the task runner's behaviour is the module's, and the module is upstream. It does not touch the umbrella's guidance; the umbrella's leg follows this one, because the umbrella's binary is built from this repo's pin. The containerd programme's remaining consumer legs stay with their own repos, tracked at opencharly/opencharly#589.

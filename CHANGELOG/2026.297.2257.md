**The data channel has two halves, in two repos, and this binary carried only
one of them.** The SDK's seam — `kit.RunnerConfig.StepEnv` — came with sdk
v0.2026297.1851 (opencharly/charly#1062). The PLUGIN's side, which is the half
that actually opens the channel — a task's RESOLVED values reach a step's
process environment, with the map CLONED before `captureStdin` mutates it — is
opencharly/plugin-task#47, which is **after** the pinned version.
opencharly/plugin-task#34 was closed against that fix, so the org closed the
data-channel issue against a fix the shipped binary did not carry.

`charly/go.mod:141` moves `github.com/opencharly/plugin-task/candy/plugin-task`
from v0.2026297.1542 to v0.2026297.2108, and `charly/go.sum` moves with it,
derived by `go mod tidy`: the superseded v0.2026297.1542 pair goes and the live
v0.2026297.2108 pair arrives.

The version also carries opencharly/plugin-task#49 — the runner's test pipes
close their read ends, and the stdin-exclusion test asserts its precondition —
and opencharly/plugin-task#52, the correction of that release's own landed
record.

**The split is measured, not asserted, and the measurement is in the gate
below.** The old pin's source carries no `StepEnv` anywhere; the new pin's
carries it in the runner and in its test; the SDK carries the seam. The gate
asserts all three, and it FAILS if the old pin turns out to carry the channel
too — in which case this diff buys nothing and the premise is false.

**Nothing else in the diff moves, and the reason is visible in the two module
versions' own manifests.** The new version's `candy/plugin-task/go.mod` asks
for a newer `go` (1.26.8), a newer `sdk` (v0.2026297.1851) and a newer `spec`
(v0.2026296.1036) — all three the versions this repo already carries — and it
adds and moves INDIRECT requirements as well (containerd, logrus, go-toml,
golang.org/x/net, grpc, protobuf). This repo's lock already pins the newer of
each pair, so `go mod tidy` re-derives the same indirect set and the ONLY pair
that moves is plugin-task's own. The COMPLETE diff of the two manifests is
pasted below — no hunk is elided.

The generated word→provider index is a PROJECTION of the corpus, and the
re-projection with the build's own `pluginsgen` invocation produced no diff to
it: the committed index already names the providers the corpus serves today.

# 2026.298.0310 — chore(deps): adopt plugin-check v0.2026298.205 — a skipped check is not a pass

## Summary

Head `482b84e95347776841b5a4f8849cf60e9098b008` — 3 files changed, 9 insertions(+), 6 deletions(-).

**`plugin-check` is COMPILED INTO the charly binary, so the pinned module version IS the behaviour of `charly check run` — and of the `summary.yml` acceptance record every R10 proof rests on.**

At the pinned version (`v0.2026295.2128`) a bed run whose declared check resolved to SKIP reported `PASS (steps=N)` and exited `0`: the skip was folded into a green headline, and the record listed every step `ok: true` while a declared check had never run. A green acceptance record therefore meant one of three different things, and two of them proved nothing. That is opencharly/charly#904.

This adopts the release that carries both halves of the fix:

- **opencharly/plugin-check#133** (squash `3d1e723`, root tag `v2026.298.0059`, module tag `candy/plugin-check/v0.2026298.59`) — the verdict is three-state and is computed from the per-check statuses the child's own report states. A run that proved nothing is a `SKIP`: the headline reads `SKIP (steps=N, skipped_checks=M)` and names the check, the exit code is `3` (`CheckSkippedExitCode`, the code the org's own `scripts/check-bed-watch.sh` already reads as "a SKIP, never a pass"), and the record carries the per-step `status:`, the `checks:` block and the run-level `skipped_checks:`. `ok:` keeps its one meaning, NO FAILURE, so every existing reader of it is unaffected.
- **opencharly/plugin-check#136** (squash `bef966df`, root tag `v2026.298.0205`, module tag `candy/plugin-check/v0.2026298.205`, closing opencharly/plugin-check#134) — the reader that extracts the per-check outcomes now reads the child's OWN report and only a report that agrees with itself, a report that says a declared check FAILED is a FAILURE, and only a plan child's log can carry a report at all.

`charly/go.mod:21` moves `github.com/opencharly/plugin-check/candy/plugin-check` from `v0.2026295.2128` to `v0.2026298.205`; `charly/go.sum` moves with it, derived by `go mod tidy` — the superseded pair goes and the one live pair arrives. The two versions' own `candy/plugin-check/go.mod` are byte-identical in their requirements (the same `/go.mod` hash `1IWFD+Sjy/R3PU+XCCPQXQyNer1N43pNLHJxlkDXJZU=`), so this is a single-module bump with no `sdk`/`spec` move behind it.

**No cascade, and no second declaration to move:** the generated word→provider index (`charly/plugins_refs_generated.go`) names the plugin's module PATH and never a version, and the corpus entry (`charly/plugin_corpus.txt`) names the repo, so neither changes.

**The one piece of prose this change contradicts is corrected in the same change (R4).** `charly/check_cmd.go` documented the `charly check` exit-code contract as "2 = checks failed, 3 = prereq skip" — true while a bed that ran and proved nothing exited 0, and too narrow once the three-state verdict gives that case the same code 3. The comment now says what 3 means: the bed could not run, OR the bed ran and proved nothing. It is a comment: the behaviour it documents is the plugin's, and the plugin is pinned above.

**Two findings came out of this change's own gate, and both are disclosed here rather than narrated.** The first gate run was RED with every step marked `0` — the two defects were in the gate harness, not in the diff, and both were the class R7 forbids (a step that cannot fail): the lint steps never ran (`golangci-lint` was not on `PATH`, and each piped its output into `tail`, so a pipeline's status — the last command's — was read as the step's), and the verdict could not be computed (the steps' statuses were concatenated into a 14-zero string and compared against a 14-zero literal, while only twelve steps exist). The harness now fails closed, and its whole log is pasted below.

The second run was RED for a different reason, and this one is worth reading twice: **the gate's own step wrote into the tree the gate was measuring.** The repo's merged control `TestWorkspaceHasOneMemberAndNoSumFile` forbids `go.work.sum` from existing beside `go.work`, and the gate's full-graph load (`go list -m all`) — run in workspace mode, which is the default for every command run inside the member — makes the go command record the COMPLETE graph's `go.mod` hashes in the workspace's own checksum lock. The gate then read its own byproduct as a product failure in the next run, and the tree-clean assertion could not see it, because the file is gitignored. The RCA named the writer by probing every command the gate runs; the root fix is in the harness — the full-graph load now runs in the member's own mode (`GOWORK=off`), and the gate asserts the artifact's absence explicitly, because `git status` cannot. The residual — the control's premise that "the single member's go.sum carries every hash" does not hold for the COMPLETE graph — is a decision on the `#1065`/`#1069` line, so it is FILED (opencharly/charly#1070) with its RCA, the writer probe and the three shapes a fix can take.

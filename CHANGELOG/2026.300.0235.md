# 2026.300.0235 — chore(deps): adopt plugin-task v0.2026299.2314 (a bump that would drop a nested checkout's work refuses)

## Summary

The compiled-in `plugin-task` pin is behind the served release, and what the release carries is a **refusal that protects an operator's commit**.

`charly/go.mod` requires `github.com/opencharly/plugin-task/candy/plugin-task v0.2026297.2108`; plugin-task's served `main` is `v0.2026299.2314` (`b523e8780bd2943a40fdc8c81b4470673c867d93`), and the delta between the two is two code fixes plus their changelogs:

| upstream commit | what it carries |
|---|---|
| `7d3b373af3` | fix(git-submodules): a bump that would drop a nested checkout's work refuses ([plugin-task#55](https://github.com/opencharly/plugin-task/issues/55)) |
| `1c451fc7a4` | fix(git-submodules): the nested-work refusal's scope is the REFUSED SUBMODULE ([plugin-task#57](https://github.com/opencharly/plugin-task/issues/57)) |

**Why this repo, and not only plugin-task.** `charly` IS the binary that runs the org's pin waves. The umbrella's `charly task sync` (its `pins` task, `MODE=bump`) is a `git-submodules` verb, and that verb lives in the **compiled-in** plugin-task — the one `charly/go.mod` pins. The umbrella's tree carries 411 submodules, and the verb rolls each one and then reconciles that path's OWN nested checkouts.

Before the fix, that reconcile was (`plugin-task v0.2026297.2108`, `candy/plugin-task/verbs.go:1488-1489`, in `reconcileNestedCheckouts`):

```go
if _, stderr, exit := hostCapture(context.Background(), projDir,
	fmt.Sprintf("git -C %s submodule update --recursive", shellQuote(abs))); exit != 0 {
```

`git submodule update --recursive` moves an already-initialized nested checkout onto the gitlink the parent records for it, **unconditionally**. It never asks whether that nested checkout carries work. So a nested checkout sitting on a LOCAL COMMIT was moved off it, with exit 0 and nothing reported — the operator's commit was no longer at HEAD, was reachable by no branch, and survived only in the reflog.

In `v0.2026299.2314` that statement is **unchanged** (`candy/plugin-task/verbs.go:1690-1691`, `reconcileNestedCheckouts` at `:1681`) — but it is now reached only after `judgeNestedLevel` (`:1550`, called at `:1442`) has judged every nested checkout the move would touch, and a refusal stops **that submodule** before its checkout is switched and before its pin is staged.

The fixed behaviour is the one thing that loses nothing: the bump **refuses**, it **names** the nested checkout, and it leaves the refused submodule exactly as it was — the operator's commit still at HEAD, the superproject's pin NOT staged, the submodule's own checkout not switched. The refusal's scope is **per-submodule** (`plugin-task#57`): a sibling that sorts after the refused one still rolls, because the bump collects per-path failures and continues.

| file | what the diff does to it |
|---|---|
| `charly/go.mod` | requires `plugin-task/candy/plugin-task v0.2026299.2314` (was `v0.2026297.2108`) |
| `charly/go.sum` | carries the new version's hash pair; `go mod tidy` drops the superseded pair |

Nothing else changes: the delta between the two versions is the refusal and its scope.

**Producer-first.** plugin-task's producer work is MERGED and TAGGED (`v0.2026299.2314`); this repo's compiled-in pin is the consumer that had not moved, so the refusal never reached the binary. The umbrella's own `plugin-task` gitlink is the NEXT consumer leg, after this one lands and this repo's merge is tagged — and the umbrella's prose citations of a plugin-task version are re-derived from this repo's pin by `scripts/check-cited-plugin-task-version.mjs`, so that re-key belongs to the umbrella's leg, not to this one.

Closes #1073

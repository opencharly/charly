## Summary

The compiled-in `plugin-task` pin is behind the served release, and what the release carries is the **moved-pin report**: the bump summary's counters change from INDEX WRITES to the pins that actually MOVED.

`charly/go.mod` requires `github.com/opencharly/plugin-task/candy/plugin-task v0.2026299.2314`. The served release is `v0.2026300.951` (tag `v2026.300.0951`, commit `669a5ee5eb68181121e6f2af36872b4491204d8d`), which carries opencharly/plugin-task#58 — *"the bump report counts the pins that MOVED, not the index WRITES"* — and opencharly/plugin-task#60, the coverage that holds each of the three counters.

**Why this repo is the leg that has to move.** `charly` IS the binary that runs the org's pin waves. The umbrella's `charly task sync` is a `git-submodules` verb, and that verb lives in the **compiled-in** plugin-task — the one `charly/go.mod` pins, not the umbrella's `plugin-task` gitlink (opencharly/opencharly#678, Finding 2). So the report the umbrella's wave PRs quote is the report **this** binary prints, and it is the two-bucket one until this pin advances.

The umbrella's own consumer leg (opencharly/opencharly#735) is blocked on exactly this: its `scripts/sync-pr-body.sh` fixture renders the producer's summary line, and it must render what the binary the umbrella BUILDS prints. Writing the new shape into that fixture before this pin advances would make the fixture describe a shape the running binary does not print — a false fix in the opposite direction.

## Summary

Head `368aac4d5a484abd8c1e4e269dc12e86d5f17aaa` — the commit this PR pushes: **3 files changed, 4 insertions(+), 4 deletions(-)**.

**The defect.** The `charly` binary this repo builds and ships COMPILES candy/plugin-box in, and the
pin it compiles is `github.com/opencharly/plugin-box/candy/plugin-box v0.2026294.21` — the release
whose `charly box build` grammar still spells the inner-concurrency flag `--podman-jobs`, with the
env binding `CHARLY_PODMAN_JOBS`. The contract renamed that knob `podman_jobs` →
`stage_parallelism` (`opencharly/spec` `spec/schema/box.cue:120-121`, spec commit `4e61d3d`), and
opencharly/plugin-box#66 renamed the FLAG to match — `--stage-parallelism` /
`CHARLY_STAGE_PARALLELISM`, tag `v2026.301.1542`.

So the shipped binary REJECTS the spelling the contract publishes, at the flag:

```
$ charly box build --stage-parallelism 2
charly: error: command "build": unknown flag --stage-parallelism
(exit 80)
```

**The RCA.**

- **Mechanism** — the flag lives in the PLUGIN's own kong grammar
  (`candy/plugin-box/box.go`, `buildGrammar.StageParallelism`), and this repo ships that plugin
  COMPILED IN at a pinned module version. The spelling a given binary accepts is therefore decided
  by the PIN, not by this repo's source; nothing in this repo's tree states the spelling at all.
- **Missed control** — the rename's controls sat on the CONTRACT (the spec's schema and its
  migration ops) and in the PLUGIN's own repo. Nothing connected the contract's rename to the
  CONSUMER's compiled-in pin, so the consumer was never asked to move. This repo's own
  `charly box validate` cannot see it either: the flag is in the plugin's grammar, and the knob
  this project's `charly.yml` carries is a CONFIG KEY, whose own retirement is a separate and
  still-open defect (opencharly/charly#938) that validates green.
- **Blast radius** — every user of the shipped binary who passes the published flag: the whole
  `charly box build` surface, plus every script, skill or CI step that spells it the way the
  contract does. One pin, two manifest lines, no behaviour of its own.
- **Root fix** — move the compiled-in pin to the release that carries the renamed flag, in BOTH
  places that carry it (the Go module pin and the `candy:` pin the bed composes), and prove the
  SHIPPED binary's own grammar with a two-binary probe: the pre-change build and the post-change
  build, same command, opposite outcomes. The probe is pasted in **How tested**.

**What lands.** Two pins, and nothing else:

**What this change does NOT do.** It does not touch the knob's CONFIG-KEY surface: this repo's own

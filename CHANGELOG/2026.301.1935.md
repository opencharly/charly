# 2026.301.1935 — fix(config): adopt the landed stage_parallelism vocabulary in the project manifest (#938)

Closes #938

## Summary

Head `a4096c21ed51b27864c4b9f7680146572be67a12` — the commit this PR pushes: **2 files changed, 8 insertions(+), 3 deletions(-)**.

**The defect.** This repo's own `charly.yml` spelled the inner build tunables `podman_jobs` / `podman_jobs_cap`. Those keys are **dead**: the cutover that landed the knob as `--stage-parallelism` / `CHARLY_STAGE_PARALLELISM` retired the podman-era spellings, and a retired key under `defaults:` is dropped by the decode — silently, because the `defaults:` block is validated against an OPEN schema struct. So the manifest's declared inner-concurrency cap of **8** was never applied: every build resolved to the sdk's fallback of **4**, and `charly box validate` reported **0 warnings, 0 errors** the whole time. That is the exact shape opencharly/spec#241 names.

**The RCA.**

- **Mechanism** — `spec.Config.Defaults` is a `spec.BoxConfig`, decoded with no strict-field check. The retired key is dropped on decode, so the value the operator declared never reaches the resolver (`candy/plugin-build/resolve.go:246-255`, `resolveDriveStageParallelism`) and the build silently asks for `buildkit.ResolveStageParallelism(0, 0)` — the sdk's fallback (`sdk/buildkit/build_helpers.go:37-74`). The schema half of the mechanism is an **open/closed asymmetry**: `spec/schema/box.cue` marks `#Box` **CLOSED** (*"an unknown key is a typo"*), but the `defaults:` block is validated against `#BoxConfig`, which is **not** closed — so a retired key under `defaults:` is *accepted* by validation and *dropped* by the decode, and no tool in the chain can see it.
- **Missed control** — the contract's rename landed its controls on the SCHEMA (the key names in `spec/schema/box.cue:120-121`), the MIGRATION TABLE (`plugin-migrate`'s `rename_key` ops) and the FLAG. Nothing connected the contract's rename to the CONSUMER's own manifest, and this repo's `charly box validate` cannot see it either: the retired key is not an unknown key *to the validator*, it is a dropped one, so the validator has nothing to reject.
- **Blast radius** — this repo's own builds: the declared cap of 8 was never in effect; the org ran at 4. One manifest block, two keys.
- **Root fix** — move this repo's manifest onto the landed vocabulary, and correct the comment that misstated the mechanism (it claimed *"inner: stages per `podman build`"*; the builder is BuildKit and the resolved value is the DAEMON's `[worker.oci] max-parallelism`, set at daemon start and **host-global per uid**).

**What lands.** Two keys and their comment:

| where | was | is |
|---|---|---|
| `charly.yml:56` | `podman_jobs: 0` | `stage_parallelism: 0` |
| `charly.yml:57` | `podman_jobs_cap: 8` | `stage_parallelism_cap: 4` |

**Why the cap is 4, and not the 8 the manifest declared.** This is the one decision in this PR, so it is measured rather than asserted:

1. The retired key was DROPPED — so this repo's builds have been running at the sdk's fallback of **4** all along. 4 is what the org's builds run at today.
2. The BuildKit daemon is **host-global per uid** (`$XDG_CACHE_HOME/charly/buildkitd`, socket `/run/user/1000/charly/buildkitd.sock`), not per project. The resolved value is the daemon's `max-parallelism`, and a differing value is a **hard error** (`sdk/buildkitdrive/daemon.go:96-99`) — measured, with the renamed key at 8: *"the running daemon was configured with max-parallelism=4 but 8 was requested"*. Carrying 8 would therefore have **failed every build on this host**, and would have forced the value onto every other project on the uid.
3. No `charly` verb stops that daemon (there is no verb for it — `charly clean` is an out-of-process plugin), so the remedy is not expressible with the binary. That is opencharly/charly#919, and it is where the operator's next step already lives.

The cap is therefore **4**: it is the value this repo already runs at, it is the sdk's conservative fallback, and it is the value the running daemon was started with. Raising it is a host-level decision, not a manifest edit — it is filed under **Filed issues**.

**The comment is corrected with the keys.** It now says what the value IS: the resolved number is the BuildKit daemon's `[worker.oci] max-parallelism` (`candy/plugin-build/buildkit.go`), set at daemon START and shared by every project on the uid — so it applies only when it matches the value the running daemon was started with.

**This is consumer leg 6b of the `stage_parallelism` fan-out** tracked in opencharly/opencharly#785. The producer (opencharly/plugin-box#66, tag `v2026.301.1542`) and the shipped-binary leg (opencharly/charly#1082) are landed; this leg is the repo's own manifest.

## Filed issues

- **opencharly/charly#919** — "The BuildKit daemon has no supervisor: a changed stage_parallelism cannot be applied while it runs". The finding this PR measures: the resolved value is the DAEMON's `[worker.oci] max-parallelism`, and the daemon is **host-global per uid**, so the manifest's cap is a REQUEST to a host-scoped service, not a per-project setting. With the cap at 8 the build refuses by name (*"the running daemon was configured with max-parallelism=4 but 8 was requested"*), and no `charly` verb stops that daemon, so the remedy is not expressible with the binary. This PR keeps the cap at 4 — the value the org already runs at — and the question *"may this host run above 4?"* is the operator's, on that thread, where it is already framed as the next step.
- **opencharly/spec#241** — "an undeclared key under `defaults:` validates clean and is silently ignored — a renamed key's old spelling disappears without a word". The GENERAL form of this PR's defect: the retired key is dropped by the decode instead of being rejected, so a declared cap of 8 was inert while every check passed. The evidence from this instance is posted on that thread, and this PR adds the schema half of the mechanism: `spec/schema/box.cue` marks `#Box` **CLOSED** (*"an unknown key is a typo"*), but the `defaults:` block is validated against `#BoxConfig`, which is **not** closed — so a retired key under `defaults:` is *accepted* by validation and *dropped* by the decode, and no tool in the chain can see it. The decision (should a retired key FAIL validation, with a remediation hint pointing at `charly migrate`?) is the schema's, and the operator separated it from this fix on #938.
- **opencharly/plugin-build#35** — "the build registry mirror is read by the drive but only reaches a buildkitd that starts AFTER it is set". The finding that made the first R10 witness (`check-boxload-pod`) unrunnable: the drive pushed to the mirror while the already-running daemon resolved the internal base against the upstream registry, so the build died with *"ghcr.io/opencharly/fedora-layer-supervisord:check-boxload-pod-2026.301.1829: not found"*. Independent of this change (a daemon registry configuration, not the build resolver's `defaults:` keys); the evidence and the measurement are on that thread.

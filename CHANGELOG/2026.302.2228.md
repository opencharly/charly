# 2026.302.2228 — fix(test): the retired-knob sweep reads the INDEX, so its scope is this repo's tracked tree

## Summary

**Predecessor:** opencharly/charly#1089 — merged as `79e8a28` (tag `v2026.302.2208`), which
delivered the retired knob's removal from `.env.example` and the claim-keyed control that owns
the fact. This PR is that PR's first review round's finding, landed after the merge.

The validator's review of #1089 raised this observation:

> The body and the test log call the sweep a scan of the "tracked tree," but the implementation
> is a filesystem `WalkDir` (it would also read untracked working-tree files not under the
> skipped dirs). In a clean CI checkout this is equivalent to tracked files, and the gate
> passed; it could theoretically produce a local false positive if a developer keeps an
> untracked file naming the knob. Consider either using `git ls-files` or softening the
> wording to "working tree."

The wording was the INTENT, so the code moves (R4). This PR makes the sweep's scope the
repository's TRACKED files, derived from the INDEX.

**The RCA for this finding.**

- **Mechanism.** The control enumerated its scope by walking the filesystem from the repo root
  (`filepath.WalkDir`) and skipping nested repos and a few directory names BY HAND. Its scope
  was therefore "every regular file under the root that is not in a skipped directory" — a
  superset of the tracked tree, not the tracked tree. The description named the intent; the
  implementation had drifted from it.
- **Missed control.** Nothing pinned the control's SCOPE. The sweep reported how many files it
  read, but no assertion compared that set against the repository's tracked-file set, so the
  drift between the claim and the implementation survived a green gate. It is the same class of
  miss opencharly/charly#1087 records — a fact asserted at the contract level but never at the
  surface level.
- **Blast radius.** A false positive for a developer who keeps an untracked file naming the
  retired knob: the gate would fail for a path the repository does not ship, which teaches
  authors to route around the control. And the repository carried TWO definitions of "the
  tracked files" — this control's walk and `scripts/check-pin-verb-scope.py`'s index
  enumeration — which can disagree (R2).
- **Root fix.** The sweep derives its scope from the INDEX with `git ls-files -s -z` and skips a
  gitlink (`160000`) and a symlink (`120000`). That is the SAME enumeration and the SAME
  exemptions `scripts/check-pin-verb-scope.py` applies, so this repository keeps ONE notion of
  "the tracked files" and the Go control and the Python gate agree by construction rather than
  by coincidence. Each tracked path's CONTENT is still read from disk, so a change that is not
  staged yet is still judged: the index decides WHICH files are in scope, the working tree
  decides WHAT they say.

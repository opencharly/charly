# 2026.306.0148 — fix(core): a compiled-in peer's idle guard watches real work, not pid 0 (#1088)

## Summary

`charly box build pod-crabbox` at `opencharly/pod-crabbox` PR #1 head `d9b11549` died at the
default 90s no-progress window **while BuildKit was working**. This change fixes the guard's
progress SOURCE, not the window (opencharly/charly#1088; item (c) of opencharly/.github#263).

The measured mechanism: the build peer is compiled in, so `providerPid` returned 0 and the
process-tree source watched nothing; a `buildctl` phase has no host reverse leg, so nothing
else fired; the phase died `signal: killed` and buildkitd logged `Solve ... Canceled`.

`charly/plugin_activity.go` now:

1. gives a compiled-in peer the HOST's DESCENDANTS as its tree (`buildctl`, the engine's
   load child), with the host root excluded so the runtime's own ticks cannot mask a wedged
   call;
2. samples CPU ticks **and** `/proc/<pid>/io` bytes (`rchar`+`wchar`), so an I/O-bound OCI
   export / engine load is observed as work;
3. follows the charly-owned DETACHED daemon trees (`buildkitd` under `rootlesskit`, which
   re-execs and is reparented to init) for a quiet BuildKit RUN, discovered generically by
   argv under the user's charly cache/runtime roots — no daemon kind word in core;
4. joins the watcher in `stop()`, so a stopped clock cannot sample after return.

The window remains `readiness.no_progress` (90s default). **No default was raised.**

# 2026.306.0314 — fix(958): check-wave-pins derives wp-pins expectations from the tree under test

## Summary

`check-wave-pins` is declared as *"the R10 gate for the wave's COMMITTED pin story"*, and its `wp-pins` step contradicted the bed's own documented principle (*"assert the versions from the graph itself — a hand-copied string would pass a diff that never moved the pin"*): it asserted two CalVer literals (`plugin-build v0.2026286.1121`, `plugin-vm v0.2026286.856`) that outlived their wave. The bed was therefore red at **both** ends of any pin advance and no wave could make it green — Finding 2 of opencharly/charly#958. The step also read `go.mod` relative to a cwd it does not control, so it depended on the deploy handing it the source tree.

This change makes `wp-pins` ask the property the bed exists to prove:

* the expected side is read from the **tree under test** (`$SRC/charly/go.mod`), with the source tree located explicitly and an actionable failure when the tree under test is not a charly checkout — the cwd assumption is removed, not worked around;
* the graph side is read from the **binary** (`go version -m`, tabs normalized), so the assertion is *"the built graph agrees with what this tree adopts"* — true for every wave, with no edit;
* both pins must be **declared**: an absent declaration, or a tree that is not a charly checkout, is a hard failure — never a vacuous pass;
* the readable echo of the declared pins reads the same file the assertions read (an unqualified `go.mod` there would reintroduce exactly the cwd assumption this change removes);
* the expected-side shell names are **lowercase on purpose**, and the step says why in place: the check walk runs the sdk's `kit.TestVarRefPattern` over the command text, and that pattern claims a braced, uppercase name as an unresolved template reference — which classifies the step's assertion `DEAD` (sdk `kit/planrun.go`) before the step ever runs. This is not a style choice; it is the mechanism that made the first bed run of this change red (see R1 below).

The two steps that exercise the substance — `wp-build-generate` and `wp-vm-list`, which prove the adopted plugins build, link and dispatch in-process — are untouched.

Refs opencharly/charly#958 (Finding 2). **Finding 1 of that issue is not in this change**: the qualified/imported-namespace invocation that fails at `deploy-add` is a resolver defect tracked separately (opencharly/charly#819), and it fails one stage before the step this change edits. This PR therefore does not close #958.

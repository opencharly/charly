# 2026.307.1232 — feat(cli): honour the request's working directory (unit 2 of #819)

## Summary

**Head `45457fc5e3ac2e88132c658c9c20f73f2cb63425` — 10 files, +55/−29.** The host's generic `"cli"` builder now honours the working directory its caller asks for:

```go
// charly/host_build_cli.go, runCliSubcommand
cmd := exec.Command(executable, req.Argv...)
if req.Dir != "" {
    cmd.Dir = req.Dir
}
```

**Empty inherits this process's cwd, so every existing caller is byte-identical in behaviour.** The field is opt-in and additive.

**Why.** A caller that runs a subcommand on behalf of an **imported** project must have the child read *that* project, while the caller itself stands in the importer's. Measured on **opencharly/charly#819**: a `kind: local` bed invoked qualified (`charly.check-task` from the umbrella) ran `${CHARLY_BIN} task list` against the umbrella, so its assertion passed vacuously instead of testing the bed's own project:

```
FAIL … [task-list-declared]  stdout: expected to contain "check-task-smoke"
  (got: hooks, map, org-map, pins, policy-b, prune, self-test, skills, sync, verify)
```

Before `opencharly/spec#290` there was nowhere to put a directory — `#CliRequest` carried `argv`, `capture`, `combined`, `best_effort`, `env` and nothing else — so this could not be fixed below the host seam.

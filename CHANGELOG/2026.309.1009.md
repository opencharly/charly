# 2026.309.1009 — feat(init): add the systemd-container init and fix the /system* mount target

## Summary

The `charly` leg of the W3.8 cutover (opencharly/charly#1030, spike #1027), rebased onto current `main`. The branch had fallen well behind; every conflict was a regenerated dependency file (`charly/go.mod`, `charly/go.sum`, `go.work.sum`, and the `go.mod`/`go.sum` pair of each `tools/` module), resolved by taking `origin/main`'s version of each and re-applying only this branch's intentional change.

- **New `systemd-container` init entry** beside `supervisord:` — a container-venue systemd: `/sbin/init` as the entrypoint, SYSTEM units (a container has no user manager), the container-environment masks from `CONTAINERD-IMAGES.md` §2 (`serial-getty@hvc0`, `systemd-udevd` + its sockets, `sys-kernel-{config,debug,tracing}.mount`, an empty `/etc/machine-id` in the IMAGE, `kernel.pid_max=32768`), and no `bootc container lint`. The krun arm is NOT claimed: no krun handler exists, so `KRUN_INIT_PID1=1` stays unproven and the comment says so.
- **Selection is data.** `requires_capability: [init_system:systemd-container]` is the key a candy provides with `capability: {init_system_hint: systemd-container}`. A box may also pin it with `init: systemd-container`.
- **`extends: systemd` shares the ONE authored `service_schema`.** The merge is zero-value inheritance per FIELD of the resolved init (`spec/spec/init_extends.go`): a non-empty child field wins and an empty one inherits. The test pins both directions — `preserve_user` is NOT inherited (the child's non-empty `requires_capability` wins) while `service_template` IS. Writing that test exposed a real defect: `service_schema` is inherited as ONE field, so the child's non-nil block had won the whole field and dropped the template. The child now leaves `service_schema` empty so the whole schema inherits.
- **R1 fix on the sibling mechanism:** both systemd assemblies' `RUN --mount` TARGET moved off the top-level `/systemd*` namespace. BuildKit does not materialize a top-level `/system*` mount target (measured in the original leg: `/systemd`, `/systemd2` and `/system` failed; `/xs-systemd`, `/etc/systemd` and `/usr/lib/systemd` passed), so the machine `systemd:` init's assembly had been mounting nothing. Both now use a neutral target, and the assembly test (below) fails if either target is reverted into `/system*`.

**Dependency change: `plugin-init` only.** The rebase takes `origin/main`'s `sdk v0.2026308.652` and `spec v0.2026308.344`, which are already newer than the pins this branch originally asked for.

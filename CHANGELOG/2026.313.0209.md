# 2026.313.0209 — feat(schema): compose the base document schema by importing the spec CUE module

## Summary

`charly` assembled its base document schema as **text**: every `schema/*.cue` body concatenated into one package-less blob (`schemaconcat.ConcatSchema`), and every plugin's served schema compiled as `baseBody + "\n" + servedCUE`. `spec` is a real CUE module now — `cue.mod/module.cue` declares `github.com/opencharly/spec` at language version `v0.16.1`, and all 64 `schema/*.cue` files are one `package schema` — so this change composes the base the way that module says it must be composed: by **import**.

The new shape, in one paragraph: `specModuleOverlay()` materializes the two embedded trees at ONE virtual module root (the schema package from `schema.FS` under `<root>/schema/`, the module declaration from `specmodule.FS` at `<root>/cue.mod/module.cue`); `buildSpecModuleInstance()` loads `./schema` from it with `load.Instances` and builds the value in the kernel's CUE context; `sharedCueSchema()` is that composed instance. Nothing is read from disk — the overlay is in memory at a fixed path, so CUE diagnostics carry no machine-specific paths — and the load fails LOUD when the source does not arrive as a module, or when the module declares no `language.version`. Those are the two ways a package load silently loses the pinned semantics, which is exactly what the module's `language.version` exists to prevent.

**What deliberately stays concatenated: the plugin half.** A plugin's served schema still arrives as TEXT and is still unified with the base — only the merge changed, from text (`base ++ served`) to values (`base & served`). That is sound rather than convenient because the load gate already requires every plugin schema to compile STANDALONE (it may reference no base def), so a served schema can only ever merge with the base's declarations — which is what `Unify` does. `schemaconcat` loses its last runtime caller in charly; it stays the spec generator's path and this cutover's parity oracle.

**The spec bump is the producer leg this unit measured itself missing.** `schema.FS` delivered the schema's source to a Go consumer but not the module that owns it — `cue.mod/module.cue` sits at the module root, outside `schema/`'s `//go:embed *.cue` tree — so the pinned language version was unreachable, and the two alternatives were both wrong (restate the declaration in charly, or let the toolchain default govern). opencharly/spec#296 (`d29dc52d2810dd1b4056024a8a5598e81e65c925`, tag `v0.2026313.48`) exports it as package `specmodule`; this PR consumes that tag.

## Change classification

- **Class:** internal mechanism change in the plugin host, plus a contract-module dependency advance. No authored schema value changes — the composed base is provably the same schema (719 fields, equal) — so nothing an author writes, and nothing a plugin serves, changes shape.
- **Consumer impact:** none for charly's users and none for plugin authors: the plugin schema contract is untouched (self-contained text, unified onto the base), and the CLI surface is unchanged.
- **Breaking change + rollback:** none — the composed schema value is identical field for field, so no authored document, plugin schema or generated type can behave differently; a revert restores the text splice and drops the spec bump together, and the spec tag it consumed stays valid for any other consumer.
- **Startup cost:** the base is composed ONCE per process (`sync.OnceValue`) instead of once per plugin registration, so the plugin gate now does a `Unify` where it used to recompile the whole concatenation.

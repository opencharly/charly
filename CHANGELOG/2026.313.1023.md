# 2026.313.1023 — feat(plugin): compose each served unit's schema, then unify it onto the base

## Summary

opencharly/sdk#490's second ordered root: the host's plugin schema gate no longer joins unit
sources into one compilation unit.

`compileBasePlusServed` compiled `strings.Join(everyLoadedUnit, "\n")` onto charly's base, and
`registerPluginUnitSchema` first compiled each unit's text standalone with no CUE module in
scope. Both shapes are text, and text cannot carry the import this cutover exists for. Measured
on the pre-change tree, with a plugin schema that imports `github.com/opencharly/spec/schema`:

```
ONE unit, old text compile            -> package "github.com/opencharly/spec/schema" imported but not defined in  (and 1 more errors)
TWO units joined, old text compile    -> expected label or ':', found 'STRING' "github.com/opencharly/spec/schema"
```

The second is a failure #490 names as independent of the first: N units joined into one file
put N import clauses in one compilation unit, which is not CUE at all.

Now each unit is COMPOSED as its own CUE module instance and the values are unified onto the
base — the unit boundary lands exactly where CUE's own package boundary is: one package per
plugin. The composer is `spec/schemacompose`, the ONE composer in the contract module: this host
may import `github.com/opencharly/spec` and may NOT import `github.com/opencharly/sdk` (this
repo's import-purity gate, "the sdk mechanism kits and the sdk root plugin-authoring package are
for PLUGINS to import, never the host"), while the serve side may import both — so the shared
home is the only place the two halves can judge the same schema with the same code.

**The running value is grown one unify per registration, not rebuilt from the base.** That is a
measured requirement, not a refinement: rebuilding made plugin loading quadratic, and
`charly/charly`'s TestMain — which registers the 63 builtin plugin schemas — went from **1.4 s to
26.4 s**, which then pushed `TestConnectPluginReady_HonorsACallerCancellation` past its 10 s bound,
because the fixture's child process could not finish its own TestMain and answer the handshake.
With one unify per registration TestMain is **1.1 s** and that test passes at 1.45 s.

The declarations the gate reads per source are unchanged: `topLevelDefNames` now reads the
composed unit's value, which carries the same top-level definitions, and the charly#770
collision identity index is untouched.

The composer's deep arms live where the composer lives: opencharly/spec#297 tagged
`v0.2026313.453`, which this change pins.

## Change classification

Core plugin-loading behaviour, no user-facing surface change.

- **What changes for a consumer:** nothing to do. Every plugin that served a schema before still
  serves it — proved by the live run over the whole builtin corpus — and a plugin may now import
  the spec schema (opencharly/sdk#491/#492 carry the serve side).
- **What is NOT done here:** a consumer that adds `cue.mod/module.cue` + an import still cannot
  have its Go params generated, because #490's ordered root 3 (the param generator keeps a module)
  is untouched, as the issue scopes. The census rows of opencharly/opencharly#945 stay.
- **Reversing it:** the commit is one file plus tests; moving `require github.com/opencharly/spec`
  back to `v0.2026313.48` and restoring `plugin_loader.go` returns the previous behaviour.

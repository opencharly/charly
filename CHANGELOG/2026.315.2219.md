# 2026.315.2219 — fix(plugin): the idle guard's daemon discovery resolves its roots through the ONE resolver

## Summary

`charly` core resolves its daemon roots through the org's ONE resolver, which now lives where core
is allowed to reach it.

`charlyDaemonPids` — the idle guard's discovery of charly-owned DETACHED daemons — composed
`$XDG_CACHE_HOME/charly` and `$XDG_RUNTIME_DIR/charly` by hand. Two consequences, both measured:

- it ignored `CHARLY_CACHE_DIR`, so on a relocated install it could not see the `buildkitd` its own
  idle guard exists to follow, and would kill a running install as WEDGED (`opencharly/charly#1119`);
- it duplicated the root computation that `sdk/storekit` owned, which core may not import.

It now asks `spec/storeroot` — the contract surface core is permitted to import — for the cache and
runtime roots, and nothing else changes: the scan of `/proc`, the argv match, the self-pid
exclusion, the seam, and the "a daemon is shared, so summing it is the correct trade" reasoning are
untouched.

**`TestImportPurity_HostImportsOnlySpecAndVettedThirdParty` passes AS WRITTEN.** No exception was
added, no residual-SDK row was declared, and `charly/import_purity_test.go` is byte-identical to
`origin/main`:

The gate is also proved LIVE in both directions (§2), because a gate nobody can trip proves nothing.

**One deliberate behaviour change, stated rather than discovered later.** The runtime root now comes
from the resolver, so with no `XDG_RUNTIME_DIR` (a container, a cron job) it becomes the STATE root
— the resolver's documented fallback — where the hand-built code simply dropped the runtime root.
That can only WIDEN the daemon set the guard follows: a path that did not match before still does
not, and a daemon whose argv names the state root is now visible. It cannot cause a false kill (more
visible daemons means more evidence of progress, never less).

**The pins move with the code, and one of them is not optional.** Bumping `spec` to a tag carrying
`spec/storeroot` crosses a signature change: `schemaparams.Generate` lost its third parameter
between `spec` `v0.2026313.453` and `origin/main`, and this repo's `plugin-candy` pin still called
the three-argument form — so a `spec`-only bump fails to BUILD, in a dependency:

```

$ go build ./...

```

`plugin-candy v0.2026313.1445` already carries the two-argument call, so it is bumped here with
`spec`. `sdk` is NOT bumped by this PR: nothing in this diff imports it, and the plugins that do
adopt the re-export when their own pins advance.

## Change classification

**Core behaviour fix, API-neutral.** No exported surface changes (`charly` core is a `package main`),
no command, flag or config key is added or removed, no wire shape moves. One behaviour changes, in
the direction the tracking issue asks for: daemon discovery follows `CHARLY_CACHE_DIR`, and the
runtime root inherits the resolver's documented state-root fallback when there is no
`XDG_RUNTIME_DIR`. `spec` moves to `v0.2026315.2118` and `plugin-candy` to `v0.2026313.1445` —
the second is forced by the first (a signature change in `schemaparams.Generate`), and neither
changes any authored document.

**Breaking change + rollback:** nothing breaks for a consumer of this repo. `charly` publishes a
binary, not a library; the binary's commands, flags and outputs are unchanged, and the two pins
move FORWARD (no consumer is asked to move anything). The one observable difference is that a
daemon under a relocated cache is now found instead of ignored — which is the fix. Rollback is one
inverse commit: reverting it restores the hand-built pair AND both pin lines, returning the module
graph to `spec v0.2026313.453` / `plugin-candy v0.2026281.948`; there is no data migration, and the
roots resolve to the same directories either way.

# 2026.316.1207 — fix(plugin): compose the kind value gate and provider-declared fold

## Summary

`validateKindValueCUE` gated every substrate/candy/host-value kind against
`spec.KindValueDefs[disc]` looked up in `sharedCueSchema()` — the **base schema alone**. A
definition a plugin declares lands in `pluginSchemas.unified` (**base & every served plugin
unit**), a different `cue.Value`, so the moment a kind body left `spec/schema` the gate would stop
finding its def and silently stop gating. `runPluginKind` chose the host-value fold from the same
host-side list (`spec.KindValueDefs` membership).

Now:

- **The gate reads the composed unit.** `kindValueDefValue` resolves the def against
  `pluginSchemas.unified` (via the new `composedSchema()` snapshot), falling back to the base only
  while nothing is composed — and, when the def is in neither the base nor the currently composed
  units, materializes the builtin units once (`sync.Once`) and retries the composed lookup.
- **The fold follows the shape the provider declares.** `kindValueDefPath(prov, disc)` asks the
  provider first: a `class:kind` capability naming a `#<Word>Value` body def in its `InputDef` is
  host-value-gated; `spec.KindValueDefs` is only the compatibility fallback for a body that has
  not moved. `capMeta` now carries that declared `InputDef` (`DeclaredKindInputDef`), so routing
  and gating read the same declaration, in both placements, with no wire/contract change.
  Substrate routing (`DeployTraits`) and the candy factory (`CandyKindCarrier`) were already
  provider-declared and are untouched.

No kind moves here. Every kind whose body still lives in the base resolves the **same def it
always did**, and the composed value is measured **equal to the base for all 11 gated kinds**.

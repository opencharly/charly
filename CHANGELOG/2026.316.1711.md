# 2026.316.1711 — fix(plugin): unify with the def as receiver so a served def's contract refs resolve

## Summary

`validateKindValueCUE` gated every host-value kind with `merged := entity.Unify(def)` — the **authored document as the receiver**. `cue.Value.Unify` resolves every reference it meets through the *receiver's* runtime, and the two sides carry different runtimes: `def` comes from the composed unit (`pluginSchemas.unified`), whose runtime carries the plugin unit's **import graph**, while `entity` is built from the authored JSON by the project loader, which has **no import clause anywhere in it**. So the moment unit 0 (`charly#1122`) moved the *lookup* to the composed value and the first corpus field forced a **contract reference** through the gate, a `schema.#…` cited by a **served** def was resolved through the entity's import-less runtime and failed.

Same def value, same authored entity, one process, **only the receiver differs**:

That failure IS the pair: the committed test asserts `entity.Unify(def)` fails **by import resolution** and then that the production gate accepts the same body — so the red line above is the first assertion holding on the un-flipped gate.

`validateAuthoredPluginInput` (`plugin_loader.go`) has always done `d.Unify(in)` — schema as receiver — which is why `#PipelineAgentInput.llm: schema.#LLMSpec` has worked since `plugin-pipeline#60`. The kind-value gate never needed it before only because **every def it resolved came from the base** (one package, no import clause). `charly#1122` moved the *lookup* and left the *order*.

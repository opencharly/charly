# 2026.317.1641 — fix(plugin): the idle guard confirms an ATTEMPTED touch, so a starved producer cannot be read as a wedged plugin (#913)

## Summary

**The defect.** `TestIdleBoundedContext_TripsOnlyWhenIdle` raced a `50ms` toucher against the `150ms`
idle window and asserted survival for `600ms`. It **red-blocked unrelated PRs** — measured on
`charly#922`, whose diff changes **no Go source and no test**: `go` went red with exactly this test
on head `0a31d0cb`, while five runs on the same tree on an unloaded host pass. The failing run's own
kill report names the mechanism: the producer was **starved past the whole window**
(`host reverse legs=7 (last 191ms ago), CPU advances=0 (last never); window=150ms`), so the guard found
nothing at expiry and cancelled a call that was still progressing. *"Nothing arrived"* and
*"nothing was sent"* are different facts, and only the second is idleness.

**The fix.** `touch()` increments `pluginActivity.touches` **before** its non-blocking depth-1 send, and
`touchAttempts()` reads it. It counts **attempts, not deliveries**: the send drops its token when one is
already pending, so a delivery count undercounts exactly when the guard is deciding whether the source is
alive. `observe` — the ONE progress measurement, and already the reason a kill needs a confirmed expiry —
treats a **grown** count as progress beside the drained host-leg event and the tree-work advance, and both
call sites thread the baseline through. Cancel now requires no delivery, **no tree-work advance AND no
attempted touch**. The progressing test arm is redesigned to advance the producer from the test's own
goroutine, so *"the source is live"* cannot be starved away; it then stops the producer and asserts
idleness **still trips** — both directions, neither dependent on a cadence.

**This round also reconciles the branch with `main` and re-bases the change onto main's guard by hand.**
`main` moved 173 commits ahead and rewrote the guard's progress source — `cpu()` → `work()`/`procWork`,
`watchedRoots()`, `excludeRoot`, the charly-owned detached daemon trees (`#984`, `#997`, `#1004`,
`#1088`/`#1102`, `#1121`). The merge is a real merge commit (`3546d49b`); the conflict was resolved by
**re-applying the attempt source onto main's structure**, not by merging text: the `touches` field,
`touchAttempts()`, `observe(wake, last procWork, lastAttempts)` with the attempt check, the
`lastAttempts` baseline at both call sites and refreshed by the wake case, and the attempt count rendered
into `stallReport` so a kill report describes all three sources it decided on. `main`'s `#1088`
daemon/descendant tests are intact.

**And it ships the instrument the finding asked for.** The state the fix addresses — *an attempt counted,
no delivery, no tree-work advance* — lasts two adjacent instructions in production, so no load control
reaches it (nine shapes measured below) and no dispatch this binary has enters it (every guarded dispatch
runs on a **compiled-in** clock whose watched tree never goes flat during real work). The change therefore
ships `CHARLY_PLUGIN_TOUCH_GATE`, a **test seam that is zero in production** and only ever **defers a
send**, so the interleaving is reproducible — plus `check-idle-guard-starved`, a `disposable: true` bed
that runs the arm on a fresh-rebuild venue and is shown to **fail when the attempt source is removed**.

### Arm by arm: what discriminates and what does not

| arm | what it asserts | discriminating? |
|---|---|---|
| bed step, **fixed** tree | the guard SURVIVES a producer that attempted progress while nothing was delivered and the tree was flat — 10/10 trials | — |
| bed step, **mutated** tree (attempt hunk reverted) | the same call is KILLED at trial 0, with the report naming `attempted touches=5` | **YES, deterministically** — the negative control above |
| seam inert by default | `pluginActivityTouchGate == 0`, and an ungated `touch()` still delivers synchronously (no wait, no goroutine) | yes (safety property) |
| seam defers only the send | the attempt is counted immediately, the caller is never held, the real send arrives late | yes (instrument property) |
| the four unit tests (mutation A/B/C) | each mutation fails its own diagnostic | yes, at unit level |
| *a live CLI dispatch entering the state* | a `charly …` command that reaches the starved state by itself | **NO — not reachable, measured below.** Stated here rather than implied |

**The seam, and why the arm is in-process.** The state the fix addresses requires a producer that has run
`touches.Add(1)` and has not completed its non-blocking send. In production that window is two adjacent
instructions, so external starvation cannot hold it:

| load shape (spike, production shape `peer pid=0` + the real heartbeat) | trials | false kills WITH the source | WITHOUT it |
|---|---|---|---|
| idle / 16 / 64 / 256 burners, window 150ms | 20 each | 0 | 0 |
| 64 burners, window 30ms | 40 | 0 | 2 |
| 256 burners, window 30ms | 40 | 1 | 5 |
| **256 burners, window 30ms — re-run** | **100** | **0** | **1** |
| 128 burners, window 20ms | 100 | 1 | 0 |
| 64 burners, window 30ms, `GOMAXPROCS=1` | 60 | 1 | 0 |

The 1-vs-5 reading did not survive re-measurement, and two shapes invert — noise, not signal. And no
dispatch this binary has enters the state: a temporary probe on the guard's arming site counted **287
`kind=local`, 48 `refs`, 21 `kind=distro`, 18 `verb=egress`, 15 `kind=init`, 5 `kind=resource`, 3
`verb=oci`, 1 `command=validate`** arming points on `box generate`, and **38 `refs`** on `candy --help` —
**every one on a COMPILED-IN clock** (`peerclock=false`), which watches the HOST's descendants and so
never goes flat during real work. With the gate set and the window at 200ms/50ms/5ms, `box generate`,
`status --json`, `clean --dry-run`, `preempt status`, `cache status`, `vm gpu status` and `candy --help`
all survive on BOTH binaries — none of them reaches the state.

So the arm is in-process — `go test` on the venue — and this body says so plainly rather than calling it a
live dispatch. It is the REAL `touch`/`observe`/`idleBoundedContext` code, not a re-implementation, and
the negative control is a real mutation of the product binary's source, not a test double.

**The seam's first form FAILED, and that is the evidence it is honest.** Sleeping *inside* `touch()` held
the producer goroutine, so the attempts stopped growing — the guard then killed in **both** arms
(10/10 vs 10/10). That is the same dead end the external load controls hit: *a producer that made no
attempt is not evidence.* Deferring only the SEND is what makes the instrument discriminate.

### The seam's production effect — zero, and fail-safe (T1–T4)

- **Zero when unset.** The only consumer is a positive comparison, `if pluginActivityTouchGate > 0 { … }`;
  unset ⇒ `0` ⇒ the branch is not taken and `touch()` is the same single non-blocking send, with no wait
  and no goroutine. Pinned by `TestPluginActivity_TouchGateIsInertByDefault`.
- **One read site, claim-keyed grep:** `grep -rn CHARLY_PLUGIN_TOUCH_GATE` over the tree returns exactly
  two hits — `charly/plugin_activity.go:218` (the doc comment) and `:1034` (the env-table row). Nothing
  else in the repo reads it.
- **No build tag — deliberate R9 trade.** A tagged seam would make the bed's binary differ from the
  released binary, which is the very "binary does not equal source" defect this round fixed. So it ships,
  and the safety argument is that the knob is **fail-safe in the only direction that matters**: it can
  only REMOVE progress evidence (a deferred send), so it makes the guard kill EARLIER, never later. It
  cannot make a wedged plugin look alive, cannot authorize anything, and is unset in every deploy. Its
  misuse mode is more false kills, not fewer.
- `TestPluginActivity_TouchGateDefersOnlyTheSend` pins that it defers the SEND and never holds the caller.

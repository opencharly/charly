# 2026.317.2037 — feat(plugin): the deploy connect serves the plugins the deploy declares, and a step receives their paths (#1131)

## Summary

The loader **already knows which built binary serves which plugin** — `loadPluginUnit` resolves it and every run prints it (`plugin <ref>: served from <path> (build <sha256>); source <dir>`) — and then threw the mapping away. A `step:` that has only a plugin NAME therefore re-derived it by scanning a store directory and taking the newest match: a guess over a layout the plugin does not own, which cannot even run on a `kind: cloud_image` venue because no store exists there (`opencharly/charly#1131`).

Four pieces, one seam, plus the defect that proving them exposed:

1. **`charly/plugin_connected_set.go` (new)** — records the served mapping (`key`, `leaf`, `view_path`, `src_dir`) as `loadPluginUnit` finishes registering a unit. Recorded AFTER registration (a unit that failed to register is not served), idempotent on `(key, leaf, view_path)`, and `snapshot()` hands out a copy.
2. **`charly/host_build_deploy_plugins_connect.go`** — the `deploy-plugins-connect` reply carries that set, so a consumer acts on PATHS IT WAS TOLD.
3. **`charly/host_build_construct_step.go`** — the `construct-step` seam injects the set into a class:step's input under `spec.ConnectedPluginsInputKey` for a step whose DECLARED `StepContract` sets `plugin_paths`. Opt-in because a step's input is validated against the plugin's own usually-closed schema; core stays blind to the step's input shape (it hands over the WHOLE set; the step selects by leaf).
4. **`charly/plugin_loader.go` — the connect now SERVES the plugins the deploy DECLARES.** The connect is dispatch-scoped (it scopes on the WORDS a plan step references), and a deploy's venue also dispatches through a **shell** no prescan can read: `charly firecracker image build` inside a `command:` step references no plan word at all. So a deployment composing `plugin-firecracker` never connected it, and the step correctly refused an incomplete set. A deploy's candy list IS its intent, so the DEPLOY connect also serves the plugin candies it declares: the node's `from:`-template `candy:` list (folded into the same typed ref list the scan receives — the merge does NOT copy it onto the node), plus its `add_candy:` and its nested children. Bounded to that closure; plugin candies only; out-of-tree sources only (a compiled-in plugin is already served); the build still goes through `sdk/buildcache`.

`charly/check_cmd.go` is the SECOND caller of `deployNodePluginContext` (the check-run path); it now threads `cfg` through as well, so both callers see the deploy's declared candy closure — the same one-line threading, no second behaviour.

**And the defect this exposed, fixed here:** `charly/plugin_provider_common.go` — charly's OWN pb→spec `StepContract` conversion built the carrier from Scope/Venue/Gate/Emits and **dropped `PluginPaths`**, so a plugin declared the flag, the transport carried it, and the host read `false`: the injection never ran. That is the third copy of one contract conversion (`spec/exec`, `sdk`, `charly`), and the new test pins the whole set by construction.

## Change classification

- **Class:** `charly` Go code (loader + two host seams + the deploy connect's declared-candy widening) plus a `spec` pin bump.
- **Breaking change + rollback:** none for an existing deployment's authored config — the reply gains an optional field, the injection is opt-in, and the widening only ADDS connects for candies the deploy already declares (measured above: 2 more served plugins, 1 more build, on a deploy that declares 2 plugin candies). What changes behaviour is a deploy that declares a plugin candy which cannot be built: it now fails at connect, by name, instead of proceeding without it — that is the intended direction (a complete set or a loud stop). Rollback is `git revert` plus the module pin returning to spec `v0.2026317.703`.
- **Consumer ordering:** producer-first. `spec v0.2026317.1755` (spec#308) → `sdk v0.2026317.1803` (sdk#505) → this PR → `plugin-deploy-firecracker` (consumes the paths, deletes the scan) → `plugin-firecracker#11` and `layer-fireactions-runner#2`.

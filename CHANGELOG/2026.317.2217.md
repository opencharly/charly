# 2026.317.2217 — fix(plugin-prescan): an imported plugin repo registers its declared command/kind words

## Summary

Fixes the prescan gap that made `import:` of a plugin repo half-work: the entities loaded, the
command word did not. Head `4840fba70af97c6654638332f9c0584c61e94700` (content commit
`1c6c32c6c6e2bca2011e4ae3d17527db6a56d057`, merged up to current `main`), 4 files, +372/−103.

**Mechanism.** `prescanDeclaredPluginWords`' import leg treated every non-`@` ref as a bare
sibling FILE (`- vm.yml`). A local-path **directory** entry therefore failed that read
silently, so the imported project's own `discover:` tree was never walked — and a plugin repo
declares no `plugin:` block at its root at all: its providers live in `candy/<name>/charly.yml`,
reachable only through that discover tree. The `@github` leg cannot cover it (it matches refs
in bytes already collected; a local-path import contributes none).

The fix stays inside the ONE existing walk (R2 — no second implementation):

| File | Change |
|---|---|
| `charly/plugin_prescan.go` (+247/−103) | `prescanDeclaredPluginWords` drives the walk with a `visited` set seeded from the root project; `prescanDiscoveredPluginManifests` is the discover walk now SHARED by the root file and every imported project (same manifest recognition, same per-class registration: command → `registerDeclaredExternalCommand`, kind → `registerDeclaredKind`, deploy → `registerDeclaredDeploySubstrate`, `plugin: primary:` sugar); `prescanImportedProjectEntries` is shape-aware (local dir → project walk; flat file → unchanged; `@github` ref → resolved as before, then walked as the project it is); `prescanProjectDir`/`absPrescanDir` recurse through the namespace graph keyed on the absolute dir, so diamond/self/cyclic imports walk each dir once; `prescanPluginManifest` splits into a path reader + `prescanPluginManifestData(bytes)` (no double read) |
| `charly/plugin_prescan_import_test.go` (+165) | the two regression tests (below) |
| `charly/readiness_config.go` (+23/−12) | `loadedReadiness` resolves through `readinessProjectDir()` = `projectDirPreParse()` (`CHARLY_PROJECT_DIR` → `-C/--dir` → `--repo` → cwd) — the R1 finding below |
| `charly/readiness_config_test.go` (+40) | the three readiness tests |

**R1 finding found and fixed in the same commit.** The walk now reaches the loader BEFORE
`main`'s chdir, so `pluginInvokeNoProgress`'s readiness query ran at the caller's cwd and
one-shot-cached `LoadUnified(".")` from a non-project directory — the umbrella's
`charly box list candies` then dropped three plugin-serve provenance lines and skipped the
project load. With the fix, live parity is restored (same 610 candy entries, same 3 plugin
connects; only stderr map-order varies, in both binaries).

## Change classification

A defect fix in the pre-parse grammar: projects that import a plugin repo by local path gain
their plugin's command/kind words (the documented intent of that import). No CLI surface is
removed and no existing resolution leg changes behaviour. **Breaking change + rollback:** none
— the bare-file leg, the root discover leg and the `@github` leg are preserved and covered by
their existing tests; rollback is reverting this commit.

# 2026.323.1703 — chore(deps): adopt sdk v0.2026323.1623, whose arbiter names a losing revision pin

## Summary

`sdk` moves **`v0.2026322.1853` → `v0.2026323.1623`**, the release carrying **opencharly/sdk#592**
(merge commit `e72ae286238c566200b00e0d5f2b47ec0bf16e5d`). The whole diff is that one `require` line
plus its `go.sum` entry, repeated through this repo's lockstep modules.

**What the bump changes, and only that.** `sdk/loaderkit.PickCandyVersion` already refused a silent
same-scope skew, but its one line named only the winner:

> candy `layer-cuda` resolved to multiple git tags with differing content within one scope
> (box=nvidia-cdi); using newest referenced v2026.323.0252 …; also referenced 5f5bb770…

A reader who had pinned a **40-hex revision** — the only immutable way to address an unmerged layer
— saw that line and could not tell that the revision was the loser, why it lost, or what to do
about it, so **opencharly/charly#1215**'s scenario read as an unfixable impossibility. sdk#592
**appends one sentence per losing non-CalVer ref in a conflicted box scope**: what the ref is, why
it loses (no recency for the CalVer order to read), that its content is therefore never composed,
and the remedy — move the `require:` that names the tag to a release containing the revision
**first** (producer-first: land, merge, tag, then move the pin), or stop naming the tag in that
scope.

**The arbitration itself does not move, on purpose.** SHA-precedence was rejected: `newerCandidate`'s
CalVer-beats-revision rule is charly#1179's fix (a stale pinned revision two hops away beat the
release carrying the actual fix), and letting a SHA win again would reopen that regression. This PR
therefore only buys the diagnosis — the *fix* for #1215's case is the producer-first order the new
sentence spells out, which is what the two composing beds below then proved.

**Why this release and not the tag the brief named.** `git ls-remote --tags … | tail -2` is a LEXICAL
sort, and the sdk's own Go-module scheme `v0.<YYYYDDD>.<HHMM Zeros stripped>` is not lexically
ordered — `v0.2026323.936` sorts after `v0.2026323.1623` because `9` > `1`. The tag that carries
sdk#592 is the one whose commit **is** the merge:

```console
$ git tag --list 'v0.*' --sort=-v:refname | head -3

v0.2026323.1553

$ git log -1 --format='%h %cI %s' v0.2026323.1623

$ git log -1 --format='%h %cI %s' v2026.232.1949
b2da101 2026-08-20T19:53:09Z fix(ci): tag sdk under its Go-module scheme v0.<YYYYDDD>.<HHMMZ> (#148)
```

`v2026.232.1949` is an **older, other line** (2026-08-20, the commit that *introduced* the `v0.`
scheme), not the newest release. The pin that reached `main` before this commit was
`v0.2026322.1853`, so the move is `v0.2026322.1853` → `v0.2026323.1623`.

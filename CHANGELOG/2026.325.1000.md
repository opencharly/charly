# 2026.325.1000 — test(charly): add the repo-cache R10 bed

## Summary

Adds the R10 bed that proves the `--repo` resolver reads the **one** charly cache root, and
that each of the three ways of naming it points at the same store — the property the XDG
cutover (spec#406/#407/#409, sdk#596, charly#1224) changed and that nothing live asserted yet.

- `repo-cache-check-app` — a `kind: local` template with no candies; the bed drives only the
  host binary's resolver, so no image and no service is built for it.
- `check-repo-cache-local` — a `disposable: true` host bed with **four** arms, each naming the
  root it seeds, all through ONE implementation (`scripts/check-repo-cache.sh`):
  - `repo-cache-xdg-default` — the XDG default, `$XDG_CACHE_HOME/charly/repos/<repo>@<ref>`;
  - `repo-cache-dir-override` — the `CHARLY_CACHE_DIR` override, `<dir>/repos/<repo>@<ref>`;
  - `repo-cache-legacy-override` — the kept **`CHARLY_REPO_CACHE`** override, which names the
    repos directory itself (the variable spec#409 deliberately restored);
  - `repo-cache-miss-control` — a **control**: an empty root must attempt a clone and fail.
- **Why a PASS means something.** The fixture repo exists nowhere, and every arm runs with every
  `https://github.com/` clone rewritten to a missing local path, so the only way an arm can
  succeed is by reading the entry it seeded — a miss fails on the spot instead of reaching the
  network or hanging on a credential prompt. The control proves that rewrite is in force.
- The witness is "resolved without a clone", **not** the printed version: an offline probe showed
  `charly --repo <ref> version` prints the binary's own CalVer regardless of the seeded entry's
  provenance. The bed does not claim otherwise.

The bed was part of the closed opencharly/charly#1223 (superseded by #1224, which did not carry
it). This PR carries **only** the bed, rebased onto current `main`; no production code, no pin.

**Round-2 changes, and their RCAs.**

1. **A1/R1/R5 (validator finding, real).** The body claimed the kept `CHARLY_REPO_CACHE`
   compatibility was asserted while both arms drove `CHARLY_CACHE_DIR`. The claim is now true: the
   legacy arm sets `CHARLY_REPO_CACHE` (with the XDG and `CHARLY_CACHE_DIR` roots pointed at an
   empty directory, so it can only pass through the override), and the miss arm is the control.
2. **R2 (validator note).** The two near-duplicate shells are replaced by one script; the four
   arms differ only in the root they seed, so a failure names the root.
3. **A bed run of my own that failed, fixed here.** The first run of the four-arm bed failed all
   four arms with `CHARLY_BIN must name the charly binary under test`. Mechanism: a check step's
   command text has `${...}` **expanded by the runner** before the shell sees it, so the variable
   is not in a child script's environment (the old inline arms worked only because the path was
   substituted into their own text). The control I had skipped was running the script the way the
   runner does; the binary is now a positional argument.

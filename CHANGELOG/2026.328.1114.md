# 2026.328.1114 — chore(deps): adopt plugin-build v0.2026328.1 — a failed build carries its output

## Summary

Adopt `github.com/opencharly/plugin-build/candy/plugin-build v0.2026328.1` (`v2026.328.0001`, merged as opencharly/plugin-build#68). `go mod tidy` also raises the direct `github.com/opencharly/sdk` requirement to `v0.2026327.1021` — the floor that release declares — so the diff carries **two** `require` lines, both accounted for here.

That release stops discarding the build's captured diagnostics:

```diff
-	if _, err := runner.Run(ctx, buildkitdrive.BuildctlBinary, args...); err != nil {
-		return fmt.Errorf("building %s: %w", box.Name, err)
-	}
+	if err := c.runBuildctl(ctx, box.Name, args); err != nil { return err }
```

with `runBuildctl` passing the captured output to `buildFailure`, which appends its last 60 lines to the error.

`sdk` is a SHARED pin: the core module anchors it and every lockstep tools module must carry the same
version, which `tools/gomod-canonical`'s `TestContractPinsMatchShared` enforces in CI. The bump moved
core's anchor and left three tool modules behind (the previous head's `go` job was red for exactly
that), so this change also carries the `charly task mods-tidy` result — the verb that control names.

| File | Change |
|---|---|
| `charly/go.mod`, `charly/go.sum` | `plugin-build` → `v0.2026328.1`; `sdk` → `v0.2026327.1021` (its floor) |
| `tools/generate-packages/go.{mod,sum}` | shared `sdk` pin adopted (`charly task mods-tidy`) |
| `tools/golden-cloudinit/go.{mod,sum}` | the same |
| `tools/golden-compile/go.{mod,sum}` | the same |

**Why it matters here.** opencharly/charly#1255: a failing `pacman` step in a base-stage `RUN` left no error text anywhere — the step log ended at the `RUN` line and the buildkitd daemon log carried none — because the only copy was discarded. Until a charly release carries this dependency, no build on any host can state why it failed, which blocks the diagnosis behind opencharly/pod-cdi#14, opencharly/charly#1254, opencharly/opencharly#1254 and the two pod-comfyui beds.

## How tested

```
$ go mod tidy            # in charly/charly
$ go build ./...         # exit 0
$ go vet ./...           # exit 0
```

The module's own coverage (the call-site test that fails if the capture is reverted) shipped in #68
and passed there.

**The changed path executed live — both arms, same host, same build.** A deliberately failing build
(a scratch box whose candy `download:`s from a closed port) run with two binaries built in the same
worktree:

| Binary | Build | Log | `did not complete successfully` | `curl: not found` |
|---|---|---|---|---|
| from this branch | `2026.328.0004` | 88 lines | 4 | 4 |
| from `origin/main` | `2026.327.1010` | 45 lines | 2 | 2 |

The failing RUN's block appears **twice** in the new binary's error and once in the old one — the
second copy is `buildFailure` appending `tailLines(out, 60)`, and its absence in the `origin/main`
binary is the discard this PR removes. Retained output (new):

```
#9 ERROR: process "...curl -fsSL \"$__u\"..." did not complete successfully: exit code: 127
 > [stage-1 5/5] RUN --mount=type=cache,… sh -c '… curl -fsSL "$__u" -o "$__c.part" …'
   0.059 /bin/sh: curl: not found
   Containerfile:35
     35 | >>> RUN --mount=type=cache,… sh -c '…'
error: failed to solve: process "…" did not complete successfully: exit code: 127
```

**What this proves, precisely.** The error object now carries the failed step's output, from the
changed code path, under a fresh CalVer build of this tree. **What it does not prove:** the original
#1255 shape — buildctl streaming *nothing* — because that failure is not deterministic: a 400 s
`box build comfyui-cdi` from the same branch did not reproduce it (recorded on #1255). On a failure
that streams, both binaries show buildkit's own copy; the difference this PR makes is that the
captured copy is no longer discarded, which is exactly what the table above measures.

## Summary

Advances the two contract pins the shipped binary is built from, so the per-host config fixes
reach the CLI:

| module | from | to |
|---|---|---|
| `github.com/opencharly/spec` | `v0.2026327.605` | `v0.2026328.1115` |
| `github.com/opencharly/sdk` | `v0.2026327.1021` | `v0.2026328.1130` |

The same two pins move in the three `tools/*` modules that mirror them (`charly task mods-tidy`),
which is what `tools/gomod-canonical`'s `TestContractPinsMatchShared` enforces.

What the binary gains:

- **One writer for `~/.config/charly/charly.yml`.** `spec/perhost` is now that file's ONLY reader,
  decoder, lock and atomic write (`Lock`, `Apply`, `Update`, `Read`, `Get`, `Set`); the git-ref
  cache, the install ledger, the host snapshot and the deploy overlay all run through it.
- **A measured lost update, fixed.** Every ledger writer read the ledger OUTSIDE the lock and
  replaced the `ledger:` section with that stale snapshot, so two concurrent ledger writes each
  dropped the other's record — 21 of 24 concurrently-added records lost, 5 of 5 runs, with the
  SDK's new cross-writer test against the pre-change tree (opencharly/sdk#632).
- **The bypass race, fixed.** `charly cache bypass --off` could print "git-ref cache bypass
  cleared — the cache resumes" and be undone seconds later by a long-lived process writing back
  the `true` it loaded before the clear (`bypassOwned`, spec v0.2026328.1009). Measured on this
  host with the pre-bump binary, 2026-11-24.
- **A non-destructive cache clear.** `charly cache refresh` / `ClearCache` no longer deletes the
  whole per-host file; it clears only the `cache:` section.

**RCA for that NOTICE (the one anomaly in the pasted evidence).** `plugins_refs_generated.go` is
the committed index of the plugin corpus. The build regenerates it from the corpus refs the git
cache currently resolves; the cache on this host resolved at least one version-less corpus ref to
a DEFAULT BRANCH (`Resolved @github.com/opencharly/plugin-deploy-pod -> main` in this host's
`charly config` output the same hour), while this checkout pins that plugin at a tag — so the
regenerated index differed and `check-generated-clean` restored the tracked file. It is a
cache-state divergence, not a change in this diff: after the build,
`cd charly && git status --short` prints nothing, so the tracked file is byte-identical to the
commit. A `--dev-plugin` build takes the same path by design.

**Live check on this host, `2026-11-24`:**

```
# pre-bump binary (2026.327.1010)
$ ./charly/bin/charly cache bypass --off
git-ref cache bypass cleared — the cache resumes
$ grep -m1 bypass: ~/.config/charly/charly.yml
        bypass: true            # undone seconds later by a concurrent charly process

# rebuilt binary (2026.328.1114), same command
$ ./bin/charly cache bypass --off
git-ref cache bypass cleared — the cache resumes
$ grep -m1 bypass: ~/.config/charly/charly.yml
        bypass: false           # read back from disk immediately after the write
```

The file then read `true` again while PRE-BUMP charly processes that had loaded the flag before
the clear were still running (another session's `charly task pin-check`; the umbrella-root
binary, which this worktree's build does not replace, predates the bump): a writer without
`bypassOwned` re-asserts the value it loaded. That is the defect this pin fixes, observed both
ways on one host in one hour. The host's flag stays `true` until no pre-bump process is alive to
write it back, at which point a single clear with the rebuilt binary sticks.

The remaining slowness of that command (4 min wall, 31 s CPU) is the warm-up ref sweep, filed as
opencharly/spec#438; it is not the config write path this PR moves.

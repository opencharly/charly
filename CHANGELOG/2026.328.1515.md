# 2026.328.1515 — fix(deps): pin plugin-box v0.2026327.2335, the release that stops INFO diagnostics gating a build

## Summary

Closes opencharly/charly#1266. charly's compiled-in `plugin-box` was a day behind the release that
carries a shipped-behaviour fix:

| module | from | to |
|---|---|---|
| `github.com/opencharly/plugin-box/candy/plugin-box` | `v0.2026326.938` | `v0.2026327.2335` |

`v0.2026327.2335` (git tag `v2026.327.2335`, `8cef2effe`) is opencharly/plugin-box#100: `charly box
validate` no longer exits non-zero on an **INFO-tier** diagnostic. Before it, an already-arbitrated
candy-version skew — a diagnostic the schema model classifies as information, not an error — gated
a build with exit 1. The pinned version predated it, so the binary still carried the old severity
rule even though the fix had shipped and been tagged.

Nothing else changes: no charly source edit, no other module moves. Found by checking that every fix
from the per-host config session was actually reachable from a shipped binary — spec
`v0.2026328.1115`, sdk `v0.2026328.1130` and charly `v2026.328.1249` were landed and pinned; this one
was not.

**The `check-generated-clean` NOTICE is upstream corpus drift, not this pin — and here is the proof.**
`plugins_refs_generated.go` maps `"<class>:<word>"` to a candy REF (no versions), and
`plugins.go` is the compiled-in wiring. Regenerating both with the corpus the build uses, into a
scratch dir:

```
$ go run ./internal/pluginsgen -root .. -config charly/charly.yml -out .pg_tmp/plugins.go \
    -gowork .pg_tmp/go.work -gowork-dev .pg_tmp/go.work.dev \
    -outrefs .pg_tmp/refs.go -corpus charly/plugin_corpus.txt
$ diff .pg_tmp/refs.go charly/plugins_refs_generated.go
118d117
< 	"kind:os":                   "github.com/opencharly/plugin-distro/candy/plugin-distro",
125d123

$ cd charly && git status --short

```

The only difference is TWO `plugin-distro` rows the committed index lacks: `pluginsgen` indexes each
corpus repo at its DEFAULT BRANCH (the corpus is a repo list, not a pin list), so the index tracks
upstream tips, not module pins. **Zero `plugin-box` lines differ and `plugins.go` is byte-identical**,
so this pin provably does not touch either generated file; the build restores the tracked copy and
leaves the tree clean. The residual — the committed index lagging the corpus by those two rows — is
filed as opencharly/charly#1268.

**Attribution tier: `analysed on a live system`, not `fully tested and validated`.** The pin, the whole
CI job and the R9 build all ran on this tree, but the BEHAVIOUR this pin carries — `box validate`
turning an INFO-tier diagnostic into a `notice:` line plus exit 0 — never executed against the fresh
build: three live two-tag fixtures were built and validated (a project naming two tags of the same
candy, which is the skew's shape), and the resolver produced no INFO diagnostic to exercise
(`charly box validate: OK — checked 36 candies, 6 distros, 7 builders; 0 warnings, 0 errors`,
`rc=0`, no `notice:` line). The behavioural proof therefore remains opencharly/plugin-box#100's own
test; what ran here is the resolution, the gate and the build.

The fix's own proof (a test that exits non-zero on INFO and zero on ERROR) is in
opencharly/plugin-box#100, whose CI gate ran there. What this PR proves is that the pin builds,
that the whole repo CI job passes on it, and that the rebuilt binary reports its own CalVer.

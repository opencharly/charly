# 2026.328.1711 — fix(plugins): refresh the compiled-in provider-ref table from the current corpus

## Summary

Closes opencharly/charly#1268. `charly/plugins_refs_generated.go` — the committed
`"<class>:<word>" → candy ref` table that `pluginsgen` writes — was regenerated from the corpus the
build uses. The only change is the two `plugin-distro` kind words the corpus declares today and the
tracked file lacked:

```
+	"kind:os":                   "github.com/opencharly/plugin-distro/candy/plugin-distro",
+	"kind:source":               "github.com/opencharly/plugin-distro/candy/plugin-distro",
```

`plugins_generated.go` (the compiled-in wiring) regenerates byte-identical, so the generated half is
one file and two lines. The PR also ADDS ONE TEST, `charly/engine_word_cutover_test.go` (+18 lines),
which pins the two words against the same table the runtime reads — added in round 2 after the first
review found the rows unproven. Two files in total: the generated data and its assertion.

Why it happened, stated so the next reader does not re-derive it: `pluginsgen` indexes each corpus
repo at its **default branch** (the corpus is a repo list, not a pin list), while
`scripts/bootstrap-charly.sh`'s `check-generated-clean` restores the tracked file when the
regenerated one differs — so every build printed

```
check-generated-clean: NOTICE — charly/plugins_refs_generated.go differs because it was indexed from a source this checkout does not pin
```

and nobody acted on it. The NOTICE disappears with this commit, which is the proof that the drift,
not the message, was the defect. The separate policy question — should a release build keep
restoring (reproducible) or fail on drift, and who owns the refresh — is filed as
opencharly/charly#1273 and listed under `## Filed issues`, so closing #1268 here does not decide it.

**Disposable target: N/A — with the reason.** No `disposable: true` bed exists for a word→ref table
(the R10 matrix's beds exercise images, pods, VMs and live services; none enumerates
`pluginProviderRefs`). The class-appropriate gate is this repo's `go` job (run above) plus the R9
build's `check-generated-clean`, which compares the regenerated table with the committed one — the
artifact is validated at the boundary that was complaining. The live-execution question is answered
by the added test below.

**What did and did not execute live, stated exactly.** The two rows are compiled into the rebuilt
binary (the build below), and the changed lookup — `pluginProviderRefs["kind:os"]` /
`["kind:source"]` — executes in `TestPluginRefsIndexCarriesTheDistroKinds`, whose red proof is above.
A CLI path that PRINTS those two words on the rebuilt binary was attempted and does not exist: the
hidden verb that lists registered providers (`charly __plugin list`) completes with `rc=0` on the
rebuilt binary but prints provider CLASSES (`command:*`, `verb:*`, …), and `grep -cE
"kind:(os|source)"` over its output is `0` — it does not report kind words at all. So no CLI surface
enumerates the two rows, and a timeout on a first attempt (the host runs six concurrent charly
sessions) is not the reason. So the tier is `analysed on a live system`, not
`fully tested and validated` — the diff's correctness is established by the executing test and the
corpus source, not by a live CLI resolution.

The decisive check is the R9 build below: with the tracked file now matching the corpus,
`check-generated-clean` prints **no NOTICE** and the tree stays clean — the artifact is validated at
the boundary that was complaining.

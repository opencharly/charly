# 2026.328.1852 — chore(deps): bump sdk to v0.2026328.1554 so the binary refuses a degraded config load

## Summary

Bumps the SDK to the release that ships the per-host config data-safety guard:

| module | from | to |
|---|---|---|
| `github.com/opencharly/sdk` (in `charly/go.mod` and the three `tools/*` modules) | `v0.2026328.1130` | `v0.2026328.1554` |

`v0.2026328.1554` is opencharly/sdk#633: `deploykit.SaveDeployConfig` now REFUSES to persist a
**degraded load** — it compares the typed re-read with the file's own deploy-key count and aborts
instead of writing a short set that erases the entries the loader could not unify. That is the
data-loss half of opencharly/charly#1269, measured on this host on 2026-11-24 when
`~/.config/charly/charly.yml` lost both of its deploy entries mid-run while the containers kept
running.

No charly source change: the guard lives in the SDK. The three `tools/*` modules mirror the
contract pins (`charly task mods-tidy`), and `charly/go.sum` was tidied for the new hashes — without
that, `go test` synthesises a `go.work.sum`, which `pluginsgen`'s workspace test forbids
(opencharly/charly#1065).

The branch has since merged `main`, and therefore also carries opencharly/charly#1272's
corpus-index refresh: the R9 build below prints **no** `check-generated-clean` NOTICE, where the
pre-merge tree did. That is #1272's fix working, not a change made here.

Note on the `tools/*` sweep line the reviewer flagged: `tools/generate-packages` is a module whose
own `module` directive is `github.com/opencharly/charly/candy/generate-packages`, and its only
package is `cmd/serve`. The sweep line is therefore correct, not misattributed:

```

$ find tools/generate-packages -name '*.go'
```

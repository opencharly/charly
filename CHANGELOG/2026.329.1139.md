# 2026.329.1139 — feat(service): capture the init tool's output for the service reply

## Summary

`charly service status` cannot judge a deployment's health from the init tool's aggregate exit code
alone: the tool exits 3 when ANY process is not `RUNNING`, and a declared run-to-completion service
that has finished is exactly that. The declaration lives in the image metadata, which the PLUGIN
reads; the rows were printed host-side, which only core could do. This PR moves the second half:
`pod-lifecycle`'s op="service" now captures the init tool's stdout into the reply's `output` and
reports its exit code in `exit_code`, instead of relaying the text and raising the code as an error
(opencharly/charly#1271).

- `charly/go.mod` / `charly/go.sum`: `spec v0.2026328.1115 → v0.2026329.803`, which is where the
  reply's `output` field comes from (opencharly/spec#442). No other dependency moves.
- `pluginDeployTarget.shellCapture` returns `(stdout, exit code, error)` without printing; `Shell`
  becomes a short wrapper over it (dispatch, print when non-empty, exit-code error), so the relay
  path behaves exactly as before.
- `tools/{generate-packages,golden-cloudinit,golden-compile}/go.mod` + `go.sum` —
  `charly task mods-tidy`, moving the three in-tree tool modules to the shared
  `spec v0.2026329.803` pin. `TestContractPinsMatchShared` fails without it, since `charly/go.mod`
  is the shared-pin anchor.
- `charly/service_capture_test.go` — the proof for both arms: a capturing target hands back the
  table and the exit code without printing, and a relaying target keeps its error and reports no
  captured reply.
- `runServiceCapture` is the optional capability the `service` branch uses: a target that can
  capture gets the reply; one that cannot keeps the exact relay-and-error behaviour.
- `cmd`'s reply path is untouched — the exit code rides the reply there for the same reason.

Consumer: opencharly/plugin-pod#32 prints the reply and judges it against the declared services.


The bed's target is `check-service-status` — a `disposable: true` pod (the `charly.yml` entity added
by opencharly/plugin-pod#32). The `skipped_checks` are that fixture's image-scope and unrelated

the consumer judged it.

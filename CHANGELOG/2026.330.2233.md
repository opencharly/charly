# 2026.330.2233 — chore(deps): spec v0.2026330.2134 (content-addressed candy staging)

## Summary

Advance the `spec` requirement from `v0.2026329.803` to **`v0.2026330.2134`**, the tag carrying
`CandyStageDirName`'s content addressing (`opencharly/spec#444`, merged 2026-11-26T21:34:49Z).

The staging directory is now named `<candy>.<sha256[:16]>` over the candy's content (paths,
executable bit, bytes) instead of `<candy>.<version>`, so a ref-only change reuses the same
Containerfile `COPY` source rather than invalidating the layers beneath it.

### The layer-hit measurement, and what actually blocked it

The intended end-to-end number — two builds of identical content, expecting a layer hit — did **not**
materialise, and the cause is **not** the candy ref:

```
build A (contentstaging-2135)     FROM …/arch-builder:2026.330.2035   wall=869 s
build B (identical tree, same candy content) FROM …/arch-builder:2026.330.2152   wall=758 s
```

The BASE builder is rebuilt under a fresh CalVer tag on nearly every build (four tags in 100
minutes), and the `FROM` resolves the newest, so every layer above it re-executes regardless of the
candy staging name. Filed as **`opencharly/charly#1292`**. So the honest claim for this pin is: the
candy COPY source is content-addressed (proved above), and its layer reuse is gated behind `#1292`
having a stable base ref.

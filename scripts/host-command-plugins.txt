# The WELDED command plugins baked beside the charly binary at /usr/lib/charly/plugins
# on every native package install (arch .pkg.tar.zst, fedora .rpm, debian .deb).
#
# Each is an out-of-process command:<word> (and, for a few, verb:<word>) plugin that
# makes `charly <word>` dispatch to the hidden `__<word>` core command. They are NOT
# compiled into charly (compiled_plugins: is verb/kind/step only), and they resolve
# ONLY from bakedPluginDirs() = $CHARLY_PLUGIN_DIR + /usr/lib/charly/plugins. Without
# them a package install would leave `charly doctor`/`clean`/`vm`/… unresolvable
# project-less.
#
# SINGLE SOURCE (R3) for the welded plugin set. The release-binary workflow
# (`.github/workflows/release-binary.yml`) builds every listed candy with
# `GOWORK=off go build` and generates its `.providers` manifest via
# `charly __plugin-providers <candy-dir>`, then publishes the tarball the distro
# repos' packaging workflows bake into /usr/lib/charly/plugins. The `charly
# generate-packages` plugin (sdk/packagekit) reads the `packaging:` section of
# charly's packaging metadata (`packaging/charly.yml`) to select each variant's plugin
# set, and `charly/packaging_test.go` asserts the variant sets cover exactly
# these 9 plugins.
#
# One `<name>@<tag>` per line; blank lines and `#` comments are ignored.
#
# The PIN is part of this file because the candy de-submodule cutover moved every
# one of these into its own repo: the release workflow clones `opencharly/<name>`
# at `<tag>` and builds `candy/<name>` from that checkout. charly/go.mod is NOT a
# usable pin source here — it carries only 7 of the 9, because the two command-only
# plugins are not compiled in and so have no require line.
#
# Bump a pin the way any other ref is bumped: to a MERGED tag, never a branch.

# 2026.210.2052 — #DistroConfig / #BuilderConfig build-vocabulary containers (#55 step 3-III, producer leg)

STEP 3-III of the everything-is-a-plugin import-purity plan relocates the build
**value-type containers** `DistroConfig` / `BuilderConfig` out of `sdk/buildkit`
into the CUE-sourced `spec` contract — the import-purity lever that lets charly
core (and plugins) reference these vocabulary containers from `spec` instead of
importing `sdk/buildkit`. Pure value/contract types (their methods are intrinsic
lookups over the type's own map — no composition behaviour), so per the
fabric-vs-capability rule they belong in the contract module. `InitConfig` is
deliberately EXCLUDED — its `ResolveInitSystem`/`ActiveInit` aggregate the whole
candy set's capabilities (`AggregateCandyCapabilities`), i.e. init-composition
POLICY, not a contract accessor — so it stays in `sdk/buildkit` and relocates
with the build engine (#65/#71). This is the PRODUCER leg; the `sdk` require-bump
+ the charly/plugin repoints ride their own follow-on PRs in the B2 dependency
order.

New CUE-sourced containers (SDD — plain structs of maps, `cue exp gengotypes`
generates them faithfully; hand-writing a wire struct is forbidden):

- `#DistroConfig.distro: {[string]: #ResolvedDistro}` (`schema/distro.cue`) —
  the distro-vocabulary container (`Distro map[string]*ResolvedDistro`).
- `#BuilderConfig.builder: {[string]: #Builder}` (`schema/builder.cue`) — the
  builder-vocabulary container (`Builder map[string]*Builder`).

Their resolution METHODS move verbatim to hand-written same-package files
(`spec/distro_config_methods.go`, `spec/builder_config_methods.go` — the existing
`distro_methods.go`/`deploy_methods.go` precedent: generated struct + hand-written
methods on the generated type): `ResolveDistro`, `ResolveInherits`,
`AllFormatNames`, `FindFormat`, `ValidFormat`, `ExpandPackageInheritance`,
`WrapDistroDef`, `DistroTagChain` (distro) + `ValidBuilderType`, `BuilderNames`
(builder). Round-trip + resolve + inherits coverage in `spec/build_config_test.go`.

Backward-compatible for spec consumers: purely additive to the schema; the
generated `cue_types_gen.go` gains the two container structs. `task cue:gen`
regeneration is a NO-OP on a clean tree (reproducibility gate green). `sdk/buildkit`
keeps thin type aliases (`DistroConfig = spec.DistroConfig`) so its build-engine
code reads unchanged — landed in the follow-on sdk leg.

Producer-first B2: this spec leg (merged + Go-module tagged) → sdk require-bump →
superproject charly + 85-plugin repoint.

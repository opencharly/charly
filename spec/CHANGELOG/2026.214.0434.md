# 2026.214.0900 — #55 import-purity: BuildCLIModel reflection mechanism relocated from sdk root into spec/clireflect

A follow-up spec leg of the 4-leg B2 PR chain (spec → sdk → plugins → super) that dissolves
the `github.com/opencharly/sdk` ROOT package. The Kong→CLIModel reflection mechanism
(`BuildCLIModel` + its helpers) is relocated from the sdk root (`sdk/climodel.go`) into a NEW
kong-bearing `opencharly/spec` slice package `spec/clireflect`, so that charly core (the host
CLI) and every command plugin emit the same `spec.CLIModel` contract WITHOUT either importing
the other, and WITHOUT dragging kong into the cuelang-bearing `spec/climodel` slice. This leg
is ADDITIVE in spec — it creates the slice and the symbols; the sdk root keeps its definition
for the duration of the cutover (a thin re-export shim is the downstream sdk leg; the super
leg repoints `charly/cli_model_cmd.go` to `clireflect.BuildCLIModel`).

## Why a NEW slice (Rule 2 — granular spec)

`BuildCLIModel` reflects a Kong command tree into the CUE-generated `#CLIModel` contract. It is
a SHARED mechanism used by BOTH charly core (the host CLI, `charly/cli_model_cmd.go`) AND a
command plugin (`candy/plugin-agent`, which reflects only its owned subcommand subtree for 3
models) — so by the fabric-vs-capability decision rule it is a FABRIC PRIMITIVE → it moves to a
`spec/<slice>`, not a plugin, and the sdk root keeps a re-export shim so candies compile
unchanged. It cannot move to charly-only (R3 duplication with the sdk copy candies use), and it
cannot stay in the sdk root (the step-1 import-purity gate requires charly off the sdk root).

It does NOT go into `spec/climodel` (which already holds `ValidateGenerated` /
`DecodeGeneratedJSON` / `ValidateCUEValue` / `ValidateCUEInput`), because `spec/climodel` is
cuelang-bearing and two of its consumers (`plugin_grpc.go`, `plugin_provider_common.go`) do NOT
use kong — merging `BuildCLIModel` there would force `alecthomas/kong` on every consumer of
`spec/climodel`, violating Rule 2 (each heavy third-party dep lives ONLY in the slice that needs
it). The new `spec/clireflect` slice contains kong; consumers that need only CUE validation
(`spec/climodel`) never pull kong, and consumers that need only CLI reflection never pull
cuelang. Go module-graph pruning + package granularity enforce this at build time.

## The relocated symbols

`spec/clireflect` (NEW package, seeded verbatim from `sdk/climodel.go`):

- `BuildCLIModel(root any, name, version, prefix string, options ...kong.Option) (*spec.CLIModel, error)`
  — reflects a Kong command tree into the generated `spec.CLIModel`; `prefix` is a dotted
  command path prepended to every leaf (e.g. `"agent"` when a command plugin reflects only its
  owned subtree).
- `KongLeafToCLILeaf(leaf *kong.Node) spec.CLILeaf` — converts one Kong leaf into the generated
  wire shape (no external callers beyond `BuildCLIModel`; exported for parity with the sdk
  original).
- `kongValueToCLIArg` / `sanitizeCLIPropName` / `cliJSONType` — the unexported helpers, moved
  verbatim.

No symbol here is a hand-written CUE wire type (SDD: wire types are CUE-sourced in
`spec/spec`). Every symbol relocated is a reflection mechanism over Kong + the generated
`spec.CLIModel`/`spec.CLILeaf`/`spec.CLIArg` contract types — NONE is a `sdk/spec/*_wire.go`
host↔plugin data-carrier struct, so no SDD hand-write exception applies.

## REPOINT decisions (load-bearing for the downstream legs)

- `BuildCLIModel` is a REPOINT for the charly caller and a re-export for the candy caller. The
  super leg re-points `charly/cli_model_cmd.go` from `sdk.BuildCLIModel` to
  `clireflect.BuildCLIModel`. The sdk leg replaces the `sdk/climodel.go` DEFINITION with a
  `var BuildCLIModel = clireflect.BuildCLIModel` re-export shim so `candy/plugin-agent` (3 call
  sites) compiles UNCHANGED. `KongLeafToCLILeaf` needs no shim — it has no external callers
  beyond `BuildCLIModel`.
- This leg does NOT touch `spec/climodel` (the cuelang-bearing slice keeps its
  `ValidateGenerated` family unchanged), `charly/` (super leg), `candy/` (plugins leg, via the
  sdk shim), or `sdk/` (sdk leg).

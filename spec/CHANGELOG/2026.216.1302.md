# 2026.216.1302 — a --repo cache fetched only one of its twelve submodules

`GitClone` populated exactly one submodule, `sdk`, selected by name. Everything
else a fetched project declares — `spec`, `plugins`, `docs`, the five
`box/<distro>` repos, the three `pkg/*` repos — stayed an empty directory.

The consequence was that `--repo` could not deliver the thing it exists for. A
`--repo` cache is a whole project someone drives with nothing but the `charly`
binary, and out-of-process plugin candies build STANDALONE in their own module
under `GOWORK=off`, resolving siblings through relative replaces. **All 86 candy
`go.mod` files carry BOTH** `replace github.com/opencharly/sdk => ../../sdk`
**and** `=> ../../spec`. With `spec/` empty, every one of those builds died on
`../../spec/go.mod: no such file`, so no out-of-process verb was reachable
through `--repo` at all. `box/<distro>` being empty removed the box definitions
too — main owns none.

The helper's own comment asserted the justification, and it was wrong on both
counts:

> Just `sdk` is initialized (the ONLY submodule a plugin build's go.work depends
> on), never the heavy `box/*` ones.

`spec` is equally required — that is the missing-file error above. And "heavy"
does not survive measurement: a shallow `--init --depth 1` of all twelve
submodules costs **~8s** and adds **24MB to a 36MB clone** (60MB total), against
~1s for the `sdk`+`spec` pair alone. (An earlier revision of this entry wrote
"60MB" as the submodules' cost. That figure was measured, but attributed to the
wrong subject — it is the whole tree, not the increment.)
The cost the special case was guarding against does not exist at `--depth 1`.

`populateSDKSubmodule` is therefore replaced by `populateSubmodules`, which
initializes every submodule the repo declares, shallow and non-recursive —
exactly the configuration proven to build. A repo declaring none is still a
clean no-op. The `insteadOf` SSH→HTTPS rewrite is unchanged, so headless runs
still need no key.

Proven by mutation. Restoring the `sdk`-only argument to the otherwise-fixed
code fails `TestGitClone_PopulatesAllSubmodules` on precisely `spec/go.mod`,
`box/fedora/charly.yml` and `plugins/README.md` while `sdk` still passes —
characterizing the defect rather than merely detecting it. The test's `sdk`
probe alone would have passed both before and after, which is why the `spec`
probe is the load-bearing one.

## A deliberate widening: an unreachable submodule now fails the fetch

The old code was a silent no-op for any repo not declaring `sdk`, so a
third-party project with a private or dead submodule fetched "fine". It now
errors. That is intended, not an oversight: a silently partial cache is the exact
defect this function exists to remove, and it cost a full debugging session
precisely because it surfaced three layers down as `../../spec/go.mod: no such
file`, with nothing pointing back at the fetch. A caller that cannot reach a
declared submodule has an incomplete project and is told so at the fetch, with
git's own stderr — naming the submodule and the reason — wrapped into the error.

The radius is narrower than `.gitmodules` suggests. `submodule update --init`
walks the INDEX, so an entry declared in `.gitmodules` with no gitlink (mode
160000) recorded is ignored and cannot fail a fetch; only submodules genuinely
committed into the tree are attempted. That behaviour is now pinned by
`TestPopulateSubmodules_UnreachableSubmoduleFailsLoudly`, which registers a real
gitlink pointing at an unreachable `file://` URL and asserts both that the fetch
fails and that the message names the offending submodule. Writing that test is
what established the index rule — an earlier version declared the submodule in
`.gitmodules` only, and `populateSubmodules` correctly returned nil.

## The fix had to heal caches the old code already broke

Populating every submodule on a FRESH fetch is only half a fix: it would have
helped new caches and left every existing one broken. Two separate gates decide
whether a cached export is reused, and neither looked at content.

**Mutable refs (`@main`).** `repoCacheFresh` has always claimed to report whether
the cache is "a complete export cloned from exactly commit" and only ever
compared the commit. A cache written by the old sdk-only code records the CORRECT
commit, so it was served as a permanent hit — the fix would not have reached it
until `main` happened to advance.

**Immutable refs (`@v2026.183.1359`) — the worse half.** `EnsureRepoDownloaded`
short-circuits on `cached && !IsMutableRef(version)`, returning `RepoCachePath`
without ever entering `DownloadRepo`, so `repoCacheFresh` never sees a tag at
all. `IsRepoCached` meant only "the directory exists". And a tag never moves, so
an incomplete tag export was pinned for the LIFE of the cache. This is the common
case: pinned `@github` candy refs. Measured on the development host before the
fix — `charly@v2026.183.1359` held **0 of its 9** declared submodules and
`charly@v2026.201.0706` held **1 of 10**, both unrepairable.

There is also no escape hatch: `charly clean --invalidate` targets image TAGS,
so no CLI verb invalidates a repo-cache entry and hand-deleting a directory would
have been the only remedy.

Both gates now consult ONE shared predicate, `submodulesPopulated` — an export
declaring a submodule with an empty directory is not complete, so it is
re-fetched. One copy, not one per gate, so the branch and tag paths cannot drift
apart. Every broken cache self-heals on next access, with no version bump, no
migration and no manual step.

Cost, stated rather than discovered: the first command that touches a stale entry
after upgrading pays a full re-fetch of that repo. It is one-time per cache entry,
and it is the price of not serving a known-broken export forever — but it is real,
and on a slow or heavily-loaded machine it can push a command that was already
near a timeout over it.

That is not hypothetical. The first attempt of this change's bed gate FAILED
exactly that way: the `check-commands-local` step
`charly status >/dev/null && charly status --json` was killed with `exit=-1` and
empty stderr. `charly status` costs ~60–105s on this project with a warm cache
and zero fetches, and that step runs it twice, so the one-time re-fetch tipped it
over. An A/B measured 106s WITHOUT the completeness check and 82s WITH it —
independently re-measured at 59.4s vs 59.7s over three runs each — so the check
is not the cost. The slowness is pre-existing and unrelated to fetching, and is
tracked as opencharly/charly#208 rather than absorbed here.

A note on the completeness predicate's own edge case, because it is the
difference between "self-heals" and "re-clones forever": a `.gitmodules` entry
with NO gitlink materializes no directory at all, whereas a gitlink that is
merely unpopulated materializes an EMPTY one. Only the latter is incomplete —
`populateSubmodules` walks the index and cannot fetch the former either. An
earlier revision of this change treated both as incomplete, which would have made
such an export permanently unfresh and re-cloned its repo on every command.

## End to end

From `/tmp` with a cold cache and no checkout anywhere, the fetched cache shows
12/12 submodules populated and `charly --repo opencharly/charly mcp serve` — an
out-of-process verb, built from that cache — reports `serving 70 tools`.

That end-to-end run exercises this fix together with two unlanded fixes in
`opencharly/charly` #207 (the prescan not resolving `--repo`, and the staleness
guard aborting on a cache), so it is evidence for the CHAIN, not for this leg in
isolation. This leg's own proof is the mutation test above and the offline
error-branch test.

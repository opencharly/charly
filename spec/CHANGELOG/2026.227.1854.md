# 2026.227.1854 — the build-scope verdict resolver refuses a stale short-name election

`charly check box <box>` could certify an image that was not the one you built,
report every step green, and give no sign. This is the resolver half of the fix
(the superproject and sdk halves land alongside).

## The defect, measured

Reproduced on 2026-08-15 (day 227): a candy edit added a `check:` step, the box
was rebuilt as `ghcr.io/opencharly/fedora-nonfree:2026.227.0835` / `:0836`, and
`charly check box fedora-nonfree` printed
`Image: ghcr.io/opencharly/fedora-nonfree:2026.216.1908` and `5 passed, 0 failed`
— running the OLD baked plan, with the newly added step absent entirely. A green
verdict with the right-looking step names, proving nothing about the artifact
under test.

Root cause, in this package. `ResolveLocalImageRef` partitions candidates into a
LABEL family (`ai.opencharly.box == <short>`) and a NAME family (the ref's
trailing repo segment matches), then takes the label family WHOLE and discards
the name family — `cands := labelCands; if len(cands) == 0 { cands = nameCands }`.
The fresh build carried `ai.opencharly.box=fedora.fedora-nonfree` (the emitter
labelled with the namespace-qualified box key while tagging the ref with the leaf
name — fixed in the sdk half), so it landed in the name family and was discarded
wholesale; the older bare-labelled images were elected, and among them the newest
tag was `2026.216.1908`.

The election's own ordering keeps the same failure reachable even with consistent
labels: its PRIMARY key is the content-derived `ai.opencharly.version` label, with
the per-build tag only as a tiebreak. An image built from a differently-versioned
source tree — a sibling worktree, a pulled release — therefore outranks a newer
build regardless of when either was produced. Both shapes are live on a
multi-worktree host; both were observed in the same `podman images` capture.

## Correction from validation: the first fix's ordering key was blind to bed tags

The first version of this guard shipped an ordering that could not see the tags
charly actually mints, and a validator proved it live: `check box docs-site-app`
certified an image ~17 hours old, green, exit 0 — the very incident this entry
opens with, sailing straight past the new guard.

`ExtractCalVerTag` is not total over minted tags. `charly box build --tag`
REPLACES the CalVer tag rather than adding to it, so every bed build carries a
single `check-<bed>-<calver>` tag, which is not three decimal dot-parts and reads
as EMPTY. With the content label tied across one source tree and the tag key
empty for every candidate, the election fell through to a lexicographic last
resort and elected the OLDEST build — while the guard's own "newest build" probe
returned `""` and was read as "nothing to worry about".

**This had been root-caused once already, and routed around rather than fixed.**
`candy/plugin-check/live_image.go` names the mechanism verbatim, from 2026-08-05,
including "the OLDEST local build of the box won". That fix made the LIVE path ask
the running container which image it is — an authoritative source a build-scope
verdict does not have — so the resolver kept the flaw and this guard was built on
top of it.

Build recency is therefore keyed on the image's **creation time**
(`LocalImageInfo.Created`, read from the same `images --format json` rows `Size`
already comes from — no extra process, no extra call). It is the only key total
over arbitrary `--tag` values, it agrees with the tag CalVer wherever that key
worked, and it does not tie. The content label remains the election's PRIMARY
key; creation time replaces the tag as the tiebreak, with the tag kept as a
tertiary for builds sharing a second under parallel load.

Two properties that only became expressible with a real ordering:

- **`SameArtifact`** — many tags on ONE image id are one artifact (a `--tag`
  build and a plain CalVer build of identical content share an id), so there is
  nothing older or newer to arbitrate and the guard stays silent instead of
  refusing a box against itself.
- **`OrderKnown`** — when any candidate reports no creation time the guard
  REFUSES with an explicit "could not establish which build is newest" rather
  than passing. Permissive-on-unknown is the same class as the silent-pick defect
  this cutover exists to remove, so it is not kept as a convenience.

### Two further corrections from validation

**The election and the newest-build probe disagreed on their last resort.** The
election's final tiebreak is ascending ref; `newestBuild`'s was descending. They
diverge only when two DISTINCT images tie on every recency key — same label
version, same creation second, no CalVer tag to separate them — but there the two
name different refs, and `RefuseIfStale` compares refs rather than keys, so the
guard refused a pair in which neither is newer than the other:

```
refused: "twin-app" resolves to …:check-a-2026.227.1000, but …:check-b-2026.227.1000
is a newer local build of the same box
```

Neither is. Distinct builds DO share a creation second under parallel load, so
this was reachable rather than theoretical. Only the deterministic TAIL is shared
(`orderTail`), so an all-keys tie can never refuse — gated by
`TestResolveBuiltImageRef_TiedKeysDoNotRefuse`.

**Sharing the WHOLE comparator, which a first attempt did, is a regression — and
it shipped green.** `moreRecent` unified both orderings, so `cands[0]` became
identically the maximum the newest-build scan returns: `NewestBuildRef == Ref`
always and `RefuseIfStale` had nothing to compare. The guard was a tautology.
Every refusal test survived it, because they all used the two-family label split,
where the newest-build scan walks the WIDER union and can still differ; no test
covered a SINGLE-family stale election, which is the exact scenario the guard's
doc comment names.

The two orderings must differ in their PRIMARY key, and the difference is the
mechanism, not duplication:

- `electionOrder` — primary `labelCalVer`. Answers *which artifact does this NAME
  mean*: a short name refers to a box's content, not to whatever was compiled most
  recently.
- `buildOrder` — primary `created`, deliberately blind to the content label.
  Answers *which of these was BUILT most recently*.
- `orderTail` — the shared deterministic last resort. Arbitrary is fine;
  DISAGREEING is not.

R3 applies to the tail, which was genuinely duplicated. It does not apply to two
answers that are supposed to be able to contradict each other — deduplicating
those deletes the contradiction the guard detects.
`TestResolveBuiltImageRef_SingleFamilyStaleElectionRefuses` is the gate that was
missing; each ordering level is now independently mutation-gated.

**A comment this cutover added was false.** It read "podman and docker both emit
it" of the numeric `Created` field — the sentence justifying refuse-on-unknown.
Measured directly: podman emits it (427/427 rows), docker does NOT (0/3;
`docker images --format json` emits `CreatedAt`/`CreatedSince`). Docker's path is
already degenerate well upstream of recency — that command emits JSON-LINES
rather than the JSON ARRAY this parser unmarshals, and carries no `Names`, no
`RepoTags` and no `Labels` — so the consequence is the RIGHT one rather than an
accident: with no creation time the resolution reports `OrderKnown=false` and a
build-scope verdict refuses instead of guessing.

An authoritative comment that does not match the system is the exact shape this
cutover exists to correct, so the sibling claim in the same function — "docker
uses `RepoTags`" — is corrected too: that is the docker INSPECT shape, dead for
`images --format json`, live only for a caller feeding this parser inspect-shaped
rows.

## `container.ResolveBuiltImageRef` — the guard

New: `ResolveLocalImage` returns the full answer (`LocalImageResolution`: the
elected `Ref`, the `NewestBuildRef` — the highest build-tag CalVer across BOTH
candidate families — and `Pinned`). `ResolveLocalImageRef` and the new
`ResolveBuiltImageRef` are both thin wrappers over that one body, so there is one
candidate gather and one ordering (R3).

`ResolveBuiltImageRef` resolves and then REFUSES when the elected image is not the
newest local BUILD, wrapping the new `spec.ErrStaleLocalImage` and naming both
refs plus the pinned re-invocation. It is for the verbs that pronounce a VERDICT
on a built artifact; every consumption path (deploy, `charly vm build`, builder
bootstrap) keeps the lenient election unchanged.

Refusing rather than silently re-electing the newest build is deliberate. Changing
the election's primary key would change what `charly update`, `charly vm build`,
and the pod deploy path resolve to — a far broader behaviour change than this
defect justifies, and one with its own wrong case (a colleague's build from older
sources winning). A stale check that errors is recoverable; one that PASSes is not,
so the ambiguity is surfaced and the operator names the artifact.

Two escapes, both pre-existing and now documented in `--help`: a full ref, or the
`<box>:<calver>` pin. The pin is why the R10 bed sequence is untouched — a bed
builds `box build <image> --tag <run-tag>` and checks `<image>:<run-tag>`.

## Coverage

`container/local_image_coneb_test.go`, over a fixture reproducing the measured
storage byte-for-byte:

- `TestResolveBuiltImageRef_RefusesStaleElection` — the regression gate. Fails on
  the pre-fix body (returns `…:2026.216.1908`, nil), and asserts the refusal names
  both refs and the runnable re-invocation.
- `TestResolveBuiltImageRef_BedTaggedElectsNewest` — every candidate bed-tagged,
  so only creation time orders them; fails on the blocked body by electing the
  08-14 image, which is the validator's live reproduction in fixture form.
- `TestResolveBuiltImageRef_BedTaggedFreshBuildIsNotRefused` and
  `…_IsNotMisdirected` — the two faces of the mirror case: a fresh bed-tagged
  build beside an older plain-CalVer one either got silently certified (equal
  label versions) or triggered a refusal naming the STALE image as the one to
  re-run against (higher label version on the fresh build). Both are gated.
- `TestResolveBuiltImageRef_SameArtifactNeverRefuses` — two tags on one image id.
- `TestResolveBuiltImageRef_RefusesWhenOrderUnknown` — refuse, do not pass.
- `TestParseLocalImagesJSON_Created` — the ordering key is actually read off the
  engine rows; a silently-absent field would make every resolve "order unknown".
- `TestResolveLocalImageRef_LenientFormStillElects` — pins the deliberate split:
  the lenient election is unchanged.
- `TestResolveBuiltImageRef_PinnedInputPassesThrough` — the escape hatch, and why
  beds never reach the guard.
- `TestResolveBuiltImageRef_ConsistentLabelsElectNewestBuild` — with the sdk
  label fix in place the guard does not fire; one family, newest build wins.
- `TestResolveBuiltImageRef_SiblingAliasIsNotANewerBuild` — guards the guard: a
  sibling deployment's `<deploy-name>:<calver>` alias is not "a newer build of
  this box", or every bed host would refuse every untagged verdict.

# 2026.227.2226 — the nested-jump shell starts on a base without bash

`wrapWithJump` hardcoded `bash` as the interpreter on the far side of every
jump — container (`podman`/`docker exec`) and SSH alike. On a busybox base that
ships no bash, the jump dies **before the script is read**: the container runtime
never finds the interpreter, so the failure surfaces as the OCI runtime's

```
crun: executable file `bash` not found in $PATH: No such file or directory:
OCI runtime attempted to invoke a command that was not found
```

with exit 127 — which reads as a container-setup INFRA failure rather than a
missing interpreter, and points the reader at the wrong thing entirely.

Measured against an Alpine 3.24 image: `podman exec <c> bash -c 'echo hi'` fails
with exactly the above; `podman exec <c> sh -c 'echo hi'` prints `hi`.

## The fix

The interpreter is now selected AT RUN TIME inside the target instead of being
baked in:

```sh
sh -c 'if command -v bash >/dev/null 2>&1; then exec bash; else exec sh; fi'
```

`sh` is the one interpreter present on every base, so the jump always starts; it
then `exec`s bash wherever bash exists, so a bash-bearing base is unaffected and
still gets real bash. The `exec` replaces the probe shell, leaving no extra
process between the jump and the script.

Verified on both legs rather than assumed — reading `$0`, which names the
interpreter the probe actually `exec`'d, NOT `$BASH_VERSION`:

| base | observed |
|---|---|
| Alpine 3.24 (busybox, no bash) | `argv0=sh  BASH_VERSION=unset` — fell back to `sh`, script ran |
| Fedora (`fedora-builder`) | `argv0=bash  BASH_VERSION=5.3.0(1)-release` — handed off to bash |
| Fedora, probe forced down `exec sh` (control) | `argv0=sh  BASH_VERSION=5.3.0(1)-release` |

The control row is why `$0` and not `$BASH_VERSION`: `/bin/sh` is a symlink to
bash on Fedora, and bash invoked as `sh` still exports `BASH_VERSION`, so that
variable reads identically whichever branch ran and cannot witness the hand-off.
`$0` differs. An earlier version of this entry cited `BASH_VERSION` for the
Fedora row — a true conclusion resting on an observation that could not have
contradicted it. See "The vacuity class is subtler than…" below; the same mistake
appeared independently in the test and in this table.

Root escalation composes unchanged — `sudo` now wraps the probe rather than a
bare bash, so a root jump into a busybox base works for the first time.

## The probe alone is not enough: the transports do not agree

Swapping one interpreter string for another is only correct where the far side
receives real argv. The three script-carrying jump kinds do not (`JumpVirshConsole`,
the fourth `JumpKind`, rejects scripted exec outright):

- **`podman` / `docker exec`** parse the emitted line ONCE — in the parent shell
  — and hand the resulting argv straight to `exec(2)`. The probe is written
  exactly as the target must receive it.
- **`ssh`** parses it TWICE. `ssh(1)` does not forward its remote-command
  arguments as argv: it JOINS them with single spaces into one string and hands
  that string to the remote login shell, which parses it again. The parent shell
  has already consumed the probe's quotes by then, so a bare probe arrives on the
  far side as unprotected text and the remote shell dies on the `;`/`then`
  before the script is ever read:

```
bash: -c: line 1: syntax error near unexpected token `then'
bash: -c: line 1: `sh -c if command -v bash >/dev/null 2>&1; then exec bash; else exec sh; fi'
```

Exit 2. That regressed the **nested** VM hops — a VM reached through a container
or through another VM (`deploy_chain.go:195`, `:277`); a top-level VM uses
`SSHExecutor` and never routes through `wrapWithJump`. The pre-probe code was
unaffected because a bare `bash` survives a re-parse intact.

`jumpShell` therefore emits the probe at the quoting depth its transport needs —
one extra layer on the SSH branch only — and says why in the code, because the
two branches now look gratuitously different and the difference is load-bearing.

## Why it went unnoticed

No bed deploys a busybox-based box. Every container bed in the fleet runs a
glibc/shadow-utils base where bash is always present, so the hardcoded
interpreter was indistinguishable from a correct one. The gap surfaced only when
an Alpine bed was authored and its `check-image` step failed on a container the
image itself was perfectly capable of running — `cat /etc/alpine-release`
returns `3.24.1` when invoked directly.

This is the fourth assumption of the same family found in one chain (the other
three are in `sdk`: the go-task install assuming `curl`, user creation assuming
`groupadd`/`useradd`, and the login shell assuming `/bin/bash`). The pattern is
a userland assumption that is invisible until a non-glibc base exercises it.

## Coverage

Two tests, guarding two different things:

- `TestWrapWithJump_ShellProbeNotHardcodedBash` asserts the probe's SHAPE on the
  three script-carrying jump kinds (podman, docker, ssh — `JumpVirshConsole`, the
  fourth `JumpKind`, rejects scripted exec outright). Non-vacuous against the
  hardcoded interpreter: restoring `shell := "bash"` fails all three subtests.
- `TestWrapWithJump_SurvivesTransportReparse` EXECUTES the emitted line through
  stubs that model how each transport actually delivers the far-side command —
  argv passthrough for the container engines, and a join-then-re-parse
  (`exec <bash> -c "$*"`) for ssh, because that join IS ssh's remote-command
  semantics.

The pairing between the two is the point, and it is reproducible in one run.
Remove the SSH branch's extra quoting layer — restoring the exact behaviour that
shipped broken — and run the family:

```

```

That is one uncut run, footer included — 6 top-level funcs, 12 leaves, 2 FAIL and
10 PASS. The footer says `FAIL`, because a run containing a failure cannot end in
`ok`; a transcript that pairs `--- FAIL` lines with an `ok` footer has been
assembled from two runs and should be distrusted on sight, however true its
claim. (The per-subtest failure detail is elided above only for width; it is the
`syntax error near unexpected token 'then'` / `exit status 2` quoted earlier.)

The green lines are the transferable lesson: on the SAME tree, in the SAME run,
every pre-existing assertion passes while the ssh path is broken. Those
assertions are not weak — they are checking the wrong thing. `strings.Contains`
can only ask what the emitted command LOOKS LIKE; it cannot ask whether the
command survives the transport that carries it, and for ssh those are different
questions. A test that pattern-matches emitted text is only as good as the
assumption that the text arrives intact.

The hermetic/live split follows from the same reasoning: the stub is a MODEL of
ssh's join-and-re-parse, so it was corroborated against a real sshd (both
directions, pasted in the PR) to prove the model faithful — but the hermetic
test is the one that keeps failing for the next person, with no network and no
sshd to arrange.

### The vacuity class is subtler than "use `Contains` less"

The transport test shipped its first round carrying a VACUOUS assertion of its
own — inside the test written to close the vacuity class. It read `$BASH_VERSION`
on the far side to prove the probe handed off to bash. But `/bin/sh` is bash on
the development host, and bash invoked as `sh` still exports `BASH_VERSION`, so
"handed off to bash" and "fell back to sh" are THE SAME OBSERVATION: forcing the
probe down `exec sh` left all five transport subtests green. The guarantee was
real, but it was being delivered by `ShellProbeNotHardcodedBash`, not by the
assertion claiming to deliver it.

The fix makes the observation branch-specific rather than interpreter-specific: a
marking `bash` is placed on the far side's PATH, reachable ONLY by the probe's
bash branch, and the ssh stub invokes its login shell by absolute path so it
cannot pre-set the marker. Forcing the probe down `exec sh` now fails all five
subtests instead of none.

The generalisable point: executing the code under test does not by itself make an
assertion discriminating. What matters is whether the OBSERVATION can differ
between the states being distinguished — and an environment that collapses two
states into one reading (here, `/bin/sh` → bash) will hide that regardless of how
the test is run. The check is mechanical: perturb the tree into the state the
assertion claims to reject, and require the assertion to fail.

`TestWrapWithJump_PodmanRoot` now asserts the intent — escalation via `sudo`
wrapping the probe, with the bash hand-off preserved — rather than the old
literal `sudo bash`, which was incidental to what it was guarding.

## The sweep's key and its scope are independent axes

The doc sweep this change owes took three attempts, and the interesting part is
how it failed twice.

| round | KEY swept on | SCOPE swept over | missed |
|---|---|---|---|
| 1 | the string `sudo bash` | the file the fix touched | every site stating the claim in other words |
| 2 | the claim "the shell running the emitted line is bash" | the files round 1's review had named | `escapeTokens`, `infra_classify.go`, the header of `deploy_executor.go`, the heredoc test's twin |
| 3 | the same claim | every `.go` comment in the repo | — |

**Fixing the key does nothing for the scope.** Round 2 swept on exactly the right
claim and still missed four sites, because the file set kept being inherited from
whatever the previous round's discussion had made salient rather than derived
from the mechanism. Each round correctly believed it had fixed the prior defect;
each was right about the defect it had named and wrong about the one it had
reproduced in a new place.

Round 3's scope comes from the mechanism instead — *every* place the tree reasons
about which interpreter runs a line:

```
git grep -niE '\bbash\b' -- '*.go'                       # 107 hits — read and classify each
  | grep -E '^[^:]+:[0-9]+:\s*//|^[^:]+:[0-9]+:.*//' \
  | grep -vE '^[^:]+:[0-9]+:[^/]*"'                      # 67 of them are prose
```

Of those 67 prose hits, four were false: `escapeTokens`'s "a bash line" (its only caller is
`wrapWithJump`, whose line this change declares must be POSIX sh — the sibling
quoter `deployShellQuote` had been fixed and this one had not);
`infra_classify.go`'s "bash ran, the command is absent" (the container far side,
in the file this entry blames for the misclassification); `deploy_executor.go`'s
"where does bash actually run"; and the three-level-nesting test's "the outer
bash terminates its heredoc" — the test twin of a production comment already
fixed one round earlier, which is the scope defect in miniature.

Everything else is accurate and stays: `SSHExecutor` and the host executors
genuinely do pin bash. One hit was inspected and deliberately not edited —
`spec/cue_types_gen.go:6144` is generated (`cue exp gengotypes`), its source is
`schema/seam.cue:443`, and it describes the `charly shell` verb rather than an
emitted deploy line, so it is a different mechanism and still true.

## Boundary — what this change does NOT cover

`wrapWithJump` is one site of a repo-wide assumption. The rest is NOT fixed here,
and is enumerated rather than gestured at, because an unnamed remainder is a
someday-TODO wearing a batch's clothes.

Enumerated from the MECHANISM — "an interpreter hardcoded as bash on a far side
that a busybox userland cannot satisfy" — not from the files this change happens
to touch. The pattern, so the count can be re-derived and kept honest as the code
moves:

```
git grep -nE '"bash"' -- '*.go' | grep -v _test.go
```

then classify each hit by VENUE, since only a far side charly does not control
can be busybox:

| venue | sites | in the batch? |
|---|---|---|
| guest over ssh — `deploy_executor_ssh.go:92,94,225,264` | 4 | yes |
| guest readiness polls — `ssh_wait.go:105,140,155` | 3 | yes |
| guest charly-install probes — `charly_install.go:151,161` | 2 | yes |
| builder container — `builder_run.go:167` (`opts.BuilderImage` is caller-chosen) | 1 | yes |
| the operator's OWN host — `deploy_executor.go:111`, `deploy_executor_live.go:43,51`, `deploy_host_shell.go:22,38` | 5 | no — charly requires bash on the machine it runs on |
| not an interpreter at all — `spec/charly_methods.go:392`, a `shell:` config-map key | 1 | no — matches the string, not the mechanism |

That accounts for all **16** hits the command returns, so the table can be
checked against its own output. The last row exists precisely so the arithmetic
closes: a hit dropped silently is indistinguishable from a hit never found, and a
cap that is not stated reads as coverage.

**Ten sites across four files in this repo**, plus the three known `sdk` siblings
(the go-task install assuming `curl`, user creation assuming `groupadd`/`useradd`,
and the login shell assuming `/bin/bash`). Two of the ten were missed by a
narrower enumeration keyed to the two files this PR's blast-radius discussion
named — the same mistake in enumeration form: a sweep, or a batch, inherits its
key from whatever prompted it unless the key is deliberately re-chosen.

Worth singling out: `deploy_executor_ssh.go:264` (`ResolveHome`, on every VM
deploy's guest-home preflight) carries a comment documenting the SAME ssh
join-and-re-split mechanism fixed above — arrived at independently, from its own
outage. Two encounters with one mechanism, neither generalised.

None of these are affected by the QUOTING defect this change fixes — but not for
the reason it is tempting to give. "Nothing re-parses them" would be false: the
ssh-venue sites go through `ssh(1)`, which re-parses on the far side, and that is
this document's headline finding. The actual reason is that **`bash -s` contains
no metacharacters**, so the second parse is a no-op on it: `ssh host bash -s`
joins to the string `bash -s`, which the remote shell re-splits into exactly the
argv it started with. It is the probe's `;` and `then` that made the re-parse
destructive, not the re-parse itself. (`builder_run.go:167` is not an ssh venue
at all — `podman run … bash -s` is argv straight through.)

They are the same USERLAND-assumption family, on a different mechanism (the
top-level VM and builder paths, not the nested jump), and this change's coverage
neither exercises them nor changes verdict on them. They belong to the
busybox-userland batch.

One further defect filed to the same batch, found while working here and left
alone deliberately: `copyIntoJumpCommand`'s `JumpSSH` branch interpolates a
single-quoted path INSIDE a single-quoted remote command, so any path containing
a `'` breaks. Unrelated to the interpreter; a drive-by fix would be invisible to
a review that has already happened.

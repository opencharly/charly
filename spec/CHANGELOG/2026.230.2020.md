# 2026.230.2020 — one filtered-candidate set, so a resolved init is always an active one

## Why

`EmitInitAssembly` enables a `use_packaged:` system unit through the image's **resolved** init only:

```go
if initName == img.InitSystem {
```

That narrowing fixed a real regression — `rc-update` emitted into images with no OpenRC, breaking 20
of 116 boxes (`opencharly/charly#313`, `#320`) — and it made correctness depend on a new invariant:
**`img.InitSystem` must always name a key of `img.ActiveInits`.**

Nothing enforced that invariant. `ResolveInitSystem` and `ActiveInit` computed the same candidate set
from the same triggers with the same `initDefRequirementsMet` predicate, written out twice, in two
loops that had to agree. They agreed only because someone kept them in step — and on one path they
did not.

`ResolveInitSystem`'s explicit-override branch **returned before `caps` was ever computed**, so the
capability filter never ran for it:

```go
if explicit != "" {
    if def, ok := ic.Init[explicit]; ok {
        return explicit, def          // returns here
    }
}
caps, _ := AggregateCandyCapabilities(layers, candyOrder)   // never reached
```

For an explicit init whose `requires_capability:` was unmet: `ResolveInitSystem` returned it,
`ActiveInit` excluded it, `img.InitSystem` named a non-key, the guard matched nothing, and **every
`use_packaged:` unit in the image went silently un-enabled** — no build error, no warning, no
diagnostic. The image builds clean and the service never starts. That is the inverse of the defect
the narrowing was introduced to fix: that one emitted an enable command nothing could run, this one
emits no enable command at all.

## What changed

`ResolveInitSystem` now consumes `ActiveInit`'s result rather than recomputing it. The trigger scan
and the capability filter live in `ActiveInit` alone; `ResolveInitSystem` applies neither and only
picks among the candidates it is handed. An explicit override is honored **only when it names a
viable candidate** — an override for an init no candy triggers, or whose capability is unmet, falls
through to auto-detect rather than resolving to a name nothing can enable.

Patching the explicit branch to compute `caps` first would have closed this instance and left the
drift surface exactly as it was. Removing the second copy of the predicate closes the instance and
the mechanism that produced it.

## A SECOND contract change rides with this, and it is declared here rather than implied

Closing the capability hole is not the only behaviour change. The old branch consulted
`ic.Init[explicit]` directly, so an explicit override could **introduce** an init that no candy
triggers at all. The new branch consults the candidate set, so an override can now only **select
among** inits already triggered.

```
before   explicit override -> any key of ic.Init            (could introduce an init)
after    explicit override -> any key of the candidate set  (can only select among triggered)
```

That is a real narrowing of the operator-facing contract, separate from the unmet-capability defect,
and an earlier revision of this entry framed the change purely as closing a hole. It is stated here
because a contract narrowing nobody declares is indistinguishable from a bug once someone hits it.

**It is the coherent extension of a rule already in place, not a new invention.** `ResolveInitSystem`
already fell through to auto-detect for an override naming a *nonexistent* init, and
`sdk/buildkit/init_config_test.go` has pinned that since before this change — that subtest is
untouched and still green. This extends "not honorable" from *unknown* to *unknown-or-non-viable*.

**Why fallthrough rather than an error.** An error return needs a channel the two-value signature
lacks, and adding one would force the same decision on the nonexistent-init case, changing landed
behaviour that has a test on it. Silent substitution is a genuine failure mode; the answer is this
declaration plus the assertions in the sibling leg, not a different return type.

## One aggregation, not two

`ResolveInitSystem` initially called `AggregateCandyCapabilities` a second time for
`caps.PreserveUser`, having just paid for it inside `ActiveInit` — three aggregations per image in
`render_prep`, in a change whose thesis is computing this once. Both now go through an unexported
`activeInitWithCaps`, which returns the candidate set and the capabilities it filtered with.
`ActiveInit` is a one-line wrapper over it, so its public behaviour is unchanged.

## Reachability, stated plainly

**Latent.** Every non-test caller passes `explicit = ""`:

```
sdk/deploykit/init_depends.go:94    ResolveInitSystem(layers, order, "")
sdk/deploykit/render_prep.go:67     ResolveInitSystem(g.Candies, candyOrder, "")
sdk/deploykit/render_prep.go:196    ResolveInitSystem(g.Candies, candyOrder, "")
```

A whole-tree grep finds no non-test caller passing a non-empty `explicit`, so no path that exists
today reaches the hole. The parameter is there for a caller not yet written, and that caller is what
would trip it — which is the argument for fixing it now rather than after something depends on it.

## Coverage

**The gate that can actually fail lives in another repo.** A `spec`-only `go test ./...` is
structurally incapable of seeing this change: `sdk/buildkit.InitConfig` is a pure type alias, so
`sdk/buildkit/init_config_test.go` exercises this method, and that is where the contract change
surfaces. The sibling leg `opencharly/sdk#144` carries the A/B — identical `sdk` tree, only the
`spec` module swapped:

```
TREATMENT  spec @ this change    ->  ok    github.com/opencharly/sdk/buildkit
BASELINE   spec @ 9a586f5 (main) ->  FAIL  .../explicit_override_naming_an_untriggered_init_falls_through
                                           = "systemd", want supervisord (auto-detect)
```

`TestResolveInitSystemAlwaysNamesAnActiveInit` asserts the invariant directly rather than inferring
it from two functions matching: for every case, a non-empty `ResolveInitSystem` result must be a key
of `ActiveInit`. Verified to fail against the unfixed code — perturbed by restoring `origin/main`'s
`init_config_methods.go` with the test in place:

```
--- FAIL: .../explicit_override_with_unmet_capability
    ResolveInitSystem = "systemd", want ""
    ResolveInitSystem returned "systemd", which is NOT a key of ActiveInit [] —
    EmitInitAssembly would enable no system units at all
```

**A second test carries the discriminating half, because the invariant test alone does not.**
`TestResolveInitSystemAlwaysNamesAnActiveInit` pins that a resolved name is always active — a
property equally satisfied by never honoring the override at all, so it stays green even with the
override branch **deleted outright**. Mutation-proven: removing the whole branch (`_ = explicit`)
left it, and the sibling leg's suite, fully green.

`TestResolveInitSystemHonorsAViableOverride` closes that. It triggers **two** inits and overrides to
the one auto-detect would not pick — supervisord is preferred for container images, so the same
composition resolves to supervisord without the override. A single-triggered-init fixture cannot
distinguish "override honored" from "auto-detect agreed", which is exactly why the first version of
this coverage proved nothing. It opens with a **control assertion** on the no-override path, so if
the preference rules ever change the test fails loudly instead of quietly ceasing to discriminate.

Against the mutant: `--- FAIL: TestResolveInitSystemHonorsAViableOverride`.

The fake `CandyReader` embeds the interface and implements only the three methods this path touches,
so any other call panics rather than returning a zero value that would quietly change what is under
test.

Full `go test ./...` green; `go vet` clean; `gofmt -l` empty.

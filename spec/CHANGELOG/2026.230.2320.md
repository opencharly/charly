# 2026.230.2320 — ResolveDeliverableRef: one resolver for both delivery verbs


Both image-delivery verbs need the same resolution and had each grown their own copy:
`charly vm cp-box` (VM venue) and `charly box load` (container venue). The bodies were
structurally identical and their justification comments near-verbatim rewords — found by
`charly#315`'s validator, in a cutover whose own thesis is that a second venue costs a
constructor, not a copy (R3).

`ResolveDeliverableRef(engine, input)` is that one resolver: an explicit ref that exists
locally is used exactly as authored — naming a tag IS the choice — and anything else goes
through the STRICT `ResolveBuiltImageRef`, which refuses to elect an image older than the
newest local build.

The strictness is easy to under-rate. Delivering a stale artifact is the wrong-artifact
class `charly check box` refuses to certify, and it is HARDER to notice at a delivery verb
than at a build one: the load succeeds and the venue simply runs the wrong image.

Coverage asserts both directions — an authored ref comes back untouched, and an
unresolvable one fails naming both the input and the remedy, so the operator is not sent
looking at the venue for a fault in their own build.

## Also: StreamLoad's two failure paths leaked, and one orphaned a live process

Routed here by `charly#315`'s validator rather than parked: `spec#34` is merged, so there
was no amendment to make, and no other leg was going to touch `container/transfer.go`.
Both changes are `spec/container`, provable by one suite — one honest R10 story.

- **`load.Start()` fails** → the pipe PAIR `save.StdoutPipe()` created had no other owner.
  The venue transfer retries once on a torn overlay, so this leaked per attempt.
- **`save.Start()` fails** → the load child is ALREADY RUNNING, so returning left it live.
  For `charly box load` that is an exec session inside somebody's deployed container, which
  nothing ever comes back for. Killed and Waited, in that order.

  The ORDER matters under one condition, and this entry stated it INVERTED in an earlier
  draft — "a load side patiently READING a pipe no one will write to", which is precisely
  the harmless case. A load side that reads gets EOF (`exec.Cmd.Start`'s deferred
  `closeDescriptors` closes save's write end when Start fails) and exits either way, in
  ~4ms. The hang belongs to a load side that does NOT read: one ignoring stdin, or wedged
  on the far side of an exec. `Wait` then blocks on a process nothing will ever end.
  `transfer.go` had it right while this file had it backwards — two artifacts in one change
  contradicting each other on the same mechanism, and this is the one that lands
  permanently.

Coverage was required to FAIL without the fix, and it earned that: the first version of the
fd fix closed only the READ end, and the test caught it — the write end lives on
`save.Stdout`, normally closed by `save.Wait()`, which never runs when save never starts.

Measured against unfixed code: open fds **8 → 24** after 8 failed starts (2 per attempt),
and the load child **still alive** after the call returned.
